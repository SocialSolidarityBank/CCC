# 화면 작업 레인

이 레포에서 화면을 만들거나 고칠 때의 순서다. 근거는 `docs/adr/0034-design-work-lanes.md`.

**여기에 규칙은 없다.** 지켜야 할 값은 전부 루트 `DESIGN-RULES.md` 에 있고 이 파일은 순서와
산출물과 돌릴 명령만 갖는다. 규칙을 여기에 옮겨 적으면 사본이 둘이 되고, 둘 중 하나가
뒤처지는 순간 폐지된 규칙을 지키게 된다(ADR-0033 유지 규약). 아래에서 `§N` 은 전부
`DESIGN-RULES.md` 의 장 번호다.

## 시작 전에

1. **`DESIGN-RULES.md` 를 읽는다.** 매번 읽는다. 짧다.
2. 이번 일의 크기를 정한다.
   - **새 화면이거나 큰 개편** 이면 1단계부터 전부 돈다.
   - **작은 수정**(글자 하나 세로 중앙, 문구 한 줄, 색 한 칸)이면 1단계를 건너뛰고 2단계부터.
     글자 하나 맞추는 일에 배치표를 그리지 않는다.

## 1. 계획, 위계 배치표와 쓸 부품 목록

새 화면과 큰 개편일 때만 돈다.

화면에 들어갈 값을 **줄 단위로** 적고, 각 줄이 위계 4단(§1) 중 어느 단인지와 어떤 부품으로
낼지를 짝짓는다. 말로 적지 말고 표로 적는다.

| 줄 | 무엇을 보여주나 | 위계 단 | 낼 부품 |
| --- | --- | --- | --- |
| 1 | (예) 케이스 제목 | ① 제목 | `WireItem` title |
| 2 | (예) 담당 실무자 | ④ 설명 | `WireItem` description |
| 3 | (예) 배정 상태 | 배지 | `WireBadge` (`WireItem` status) |

체크
- [ ] 모든 줄에 단이 하나씩 붙었다
- [ ] 이웃한 두 줄이 같은 단이면 그것이 나열인지 확인했다(§0 의 낱말 둘)
- [ ] §1 이 '장치를 쓰라' 고 하는 조건에 걸리는 묶음을 찾고, 걸리면 어느 장치를 쓸지 골랐다
- [ ] 부품 칸이 빈 줄이 없다. 쓸 부품이 없으면 그 자리에 **어떤 부품을 고칠지** 적는다(§2)

계획이 부품 이름을 대면 구현은 만들기가 아니라 조립이 된다. 계획이 말로만 끝나면 구현은
또 손으로 쌓는다.

## 2. 구현, 배치와 색과 문안을 한 레인에서

배치를 정한 사람이 색과 문안도 정한다. 위계는 크기와 굵기와 색이 한 묶음이라 색만 떼면
경계가 판정 단위 한가운데를 지나간다(ADR-0034 결정 1).

**부품 우선이 기본값이다.** 청소가 아니라 이 레포에서 규칙 채택률을 올리는 유일한 장치다.

- 손으로 쌓기 전에 `apps/web/app/components/wire/` 에 쓸 부품이 있는지 **먼저 본다**
- 모양이 모자라면 자기 클래스를 만들지 말고 **부품을 고친다**(§2)
- 이미 손으로 쌓여 있는 남의 화면을 함께 옮기지 않는다. 그것은 별도 스윕 티켓(CCC-90)이고
  끼워 넣으면 범위가 부푼다

체크
- [ ] 계획표에 적은 부품을 실제로 썼다
- [ ] 새 클래스를 만들었다면 그 이유가 부품으로는 못 푸는 것이다
- [ ] 화면 문자열은 `DESIGN.md` §10 과 `CLAUDE.md` 11장 부호 규칙을 따른다

값과 조합은 커밋할 때 자동으로 걸린다(아래 관문). 손으로 미리 보고 싶으면:

```bash
pnpm guard:tokens && pnpm guard:align && pnpm guard:hierarchy
```

이웃 관계까지 보려면(브라우저를 띄워 1분쯤 걸린다. CI 가 같은 것을 본다):

```bash
pnpm design:hierarchy
```

선언된 정렬 단언(가로선 여백·불릿 중앙 등)까지 실측하려면(마찬가지로 브라우저, CI 동일):

```bash
pnpm design:align
```

## 3. 검수 요청, 읽기 전용 에이전트

**자기가 만든 것을 같은 맥락에서 승인하지 않는다**(`CLAUDE.md` 실행 규약). 검수는 격리된
읽기 전용 에이전트가 한다.

Agent 도구로 `design-reviewer` 를 부른다. 넘길 것 셋:

- 바꾼 파일 경로
- 이 화면이 무엇을 하는 화면인지 한 줄
- 1단계를 돌았다면 그 배치표

**검수를 부르기 전에 관문을 먼저 통과시킨다.** 값 위반이 남아 있으면 검수가 그것을 대신
잡느라 자기 일을 못 한다. 검수는 값이 전부 합법인데 뜻이 틀린 자리를 찾는 사람이다.
무엇을 보는지는 `.claude/agents/design-reviewer.md` 가 갖는다.

## 4. 최종 수정, 검수 결과를 구현 레인이 받는다

검수는 고치지 않는다. 지적을 받아 고치는 것은 2단계와 같은 맥락이라 여기서 이어 한다.

- 고친 것과 고치지 않은 것을 가른다. **안 고친 것은 왜 안 고쳤는지 한 줄 적는다**
- 규칙 자체를 바꿔야 하는 지적이면 여기서 고치지 말고 티켓으로 낸다. 규칙 변경은 `DESIGN.md`
  와 `DESIGN-RULES.md` 를 같은 커밋에서 고치는 일이다(ADR-0033)
- 고친 뒤 관문을 다시 통과시킨다

## 관문은 단계 밖에 있다

| 언제 | 무엇을 보나 |
| --- | --- |
| 커밋할 때마다(`.githooks/pre-commit`) | 훅이 갖는 검사 전부. 목록은 `.githooks/pre-commit` 이 정본이다 |
| CI | 위 검사 전부 + `pnpm design:hierarchy`(이웃 관계 실측) |

**어느 화면을 어느 폭에서 재는지는 여기에 적지 않는다.** 그 목록은
`apps/web/app/kit/hierarchy-harness.test.tsx` 의 `SCREENS` 와
`scripts/design/hierarchy-measure.py` 가 갖는다. 숫자를 옮겨 적으면 규칙 사본과 같은 이유로
뒤처진다(실제로 `DESIGN-RULES.md` 의 화면 개수가 이미 어긋나 있다, 2026-08-11 실측).

린트를 마지막 단계로 적지 않는 이유는, 그렇게 적으면 그 앞 단계들은 위반을 내도 된다는 뜻이
되어 버리기 때문이다(ADR-0034 결정 2). 관문은 매 단계 자동으로 돈다.
