> 답하려면 매번 배포 로그를 뒤져야 했다. 이 문서가 그 답을 갖는다.

**v0.3.2** (커밋 `1ae1833`, 2026-08-23 배포)

## 규칙

**1. 번호가 사는 곳은 네 군데이고 값은 항상 같다.**

| 자리 | 무엇 |
| --- | --- |
| `package.json` | 레포 전체 |
| `apps/web/package.json` | 웹 |
| `apps/api/package.json` | API |
| git 태그 `v<번호>` | 그 번호로 운영에 나간 커밋 |

세 `package.json` 이 어긋나면 `pnpm deploy:production` 의 사전 점검이 배포를 막는다. 문서에만 적은
규칙은 지켜지지 않으므로 검사에 넣었다.

**2. 번호는 운영에 나가는 코드가 바뀔 때만 올린다.**

- 화면이나 기능이 새로 생기면 가운데 자리: `0.1.0` → `0.2.0`
- 고침과 다듬기만이면 끝자리: `0.1.0` → `0.1.1`
- 문서, 개발 도구, 스킬만 바뀐 배포는 **번호를 올리지 않는다.** 아래 이력에 행만 더한다

**3. 올리는 시점은 배포 직전이 아니라 PR 안이다.** 운영에 나갈 변경을 담은 PR 이 세 `package.json` 을
함께 고치고, 배포가 성공한 뒤에 태그를 단다.

```bash
git tag -a v0.1.0 <커밋> -m "운영 배포 v0.1.0" && git push origin v0.1.0
```

**4. `1.0.0` 은 실서비스 개시와 함께 붙인다.** 지금 열려 있는 조건은 보존과 파기 파이프라인
(`CLAUDE.md` 8장)과 D46 이다. 그 둘이 닫히기 전에는 `0.x` 로 둔다. 배포가 초록인 것과 실제 당사자
정보를 넣어도 되는 것은 다른 문제다.
