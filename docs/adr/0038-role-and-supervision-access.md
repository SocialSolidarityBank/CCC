# ADR-0038: 복수 역할, 팀 감독, 요청형 당사자 접근

- 상태: 승인 (2026-08-22 Q 그릴링, D74)
- 결정자: Q
- 관련: ADR-0002(담당 중심 접근), ADR-0005(PII 표시), ADR-0016(당사자 가입 링크), ADR-0017(D40 역할 통합), ADR-0035(D63, D65 배포와 로컬 우선)
- 대체: ADR-0017의 "기관 관리자 한 역할이 계정, 기술, 배정을 모두 처리"하는 부분

## 배경

현재 `users.role`은 `admin`, `counselor`, `service` 중 하나만 저장한다. 이 구조는 한 사람이 기관 관리자와 실무자를 겸할 수 있다는 ADR-0002의 원칙을 표현하지 못하고, 코드의 `admin` 분기는 담당 배정 없이 기관 내 모든 상담 내용을 열어 정책과 충돌한다.

기관 규모가 커지면 상담 운영, 기술 운영, 팀 관리감독이 서로 다른 책임자가 된다. 작은 기관에서는 한 사람이 여러 책임을 맡더라도 역할을 합치지 않고, 각 권한의 근거를 따로 남겨야 한다.

## 결정 1: 역할은 독립된 권한 묶음이다

기관 사용자에게 다음 역할을 복수로 부여할 수 있다.

1. **기관 관리자**: 업무 역할, 팀, 담당 배정, 감독 관계를 직접 설정한다.
2. **기관 기술 관리자**: 직원 계정, 인증, API, 처리 장비를 관리한다.
3. **실무 책임자**: 기관 관리자가 수동 지정한 팀의 케이스를 관리감독한다.
4. **실무자**: 자신에게 배정된 케이스를 상담하고 기록한다.

처리 장비의 `service` 신원은 사람 역할과 분리한다. 관리형 서비스의 **플랫폼 운영자**도 기관 역할이 아니라 배포 형태에 따라 조건부로 존재하는 별도 신원이다. **당사자**는 상시 직원 계정이 아니라 목적과 만료가 제한된 요청 접점의 주체다.

역할은 허용 권한을 합산한다. 계정 비활성, 기관 불일치, 만료된 담당과 감독 관계, 서비스 신원의 사람 전용 기능 접근은 모든 역할보다 먼저 거부한다.

새 기관의 기관 생성자는 기관 관리자와 기관 기술 관리자를 함께 받는다. 이후 역할을 나눌 수 있지만 마지막 기관 관리자나 마지막 기관 기술 관리자는 대체자 없이 제거하거나 비활성화할 수 없다.

업무 권한과 기술 권한은 이중 승인을 요구하지 않는다. 기관 관리자는 업무 역할과 관계를 직접 설정하고, 기관 기술 관리자는 계정과 기술 설정을 직접 처리한다.

## 결정 2: 정보 접근은 역할과 관계를 함께 본다

| 주체 | 기본 식별정보 | 보호 PII | 상담 내용 | 기술 설정 |
| --- | --- | --- | --- | --- |
| 기관 관리자 | 기관 전체 | 기관 전체, 전건 감사 | 담당 케이스만. 예외는 긴급 접근 | 없음 |
| 실무 책임자 | 감독 팀 전체 | 감독 팀 전체, 전건 감사 | 감독 팀 전체, 읽기 전용, 전건 감사 | 없음 |
| 담당 실무자 | 기관 전체 | 담당 케이스 | 담당 케이스 | 없음 |
| 비담당 실무자 | 기관 전체 | 없음 | 없음 | 없음 |
| 기관 기술 관리자 | 없음 | 없음 | 없음 | 직원 계정과 기관 기술 설정 |
| 플랫폼 운영자 | 없음 | 없음 | 평상시 없음 | 관리형 서비스 운영 정보 |
| 당사자 | 요청 범위의 본인 정보 | 요청 범위의 본인 정보 | 당사자 공유된 공식 기록만 | 없음 |
| 처리 장비 | 없음 | 없음 | 마스킹 일감과 허용된 결과 제출만 | 없음 |

기본 식별정보는 이름, 연락처, 참여 사업, 담당 실무자다. 보호 PII는 계좌, 생년월일, 주소, 긴급연락처처럼 더 좁게 열어야 하는 정보다.

기관 관리자가 기관 전체 PII를 볼 수 있다는 사실은 기관 전체 상담 내용을 볼 수 있다는 뜻이 아니다. 상담 내용은 담당 배정 또는 긴급 접근에서만 열린다.

실무 책임자는 자기 팀원의 케이스에서 담당 실무자보다 넓은 전면 열람 권한을 갖는다. PII와 상담 내용을 모두 볼 수 있지만 수정, 승인, 공동 담당 지위는 얻지 않으며 모든 열람을 감사한다.

## 결정 3: 팀 감독은 수동 부여하고 확인으로 끝낸다

기관 관리자가 실무 책임자와 감독할 팀을 직접 지정한다. 직급이나 팀 소속만으로 권한이 자동 발생하지 않는다. 감독 관계가 끝나면 PII와 상담 내용 열람 권한도 즉시 끝난다.

실무 책임자는 팀원 전원의 공식 상담 기록을 확인할 수 있다. 별도 `확인함` 상태나 승인 버튼은 만들지 않고 열람 감사 로그로 확인한다. 기록 사용을 막거나 원기록을 수정하지 않는다.

실무 책임자는 기록의 특정 위치에 감독 코멘트를 남길 수 있다. 코멘트는 해당 실무자에게 알리고 같은 위치에 표시하지만 브리핑, AI 재료, 보고서, 당사자 화면에서는 제외한다. 책임자가 바뀌어도 우선 보존하고 현재 책임자에게 인계하며, 실제 운영에서 업무 피드백 노출 문제가 확인되면 유형이나 열람 범위를 제한한다.

## 결정 4: 플랫폼 운영자는 관리형 서비스에서만 존재한다

Apache 2.0 자체 운영형에서는 사용기관이 서버와 앱을 운영하므로 배포기관의 플랫폼 운영자는 없다. 관리형 서비스에서만 배포기관의 플랫폼 운영자가 존재한다.

플랫폼 운영자는 평상시에 처리 상태, 큐 수, 버전, 오류 코드, 가명 ID 같은 운영 정보만 본다. 기관 기술 관리자가 기관, 케이스, 목적, 만료 시각을 지정해 지원 접근을 열면 마스킹된 기록과 AI 결과를 볼 수 있다. PII 금고 복호화는 허용하지 않고 모든 접근을 감사하며 기관에 알린다.

## 결정 5: 당사자 접점은 요청형이다

당사자는 상시 포털을 탐색하지 않는다. 실무자가 동의, 필요한 정보, 중요 정보 변경, 목표, 액션 아이템, 공유 가능한 승인 요약을 주고받을 때 케이스, 목적, 만료, 1회 사용을 묶은 요청 링크를 연다.

당사자는 연락처와 주소를 직접 수정하고 동의를 철회할 수 있다. 실명, 생년월일, 계좌, 긴급연락처 변경은 담당 실무자에게 요청한다. 원문 메모, 녹취, 내부 리스크 플래그, 감독 코멘트, 감사 로그는 보지 않는다.

관리형 서비스는 HTTPS 요청 링크를 사용한다. 로컬 저장형의 대면 업무는 기관 기기나 내부망 QR을 사용한다. 완전 로컬 설치의 원격 요청은 종단간 암호화된 임시 전달함을 사용하며 로컬 서버를 외부에 공개하지 않는다.

배포기관은 초보자용 기본 전달함을 제공할 수 있다. 전달함은 해독할 수 없는 암호문과 최소 전달 정보만 보관하고, 로컬 앱 수신, 1회 사용, 만료 시 자동 폐기한다. Apache 2.0 사용기관은 같은 계약의 전달함을 직접 운영하거나 교체할 수 있다.

## 구현 범위

지금 구현한다.

1. 기존 단일 역할 데이터를 보존하는 복수 역할 저장 구조와 백필
2. 기관 사용자 역할, 팀, 팀 소속, 감독 권한의 스키마
3. 기본 거부 권한 판정 경계와 역할별 회귀 테스트
4. 기관 관리자의 담당 외 상담 내용 상시 접근 차단
5. 기관 생성자의 초기 역할과 마지막 관리자 보호를 표현할 데이터 계약

필요한 시점에 구현한다.

1. 역할과 팀 관리 화면
2. 감독 코멘트 작성과 알림 화면
3. 당사자 요청 링크와 변경 요청 화면
4. 암호화 임시 전달함 서비스
5. 플랫폼 운영자 지원 접근 화면

이번 구현은 쓰지 않는 화면과 업무 흐름을 미리 만들지 않는다. 권한 경계와 저장 구조를 먼저 깔고, 실제 사용 표면은 해당 배포 형태와 운영 단계가 열릴 때 추가한다.

## 기각한 대안

- **다섯 역할의 모든 화면을 지금 구현**: 사용하지 않는 흐름과 상태가 늘어 기각.
- **역할 분리 전체를 나중으로 연기**: 현재 기관 관리자의 초과 상담 열람을 계속 남겨 기각.
- **기관 관리자 한 역할에 기술과 상담 운영을 다시 통합**: 작은 기관의 겸임은 복수 역할로 해결할 수 있고 책임 경계가 사라져 기각.
- **실무 책임자를 모든 케이스의 공동 담당으로 자동 등록**: 상담 관계와 관리감독 관계가 섞여 기각.
- **감독 확인을 승인 절차로 구현**: 업무를 멈추고 D5의 수기 기록 즉시 공식화와 충돌해 기각.
- **완전 로컬 서버를 임시 터널로 자동 공개**: 초보자용 기본값으로 안전하지 않아 기각.
