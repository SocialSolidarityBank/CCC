# ADR-0044: 공용 클라이언트 진입, 당사자 요청 링크 단일화, 실무자 발 배정 요청

- 상태: Accepted
- 결정일: 2026-09-06
- 결정 번호: D86
- 관련: ADR-0016 D39, ADR-0014 D36, ADR-0038 D74, ADR-0041 D80·D82, ADR-0040 §9
- 대체: ADR-0016의 "가입 링크가 자기 확인 페이지 입구이기도 하다"(재사용)를 폐기한다. ADR-0014 D36의 "케이스를 하나도 담당하지 않으면 허브 진입 차단" 부분을 대체하고 "상담 내용은 담당만" 부분은 유지한다. ADR-0038의 배정 요청(기관 관리자 발)은 유지하고 실무자 발 방향을 추가한다.

## 배경

앞으로 만들 여섯 화면(랜딩, 로그인, 기관 초기 설정, 실무자 초대, 당사자 초대, 어드민)을 그리기 전에 ADR-0041 이후 열려 있던 갈림길 셋을 닫아야 했다. 2026-09-06 그릴링에서 Q가 정했다.

1. ADR-0041 D80은 "설치기가 허용 origin과 `apiBase`를 묶는다"고만 적어, 기관마다 자기 origin을 갖는지 공용 클라이언트가 기관을 고르는지가 열려 있었다.
2. ADR-0016(가입 링크 재사용)과 ADR-0038(목적·만료·1회 사용 요청 링크)이 당사자 접점을 다르게 적었고, 현 `/join/participant/[token]`은 ADR-0016대로 소비된 토큰에 자기 확인 페이지를 연다.
3. ADR-0014 D36(비담당이면 허브 차단)과 ADR-0038 D74(비담당 실무자도 기관 전체 기본 식별정보 열람)가 서로 대체 선언 없이 공존했다.

1차 설계 대상은 Community Cloud다. 초대·MFA·기관 설정이 전부 있는 유일한 모드라 Local Office·Local Single은 그 부분집합으로 적는다.

## 결정

1. **공용 클라이언트 + 기관 코드.** 배포기관이 `app.ccc.kr` 한 곳에 `apps/client`를 배포하고, 기관마다 사람이 읽는 **기관 코드**(예: `ssbank`)를 `install` 때 부여한다. 배포기관의 Cloudflare에는 기관 코드 → `apiBase` 매핑만 놓이며 상담 데이터는 지나가지 않는다(D80 유지). 로그인은 **기관 코드 → 그 기관의 Supabase Auth(이메일·비밀번호·MFA)** 두 단이고, 기관 URL(`/k/<코드>`)로 들어오면 첫 단을 건너뛴다. 기관 코드를 쳐 보면 CCC 사용 사실은 드러나며, 오픈소스 제품이라 문제로 보지 않는다. 기관별 origin(대안 A)은 배포기관이 정적 클라이언트를 제공한다는 D80과 어긋나고 `install`을 무겁게 해 기각했다. 무작위 코드와 입력칸 없는 URL 전용(대안 c)은 기기 교체 마찰 때문에 기각했다.
2. **"기관 워크스페이스 생성" 화면은 없다.** 기관은 기관 기술 관리자가 `install`로 만든다(D83). 브라우저에서 사용기관이 생기는 폼은 두지 않는다. 그 뒤 기관 생성자의 첫 로그인 화면이 **기관 초기 설정**(기관 이름, 첫 사업, 동의 6영역 문안, 보유기간)이고 현 `/onboarding`의 후신이다. 랜딩의 "기관 등록 시작"은 폼이 아니라 세 모드 도입 안내·설치 가이드·문의로 간다.
3. **실무자 초대는 이메일 1개에 묶인 1회용 링크뿐이다.** 익명 링크는 폐지한다. 초대 화면의 칸은 만드는 사람이 가진 역할의 합이 정한다. 기관 관리자 역할이 있으면 업무 역할을 하나 이상 반드시 골라 가입 즉시 살리고, 기관 기술 관리자 역할만 있으면 역할 칸 없이 초대해 가입자가 **역할 대기**가 된다. 역할 대기는 로그인만 되고 어디에도 닿지 않으며 기관 관리자가 사용자 화면에서 역할을 준다. ADR-0038의 계정·역할 분리는 유지하되 겸임자(대부분의 작은 기관)는 한 번에 끝난다.
4. **당사자 접점은 요청 링크 하나다.** 모든 링크는 기관·목적·**만료 기본 7일·1회 사용**에 묶인다. 현재 구현하는 목적은 가입 하나다. 가입 목적은 아직 케이스가 없으므로 현재 워크스페이스의 사업과 발급 실무자에 묶이고, 제출이 성공하면 당사자와 케이스를 원자적으로 만든다. 나중에 더할 가입 뒤 목적은 기존 케이스에 묶는다. 1회 사용의 소진은 GET이 아니라 명시적 제출 성공과 원자적으로 일어나고 중복 제출은 중복 결과를 만들지 않는다(메신저 미리보기와 보안 스캐너가 링크를 먼저 열어도 당사자 몫이 남아야 한다). 사용이 끝난 링크는 담당 실무자 이름과 안내 한 줄만 보인다. 자기 확인 페이지와 링크 재사용은 폐기한다. **링크는 전달 채널을 모른다.** 지금 채널은 복사·QR 둘이고, 카카오톡·문자 발송과 '일정 선택' 목적은 법무 게이트 뒤 Community Cloud 전용 발송 어댑터 추가로 붙인다. 카카오 로그인으로 들어가는 상시 자기 페이지는 D74와 충돌하므로 채택하지 않는다. 발송용 컬럼·포트를 지금 예약하지 않는다. 로컬 두 모드는 외부에서 링크가 열리지 않으므로 메신저 발송 대상이 아니고 원격은 암호화 임시 전달함이 맡는다.
5. **비담당 실무자에게 허브는 2단 축소로 열린다.** 기본 식별정보 격자, 담당 실무자, 참여 사업만 렌더하고 상담 기록·목표·보호 PII 구획은 자물쇠나 빈 카드 없이 렌더하지 않는다. 담당이면 현 허브 그대로다. D36의 허브 차단은 이것으로 대체된다.
6. **담당 배정 요청(실무자 발).** 축소 허브의 행동 하나가 "나를 이 케이스의 담당으로" 요청이며 사유 한 줄을 붙인다. `support_case_assignees`에 `status='requested'`, `acceptance_requested_by=본인` 행 하나를 만들고 새 표·새 상태는 없다. 요청 자체는 권한이 아니다. 기관 관리자가 배정 화면에서 승인하며 그 자리에서 공동 담당 추가 또는 기존 담당 종료(이관) 중 하나로 확정한다. 요청자가 본인이라 별도 수락 단계는 없고 거절은 `ended`+사유다. 퇴직·휴가·팀 이동으로 케이스를 이어받을 때처럼 기관 관리자가 먼저 움직이기 어려운 상황이 용도다.
7. **어드민은 역할별 페이지가 아니라 한 벌의 설정 화면에서 내 역할의 합만큼 탭이 보인다.** 기관 관리자: 기관, 사용자·역할, 실무자 초대, 팀·감독, 배정, 보존·파기 검토, 동의 문안·보유기간. 기관 기술 관리자: 사용자(활성·비활성·MFA 초기화), 실무자 초대, AI·STT·연결. 실무 책임자·실무자에게 어드민 탭은 없다(감독은 허브에서 읽는다).
8. **Local 원격 요청의 기본 경로는 암호화 임시 전달함이다(2026-09-06 후속 그릴링).** 사용기관 대부분은 기관 기술 관리자를 따로 두지 않고 AI 에이전트에 오픈소스 코드 `install`을 맡긴다. 그러면 ADR-0038의 "기관이 안전한 외부 접점을 선택한 경우"라는 조항은 선택하는 사람이 없어 성립하지 않는다. 그래서 Local Office와 Local Single의 원격 가입 경로는 배포기관이 운영하는 전달함 하나로 정하고, 기관 선택 외부 접점 조항은 남기되 기본값이 아니며 설치 문서에서 권하지 않는다. Cloudflare Quick Tunnel 자동 설치를 다시 검토해 기각했다. 결정적 이유 하나: 당사자 브라우저와 기관 PC 사이에서 Cloudflare가 TLS를 한 번 풀기 때문에 가입 폼의 이름·연락처가 기관 밖 사업자 서버에서 평문으로 열린다. 이것은 D80(상담 데이터는 Cloudflare를 지나지 않는다)과 R3를 첫 화면인 가입에서부터 깨고, 동의서에 "정보는 기관만 봅니다"라고 쓸 수 없게 한다. 전달함은 당사자 기기에서 일회용 공개키로 봉인하고 기관 PC에서만 열어 중간자가 읽을 수 없다. 주소가 재시작마다 바뀌어 7일 링크가 깨지는 것, 기관 PC가 꺼지면 링크가 죽는 것, 로그인 화면까지 열리는 것은 부수 이유다. 전달함은 링크 계약(기관·목적·만료·1회 사용, 제출 성공 시 소진)을 바꾸지 않는다.

## 결과

- 로그인·가입 화면이 앱 안에 생긴다. Cloudflare Access는 Community Cloud 업무 인증의 전제가 아니게 된다(ADR-0041 유지).
- 현재 당사자 화면은 가입 목적의 `/join/participant/[token]` 하나다. 소비 후 자기 확인 분기와 그 API 응답은 제거한다. 다른 목적은 각각의 입·출력 계약을 정한 뒤 같은 요청 링크 형식으로 더한다.
- 배포기관에 기관 코드 목록이 생긴다. 사용기관이 CCC를 쓴다는 사실 이상은 담지 않는다.
- Local Office는 1·2에서 기관 코드 단과 Supabase가 빠지고 설치기가 첫 관리자를 만든다. Local Single은 기관 코드·실무자 초대·어드민·비담당 허브·담당 배정 요청이 없고, 당사자 요청 링크 계약만 같다.
- 전달함 티켓은 Local 당사자 초대 티켓의 선행이 된다. `install`은 대화형 계정 생성과 시크릿 출력 없이 끝나야 한다(E0 설치 티켓 제약).
- 용어 신설·개정: `CONTEXT.md`의 기관(=사용기관), 배포기관, 기관 코드, 기관 초기 설정, 실무자 초대, 역할 대기, 담당 배정 요청, 당사자 요청 링크, 당사자 가입 링크.

## 구현 소유

- 화면 배치표와 시안: `design-adjustments` 워크트리 후속. 이 ADR과 `DESIGN-RULES.md`를 입력으로 사용한다(디자인 소유 잠금)
- 기관 코드 매핑과 `apps/client` 로그인 두 단: E0/E1 클라이언트·설치 티켓
- 실무자 초대 역할 동봉·역할 대기: ADR-0038 후속 티켓
- 요청 링크 만료·1회 사용·자기 확인 폐기: 당사자 초대 티켓
- 실무자 발 배정 요청: 배정 화면 티켓(마이그레이션 0건 예상)
