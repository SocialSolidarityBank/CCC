# ADR-0047: 월간 격자, 목록 간격, 당사자 화면 규칙 12건

- 상태: Accepted(2026-09-09 그릴링, 포크 12건 Q 확정)
- 결정일: 2026-09-09
- 결정 번호: D88
- 관련: D54(전체 일정 화면), D75·CCC-133(일정 다중 뷰), D60(여백 3단), D59(카드 성격), D38·D24·D31(당사자 HERO와 PII 표시), D14(감사), ADR-0033(규칙 문서 2벌), ADR-0034(design-lane)
- 대체: D54의 "달력 격자 아님", CCC-133의 월간 아코디언, D60 ③ 여백 3단, D38의 HERO 세 항목과 상태 태그, D31 2026-09-02 조항 중 목록 응답의 이메일 제외
- 시안: `artifacts/2026-09-09-workflow-prototypes/`(합성 데이터, 저장 없음). 세션 스펙 `docs/superpowers/specs/2026-09-09-schedule-participant-design.md`

## 배경

일정 화면과 당사자 화면을 시안으로 다시 그리는 과정에서 현행 규칙과 어긋나는 자리가 12곳 나왔다. 시안을 그대로 받으면 규칙이 조용히 죽고, 규칙을 그대로 지키면 시안이 풀려던 문제가 남는다. 어긋난 자리마다 무엇을 대체하고 무엇을 지키는지 정한다.

## 결정

### 1. 월간 본문은 우리가 그린 7열 격자다

달력 라이브러리를 도입하지 않는다. 셀 높이는 148 고정(767 이하 88), 날짜는 숫자만, 요일 줄은 월요일부터 일요일까지 이어지는 `--gradient-brand` 면 하나다. 넘치는 일정은 `+N건`으로 접고 누르면 그 날짜의 일간 보기로 간다. 팝오버는 만들지 않는다.

요일 글자는 두 테마 고정 `--on-action`이다. 그라데이션 면이 두 테마에서 같은 밝은 파스텔이라 `--ink`를 쓰면 다크에서 흰 글자가 흰 면에 얹힌다. 토·일·공휴일 코랄은 셀 안 날짜 숫자가 가진다.

근거: FullCalendar 6.1.19는 gzip 82KB이고 이 화면이 쓰는 것은 격자 배치뿐이다. 격자와 이동은 대략 200줄이고, 라이브러리 표면을 CSS로 덮으면 `guard:tokens`와 `guard:hierarchy`가 닿지 않는 자리가 생긴다.

### 2. 종일 일정을 데이터로 갖는다

`counseling_schedules`에 컬럼 둘을 더한다.

```sql
ALTER TABLE counseling_schedules ADD COLUMN all_day INTEGER NOT NULL DEFAULT 0;
ALTER TABLE counseling_schedules ADD COLUMN display_color TEXT
  CHECK (display_color IS NULL OR display_color IN ('mint','lavender','coral','cyan','light-magenta'));
```

시각 미정을 `00:00`으로 저장하는 규약은 기각한다. 자정에 잡힌 예약과 구분되지 않아 되돌릴 수 없다. 색은 실무자가 고르고 승인된 다섯 이름만 받는다(D47 형제 배지 순서). 용어는 `CONTEXT.md`의 `종일 일정`이다.

### 3. 당사자 목록 응답에 이메일과 사업 이름을 싣는다

D31 2026-09-02 조항 가운데 "일반 기록 응답에는 이메일을 싣지 않는다"를 목록 화면에 한해 대체한다.

뒤집는 이유는 실무 요청이다. 목록에서 사람을 특정하고 연락 수단을 고르는 일이 실제 업무인데 지금은 그때마다 허브로 한 번 더 들어가야 한다.

복호화 비용은 없다. 목록 경로는 이미 `enc_email`을 읽어 복호화한다(`loadParticipantContacts`의 `includeEmail` 기본값 `true`). 값은 두 층에서 버려진다. `packages/core/src/gateway.ts`의 `listAssignedParticipants` 반환 객체가 먼저 빼고, `packages/http-api/src/request-handler.ts`의 `assignedParticipantResponse`가 그 결과를 직렬화한다. 그래서 게이트웨이 반환 계약과 직렬화를 함께 넓혀야 한다. 감사는 행을 늘리지 않고 그 행의 `fields`에 `email`을 더한다(D24 화면 조회 1건 = 감사 1행). 참여 사업은 건수 대신 이름 목록을 싣는다. 검색 범위는 이름, 당사자 ID, 연락처, 이메일, 사업이다. 계좌는 계속 싣지 않는다.

### 4. 목록 간격은 카드 성격이 정한다(여백 4단)

| 자리 | 값 |
| --- | --- |
| 페이지 세로 스택 | 32 `--section-gap` |
| 읽는 목록 안 카드 | 20 `--space-5` |
| 고르는 목록 안 카드 | 8 `--space-2` |
| 행 카드 스택 | 16 `--space-4` |

가르는 기준은 D59와 같다. 훑어 하나를 고르는 목록이면 8, 글을 읽는 목록이면 20이다. 전부 8로 좁히는 안은 시안에서 글이 담긴 카드가 붙어 한 건의 끝이 흐려져 기각했다. 새 토큰은 없다.

### 5. 여백 계단 규칙은 그대로 둔다

`4의 배수 + 하프스텝 2·6·10·14`를 8의 배수 기준으로 다시 세우자는 안은 기각한다. 8의 배수는 이미 4의 배수 안에 있어 새 제약은 하프스텝 폐지뿐인데, 폐지하면 픽셀로 확정한 값 둘을 되돌려야 한다. 사이드바 메뉴 항목 사이 2px(2026-09-03 Q)과 컨트롤 안쪽 패딩 10px `--control-pad`다.

### 6. 월간 격자 셀 글자는 12px이다

14px 하한의 다섯 번째 예외로 등재한다. 자리 이름은 월간 격자 셀의 날짜 숫자와 일정 이름이고 소유자는 `.month-date`와 `.calendar-event-title`이다. 셀 밖(요일 줄, `+N건`)에는 퍼지지 않는다.

14로 올리면 셀 148px에 들어가던 일정이 3줄에서 2줄로 줄고, 셀을 키우면 다섯 주에서 세로가 100px 늘어난다. 13px 레일 예외를 재사용하는 안은 그 조항이 "상담 기록 좌측 레일"이라는 자리 이름에 묶여 있어 기각한다.

### 7. 단계 표시는 `WireSteps`로 두고 지나온 단계만 누르게 한다

시안이 일정 등록의 단계 표시를 탭으로 바꾼 것을 되돌린다. 탭은 순서 없는 화면 전환을 뜻해 1단계를 끝내야 존재하는 2단계가 눌릴 것처럼 보이고, 스크린리더도 "선택 안 됨"으로만 읽어 왜 못 가는지 알려주지 못한다. 대신 이미 지나온 단계 칩만 버튼으로 만든다. 현재와 앞 단계는 읽기 항목이고 `aria-current="step"`과 완료·현재·대기 어휘는 그대로다.

### 8. 당사자 허브 HERO는 일곱 항목이고 생년월일을 싣는다

당사자 ID, 연락처, 이메일, 생년월일, 기록 현황, 최근 상담, 진행 상태다.

생년월일을 싣는 이유는 실무 요청이다. 값은 등록 때 받아 `enc_birth_date`에 있고(마이그레이션 0015) 허브 응답에서만 빠져 있었다. 같은 금고 행이라 질의는 늘지 않고 복호화 1건이 늘며, 감사는 행을 늘리지 않고 `fields`에 `birth_date`를 더한다. 생년월일은 개인정보 수집·이용 동의로 이미 받은 항목이고 열람 범위도 담당 실무자와 기관 관리자라 동의 문안은 바꾸지 않는다.

상태 태그는 없앤다. 진행 상태를 정보 격자 항목 하나로 통일한다. 같은 사실을 한 카드에 두 번 두지 않고, 격자 항목이면 종결 시점처럼 값을 함께 적을 자리가 생긴다. 4열 규칙에서 "네 항목" 제한을 지우고 폭 기준만 남긴다. HERO 내부 폭 960px 이상 4열, 760px 초과 960px 미만 3열, 760px 이하 라벨 행이다.

### 9. 읽는 화면의 안내 문구와 예시 문구는 13px이다

2026-09-04 Q가 정한 상담 기록 작성 화면의 12/400은 유지한다. 이번 판정은 읽는 화면의 안내 문구와 예시 문구 한 자리에만 적용하고 소유자 클래스 `.report-description`을 신설한다. 14로 두면 안내가 본문과 같은 크기라 읽을 것과 참고할 것이 구분되지 않는다.

### 10. 좁은 화면에서 카드 행동은 세로 전폭 스택이다

767 이하에서 당사자 카드의 행동 버튼 셋을 세로로 쌓고 카드 폭 전체로 편다. 버튼 글자는 지우지 않는다. 아이콘 전용은 글리프 암기를 요구해 하루 몇 번 여는 목록에 맞지 않아 기각한다. 순서는 데스크톱과 같다. 전폭인 이유는 카드 안 사업 선택창과 좌우 끝선이 맞고 누름 면적이 293px로 넓어지기 때문이며, 카드 높이는 내용 폭 안과 589px로 같다.

### 11. 같은 대상의 보기와 등록은 같은 글리프에 더하기로 가른다

2026-08-30 Q가 당사자 메뉴에 쓴 어휘(목록은 사람, 등록은 사람 + 더하기)를 일정에도 적용한다. 일정 보기는 달력, 일정 등록하기는 달력 + 더하기 `calendar-plus`, 상담 기록하기는 펜 `record` 하나로 통일한다. 더하기는 달력 몸통 안에 넣는다. 옆에 붙이면 16px에서 테두리와 겹친다. 화살표는 방향만 말하므로 기록 행동에서 빼고, 시계 `upcoming`은 일정 메뉴에서 쓰지 않는다.

### 12. 리포트 구획 번호는 부품이 만든다

`01. 상황변화`처럼 제목 문자열에 번호를 박지 않는다. 번호는 구획 목록의 순서에서 뽑아 두 자리로 채우고, 제목 문자열은 `상황변화`뿐이다. 마크업은 `.report-section-title` 안에 `.report-index` + 제목 두 조각이며, 번호는 제목과 같은 계단을 쓰고 색만 `--sub`로 물러선다. 자리는 `2ch` 고정에 `font-variant-numeric: tabular-nums`다.

문자열에 박으면 구획을 넣고 뺄 때 사람이 번호를 고쳐야 하고 화면 문자열 검사가 중복 번호를 잡지 못한다.

## 실측 증거

- 월간 격자: 셀 35개, 높이 148, 모바일 88, 가로 넘침 없음. 요일 글자 두 테마 모두 `rgb(61,52,69)`, 다크 일정 이름 `rgb(242,239,244)`
- 모바일 업무 바: 기간 이동 한 줄, 보기 선택과 오늘과 등록이 같은 줄(top 194), 넘침 없음
- 목록 간격 비교 시안 `spacing.html`: 20 열 20px, 8 열 8px 실측
- 카드 행동 세로 스택 390px: 세 줄, 버튼 높이 32, 줄 사이 8, 버튼 폭 293
- 리포트 번호(`align-check`, 1440): 번호 다섯 개 center-x delta 0px, 번호가 제목 줄 안 세로 중앙 delta 0px, 꺽쇠 delta 0.5px. 번호 left 337, 제목 left 365.4로 다섯 개 동일

## 결과

- 규칙 문서는 `DESIGN-RULES.md`와 `DESIGN.md`를 같은 커밋에서 고친다(ADR-0033).
- 화면 코드와 마이그레이션은 이 결정 뒤의 별도 작업이다. 마이그레이션 1건, 목록·허브 응답 확장, 월간 격자 부품, `WireSteps` 되돌아가기, 아이콘 교체, `.report-description` 정리가 남는다.
- 시안은 합성 데이터 전용이고 배포물이 아니다.
