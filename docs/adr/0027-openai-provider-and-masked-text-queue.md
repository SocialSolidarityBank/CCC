# AI 사업자는 OpenAI로 확정하고, 사업자로 나가는 텍스트는 장비 마스킹을 거친 것만으로 제한한다

ADR-0022 의 **사업자 정체성 부분을 대체**한다. 처리 위치에 대한 결론(2차 마스킹은 장비에만 있고, 마스킹을 거치지 않은 텍스트는 사업자로 나갈 수 없다)은 그대로이며 오히려 강화된다.

## 착수 전 실측 — ADR-0022 의 "0건"은 사실이 아니었다

ADR-0022 는 "레포 전체에 LLM 사업자를 부르는 코드가 0건(`anthropic` 문자열 0건)"이라고 적었다. **`anthropic` 만 grep 한 결과였다.** 실제로는 완성된 어댑터가 이미 있다:

- `apps/api/src/ai-provider.ts` 의 `CodexProviderAdapter` 가 `https://api.openai.com/v1/responses` 를 호출한다. 구조화 출력 스키마, 출력 검증(`validateAiProviderOutput`·`validateDiscrepancyDetectionOutput`), 금지 출력 차단(R5), 설정 해시 고정(`canonicalAiProviderConfigHash`)까지 갖췄다.
- D51 ④ 의 두 호출 자리도 이미 배선돼 있다 — `request-handler.ts` 의 `generateAiDraft`(승인 대상: 핵심 한 줄 + 제안)와 `runDiscrepancyDetection`(불일치, 승인 대상 아님).
- 커밋 순서로 확인했다: 어댑터(`db16e51`, CCC-43)가 ADR-0022(`a8be556`)의 **조상**이다. D51 은 이 코드의 존재를 모른 채 결정됐다.

**켜진 적은 없다.** `apps/api/wrangler.toml` 에 `AI_PROVIDER_CONFIG` 도 `CODEX_API_KEY` 도 없어 `resolveAiProviderAdapter` 가 항상 `AiProviderUnavailableError` 를 던진다. 구현됐지만 한 번도 실행되지 않은 코드다.

## 결정 1 — 사업자는 OpenAI (2026-07-31 Q)

CLAUDE.md §2·§5·R3 와 D51 은 Claude API 를 명시하지만, 코드는 ADR-0022 이전부터 OpenAI 를 부르고 있었다. Q 결정으로 **OpenAI 를 정본으로 확정**하고 문서를 코드에 맞춘다. 처음 검토했던 OpenRouter 는 채택하지 않았다 — 아래 법적 사유가 결정적이었다.

**프로바이더 슬러그 `codex` 는 바꾸지 않는다.** 그 문자열이 설정 해시 튜플에 들어 있어, 이름만 바꿔도 활성 프로바이더 설정 해시가 어긋나 재활성화 전까지 fail-closed 된다(의도된 동작). 기능 이득 없이 운영 절차만 늘어난다.

### 법적 부수 효과 — 왜 OpenRouter 가 아닌가

`docs/consent/legal-risk-assessment-v1.md` R1 과 `legal-review-packet-v1.md` 질문 3 은 국외 이전(개인정보보호법 제28조의8) 분석을 **"Anthropic, 미국"이라는 단일 수령자** 위에 세웠고, 법이 요구하는 고지 항목에 **"받는 자의 이름과 연락처"·"이전되는 국가"** 가 들어 있다. OpenRouter 는 여러 사업자로 넘기는 중계자라 그 두 칸을 기본 상태에서 채울 수 없다 — 분석의 전제가 깨진다.

OpenAI 직접 호출은 **단일 수령자 구조를 그대로 유지**한다. 따라서 문서 3종은 수령자명만 바꾸면 되고 분석 구조는 손대지 않는다. L4(수령자 명시 여부)는 **여는 조건이 그대로 살아 있다** — 법률 검토 트랙 동결(D46)은 이 결정으로 풀리지 않는다.

`yellow` 남는 사실 하나: OpenAI API 는 기본적으로 남용 감시 목적으로 입력을 일정 기간 보관한다(학습에는 미사용). 보관 정책은 사업자마다 다르므로, 실제 당사자 운영을 시작할 때 이 조건을 확인하는 것이 재개 항목에 포함된다.

## 결정 2 — 불일치 검출의 재료를 스냅샷으로 제한한다 (R3 위반 해소)

두 호출 경로의 재료가 서로 달랐다.

| 경로 | 보내던 텍스트 | 판정 |
|---|---|---|
| 승인 대상 초안 | `ai_masked_source_snapshots` — 장비가 NER 마스킹한 스냅샷 | 문제 없음 |
| 불일치 검출 | `sessions.memo` **원문** + 승인 요약을 `maskRegisteredPii` **1차만** 걸어서 | **R3 위반** |

ADR-0022 가 경고한 바로 그 구멍이다 — 수기 메모의 "아들 김철수"는 금고에 없어 1차 치환이 잡지 못한다. 켜진 적이 없어 실제 유출은 없었지만, 켜는 순간 발생한다.

`collectDiscrepancyDetectionSources` 는 이제 **회차별 최신 마스킹 스냅샷만** 재료로 삼는다. 스냅샷이 없는 회차는 재료에서 빠지고, 트리거 회차에 스냅샷이 없으면 검출 자체가 스킵된다(D8: 다음 공식화 때 재검출).

## 결정 3 — 텍스트 일감 큐 (ADR-0022 이행)

결정 2 는 "수기 메모 회차에는 스냅샷이 영영 안 생긴다"는 문제를 남긴다. 장비의 일감 목록이 `audio_r2_key IS NOT NULL` 로 걸러지기 때문이다. ADR-0022 가 예고한 대로 **텍스트 일감 표를 신설**한다(마이그레이션 0029 `ai_text_work_queue`).

- 기록이 공식화될 때마다(수기 저장 · AI 정리 승인) 한 행이 쌓인다. 재대기는 회차당 1건(부분 유니크 인덱스), 완료 행은 불변이다.
- 장비는 같은 폴링에서 두 큐를 함께 가져간다(`GET /pipeline/text-jobs`). 원문은 1차 치환까지 끝난 상태로 받아, NER·사전·정규식 계층을 얹은 뒤 기존 `POST /sessions/:id/ai/source` 로 스냅샷을 만든다.
- **검출 시점이 옮겨진다**: 이제 스냅샷이 도착하는 순간 불일치 검출이 돈다. 기록 저장 시점에도 시도하지만 스냅샷이 없으면 조용히 스킵된다.
- **처리할 수 없는 일감은 장비에 보이지 않는다.** 큐는 삭제가 없으므로(0029 트리거), ② 동의 근거가 없거나 파일럿이 꺼져 있거나 마스킹할 공식 텍스트가 없는 행을 내보내면 장비가 매 폴링마다 같은 행에 걸려 실패하고 큐가 영원히 쌓인다. `listTextWorkItems` 가 그 세 조건을 목록 단계에서 건다 — 조건이 갖춰지는 순간(② 동의가 기록되는 순간) 같은 행이 저절로 보이므로 일감을 다시 쌓을 필요가 없다.
- 기존 표를 재사용하지 않은 이유는 ADR-0022 그대로다 — `ai_status` 는 승인 이력과 부딪히고, `ai_work_items` 의 `UNIQUE (session_id, kind)` 는 재검출을 막는다.

## 결정 4 — 동의 근거 배선 (ADR-0022 이행)

화면의 D49 ② 동의(`support_cases.consent_*_at`)와 AI 초안을 막는 `pilot_text_ai_consent_evidence` 가 서로 모르는 채 둘 있었다. 그대로 두면 **동의를 다 받은 케이스에서도** 0026 트리거가 초안 저장을 거부한다. API 경로도 서버 액션도 구현돼 있었지만 **어떤 화면도 호출하지 않았다**.

이제 ② 체크가 근거 행을 만든다 — 등록(`createParticipantWithSupportCase`)과 정보 페이지 수정(`updateParticipantConsent`) 두 자리 모두. 그 시점의 **문안 버전과 해시**를 함께 남기므로 "어느 문안에 동의했는가"에 답할 수 있다(D46 동결이 풀릴 때 필요한 것이 이것이다). 문안 조각의 정본은 `db/consent-notice.ts` 이고 화면 문안이 그것을 그대로 렌더한다 — 해시와 화면이 어긋날 수 없다.

- 철회는 새 근거를 만들지 않는다(근거 표는 append-only). 사용 차단은 `consent_text_ai_at` 이 맡는다.
- 파일럿 스위치(`TEXT_AI_PILOT_ENABLED`)는 **사용**을 막을 뿐이므로, 근거는 스위치 상태와 무관하게 남는다.
- 실무자가 새로 할 일은 없다. 화면도 바뀌지 않는다.

## 실측 (2026-07-31, 미리보기 환경)

배선을 만든 뒤 **미리보기에서 종단으로 한 번 돌렸다.** 수기 저장 → 큐 적재 → 장비 마스킹 → 스냅샷 저장 → 일감 완료가 전부 성공했고, 큐는 0으로 돌아왔다.

그 과정에서 세 가지가 드러났다.

**① 미리보기에서는 장비 시점이 없었다.** 코드 게이트는 항상 사람(실무자·관리자) 신원만 공급하므로 `service` 전용 엔드포인트를 부를 수 없었다 — 즉 이 결정을 만든 뒤에도 **실물로 확인할 방법이 없는 상태**였다. 관리자 시점과 같은 규칙으로 종단 점검 코드를 하나 더 뒀다(`PREVIEW_E2E_ACCESS_CODE`, 코드+이메일 둘 다 있어야 열림, 헤더로 고르는 신원은 환경 변수에 적힌 이메일로 제한). 절차는 `docs/ops.md`.

**② 기존 케이스는 동의를 다시 저장해야 한다.** 시드 케이스는 `consent_text_ai_at` 이 이미 차 있었지만 근거 행은 0건이었다 — 그 컬럼이 이 배선 이전에 찍혔기 때문이다. 화면에서 ②를 다시 저장하고 나서야 근거 행이 생기고 일감이 장비에 보였다. **운영 전환 시 기존 케이스 전부에 해당한다.**

**③ `red` 인명 마스킹은 NER 모델이 있어야 동작한다.** `[전화번호]`·`[질환]` 은 정규식·사전 계층이 잡았지만 `아들 김철수` 는 스냅샷에 그대로 남았다(NER 미설정으로 돌린 결과). 이 문서가 인용한 바로 그 사례다 — 장비에 `CCC_NER_MODEL_ID` 를 설정하지 않으면 2단 방어의 인명 계층이 비어 있다. **결정 2가 닫은 것은 "마스킹을 거치지 않은 텍스트가 나가는 길"이지, 마스킹의 품질이 아니다.**

**`red` 그리고 관측이 없다.** 스냅샷 POST 는 `ok`로 끝나고 예외·로그가 0건이었다. 실패를 삼키는 계약(D8) 때문에 **사업자를 불렀는지·실패했는지·정말 불일치가 없었는지 바깥에서 구분할 수 없다.** 최소 관측 수단은 별도 티켓으로 뺐다.

## 결과

- 사업자를 바꿀 때 고칠 자리는 여전히 한 곳(`ai-provider.ts`)이다. LLM 호출을 장비로 옮기지 않은 이유는, 옮기면 이미 동작하는 출력 검증·금지 출력 차단·설정 해시 fail-closed 를 파이썬으로 다시 만들어야 하고, R3 의 실질(마스킹 안 된 텍스트가 나가지 않는 것)은 결정 2·3 으로 이미 닫히기 때문이다.
- 처리 장비가 꺼져 있으면 수기 메모 회차의 불일치 검출도 다음 영업일까지 안 나온다(D8 SLA 안, 브리핑은 수기 메모 폴백으로 계속 동작 — D5).
- `docs/api-contract-pipeline.md` 에 텍스트 일감 엔드포인트 3개를 추가해야 한다.
- 문서 정정 대상: CLAUDE.md §2 표 2행, R3 의 Claude 언급 3곳, §5 파이프라인 도해와 모델 정보, 9장 D57 행. 동의 문서 3종의 수령자명(Anthropic → OpenAI).
