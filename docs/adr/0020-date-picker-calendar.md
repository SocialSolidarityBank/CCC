# ADR-0020 — 상담 일시 입력: 달력 + 직접 입력 병행, 달력 알맹이는 react-day-picker

- 상태: 채택 (2026-07-30)
- 결정: **D48**
- 관련: D34(색·깊이) · D37(레이아웃) · D30(shadcn 골격 차용) · 레인 D 1군(`artifacts/ui-revision-sweep-v1/lane-d-prep.md`)

---

## 맥락

UI 수정 스윕의 훑기 결함 **R6** — 날짜 입력칸이 `mm/dd/yyyy` 로 보인다 — 를 고치는 과정에서
원인이 밝혀졌다. 네이티브 `<input type="date">` 는 **제출값**(`YYYY-MM-DD`, 어디서나 같음)과
**보이는 글자**(보는 사람의 브라우저 UI 언어를 따름)가 다른 부품이다. 페이지 로케일은
무시된다. 즉 같은 화면이 **팀원마다 다르게 보인다.**

레인 D 1군에서 **생년월일 2곳**은 글자 입력칸(`DateTextInput`)으로 바꿔 해결했다. 근거는
**KRDS(대한민국 정부 디자인 시스템)** 의 `날짜 입력 필드` 규격이다 — 생년월일처럼 **이미 아는
날짜**는 단일 입력 필드로 받는다.

같은 규격이 **나머지 4곳은 다르게** 지정한다. KRDS 는 날짜 선택기(달력)를 쓸 조건을
*"서비스 이용 시점으로부터 멀리 떨어진 과거 날짜나 미래 날짜를 입력해야 하거나, **요일 정보가
중요한 상황**"* 이라고 못박는다. 상담 일시는 정확히 그 조건이다 — 실무자는 "다음 주 화요일
오후"처럼 **요일로** 상담을 잡는다.

대상 4곳:

| 화면 | 파일 | 값 |
| --- | --- | --- |
| 상담 등록 | `apps/web/app/schedules/new/schedule-wizard.tsx` | 상담 일시 |
| 인테이크 위저드 | `.../records/intake/intake-wizard.tsx` | 상담 일시 |
| 상담 기록 작성 | `.../records/new/record-onepage.tsx` | 상담 일시 |
| 액션 아이템 | `.../records/new/action-item-fields.tsx` | 기한 |

## 결정

### 1. 달력을 달되 입력칸을 없애지 않는다 — 둘 다 쓴다

Q 결정(2026-07-30)이자 KRDS 요구다:

> *"날짜 선택기를 사용하는 경우에도 입력 필드를 사용 불가나 읽기전용 상태로 변경하지 않고
> **키보드를 이용하여 사용자가 직접 날짜를 입력할 수 있도록** 한다."*

즉 달력은 입력칸을 **대체하지 않고 옆에 붙는 보조 장치**다. 1군이 만든 `DateTextInput`
(숫자만 치면 하이픈 자동)이 그대로 본체이고, 오른쪽에 달력 버튼이 하나 붙는다.

### 2. 달력 알맹이는 `react-day-picker`(MIT, v10) — 이 레포의 첫 화면 라이브러리

**이것이 이 ADR 이 필요한 이유다.** 지금 `apps/web` 의 화면 의존성은 `lucide-react`(아이콘) ·
`pretendard`(서체) · `qrcode.react` 뿐이고, `components/wire/` 의 부품은 **전부 손으로**
만들었다. 라이브러리를 하나 들이는 것은 스윕 항목이 아니라 방향 결정이다.

**직접 만들지 않는 이유는 접근성이다.** 달력의 어려운 부분은 그리는 것이 아니라
**키보드 방향키로 날짜 격자를 이동하는 동작과 스크린 리더 낭독**이고, 이건 손으로 만들 때
가장 조용히 틀리는 영역이다. KRDS 도 *"달력에서 제공되는 모든 기능을 키보드로 실행할 수
있도록 한다"* 를 요구한다. 검증된 구현에 맡긴다(Q 선택).

라이선스·의존성 확인(2026-07-30, npm 레지스트리 실측):

| 항목 | 값 |
| --- | --- |
| 버전 | 10.0.1 |
| 라이선스 | **MIT** (명시) — §5 '라이선스 미표기 저장소 금지' 기준 통과 |
| peer | React `>=16.8.0` (이 레포는 19) |
| 의존성 | `date-fns@^4.1.0` · `@date-fns/tz@^1.4.1` (라이브러리가 직접 물고 온다) |

`date-fns` 가 함께 들어온다 — 한국어 월·요일 표기(`ko` 로케일)를 이 라이브러리가 그 로케일로
처리한다. **날짜 계산·표시를 앱 코드에서 `date-fns` 로 옮기지는 않는다** — 우리 쪽 형식 처리는
1군의 `formatDateDigits` 로 이미 있고, 의존 표면을 달력 한 곳으로 묶어 둔다.

### 3. 겉모습은 D34 토큰으로 정의한다 — 새 색을 만들지 않는다

D34 는 화면 1개에서 역추출한 것이라 "입력칸·모달·포커스는 미관찰"을 스스로 적어 뒀다.
그런데 **팝오버에 필요한 값은 이미 전부 있다** — 새로 발명하지 않는다.

| 요소 | 값 | 출처 |
| --- | --- | --- |
| 팝오버 패널 | `--panel` 흰 면 · `--radius-card` 12 · `--shadow-soft` | DESIGN.md §3-1·§3-2 (모달과 같은 계약) |
| 쌓임 층 | `z-index: 30` (드롭다운) | §4-5 z-index 4층 |
| 선택된 날짜 | `--blue-base` **면** + `--ink` 글자 | §1-2 (`base` 는 면 전용) · 블루 = 시간·상태 축 |
| 오늘 | `--blue-tint` 배경 + `--ink` 글자 | 같음 |
| 요일 머리글 | 14/700 `--sub` | §2 |
| 포커스 | `outline: 2px solid var(--blue-deep)` + offset 2 | §5 포커스 계약 |
| 월 표기 | `2026년 8월` · 요일 `일 월 화 수 목 금 토` | KRDS 달력 규격 |

`red` **읽어야 하는 날짜 숫자에 `deep` 글자를 쓰지 않는다.** `--blue-deep` 은 흰 위 대비
2.47 로 WCAG 미달이다(§9 알려진 예외는 **보조 정보 한정**). 날짜는 읽어야 하는 값이므로
`--ink` 를 쓰고, 블루는 **면과 배경으로만** 나타난다. D47 이 세운 칩 규칙과 같은 원리다.

`green` **테두리에 그라데이션을 두르지 않는다** — DESIGN.md §5 의 락이다(그라데이션 stroke 는
리스크 배너와 '활성' 상태 전용). 팝오버는 그림자로 뜬다.

### 4. 시간은 별도 칸이다

`react-day-picker` 에는 시간 입력이 없다. 상담 일시 3곳은 **날짜 칸 + 시간 칸** 두 개가 되고,
제출값은 지금과 같은 `YYYY-MM-DDTHH:mm` 문자열로 합쳐 보낸다 — **서버·게이트웨이는 손대지
않는다**(1군과 같은 규율). 액션 기한 1곳은 날짜만이라 시간 칸이 없다.

## 결과

**얻는 것**

- 날짜 표기가 보는 사람 환경에 흔들리지 않는다 — R6 이 4곳에서 닫힌다
- 요일이 보인다 — 상담을 요일로 잡는 실제 흐름과 맞는다(KRDS 조건)
- 키보드 이동·스크린 리더 낭독을 검증된 구현이 담당한다
- 마우스·키보드 어느 쪽도 막지 않는다(KRDS 요구)

**치르는 것**

- `yellow` **이 레포의 첫 화면 라이브러리다.** 다음에 "부품 하나만 더" 요청이 왔을 때
  기준선이 낮아진다. 그래서 이 ADR 이 **선례가 아니라 예외**임을 못박는다 — 부품 도입은
  계속 ADR 사항이고, 판단 기준은 "**접근성처럼 손으로 만들면 조용히 틀리는 영역인가**"다.
- `yellow` 번들이 커진다(`react-day-picker` + `date-fns` + `@date-fns/tz`). 달력을 쓰는
  화면에서만 불러오도록 묶는다.
- `yellow` D34 에 없던 팝오버 시각 언어가 생긴다. 위 표가 그 정의이고, **전부 기존 토큰의
  조합**이라 새 색·새 반경·새 그림자는 0개다.

**하지 않는 것**

- 생년월일 2곳에는 달력을 달지 않는다 — KRDS 가 단일 입력 필드로 지정한 자리다(1군 유지)
- 앱 코드 전반의 날짜 계산을 `date-fns` 로 옮기지 않는다 — 의존을 달력 한 곳에 가둔다
- 새 마이그레이션 없음 · 서버 액션·게이트웨이 변경 없음(제출값 형식 동일)

## 개정 (2026-07-31) — 날짜·시각을 한 상자, 한 패널로

Q 보고: "날짜 선택 창이 너무 구리다. 날짜랑 시간을 같이 고르는 부품으로 바꿔 달라."

**진단은 부품 교체가 아니라 두 가지였다.**

1. **모양** — `DateTimePickerControl` 이 테두리를 각자 가진 세 부품(날짜칸 · 달력버튼 · 시각칸)을
   나란히 세워, 하나의 값을 적는 자리로 읽히지 않았다. 달력을 열어도 시각은 따로 쳐야 했다.
2. **`red` 실제 결함** — 선택한 날짜에 색이 칠해지지 않았다. 이 ADR 이 정한 "선택일 = blue base 면"
   규칙이 `var(--blue-base)` 로 쓰였는데 **그 토큰은 존재하지 않는다**(정본은 `--blue`,
   `design/tokens.css:22`). 값이 비어 있으니 배경이 투명해져 선택 표시가 라이브러리 기본
   테두리뿐이었다. 같은 오타가 `--rdp-accent-color` · 오늘 날짜 테두리까지 3곳이었다.

**바꾼 것**

- 날짜칸과 시각칸이 **테두리 하나를 공유**한다(`.wire-datetime-fields`, 세로선 1px 로만 나뉨).
  초점 링도 껍데기가 받는다 — 안쪽마다 링이 뜨면 상자가 둘로 보인다.
- 팝오버 하나에 **달력 + 시각 목록(07:00~21:00, 30분)** 이 나란히 선다. 열면 이미 고른 시각으로
  목록이 감긴다(`scrollIntoView` 가 아니라 부모 `scrollTop` — 전자는 페이지까지 감아 화면이 튄다).
- 날짜를 골라도 **닫지 않는다**(시각이 남았다). 닫는 길은 `완료` · Escape · 바깥 누르기 셋이고
  전부 초점을 여는 버튼으로 되돌린다.
- `--blue-base` → `--blue` 3곳 정정.

**바뀌지 않은 것** — 이 ADR 의 본문이 정한 것은 전부 그대로다.

- 두 칸 다 키보드로 직접 칠 수 있다(KRDS: 선택기가 입력 필드를 대체하지 않는다)
- 달력 알맹이는 `react-day-picker` 그대로. shadcn/ui 의 날짜 선택기도 같은 조합
  (react-day-picker + 팝오버)이라, Q 가 고르라고 한 5개 중 shadcn 이 맞는 답이고
  **그 엔진은 이미 이 레포에 있다** — 갈아끼울 일이 아니라 팝오버를 다시 그릴 일이었다.
  heroui 는 React Aria + `@internationalized/date` 를 함께 끌고 오므로 예외를 한 번 더 여는 셈이다.
- 제출값 `YYYY-MM-DDTHH:mm` · 보이는 두 칸의 이름(`<name>Date`·`<name>Time`, 임시본 복원용) ·
  숨은 칸. **서버 액션·게이트웨이·마이그레이션 변경 0.**
- 새 색·새 반경·새 그림자 0개.
