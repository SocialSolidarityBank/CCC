# ADR-0014: 사업 워크스페이스 중심 IA — 사이드바 셸 · 참여자 정보 허브 · 참여자 우선 등록

- 상태: 승인 (2026-07-26, Q — 그릴링 세션). 결정 번호 **D35**.
- 번호 이력: 최초 D34로 적었으나, 같은 날 `design/refero-system`이 파스텔 액센트 시스템을 D34로 확정·태그(`design-system-v0.1`)했으므로 **D35로 내렸다**(2026-07-26 Q 결정). main의 D34는 그 브랜치가 머지될 때 채워진다.
- 관계: **D21(상담 일정 화면)의 상단 헤더 구조를 대체**한다. 시각 언어는 **D34/ADR-0012(CCC-design-system V0.1)를 따른다** — 이 ADR은 배치·동선만 정하고 색·형태·컴포넌트 계약은 `DESIGN.md`가 정본이다. D22·D24·D31(브리핑 구조·PII 표시), D27(멀티테넌트), D30/ADR-0008(디자인 락), D33/ADR-0013(목표 3층)은 불변.
- 배경 발단: 2026-07-26 Q의 미리보기 실사용 점검 — "헤더에 등록만 2개 있고 설정은 프로필과 중복", "사업별로 보이는 내용이 다른데 사업 접근성이 낮다", "전체 사업 보기가 비직관적", "상담 등록에서 참여자를 먼저 골라야 할 정보가 뒤에 나온다".

## 배경

기존 IA는 **개별 상담 일정 중심**이었다. 홈(`/`)에서 조직 아코디언 → 사업 한 줄 → 상담 카드 → 브리핑으로 내려가는 단선 구조라, 브리핑에 도착한 뒤 옆으로 움직일 길이 없었다. 참여자라는 사람 단위로 모아 보는 자리도, 사업을 바꿔 다는 자리도 없었다.

동시에 같은 말이 두 층을 가리키고 있었다. 화면의 "참여 사업"은 조직이 운영하는 **사업**(`programType`)이기도 했고 참여자 1명 × 사업 1개인 **케이스**(`supportCaseId`)이기도 했다. 이 상태로는 "사업별 워크스페이스"가 어느 층인지 정할 수 없었다.

## 결정

### 1. 용어 3종 확정 (CONTEXT.md 반영 완료)

| 용어 | 뜻 |
| --- | --- |
| **사업** | 조직이 운영하는 지원 프로그램 자체. 참여자와 무관한 조직 단위 |
| **참여 사업** | **케이스의 화면 표기**. 참여자 1명 × 사업 1개 |
| **워크스페이스** | 지금 선택된 **사업 컨텍스트**. 새 데이터 개념이 아니라 화면의 상태 |

### 2. 셸 = 사이드바. 축은 장소 / 행동으로 가른다

상단 헤더를 폐기하고 좌측 사이드바(240px)로 간다. 배치 원칙은 **사이드바 = "어디를 보나"(장소), 페이지 우상단 = "무엇을 하나"(행동)**다.

```
┌────────────────────┐  ┌──────────────────────────────────┐
│ ⬡ 사회연대은행      │  │ 상담 일정   [참여자 등록][상담 등록] │
│ ▾ 마이크로크레딧…   │  │                                  │
│  ────────────────  │  │  ⌕ 참여자 검색                    │
│ 📅 다가오는 일정    │  │  ◷ 오늘 상담 / 다가오는 상담       │
│ 🗓 전체 일정        │  │                                  │
│ 👤 참여자           │  └──────────────────────────────────┘
│                    │
│ ⚙ 설정              │
└────────────────────┘
```

- **사업 전환기는 조직명 바로 아래, 메뉴 위**에 둔다. 워크스페이스는 그 아래 모든 메뉴(일정·참여자)의 **범위를 정하는 것**이므로 위에 있어야 포함 관계가 눈으로 읽힌다. 사업이 1개인 동안은 드롭다운 없이 라벨만 표시하고, 2개부터 `▾`가 생긴다.
- **등록 2개는 사이드바에 넣지 않는다.** 섞으면 누를 때마다 "화면이 바뀌는 것"과 "새로 만드는 것"을 판별해야 하고, 등록은 들어가면 위저드라 되돌아 나올 데가 모호해진다.
- 설정은 사이드바 1곳만 남긴다(구 헤더 좌측 링크 + 프로필 드롭다운 이중 진입 폐기).
- `/`는 마지막에 선택한 사업의 일정으로 곧장 보낸다. 사업이 1개뿐인 지금 조직 아코디언은 항상 같은 곳으로 가는 빈 클릭이다.
- '오늘 상담'은 별도 메뉴로 나누지 않는다 — 한 화면에 오늘+다가오는이 함께 있어야 "오늘 걸 보려면 어느 메뉴지"를 판단하지 않는다.

### 3. 참여자 정보 페이지를 허브로 승격

기존 `/participants/[beneficiaryId]`(제목 "참여 사업", 사업 카드 목록뿐)를 **참여자 정보**로 승격한다. 참여자 본인 정보 + 참여 중인 사업 목록을 담고, 사업별로 브리핑·기록으로 갈라진다. 사이드바 '참여자' 메뉴의 도착지이기도 하다.

사람은 사업보다 크므로 **이 페이지는 워크스페이스 범위를 벗어난다** — 현재 선택된 사업 밖의 참여 사업도 보인다.

### 4. 브리핑의 출구는 버튼 2개, 이름 바로 아래

```
┌─ HERO 카드 ─────────────────────────────────┐
│ 김미영 (swallow-003)  [상담 준비]      [상담 시작] │  ← 1행 유지
└────────────────────────────────────────────┘
  [참여자 정보] [상담 기록]                        ← HERO 밖
┌─ 리스크 배너 ───────────────────────────────┐
```

**이동 버튼 2개는 HERO 카드 밖, 바로 아래 줄에 둔다**(2026-07-26 Q 확정). D34/DESIGN.md §5 `HERO 좌측 묶음`이 "`이름 (가명 ID)`를 한 줄로 두고 배지는 오른쪽 간격 20, 2행으로 나누면 HERO의 위아래 여백이 깨진다"고 규정하므로, 버튼을 HERO 안에 넣으면 그 계약을 깬다. 밖에 두면 규정을 지키면서 "이름 아래"라는 위치 의도도 살아남는다. 리스크 배너는 그 아래로 내려간다.

이름 표기는 D34/DESIGN.md §5 '이름 표기' 계약을 따른다 — 어디서나 `이름 (가명 ID)` 한 줄이고, 실명은 그 자리의 제목 크기(HERO 28/700) `--ink`, 가명 ID는 항상 16/400 `--sub`, 사이 간격 4다.

- **브레드크럼은 기각**했다. `사업 › 참여자 › 이번 상담` 표기는 상담사에게 학습이 필요한 관례다 (Q 판단).
- `← 목록으로` / `전체 사업 보기`는 삭제한다. 워크스페이스 복귀는 사이드바가 상시 담당하므로 중복이고, "전체 사업 보기"는 이름 자체가 무엇을 여는지 알려주지 못했다.
- 두 버튼은 **이름·가명 ID 바로 아래**에 붙인다. 둘 다 "이 사람에 대해 더 보기"라서 이름 옆에 있어야 무엇의 정보인지 읽히고, 아래 툴바로 내리면 '전체 열기/닫기'(화면 조작)와 섞여 성격이 흐려진다.
- `상담 시작`은 이동이 아니라 기록 작성 진입이므로 우상단(행동 자리)에 남는다.
- ✔ 가명 ID 위치는 **해소됐다** — D34/DESIGN.md가 `이름 (가명 ID)` 한 줄 상시 노출로 확정했다(숨김·조건부 노출안 기각). 세션 중 열려 있던 "실명 아래 한 단" 안은 채택되지 않았으므로 버튼 줄과 자리를 다투지 않는다.

### 5. 상담 등록은 참여자 선택이 먼저

1단계 순서를 **참여자 → 상담 유형 → 일시**로 바꾸고, 참여자를 고르기 전에는 뒤 항목을 보이지 않는다.

- **조직·참여 사업 선택은 삭제**한다 — 사이드바 워크스페이스가 이미 정해준 값이라 다시 묻는 것이 중복이다.
- **상담 방법은 숨긴다** — 현재 '대면' 하나뿐이다(D4). 선택지가 늘면 되살린다.
- **상담 유형은 케이스 상태에 따라 자동 기본값**을 잡는다: 인테이크가 없으면 '인테이크', 있으면 '기본 상담'. 다른 유형은 "다른 유형 선택"을 펼쳐야 나온다.
- 이미 인테이크가 있는 케이스에서 '인테이크'를 펼치면 **경고 + 기존 인테이크 기록지 링크**가 함께 뜬다. 선택 자체는 막지 않는다.

## 고려한 대안과 기각 이유

- **사이드바에 '등록' 그룹을 만든다** (Q의 초안): 장소와 행동이 한 기둥에 섞인다. 새 UI가 이미 등록을 페이지 우상단 액션으로 옮겨 둔 상태라 그대로 둔다.
- **브레드크럼**: 출구 2개를 한 줄로 줄이면서 현재 위치까지 알려주는 이점이 있었으나, 비개발자 상담사에게 익숙하지 않다는 이유로 Q가 기각.
- **인테이크 선택지 완전 제거**: 가장 깔끔하지만 CCC-14에서 Q가 이미 내린 "차단이 아니라 경고" 결정을 번복한다. 장기 중단 후 재개로 인테이크를 다시 해야 할 때 우회로가 없어진다. 자동 기본값 + 접힘이 두 요구를 모두 만족한다 — 평소엔 안 보이고, 필요하면 열 수 있다.
- **홈 아코디언 유지 + 사업 1개일 때만 자동 통과**: 가장 적게 고치지만, 사업이 2개가 되는 순간 매번 거쳐야 하는 화면으로 되돌아온다.

## 결과 — 후속 작업

- `yellow` **참여자 정보 페이지의 PII 미표시는 D31 위반이다 — 다만 남은 일은 화면뿐이다.** 이 페이지는 실명이 아니라 "참여자 ID swallow-003"을 제목으로 쓴다(`apps/web/app/participants/[beneficiaryId]/page.tsx:71`). **원인 진단을 2026-07-26 정정한다**: API는 이미 PII를 내려준다 — `listSupportCasesForBeneficiary`가 `participant`(이름·연락처)를 싣고(`db/gateway.ts:6568`), 라우트가 `participantName`·`participantPhone`으로 응답에 넣으며(`apps/api/src/request-handler.ts:793`), 화면 단위 감사도 이미 남는다(`db/gateway.ts:6566`). 남은 작업은 웹 타입(`apps/web/app/lib/api.ts:210` `ParticipantDetail`)에 두 필드를 더하고 제목을 `이름 (가명 ID)`로 바꾸는 것뿐이다. **감사를 새로 붙이지 않는다** — 이미 있어 중복이 된다.
- **'전체 일정'은 신규 화면**이다. 현재는 오늘+향후 7일(`getUpcomingSchedules`)만 있다.
- **CCC-15(목표 3층)는 이 IA가 확정된 뒤에 구현**한다. CCC-15가 고치는 화면(브리핑 게이지, 상담 등록 2단계 목표 입력)이 정확히 이 ADR이 옮기는 화면이라, 순서를 뒤집으면 같은 파일을 두 번 갈아엎게 된다.
- ⚠ **디자인 시스템 적용 작업과 겹친다.** `docs/handoffs/2026-07-26-design-system-v0.1-to-app.md`(design 브랜치)는 `--wire-*` 토큰 치환과 컴포넌트 계약 12종 구현을 계획하는데, 그중 **사이드바가 2절의 셸과 같은 대상**이다. 두 번 만들지 않으려면 사이드바는 한쪽에서만 만든다 — 이 ADR은 **무엇을 어디에 두는지**만 정하고, 그것을 **어떤 색·형태로 그리는지**는 DESIGN.md가 정한다. 그 핸드오프의 "화면 티켓과 병렬 금지" 목록(CCC-12·11·14·15)은 이 ADR의 티켓(CCC-18·17·16)이 만들어지기 전에 작성돼 그 셋이 빠져 있다.
- CCC-14(인테이크 게이트)는 5절의 필드 순서 변경이 **선행 조건**이다 — 참여자가 정해지기 전에는 "이미 인테이크가 있습니다" 경고를 띄울 시점 자체가 없다.

## 개정 — 착수 전 확인 2건 (2026-07-26, Q 확정)

이 ADR을 실제 화면에 적용하기 직전에 열려 있던 판단 2건을 Q가 닫았다. 착수 전 확인 목록의 세 번째 항목(비담당 사업 참여자의 PII 범위)은 **질문 자체가 성립하지 않아 폐기**한다 — 코드를 확인하니 담당하지 않는 참여자는 검색 결과에도 뜨지 않고(`db/gateway.ts:6638`), 참여자 페이지도 권한 있는 사업이 0건이면 `ForbiddenError`로 막는다(`db/gateway.ts:6548`). 그 자리에서 실제로 열려 있던 질문은 아래 1번이다.

### 1. 참여자 정보 페이지는 같은 조직의 전 참여 사업을 보여준다 (D36)

한 참여자가 사업 A(내 담당)와 사업 B(동료 담당)에 함께 참여할 때, **사업 B도 목록에 나온다.** 다만 보이는 것은 **어떤 사업에 참여 중인지와 참여자 정보까지**이고, **상담 내용(세션 기록·브리핑·목표)은 담당 케이스만** 열린다.

Q의 근거: *"어차피 정보는 담당자인 나한테 오픈됨"* — 이 페이지를 여는 사람은 이미 그 참여자의 담당자라 PII를 보고 있다. 그 사람에게 "이 참여자가 사업 B에도 있다"는 사실을 가리는 것은 지킬 것을 지키지 못하면서 중복 지원 확인만 어렵게 만든다.

**전제가 되는 게이트는 그대로 둔다** — 그 참여자의 케이스를 **1건도 담당하지 않으면 페이지 자체가 열리지 않는다**(`ids.length === 0 → ForbiddenError`). Q의 근거가 "나는 이미 담당자다"에 기대고 있으므로, 이 게이트를 풀면 근거가 무너진다. 구현할 때 **접근 판정용 집합(담당 케이스)과 표시용 집합(조직 전체 케이스)을 분리**하고, 게이트가 여전히 막는다는 것을 테스트로 고정한다.

D7("담당자+관리자 열람")과의 관계: D7을 넓히는 것이 아니라 **적용 대상을 좁혀 다시 말한다** — 담당 케이스만 열리는 것은 **상담 내용**이고, **참여 사업의 존재와 담당자 이름**은 같은 조직 상담사에게 보인다. D25(배정 책임자 PII)는 불변.

`yellow` **동의서 문안에 반영이 필요하다.** CLAUDE.md §8의 열람 범위 문구가 지금 "담당자 및 배정 책임자"인데, 여기에 "같은 조직 상담사에게는 참여 중인 사업 목록과 담당자 이름이 보인다"가 더해져야 한다. 법률 검토 항목에 포함한다.

**구현에서 걸러낸 부수 공개 1건 (2026-07-26).** 담당자 이름을 실을 때 `users.name` 미입력을 **이메일로 폴백하면 안 된다.** 다른 화면(관리자 디렉터리)은 그렇게 하지만, 이 목록은 D36 으로 **담당하지 않는 사업까지** 상담사에게 내려간다 — 이메일 폴백을 두면 `listUsers`(admin 전용)로 막아 둔 직원 이메일이 상담사에게 새고, 그건 어떤 결정도 승인하지 않은 공개다. 이름이 없으면 그 담당자를 목록에서 빼고 화면은 담당 줄을 그리지 않는다. 테스트가 응답에 이메일이 섞이지 않는지 확인한다. **직원 표시 이름 입력을 권장하는 것이 후속 과제**다 — 지금은 이름이 비면 "누구에게 물어보나"에 답하지 못한다.

### 2. 마지막 선택 사업은 계정 설정(DB)에 저장한다

`/`가 마지막에 보던 사업의 일정으로 직행하려면 그 값을 어딘가 기억해야 한다. Q는 **브라우저 로컬이 아니라 계정 설정**을 골랐다 — 집 컴퓨터와 사무실에서 같은 사업으로 들어가야 한다.

구현 결과 CCC-18의 범위가 커진다: `users` 테이블에 추가 전용 컬럼(마이그레이션 0011 패턴), gateway 읽기·쓰기 쌍(R1, 쓰기는 D14 감사), API 라우트, 그리고 `/`의 리다이렉트. **저장값이 없거나 그 사업이 사라졌으면 첫 사업으로 폴백**하고 404를 내지 않는다.

## 개정 2 — 사이드바에 나가는 길과 고르는 길을 낸다 (2026-07-31, Q 요청)

§2가 정한 축(**사이드바 = 장소 / 페이지 우상단 = 행동**)은 그대로다. 이번에 더한 셋은 그 축을 어기지 않는다 — 셋 다 '장소'이거나, 축 바깥의 '되돌리기'다.

### 1. 기관명이 홈 버튼이다

`.brand`가 글자에서 `/` 링크가 된다. 서비스 로고를 누르면 처음 화면으로 가는 것은 웹의 보편 관례라 '홈' 메뉴를 새로 만드는 것보다 배울 것이 적고, 메뉴가 하나 늘지도 않는다.

목적지는 `/programs/:type/schedule`이 아니라 **`/`**다. 경로가 사업을 알려주지 않는 화면(당사자·설정)에서는 사이드바가 폴백(첫 사업)을 쓰므로, 거기서 직접 링크하면 **방금 보던 사업이 아닌 첫 사업으로 간다.** `/`는 서버가 계정 설정의 마지막 선택 사업을 읽어 보낸다(위 '개정 1 — 2번').

### 2. 사업 전환기가 실제 드롭다운이 된다

§2는 "사업이 1개인 동안은 드롭다운 없이 라벨만"이라 적고 형태 결정을 2개 시점으로 미뤄 뒀다. 그 미결을 지금 닫는다 — 사업이 2개 이상이면 팝오버 목록이 열리고, **1개면 지금까지처럼 글자로 남는다**(누를 데가 자기 자신뿐인 목록을 여는 것은 누를 곳이 있다고 알려 놓고 아무 일도 안 하는 것이다).

`red` **listbox가 아니라 열고 닫는 목록(disclosure)이다.** 처음에는 `role="listbox"` + `role="option"`으로 적었다가 되돌렸다: ARIA는 `option` 안에 링크 같은 조작 가능한 자식을 금지하고(둘이 같은 노드를 두고 다툰다), `listbox`라고 알리면 화살표 키 이동을 기대하게 만든다. 여기 필요한 것은 '누르면 그 사업으로 가는 링크 목록'뿐이라 **역할을 참칭하지 않는다.** 현재 항목은 `aria-current`로 알린다(메뉴 링크와 같은 방식). 팝오버 동작(바깥 클릭 닫기 · Escape로 닫고 초점을 방아쇠로 되돌리기)은 `date-picker-control.tsx`의 것을 그대로 쓴다.

### 3. 로그아웃 — 나가는 길을 만든다

지금까지 이 앱에는 **나가는 길이 없었다.** 신원은 미리보기 코드 게이트(CCC-6) 또는 운영의 Cloudflare Access가 정하므로, 로그아웃은 "세션을 지우고 신원을 다시 묻는 화면으로 보낸다" 한 가지 뜻이고 목적지는 환경이 정한다:

| 환경 | 지우는 것 | 가는 곳 |
| --- | --- | --- |
| 미리보기(`CCC_PREVIEW='true'`) | `ccc_preview` 쿠키 | 코드 입력 화면 `/preview` |
| 그 외 | (Access가 관리) | `/cdn-cgi/access/logout` |

**GET 링크가 아니라 서버 액션 폼**이다. HttpOnly 쿠키는 클라이언트가 못 지우고, GET이면 프리페치·크롤러가 세션을 끊을 수 있다. 테스트가 이것을 잠근다.

함께 고친 것: **`/preview`도 셸 없이 렌더한다.** 지금까지는 코드 입력 화면에 사이드바가 그대로 떠서, 로그아웃해도 앱 메뉴가 남아 **나갔는데 안 나간 것처럼** 보였다. `x-ccc-public` 헤더가 뜻하는 것은 '신원을 아직 모르는 화면'이고 `/preview`가 정확히 그것이다(새 판단을 더한 것이 아니라 같은 판단에 화면 하나를 넣었다). 이 헤더는 셸 제외에만 쓰이고 어떤 데이터 접근도 가로막지 않는다.

## 개정 3 — 뒤로 가기를 화면에도 낸다 (2026-07-31, Q 요청) — D47 ⑤ 보완

D47은 "브리핑 복귀는 **브라우저 뒤로가기**"로 정하고 앱 안 뒤로가기를 두지 않았다. 그 전제는 **쓰는 사람이 브라우저 뒤로가기를 안다**는 것인데, 심사위원처럼 처음 여는 사람에게는 보이는 출구가 하나도 없다.

그래서 브라우저 기능을 대체하는 것이 아니라 **화면에도 같은 출구를 하나 낸다** — 하는 일은 `router.back()`으로 똑같다. 자리는 **모든 화면 페이지 제목 위 좌상단** 한 곳이고, D35 축을 건드리지 않는다(뒤로가기는 장소도 행동도 아닌 '되돌리기'다).

`yellow` **돌아갈 곳이 없으면 버튼을 그리지 않는다.** 처음에는 그 경우 홈으로 보내려 했는데, 홈(`/`)은 일정으로 **리다이렉트**하는 경로다 — 리다이렉트는 히스토리를 쌓지 않고 갈아치우므로, 링크를 받아 연 사람은 일정 화면에 `history.length === 1`로 도착하고 거기서 홈으로 보내면 **같은 화면으로 되돌아와 아무 일도 안 일어난 것처럼** 보인다. 갈 곳이 없으면 출구를 만들지 않는 편이 정직하다.

레이아웃 함정 하나: `.narrow`는 `--page-max`를 **`.page-content` 자기 자신에** 얹으므로 형제인 뒤로가기 줄이 물려받지 못한다. 좁은 화면(960)에서 '뒤로'가 제목보다 80px 왼쪽에 서는 것을 리뷰가 잡았고, `:has(+ .page-content.narrow)`로 맞췄다.

## 개정 4 — '고정' 자리표시자를 뺀다 (2026-07-31, Q 요청)

다가오는 일정 툴바의 비활성 `고정` 버튼을 제거한다. 누를 수 없는 버튼이 계속 보이면 "아직 안 만든 것"이 아니라 **"고장난 것"**으로 읽힌다. 기능이 실제로 생길 때 다시 넣고, 그때까지 되살아나지 않도록 테스트가 잠근다.
