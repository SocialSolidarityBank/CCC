# ADR-0045: 사업 도입 확인, 사업별 저장 위치와 처리 경로 선택

- 상태: Accepted(2026-09-07 그릴링, 검수 후속 6건은 같은 날 Q 확정. 아래 "Q 확정 기록")
- 결정일: 2026-09-07
- 결정 번호: D87
- 관련: ADR-0035 D63(자료 관리 책임은 사용기관), ADR-0041 D76·D77·D79·D81, ADR-0043 D85, ADR-0044 D86(기관 초기 설정), S2, S7, S8
- 대체: 없음. 채택하지 않은 초안 셋(`inbox/0044-public-project-admission-and-cloud-selection.md`, `inbox/public-project-admission-review.md`, `inbox/2026-09-06-project-ai-eligibility-adr-review.md`)은 "배포기관이 사업마다 심사한다" 축이라 폐기한다. 이 결정은 ADR-0044(D86, 2026-09-06 #282 머지)와 번호가 겹치지 않도록 0045로 발급했다
- 검수: `inbox/2026-09-07-project-admission-review-result.md`(2026-09-07, 읽기 전용 검수 1회). 아래 문안은 그 수정안을 반영한 것이다

## 배경

공공 발주 사업이 늘면서 사업마다 저장 위치와 외부 처리 가능 여부가 갈린다. 배포기관이 계약서를 받아 심사하면 자료 관리 책임을 사용기관이 진다는 D63이 무너지고, 담당자가 답할 수 없는 법적 성격 질문이 화면에 들어온다. 8문항 심사표(2026-09-06 초안)와 4문항 질문식(2026-09-07 1차 제안)은 둘 다 답을 표로 계산해 결과를 내는 순간 판단이 배포기관 쪽으로 넘어와 기각했다. 그래서 심사표가 아니라 선택지와 정확한 고지, 확인 기록을 만든다.

검수(2026-09-07)가 확인한 현재 상태는 다음과 같다. 이 ADR은 이 상태 위에서 결정을 적는다.

- 사업(program)은 데이터로 존재하지 않는다. 온보딩이 기관 이름과 첫 사업 표시 이름 문자열 하나를 `organization_settings`에 저장하고(`migrations/sqlite/0023_organization_onboarding_names.sql`), `programs` 표는 만들지 않기로 되어 있다. 사업 등록 폼도 없다
- 저장 위치는 설치 단위다. 배포 모드는 서명된 install manifest가 정하고(`packages/http-api/src/capabilities.ts`), 세 모드의 저장소는 D76 표가 고정한다
- STT와 LLM 모드는 설치 단위 환경 변수다. 승인 registry가 비어 있어 `sttMode`는 `off`, `sttEngine`은 `null`이고 local·azure 선택지는 모두 비활성이다(D77, S2). 서버는 Azure 키 존재를 항상 `false`로 본다
- Azure STT는 마스킹 전 원음을 받고(D85, S8), OpenAI는 장비가 만든 마스킹 스냅샷만 받는다(R3)
- `storage_mode`, `processing_mode`, `admission_confirmed*`는 레포에 0건이다. 실데이터 거부(E9-3), 원음 입장(E5-6, SG8), 동의 6영역 표(0049)는 미구현이다
- 네이버 클라우드, NCP, CSAP는 문서와 코드 어디에도 없다

## 결정

1. **판단은 사용기관이 하고, CCC는 정확히 고지한다**(D63). 배포기관은 선택지, 설명 문안, `확인하는 법` 매뉴얼, 확인 기록만 제공한다. 계약서를 받아 심사하지 않고, 사업별 계약서 확인 기록지는 만들지 않는다(사용기관 내부 서류다). 경기극저신용 사업을 포함해 배포기관 자신의 사업도 다른 사용기관과 같은 화면에서 같은 선택을 한다. 개발상 따로 관리하지 않는다.

2. **두 축을 사업 단위 속성으로 둔다.** 저장 위치(기본형 / 공공형 / 나중에 정하기)와 처리 경로(외부 허용 / 기관 안 / 나중에 정하기). 기존 `program_type`(`financial_support_v1`)은 상담 기록 템플릿 식별자이고 CHECK가 값 하나만 허용하므로(`migrations/sqlite/0006_participant_support_case_cutover.sql`) 이 축과 별개다. 사업 하나가 `program_type`, 저장 위치, 처리 경로 세 값을 갖는다.

3. **사업 실체를 신설한다.** 이 축은 표 없이 붙지 않으므로 `programs` 표를 만들지 않기로 한 온보딩 결정(CCC-32, 마이그레이션 0023)을 이 ADR이 되돌린다. 기관 초기 설정의 "첫 사업"은 사업 목록의 첫 행이 되고, 사업 등록 폼(관리자만)이 새로 생긴다. 표의 모양은 티켓이 정한다. 기관 단위로 좁히는 대안은 공공 사업 하나만 조건이 다른 경우를 표현하지 못해 기각했다.

4. **저장 위치 선택은 요구 사항의 기록이고, 설치 경계를 넘지 않는다.** 한 설치는 한 저장 위치를 갖는다(D76). 라디오는 "이 사업의 발주처가 무엇을 요구하는가"를 기록하며, 현재 설치가 그 요구를 충족하지 못하면 그 사업은 `나중에 정하기`와 같은 잠금 상태가 되고 폼 머리에 "이 설치는 기본형입니다. 다른 저장 위치는 설치를 따로 해야 합니다"를 표시한다. Local Single과 Local Office 설치에서는 기본형(Supabase 서울) 선택지가 성립하지 않으므로 저장 위치 구획을 렌더하지 않는다. 저장 위치를 기관 단위로만 두는 대안은 "이 사업만 조건이 다르다"를 적을 곳이 없어 기각했다.

5. **네이버 클라우드 공공형은 다음 구현 작업이며 이번 범위에서 빼지 않는다.** 다만 저장 어댑터는 D79 Database 포트 위에서 별도 ADR을 거친 뒤 붙는다. 그 전까지 라디오에 **비활성**으로 보이고 아래에 "준비 중입니다. 이 조건에 해당하면 도입 문의로 알려 주세요. 별도 계약과 설치가 필요합니다" 안내가 붙는다. 고를 수 있게 두면 선택은 됐는데 저장은 안 되는 상태가 생겨 담당자가 설정이 끝난 줄 알기 때문이다. 어댑터가 붙는 날 활성으로 바꾼다(문안 버전 상승).

6. **처리 경로 선택은 상한이지 능력이 아니다.** 실제 가능 여부는 설치의 `sttMode`, `llmMode`, 승인 registry가 정한다. 사업이 `외부 허용`이어도 설치가 꺼져 있으면 꺼진 것이고, 사업이 `기관 안`이면 설치가 외부를 켰어도 그 사업의 원음과 텍스트는 외부로 나가지 않는다. 실효 값은 두 값 중 더 좁은 쪽이다. `기관 안`은 LLM `off`와 정확히 대응하고 STT는 `local`만 허용하지만, STT-G1~G3과 Q 승인 전에는 `sttEngine`이 `null`이라 실제 동작은 녹음 AI 없는 수기 기록이다. 문안은 이 사실을 숨기지 않고, 기관이 보유한 PC·노트북·서버에서 처리하며 일정 이상의 성능(최소 권장 사양)이 필요하다는 사실도 같이 적는다(2026-09-07 Q 지시). 최소 권장 사양의 숫자는 STT-G1~G3(E5-8) 결과로 정하며 그 전에는 매뉴얼에 "측정 뒤 확정"으로 둔다.

7. **미확인은 확정 선택이 아니라 `나중에 정하기`다.** 계약서를 확인하지 못한 사업을 `기관 안`에 흡수하면 확인 체크 문구와 모순되므로 `기관 안` 설명에서 "확인하지 못한" 절을 뺀다. 기본 선택은 없고 미선택은 저장 불가가 아니라 `나중에 정하기`로 둔다(억지로 고르게 하는 것이 더 위험). 명시 선택과 무선택은 저장 값이 같아도 `audit_log` detail에서 구분한다.

8. **확인 체크의 계약.** 폼 마지막 체크 "위 선택은 우리 기관이 계약 조건을 확인하고 정한 것입니다"를 관리자만 할 수 있고, 저장 항목은 관리자 ID, 시각, 선택값 스냅샷, 설명 문안 버전, 문안 sha256이다(동의 6영역의 `copyVersion`·`copyHash` 선례, S7). 무효화 사건은 셋이다. ① 선택 변경 ② 설치의 STT·LLM 설정 변경(설치 단위 값이므로 그 설치의 모든 사업 확인이 한꺼번에 무효화된다) ③ 설명 문안 버전 변경. 무효화되면 재확인 전까지 4·6의 잠금과 같다. 두 축 중 하나라도 `나중에 정하기`면 체크를 요구하지 않는다(확인한 것이 없는데 확인 문장에 서명하게 되기 때문). **화면은 무효화를 "무효화"라는 말로 설명하지 않는다**(2026-09-07 Q 지시): 무엇이 밖으로 나가게 됐는지, 그래서 왜 다시 봐야 하는지, 확인 전에 무엇이 잠기는지를 초등학생도 읽을 수 있는 말로 적는다(아래 문안 v1 "다시 확인 안내"). ②는 관리자 한 명의 설정 한 번이 사업 여러 개를 잠그므로, `AI·STT·연결` 탭이 저장 전에 "저장하면 N개 사업을 다시 확인해야 합니다"를 보여 준다.

9. **선택지 문안은 조건형이고, 사업 유형 어휘를 쓰지 않는다.** "이 사업은 X다"가 아니라 "X인 경우"로만 말한다. 자체사업, 보조사업, 민간위탁, 용역 같은 재원·계약 형식 어휘와 개인정보 처리위탁을 한 문장에 섞지 않는다. 담당자가 답할 수 없는 앞절(재원 유형, 법적 성격)은 결과를 바꾸지 않으므로 전부 지운다. 아래가 확정 문안 v1이다. 문안을 바꾸면 새 버전과 sha256을 발행한다.

### 확정 문안 v1 (사업 등록 폼)

**데이터 저장 위치** (Community Cloud 설치에서만 렌더)

- 폼 머리 안내: "이 설치는 기본형입니다. 다른 저장 위치는 설치를 따로 해야 합니다."
- `기본형(기관 소유 Supabase 서울 프로젝트)`: 발주처가 클라우드 종류나 보안 인증을 따로 요구하지 않는 경우
- `네이버 클라우드 공공형`(비활성): 발주처가 국내 공공 클라우드나 CSAP 인증을 요구하는 경우. 아래 안내: "준비 중입니다. 이 조건에 해당하면 도입 문의로 알려 주세요. 별도 계약과 설치가 필요합니다."
- `나중에 정하기`: 사업은 만들어지고, 정하기 전까지 당사자 등록과 녹음·AI 처리는 열리지 않습니다.

**녹음과 AI 정리**

- `외부 업체 처리 허용`: 계약서에 외부 처리나 국외 이전을 막는 조항이 없는 경우. 아래 고정 문구 두 줄:
  - "AI 정리(OpenAI, 미국 회사): 이름, 전화번호, 계좌번호를 지운 글만 보냅니다."
  - "음성 인식(Azure, 서울에 있는 마이크로소프트 서버): 녹음 파일을 지우기 전 그대로 보냅니다. 목소리가 밖으로 나가므로 당사자에게 따로 허락을 받아야 하고, 관리자가 연결을 확인해야 켜집니다. 지금은 켤 수 없습니다."
- `기관 안에서만 처리`: 계약서가 외부 처리를 금지하는 경우. 아래 고정 문구: "이 사업의 상담 자료는 기관 밖으로 나가지 않습니다. 기관이 가진 PC, 노트북, 서버에서 처리하며 일정 이상의 성능이 필요합니다(최소 권장 사양은 `확인하는 법` 참고). 지금은 기관 안에서 도는 음성 인식이 아직 없어 녹음 없이 손으로 기록합니다. 준비되면 이 설명이 바뀌고 다시 확인을 받습니다."
- `나중에 정하기`: 위와 같음.

**다시 확인 안내** (확인이 무효화된 사업의 등록 폼 머리와 사업 목록 배지 옆)

- 선택 변경: "고른 내용이 바뀌었습니다. 바뀐 내용을 다시 읽고 확인해 주세요. 확인 전에는 새 당사자 등록, 녹음, AI 정리가 잠깁니다."
- 설치 STT·LLM 설정 변경: "기관의 음성 인식이나 AI 설정이 바뀌어서, 이 사업의 상담 자료가 밖으로 나가는 방식도 바뀌었습니다. 무엇이 나가는지 다시 읽고 확인해 주세요. 확인 전에는 새 당사자 등록, 녹음, AI 정리가 잠깁니다."
- 문안 버전 변경: "설명 글이 바뀌었습니다. 바뀐 설명을 다시 읽고 확인해 주세요. 확인 전에는 새 당사자 등록, 녹음, AI 정리가 잠깁니다."
- `AI·STT·연결` 탭 저장 전: "이 설정을 저장하면 N개 사업의 자료가 밖으로 나가는 방식이 바뀝니다. 그 사업들은 관리자가 다시 확인하기 전까지 새 당사자 등록, 녹음, AI 정리가 잠깁니다."

세 안내는 "무효화"라는 낱말을 쓰지 않는다. 문안 버전은 라디오 설명과 이 안내를 한 묶음으로 센다.

각 구획 아래 `확인하는 법` 링크 하나(`docs/manual/project-admission-check.md`). 폼 아래 안내 한 줄: "발주처가 지정한 업무 시스템이 따로 있으면, 그 시스템에 남겨야 하는 기록을 CCC가 대신하지 않습니다."(구 "CCC 기록은 보조 기록입니다"는 지위 판정이라 뺐다.)

확인 체크: "위 선택은 우리 기관이 계약 조건을 확인하고 정한 것입니다."

10. **모를 때 돕는 세 층은 한 벌이다.** 라디오(우리 사업은 어느 쪽인가, 기관이 고른다) / `확인하는 법` 매뉴얼 1장(용어 풀이, 계약서에서 볼 조항 이름, 물어볼 부서) / 매뉴얼 안 "AI에게 물어보기" 절(조언형 복붙 프롬프트). 프롬프트는 조항의 존재와 원문만 추출하고 어느 쪽을 고를지 판단하지 않는다. "최종 확인할 부서 제안"은 LLM이 기관 조직을 모른 채 지어내므로 프롬프트에서 빼고 매뉴얼의 고정 목록으로 둔다. 붙여 넣기 전 사람 이름과 연락처를 지우라는 안내를 프롬프트 바로 위에 둔다. 계약서를 LLM에 넣는 것은 기관 안에서 기관이 하는 일이라 CCC 파이프라인(R3)과 무관하다.

## 결과

- **이 ADR은 문안과 계약을 정할 뿐 잠금을 구현하지 않는다.** `나중에 정하기`, 미확인, 무효화 상태의 차단은 API 거부(실데이터 생성, import, 원음 업로드, AI 활성화)로 구현하며 현재 코드에 한 줄도 없다. 화면 숨김으로 구현하지 않는다(E9-3과 같은 문장). 문구만으로 차단이 구현됐다고 보지 않는다.
- 사업 표 신설은 마이그레이션 1건 이상과 기관 초기 설정 화면 변경을 부른다. 처리 경로가 사업 단위가 되면 원음 입장(SG8, S8 admission CAS)과 Agent claim(SG5, S5)에 사업 축이 추가된다.
- `기관 안에서만 처리`는 STT-G1~G3과 Q 승인 전까지 수기 경로다. 승인 뒤 문안이 바뀌면(8-③) 그 사업들의 확인이 무효화되고 재확인을 받는다.
- 외부 처리 선택지의 Azure 줄은 D77(관리자 명시 선택, health check, 승인 registry)과 D85·S7(별도 외부 STT 동의)의 조건을 고지에 포함한다. 조건이 충족되기 전에는 "지금은 켤 수 없습니다"가 사실이다.
- S14는 아직 없다. S11이 국외 이전 잔여 위험을 S14와 E9-3 소유로 넘기고 있으므로 외부 처리 고지 문안은 S14가 생길 때 다시 대조한다.
- 용어 신설: `CONTEXT.md`의 사업 도입 확인, 저장 위치, 처리 경로.
- 폐기 초안의 루트 워크트리 미커밋 파일(`docs/adr/0044-…`, `docs/policy/public-project-admission-review.md`, `CLAUDE.md` §8 한 줄, ADR-0041 후속 주석, `CCC_OPEN_PILOT_PLAN.md` 절)은 이 레인에서 다시 쓴 것으로 대체되며 루트 것은 건드리지 않는다.

## Q 확정 기록 (2026-09-07)

검수가 낸 여섯 질문과 Q의 답이다. 결정 3~8이 이 답을 반영한 본문이다.

1. 사업을 표로 만드는가: 만든다(결정 3)
2. 사업마다 저장 위치가 다를 수 있는가: 라디오는 발주처 요구의 기록이고 설치가 못 맞추면 잠금(결정 4)
3. 네이버 공공형: 비활성 + "준비 중, 도입 문의" 안내(결정 5). 이 레인의 기본값(고를 수 있되 잠금)을 검수 권고로 바꿨다
4. `기관 안에서만 처리`의 수기 경로 고지: 쓴다. 추가로 "기관이 보유한 PC·노트북·서버에서 처리하며 일정 이상의 성능(최소 권장 사양)이 필요하다"를 같이 적는다(결정 6)
5. 미확인은 `나중에 정하기`: 맞다(결정 7)
6. 무효화 사건 셋: 맞다. 다만 화면은 "무효화"라는 말 대신 무엇이 나가고 왜 다시 봐야 하는지를 초등학생도 알 만큼 쉽게 적는다(결정 8, "다시 확인 안내")
