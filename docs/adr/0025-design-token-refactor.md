# 디자인 토큰 리팩터 — 계단을 닫고, 규칙을 문서에서 검사로 옮긴다

색 토큰은 v3(D34·ADR-0012)에서 pen을 SSOT로 삼아 정리를 마쳤다. 그런데 **색 외 축은 비어 있었다** — 특히 글자 크기 토큰이 하나도 없어 `font-size`가 전부 원시 px이었고, 14px 한 값이 배지·칩·라벨·도움말·메타 다섯 역할에 쓰이고 있었다(코드 89곳).

이름이 없으니 이탈을 셀 방법도 없었다. 2026-07-31 감사에서 실제로 나온 것:

| 발견 | 상태 |
| --- | --- |
| `var(--blue-base)` 2곳 | **정의된 적 없는 토큰**. tokens.css는 `--blue`를 선언하고 DESIGN.md §8이 이중 이름을 폐기했는데(2026-07-26) 날짜 선택기만 옛 이름을 부르고 있었다 → **달력에서 선택한 날짜에 면이 칠해지지 않았다** |
| 계단 밖 글자 크기 12px·13px 4곳 | 그중 둘(`consent-upload-slot-state` 라벤더 deep 12px · `register-program-fixed-label` 민트 deep 13px)은 §9가 못 박은 "미달 색은 **14px 이상·굵기 700에서만**"을 정면으로 어기고 있었다 |
| `z-index:30` 리터럴 1곳 | 층 이름(`--z-dropdown`)이 있는데 숫자를 직접 씀 |
| 간격 원시 px 30곳 | §3-4가 허용한 하프스텝(2·6·10)인지 눈대중인지 구분할 방법이 없었다 |
| `.button` 4종 + `.button-sm` | **마크업이 한 곳도 쓰지 않는 죽은 CSS**. 앱은 전부 `WireButton`을 쓴다 |

## 결정

**두 갈래로 나눠 넣는다.** 방법론("토큰으로 치환하고 시각 변화 0")과 요청 항목("버튼 구분·컬러 강화·체크박스 수정")이 서로 충돌하기 때문이다 — 후자는 의도된 시각 변경이다. 섞으면 어느 쪽도 검증할 수 없고, 디자인 변경이 160곳짜리 치환 diff에 묻힌다.

### 1군 — 기계적 치환 (시각 변화 0, 커밋 1)

- **크기 계단 5단 신설**(`--text-2xl` 28 · `--text-xl` 24 · `--text-lg` 18 · `--text-md` 16 · `--text-sm` 14)과 **행간 6종**. 계단은 **닫혀 있다**.
  - 이름을 역할(`--text-badge`)이 아니라 계단으로 붙인 이유: 14px 하나가 다섯 역할에 쓰이는 현실에서 역할 이름은 자리마다 판단을 요구하고, 그 판단이 곧 드리프트다. 역할 대응은 DESIGN.md §2-1 표가 갖는다.
  - 크기만 토큰화하고 행간을 원시값으로 두면 같은 크기가 자리마다 다른 리듬으로 앉으므로 짝으로 넣는다.
- **광학 하프스텝 4종 토큰화**(`--space-0-5` 2 · `--space-1-5` 6 · `--space-2-5` 10 · `--space-3-5` 14). 값을 새로 들이는 것이 아니라 §3-4가 이미 열어 둔 값에 이름을 준 것이다.
- 리터럴 치환: font-size 165곳 · line-height 8곳 · 간격 30곳 · z-index 1곳. **전부 값 보존.**
- `--blue-base` → `--blue`. **별칭을 새로 두지 않는다** — 별칭은 §8이 없앤 "한 계열 두 이름" 상태를 되살린다.

### 2군 — 계약 변경 (의도된 시각 변경, 커밋 1)

1. **버튼**: 죽은 `.button` 4종을 지워 버튼 규칙의 주인을 `.wire-button` 하나로 만든다. 무해한 죽은 코드가 아니라 **드리프트의 저장고**였다 — 같은 계약이 두 벌이라 §5를 고칠 때마다 어느 쪽을 고칠지가 판단거리였다.
   - **일반↔강조 구분을 테두리에서 면·깊이로 옮긴다.** 세컨더리 테두리를 `--line-control`(흰 위 1.28)에서 프라이머리와 **같은** `--line-action`(잉크 50%)으로 올렸다. 1.28짜리 테두리는 흰 카드 위에서 사실상 안 보여 버튼이 버튼으로 읽히지 않았고, 입력칸과 달리 버튼에는 라벨이 형태를 알려 주는 장치(§9 완화)가 없다.
   - **호버·누름 상태 신설.** 지금까지 버튼의 상태는 `disabled` 하나뿐이라, 누를 수 있는지는 알아도 지금 가리키는 것이 무엇인지는 알 수 없었다. 새 색 없이 사이드바 내비가 쓰던 잉크 워시를 빌린다.
2. **카드 안 패딩을 3종으로 확정**(머리·행 16/24 · 본문 20/24 · 좁은 보조 패널 16/20). 사방 20과 사방 24가 섞여 있어 같은 페이지 카드끼리 글자 시작선이 4px씩 어긋났다. **세로는 역할이, 가로는 24 하나가 정한다.**
3. **체크박스·라디오·고른 행의 켬 = 면 채움** (Q 결정). 채움은 **프라이머리 버튼과 같은 `--gradient-action`** 이다.
   - 이전에는 켬과 끔이 12px 체크 글리프 하나로만 갈렸다. 18px 상자 안에서 그 차이는 훑을 때 잡히지 않는데, 동의 체크박스(D23·D49)는 "표시했나 안 했나"가 곧 법적 기록인 자리다.
   - 리스트 행의 구 선택 표시(`--muted`)는 **호버와 같은 값**이라 고른 것인지 지나가는 중인지 구분되지 않았다.
   - 리스크 변형은 §5의 "테두리만 `--risk`, 나머지는 기본과 같다"(2026-07-26 Q)를 **그대로** 따른다. 바뀐 것은 체크 획 하나로, 핑크 획은 채운 면 위에서 대비 1.85·1.44라 보이지 않아 `--ink`로 옮겼다. 리스크를 알리는 것은 획이 아니라 테두리이므로 신호는 잃지 않는다.
4. 계단 밖 12px·13px 4곳 → `--text-sm`. 그중 둘은 §9 위반 해소라 선택이 아니라 필수였다.

### 3군 — 강제 장치

`scripts/design/token-audit.mjs`(`pnpm guard:tokens`)를 신설한다. 미정의 토큰 참조 · z-index/크기/간격/반경 리터럴 · 굵기 400·700 이탈 · 원시 hex를 잡는다.

문서는 확률적 참고고 검사는 결정론이다 — 위에 나열한 발견 다섯은 전부 **DESIGN.md에 이미 규칙이 있는데도** 생겼다. 규칙이 없어서가 아니라 재는 사람이 없어서 생긴 것이다.

## 하지 않은 것

- **색값은 한 개도 바꾸지 않았다.** pen이 SSOT이고 값은 Q 결정이다(§1 머리말). "컬러 Variation 강화"는 D47 ⑦의 읽기("색은 축을 바꾸지 않고 안 쓰던 자리를 채운다")를 따라 **상태**(호버·누름·켬·선택)에만 색을 넣었다. 새 색조를 들이는 것은 §7-1·§1-4 규율 7 위반이고 ADR-0012 개정 사항이다.
- **굵기는 토큰으로 치환하지 않았다.** 400·700은 그 자체로 읽히는 값이라 이름을 붙여도 읽는 사람이 얻는 것이 없고, 막아야 할 것("500이 새로 들어오는 일")은 이름이 아니라 검사가 막는다.
- **`artifacts/`는 손대지 않았다.** 지나간 시안 증거이지 앱 코드가 아니다.
- **12개 템플릿 리터럴의 순서는 그대로다.** 합쳐지는 순서가 곧 우선순위이고 그 사실이 코드 주석에 기록돼 있다 — 규칙을 리터럴 사이로 옮기면 이기는 쪽이 조용히 뒤집힌다.

## 결과

- `yellow` **`.button` 삭제 외의 죽은 CSS는 남겨 뒀다** — 감사 중 `.case-list` · `.case-row` · `.gas` · `.lines` · `.field-grid` · `.pii-reveal-control`도 마크업이 없는 것을 확인했으나, 요청 범위(버튼 규칙)를 넘으므로 건드리지 않았다. 별도로 정리할 거리다.
- `yellow` **다크 모드는 여전히 없다**(§5 `[추론]` 목록 그대로). 크기·간격 토큰이 생겼다고 색 축이 준비된 것은 아니다.
- 검증: `guard:tokens` 위반 0 · `next build` 성공 · `tsc --noEmit` 통과 · vitest 249/249 통과 · `/kit`에서 버튼 4종과 체크박스 4상태를 렌더로 확인(`artifacts/design-system-v3/`).
