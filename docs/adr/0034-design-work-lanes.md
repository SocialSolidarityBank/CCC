# ADR-0034: 디자인 작업을 레인 둘로 나눈다

- 상태: 승인 (2026-08-10 Q 그릴링)
- 결정자: Q
- 관련: ADR-0033(디자인 규칙 문서 분리) · CCC-79(DESIGN-RULES.md) · CCC-80(위계 자동 검사) · CCC-85(커밋 훅)
- 후속: CCC-92(스킬과 검수 에이전트 구현) · CCC-91(하니스 기하 확장) · CCC-90(부품 이전 스윕)

## 배경

원안은 디자인 작업을 에이전트 6개로 나누는 것이었다. 계획, 레이아웃 배치, 컬러와 텍스트,
검수, 최종 수정, 린트와 리팩터링. 각각을 마크다운 파일로 두고 순서대로 태운다.

그릴링에서 진단을 먼저 물었다. Q 의 답은 "규칙 위반이 계속 새어 나간다" 였다. 그래서 실제로
무엇이 새는지 실측했다.

### 실측 1. 정적 위반은 이미 0 이다

| 검사 | 결과 |
| --- | --- |
| `guard:tokens` (값) | 위반 0 |
| `guard:align` (정렬) | 위반 0 |
| `guard:hierarchy` (조합) | 새 위반 0, 기준선 1건(일부러 남긴 킷 반례) |
| 인접 기준선 (이웃 줄) | 0건 |

남아 있는 위반은 검사가 고장 났는지 보려고 일부러 남긴 반례 하나뿐이다. "규칙 위반이 샌다" 는
현재 코드 상태와 어긋난다.

한편 이 검사 3종과 규칙집은 **전부 2026-08-10 에 들어왔다**(#114, #115, CCC-85). 12차까지 갔던
08-07 의 수정 폭풍은 규칙집도 검사도 없던 시절 이야기다. 즉 자동 검사가 붙은 뒤에 만든 화면이
아직 하나도 없는 상태에서 파이프라인을 설계하고 있었다.

### 실측 2. 실제로 샌 것은 규칙이 없는 자리였다

최근 화면 수정 커밋 14건의 내용을 분류했다.

| 종류 | 실제 예 | 검사가 잡나 |
| --- | --- | --- |
| 기하와 위치 | 로딩 글자 세로 중앙, 인테이크 레일 붙박이, 레일 폭 계단 | 못 잡음 |
| 의미 판단 | 참여 사업을 배지로, 필수 표시를 칸으로, 선택 카드 채움 | 못 잡음 |
| 규칙 자체의 번복 | 도움말 12 에서 14 로 통일 | 위반이 아니라 결정 변경 |
| 기능과 연결성 | 죽은 목표 입력 제거, 라우트 중복 정리 | 디자인 문제가 아님 |

Q 가 고른 것은 앞의 둘과 "부품을 안 쓰고 손으로 쌓는 것" 셋이었다. 셋의 처방이 서로 다르다.

### 실측 3. 부품 채택률이 4% 다

`DESIGN-RULES.md` §2 가 "손으로 쌓지 않는다" 고 못 박은 부품 2종의 실제 사용 범위다.
**2026-08-10 시점 스냅숏이고, 부품이 생긴 바로 다음 날 잰 값이다** (CCC-79, #114 가 같은 날
머지됐다). 시간이 지나 이 표를 다시 보는 사람은 낮은 숫자를 게으름으로 읽지 말 것.

| | 개수 |
| --- | --- |
| `WireCardSection` 쓰는 파일 | 5 |
| `WireItem` 쓰는 파일 | 5 |
| 전체 tsx | 123 |

부품이 어제 생겼으니 당연한 숫자지만, 나머지 96% 는 여전히 손으로 쌓는다. 에이전트가 규칙을
아무리 잘 읽어도 규칙이 박힌 부품을 안 쓰면 매번 규칙을 기억해야 한다. 이것은 단계를 나눠서
푸는 문제가 아니라 채택률 문제다.

### 실측 4. 하니스는 기하를 안 잰다

`scripts/design/hierarchy-measure.py` 는 브라우저를 띄워 폭 1280, 767, 390 에서 계산값을 읽는다.
그런데 `MEASURE_JS` 안에서 계산값을 꺼내는 함수는 `trip()` 하나이고, 그것이 읽는 속성이
`fontSize/fontWeight/color` 셋뿐이다. 세로 중앙, 붙박이, 정렬은 재지 않는다.
(`getBoundingClientRect` 는 두 줄이 같은 줄에 섰는지 가르는 데만 쓰고 기하 판정에는 안 쓴다.)
CCC-88 의 "로딩 글자 세로 중앙" 은 하니스가 구조적으로 못 보는 것이 아니라 아직 안 보게
만든 것이다. 장치는 이미 있고 눈만 없다.

## 결정

### 1. 레이아웃 배치와 컬러·텍스트를 가르지 않는다

원안의 2번과 3번을 한 구현 레인으로 합친다.

위계 4단은 크기와 굵기와 색 **셋이 한 묶음**이고 검사도 그 묶음을 본다. 배치가 크기와 굵기를
정하고 색을 다른 레인이 정하면, 경계선이 판정 단위 한가운데를 지나간다.

`guard:hierarchy` 는 표 밖 조합을 커밋 훅에서 잡지만, **이웃 관계를 보는 하니스 실측은 CI 에
있다**(브라우저를 띄워 1분이 걸려 훅에 안 걸었다, CCC-85). 색만 바꿔 이웃한 두 줄을 같은 옷으로
만들면 값은 전부 합법이라 커밋 훅을 통과하고 CI 에서야 걸린다. 그리고 그 두 줄을 왜 그렇게
뒀는지는 배치를 정한 쪽이 아는 판단인데, 색을 정하는 쪽은 그 맥락을 못 받는다.

### 2. 린트는 단계가 아니라 관문이다

원안 6번에서 린트를 뺀다. `guard:hierarchy` 와 `guard:hierarchy:test` 는 이미 커밋 훅에 걸려
있고 둘 다 0.3초다. 매 단계 자동으로 돈다. 마지막 단계에 다시 적으면, 그 앞 단계들이 토큰
위반을 내도 된다는 뜻이 되어 버린다.

### 3. 부품화는 꼬리가 아니라 구현 레인의 기본값이다

30일치 `refactor(design)` 커밋은 예외 없이 부품화와 통일이었다. 공용 부품으로 옮기기, 손 배지
14곳 정리, 접힘 칸을 카드 부품으로, 잔여 CSS 걷고 검사로 막기. 이 레포에서 리팩터링은 청소가
아니라 **부품 채택률을 올리는 유일한 장치**다.

그것을 맨 마지막에 두면 레버가 가장 큰 일을 가장 잘 건너뛰는 자리에 놓는 셈이다. 그래서
둘로 가른다.

- **앞으로 만들 것**: 새 화면은 처음부터 부품으로. 구현 레인의 기본값이다. 손으로 쌓기 전에
  쓸 부품이 있는지 먼저 본다. 부품이 모자라면 자기 클래스를 만들지 말고 부품을 고친다.
- **이미 있는 96%**: 파이프라인 밖 스윕 티켓으로 따로 낸다. 화면 작업에 끼워 넣으면 범위가
  부푼다.

### 4. 산출물은 프로젝트 스킬 하나와 검수 에이전트 하나다

계획, 구현, 최종 수정은 맥락이 이어져야 하므로 한 레인이다. 순서와 체크리스트는 프로젝트
스킬이 갖는다. **검수만 읽기 전용 에이전트로 격리**한다. 자기가 만든 것을 같은 맥락에서
승인하지 않는다는 기존 규칙(`CLAUDE.md`)이 그대로 지켜진다.

검수 에이전트의 모델은 `opus` 다. 기계가 원리적으로 못 보는 의미 판단이 이 에이전트의 유일한
일이고, 다른 에이전트가 없어 비용이 한 레인에만 붙는다.

#### 검수 에이전트가 보는 것 (이 목록이 곧 그 에이전트의 일이다)

검사가 이미 통과한 화면을 받아서, **값이 전부 합법인데 뜻이 틀린 자리**만 찾는다. 항목은 위
실측 2 의 분류와 `DESIGN-RULES.md` 가 검수에 남겨 둔 몫에서 나왔다.

1. **이 값이 배지냐 본문이냐.** 분류와 상태를 나타내는 낱말이 민짜 본문 글자로 남아 있는가
   (§1 "상태 낱말은 배지로 올린다"). 실제 사례: 참여 사업, 회차 표시.
2. **중요한 값이 민짜 본문으로 서 있는가** (§1, 원문 §2-3). 강조 어휘는 배지, 굵기 600,
   계열 컬러 셋뿐인데 그 중 아무것도 안 쓴 채 중요한 값이 놓였는가.
3. **색 계열이 뜻과 맞는가.** 토큰이 합법인 것과 계열이 맞는 것은 다른 문제다. 검사는 앞만
   본다. 블루는 일정과 시간, 민트는 사람과 소속, 라벤더는 AI 산출과 주의, 리스크 핑크는
   확인된 경고 전용이다(§4). "여기만 예쁘게" 고른 자리를 찾는다.
4. **셋 이상 쌓였을 때 고른 장치가 맞는가.** 규칙은 넷 중 하나를 쓰라고만 한다(가로선, 카드
   분리, 배지로 올리기, 2열로 가르기). 어느 것이 맞는지는 뜻의 문제다.
5. **하니스가 나열로 보고 건너뛴 자리.** 실측은 같은 클래스를 단 형제와 40자 넘는 두 문단을
   나열로 보고 넘긴다(`PROSE_LEN`, 같은 `class` 비교). 그 근사가 틀린 자리는 사람만 안다.
   `DESIGN-RULES.md` 가 "이웃 관계는 하니스와 검수가 맡는다" 고 적은 몫의 나머지다.
6. **정보의 자리.** 필수 표시, 빈 상태 문구, 선택 상태를 어디에 어떻게 내는가. 규칙이 값을
   정해 주지 않는 자리다.

**하지 않는 것**: 검사를 다시 돌려 값을 확인하지 않는다(커밋 훅과 CI 가 이미 봤다).
규칙을 옮겨 적지 않는다. 코드를 고치지 않는다 — 고치는 것은 구현 레인의 일이다.

### 5. 에이전트 파일은 규칙을 다시 쓰지 않는다

`DESIGN-RULES.md` 를 읽으라고 시키기만 하고, 자기 역할과 산출물과 돌릴 검사 명령만 갖는다.

ADR-0033 이 규칙 사본 하나를 만들면서 이미 유지 규약을 박았다. "규칙을 바꾸는 커밋은
`DESIGN-RULES.md` 도 같은 커밋에서 고친다. 요약본이 뒤처지면 없느니만 못하다." 그 요약본을 만들
때 실제로 폐지된 12px 규칙을 박을 뻔했다(리베이스 뒤 원문을 다시 안 읽어서). 파일마다 규칙을
발췌해 넣으면 사본이 1개에서 여러 개가 되고, 그 중 하나만 뒤처져도 에이전트가 폐지된 규칙을
지키게 된다.

### 6. 계획은 위계 배치표와 쓸 부품 목록을 낸다

1번 단계의 산출물을 말이 아니라 표로 고정한다. 화면에 들어갈 값을 줄 단위로 적고, 각각을
위계 4단 중 어느 단에 놓을지와 어떤 부품으로 낼지를 짝짓는다. 구현은 그 표를 보고 조립한다.

계획이 부품 이름을 대면 구현이 만들기가 아니라 조립이 된다. 이것이 실측 3 의 채택률에 직접
닿는 자리다. 계획이 말로만 끝나면 구현은 또 손으로 쌓는다.

**새 화면과 큰 개편일 때만 돈다.** 글자 하나 세로 중앙 맞추는 일에 배치표를 그리지 않는다.

## 최종 모양

```
1. 계획    위계 배치표 + 쓸 부품 목록      (새 화면·큰 개편만)
2. 구현    배치·색·문안을 한 레인에서       (부품 우선이 기본값)
3. 검수    읽기 전용 에이전트, 의미 판단     (격리, opus)
4. 최종수정 검수 결과를 구현 레인이 받는다
```

관문은 단계 밖에 있다. 커밋 훅이 `guard:hierarchy`, CI 가 하니스 실측을 본다.

## 파이프라인 밖으로 낸 것

이 둘은 에이전트로 푸는 문제가 아니라서 별도 티켓으로 뺐다.

1. **하니스가 기하를 재게 한다** (CCC-91). `MEASURE_JS` 의 `trip()` 에 세로 중앙, 붙박이,
   정렬을 더한다. 브라우저와 폭 3종은 이미 있다.
2. **부품 96% 이전 스윕** (CCC-90). 손으로 쌓은 자리를 `WireCardSection`, `WireItem` 으로
   옮긴다. 함께 검사 한 줄(손 카드 div 금지)을 붙일지 검토한다. CCC-78, CCC-81, CCC-83 은
   없는 부품을 새로 만드는 일이라 이것과 다르다.

## 버린 안과 이유

- **에이전트 6개**: 두 단계(2번, 3번)의 경계가 판정 단위를 갈랐고, 두 단계(6번의 린트,
  리팩터링)는 관문과 기본값이라 단계가 아니었다.
- **에이전트 4개 마크다운**: 계획과 구현 사이에서 "왜 그렇게 정했는지" 가 끊긴다. 검수 결과를
  받는 최종 수정도 구현 맥락을 다시 쌓아야 한다.
- **스킬 하나만**: 검수를 같은 맥락에서 하게 되어 자기 승인 금지 규칙을 어긴다.
- **3번을 문안 전담으로**: 이음매가 위계 묶음을 안 지나가는 대안이었지만, 문안만 따로 다룰
  만큼 양이 많은지 확인되지 않았다.

## 미결

- ~~**진입점을 아직 안 뒀다.**~~ **해소(2026-08-11, CCC-92).** ADR-0033 은 규칙 파일을
  만들면서 `CLAUDE.md` 의 진입점 한 줄을 같은 커밋에 넣었다. 가리키는 곳이 없는 규칙은 안
  지켜지기 때문이다. 이 ADR 은 스킬과 에이전트가 아직 없어 가리킬 대상이 없으므로 진입점을
  미뤘고, 스킬(`.claude/skills/design-lane/`)과 에이전트(`.claude/agents/design-reviewer.md`)
  를 만드는 커밋이 `CLAUDE.md` "Design docs" 절에 한 줄을 함께 넣었다.
- 파이프라인의 효과는 **검사가 붙은 뒤 만든 첫 화면**에서야 잰다. 지금은 검사가 오늘
  들어왔고 그 뒤 만든 화면이 없어 대조군이 없다.
- 부품 이전 스윕의 범위와 순서는 티켓에서 정한다.
