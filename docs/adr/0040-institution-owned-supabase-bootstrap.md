# ADR-0040: 기관 소유 Supabase 자가 구축 경계

- 상태: 승인 (2026-08-31, GitHub #204, CCC-140)
- 결정자: Q
- 관련: ADR-0001(배포 단위), ADR-0007(멀티테넌트), ADR-0035(D63, D65 배포 문과 로컬 우선)
- 확장: D63의 기관 자체 클라우드 문을 반복 가능한 지원 경로로 연다
- 비대체: 관리형 웹과 로컬 D1 경로는 그대로 둔다

## 배경

기관이 자기 Supabase 계정, 결제, 데이터베이스를 직접 소유하려면 프로젝트 생성 뒤의 설정을 반복할 수 있어야 한다. 수동 체크리스트만 두면 리전, 권한, PostgreSQL 스키마, RLS, Auth, 비공개 음성 저장소 중 하나가 빠져도 설치가 진행될 수 있다. 반대로 배포기관이 기관의 관리 자격증명을 보관하면 D63의 책임 경계가 흐려진다.

자가 구축 키트는 기관 소유 CCC 배포 인스턴스 한 개와 기관 소유 Supabase 프로젝트 한 개를 연결한다. 하나의 공유 CCC 런타임이 요청마다 다른 기관 데이터베이스를 고르는 구조는 만들지 않는다.

## 결정 1: 기관 소유 Supabase는 별도 배포 문이다

기관 자체 클라우드 문에서는 Supabase PostgreSQL, Supabase Auth, Supabase Storage를 한 프로젝트로 사용한다. 운영 프로젝트는 서울 리전이어야 한다. 로컬 Supabase는 개발과 설치 검증에만 쓸 수 있고 운영 준비 증거가 될 수 없다.

이 결정은 관리형 웹의 Cloudflare D1, Cloudflare Access, R2를 즉시 대체하지 않는다. D65의 로컬 우선 경로도 유지한다. 한 배포 환경은 한 데이터베이스와 한 음성 저장소만 선택하며 이중 쓰기와 동기화 데몬은 금지한다.

## 결정 2: PostgreSQL과 RLS는 기존 권한 규칙을 이중으로 지킨다

업무 SQL은 계속 `db/gateway.ts`만 실행한다. PostgreSQL은 현재 CCC 스키마의 단일 기준선과 이후 순방향 마이그레이션을 사용한다. 브라우저는 업무 표를 직접 조회하지 않고 Workers가 전용 최소 권한 역할 `ccc_worker`로 연결한다.

모든 업무 표의 기관 경계는 `org_id`다. PostgreSQL RLS는 이 경계를 한 번 더 검사하지만 gateway의 담당, 역할, 감사 검사를 대신하지 않는다. 설치 버전과 체크섬은 `public.ccc_schema_migrations`에 기록한다. 설치 이력 없는 기존 표나 기관 데이터는 자동 채택하지 않는다.

## 결정 3: Auth와 Storage는 안전 기본값을 공유한다

Supabase Auth는 초대 뒤 비밀번호 설정 흐름을 사용한다. 공개 가입은 닫고 관리자 MFA, 초대 만료와 회수, 퇴사 세션 회수 계약을 유지한다.

원본 음성은 비공개 `ccc-session-audio` 버킷에 둔다. 공개 객체 URL은 만들지 않고 애플리케이션 권한 확인 뒤 Workers가 중계한다. 30일 삭제는 애플리케이션 수명 기록과 cron이 감사 증거를 남기는 계약이며 공급자 설정만으로 대체하지 않는다.

## 결정 4: 외부 설정의 첫 동작은 읽기 전용 plan이다

공개 진입점은 `pnpm supabase:bootstrap -- plan`이다. CCC-140에서는 `plan`만 연다. `apply`, `verify`, `status`는 후속 티켓에서 같은 진입점에 추가한다.

호스팅 프로젝트의 plan은 Supabase Management API의 프로젝트 조회, Auth 설정 조회, `database/query/read-only`만 사용한다. 데이터베이스 쿼리는 공급자가 `supabase_read_only_user`로 실행하는 읽기 전용 경로다. 로컬 plan은 `BEGIN READ ONLY` 트랜잭션으로 같은 카탈로그 검사를 수행한다.

plan은 실행 전후의 스키마, 정책, 버킷, Auth, 기관 데이터 지문을 비교한다. 서울 리전 증거 누락, 다른 리전, 기존 데이터, 지원하지 않는 설치 버전, 읽는 동안의 상태 변경은 적용 전 차단 사유다. 적용 예정 자원 이름과 비개발자가 실행할 다음 행동을 함께 보여준다.

## 결정 5: 시크릿은 입력과 출력에서 분리한다

Management API 토큰은 `SUPABASE_ACCESS_TOKEN` 환경변수로만 받는다. 토큰과 데이터베이스 연결 문자열은 명령행 인자가 아니다. 프로젝트 식별자는 비시크릿 설정이라 `--project-ref` 또는 `CCC_SUPABASE_PROJECT_REF`로 받을 수 있다.

표준 출력, 오류 출력, 임시 파일에는 URL, 토큰, 연결 문자열, 서비스 역할 키, 공급자 원문 오류를 남기지 않는다. plan은 임시 결과 파일을 만들지 않는다. 누락, 무효, 권한 부족 자격증명은 각각 `CREDENTIAL_MISSING`, `CREDENTIAL_INVALID`, `CREDENTIAL_INSUFFICIENT`로 구분하고 원문 응답 대신 고정된 한국어 복구 안내만 출력한다.

## 구현 범위

CCC-140에서 구현한다.

1. 로컬과 호스팅 프로젝트의 읽기 전용 상태 수집
2. 서울 리전, 읽기 권한, 기존 데이터, 설치 버전 검사
3. PostgreSQL, RLS, Auth, Storage 적용 예정 자원 계획
4. 실행 전후 지문 비교와 차단 사유
5. 시크릿 없는 한국어 및 JSON 출력
6. 유효, 잘못된 리전, 자격증명 오류, 기존 데이터의 블랙박스 검증

후속 티켓으로 남긴다.

1. 기준선과 마이그레이션을 실제로 적용하는 `apply`
2. 외부 동작과 영수증을 만드는 `verify`
3. 설치 뒤 드리프트를 읽는 `status`
4. 실제 기관 데이터 이전과 운영 전환
