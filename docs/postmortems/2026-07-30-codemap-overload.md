## 6. 구현 방향 (2026-07-30 Q 지시 반영 — 계획, 아직 실행 안 함)

### 6-0. 먼저 정정할 전제 1개

Q의 읽기는 **결론이 맞고 경로가 다르다.** "훅이 붙어 있으니 세션마다 인덱싱이 돌아 부하가 곱셈"이 아니다 —
훅 스크립트는 실측하면 **텍스트를 `cat` 하는 것뿐**이고 인덱싱을 직접 돌리지 않는다.

대신 **더 나쁜 게 있다.** 훅 본문 3번 줄이 이렇다:

> `3. If a project is not indexed yet, run index_repository FIRST.`

즉 인덱싱을 **모델에게 시킨다.** 그리고 스크립트 주석에 발화 조건이 적혀 있다 —
`Fires on startup/resume/clear/compact`. **컴팩션마다 다시 주입된다.** 긴 세션은 한 번이 아니라 여러 번 맞는다.
그래서 Q의 처방 ①은 그대로 맞고, 근거는 "부하 곱셈"보다 **"모든 프로젝트·모든 컴팩션에 인덱싱 지시가 재주입된다"** 가 정확하다.

같이 못 박아 둘 사실 2개 (같은 실수를 다음 세션이 반복하지 않도록):

- **`codebase-memory-mcp` 는 07-29 15:22에야 존재했다.** 지배적 동시 멈춤은 **11:32·11:36·11:46** 이다.
  이 서버가 그 멈춤의 원인일 수 **없다.**
- **CCC-new 에는 `.codegraph` 인덱스가 없다.** 멈춘 세션들에서 codegraph 는 아무것도 서비스하지 않았다.
  (인덱스가 있는 프로젝트는 다른 8개 — WIQI·ggbss-web·archive 계열 등.)

→ 따라서 Q의 처방 3개는 **전부 채택**하되, ②(codegraph 기본 비활성)는 *이번 멈춤의 처방이 아니라
다른 8개 프로젝트를 위한 위생 조치*로 등급을 내려 잡는다.

#### §6-3-실측 (2026-07-30, Q 승인 후 실행)

**(가) 파일 감시는 기본 켜짐 — 1차 근거는 도구 자신의 help다**

```
$ codegraph serve --help
  --no-watch   Disable the file watcher (no auto-sync; useful on slow filesystems ...)
```

끄는 옵션이 **따로 있다**는 것은 켜짐이 기본이라는 뜻이다.
그리고 현재 등록은 `{"command":"codegraph","args":["serve","--mcp"]}` — **`--no-watch` 가 없다.**

**(로) 세션마다 상주 데몬이 뜨고, 쌓인다**

인덱스가 있는 프로젝트(`~/services/archive-mcp`)에서 `codegraph serve --mcp` 를 20초 띄워보니
**한 번 호출에 프로세스 5개가 사슬로 뜬다** — 래퍼 → node → 네이티브 node → `--path` 붙은 작업 프로세스
→ **watchdog**(메인 스레드가 60초 응답 없으면 부모를 `SIGKILL` 하는 감시자). `--path` 프로세스는 RSS 128 MB 였다.

그리고 내 테스트와 **무관하게** 이미 떠 있던 것들:

| 항목 | 실측값 |
|---|---|
| codegraph 관련 프로세스 | **15개** |
| 총 RSS | **322 MB** |
| 최상위 사슬 수(= 붙어 있는 세션 수) | **4개** |
| 가장 오래 산 것 | **1시간 17분** |

부모 PID 4개가 서로 다르다 — **세션 하나당 사슬 하나**이고, 세션이 살아 있는 동안 **계속 살아 있다.**

**(다) 내가 앞서 한 진술을 정정한다**

조사 초반에 `ps` 로 "codegraph·codebase-memory 프로세스 0개"를 확인하고
**"등록만으로는 뜨지 않는다(지연 기동)"** 고 썼다. 앞부분은 맞다 — 등록만으로는 뜨지 않는다.
**뒷부분이 틀렸다**: 한 번 뜨면 세션이 끝날 때까지 상주하고, 세션 수만큼 곱해진다.
0개였던 것은 그 시점에 아무 세션도 codegraph 를 호출하지 않았을 뿐이다.
**즉 Q가 처음 말한 "세션마다 자동 부착 + 동시 다발 = 곱셈"은 codebase-memory 가 아니라 codegraph 에서 사실이다.**

**(라) 작업 프로세스는 고아가 되어 살아남는다 — 가장 강한 증거**

20초 테스트가 끝나고 부모 사슬이 전부 종료된 뒤에도, `--path` 작업 프로세스와 그 watchdog 이
**부모 PID 1(고아)로 재부착되어 계속 살아 있었다** — 종료 후 3분 시점에 RSS 76 MB + 39 MB.
직접 `kill` 로 치웠다.

이게 왜 중요한가: "세션마다 하나씩 뜬다"보다 한 단계 나쁘다. **세션이 끝나도 안 죽을 수 있다.**
즉 워크트리를 여러 개 열고 닫기를 반복하면 아무 세션에도 속하지 않은 데몬이 남는다.
`~/AGENTS.md` 의 "기본 file watching 금지" 원칙이 이런 경우를 겨냥한 것으로 읽힌다.

`yellow` **한계**: 고아화가 항상 일어나는지, 아니면 stdin 파이프가 끊기는 이번 테스트 방식에서만
일어나는지는 1회 관측으로 못 가른다. 실제 Claude 세션 종료 시에도 남는지는 다음에 세션을 정상 종료해 보고 확인해야 한다.

**(마) 그래서 처방이 하나 늘었다 — 이게 가장 싸다**

등록에 **`--no-watch` 한 단어를 넣는 것**이 파일 감시를 끄는 가장 작은 변경이다.
범위 축소(8개 프로젝트로 한정)와 **성격이 다르다**:

| 처방 | 무엇을 없애나 | 비용 |
|---|---|---|
| `--no-watch` 추가 | 파일 감시(상시 CPU·핸들) | 등록 문자열 1곳. 대신 인덱스가 자동 갱신되지 않아 **수동 재색인 필요** |
| 범위를 8개로 축소 | **인덱스도 없는 프로젝트에서 뜨는 데몬 전체** (CCC-new 가 여기 해당 — 답할 데이터가 없는데 데몬은 뜬다) | 등록 이동. 인덱스 있는 곳에서는 동작 동일 |

**둘은 배타적이지 않다.** 권장은 **범위 축소 + `--no-watch` 동시 적용**이고,
순서는 범위 축소가 먼저다(효과가 크고 부작용이 없다 — 인덱스 없는 프로젝트에서는 잃는 기능이 0이다).
| **어떻게 검증** | 등록 제거 후 새 세션에서 `mcp__codegraph__*` 가 도구 목록에 없는지, 인덱스 있는 프로젝트에서 프로젝트 범위 등록이 정상 동작하는지 각각 1회. |
