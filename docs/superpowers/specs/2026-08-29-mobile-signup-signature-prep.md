# 모바일 가입과 서명 준비 스펙

- 상태: 준비 스펙 (2026-08-29 작성, 구현 착수 전. 결정 포인트는 Q 확인 후 확정)
- 관계: D39(ADR-0016), D23, D26, D44·D46·D49, D3, D14, D24, D37

## 배경

현재 가입 흐름은 D39 프로토타입으로 한 바퀴 완주할 수 있다. 온보딩에서 시작해 실무자 초대(`/join/worker/[token]`), 당사자 링크 발급(`/participants/invite`), 당사자 자기 가입(`/join/participant/[token]`), 인테이크로 이어진다. 자기 가입 폼은 이름·연락처·이메일 입력과 개인정보 수집·이용 동의, AI를 활용한 녹취기록 동의 두 체크를 제공한다(`apps/web/app/join/participant/[token]/signup-form.tsx:58-124`). 개인정보 동의가 없으면 서버 오류를 표시하고, 제출 중에는 폼을 비활성화하며, 성공 시 인라인 완료 패널을 보여 준다(`apps/web/app/join/participant/[token]/signup-form.tsx:18-55`).

실무자 초대 화면도 이름·이메일 입력, 오류 상태, 제출 중 상태, 완료 패널로 구성된다(`apps/web/app/join/worker/[token]/signup-form.tsx:17-84`). 실무자 가입에는 당사자 동의가 없고, 완료 후 Cloudflare Access 로그인 안내를 제공한다. 두 공개 페이지는 각각 유효한 토큰을 조회한 뒤 `WireCard` 안에 폼을 렌더링한다(`apps/web/app/join/participant/[token]/page.tsx:80-103`, `apps/web/app/join/worker/[token]/page.tsx:6-35`). 당사자 링크는 가입이 완료되면 같은 토큰으로 자기 확인 화면을 여는 현재 동선을 유지한다(`apps/web/app/join/participant/[token]/page.tsx:105-113`).

공개 가입 API 표면은 `PUBLIC_SIGNUP_ENABLED === '1'`일 때만 열리고, 그 밖의 값에서는 404로 닫힌다. 미리보기 모드에서는 별도 코드 게이트도 적용된다(`apps/api/src/request-handler.ts:2014-2031`). 따라서 UI를 다듬더라도 이 fail-closed 게이트를 우회하는 새 공개 경로를 만들지 않는다.

초대 토큰은 `invite_tokens`의 `token`, `org_id`, `kind`, 발급자, 상태, 발급·소비 시각과 소비 결과를 보유하지만 `expires_at`은 없다(`migrations/0021_invite_tokens.sql:27-42`). 기존 주석도 만료 정책을 실제 인증 설계와 함께 정하도록 남겨 둔다(`migrations/0021_invite_tokens.sql:19-20`). 0044는 발급자 비활성화 시 사용할 수 있도록 `revoked_at`을 추가하고, 철회된 토큰의 소비를 막는다(`migrations/0044_assignment_lifecycle.sql:74-83`).

동의의 현재 원본은 `support_cases.consent_*_at` 현재값과 `participant_consent_records` append-only 이력이다. 이력은 당사자·사업·기록자·기록 시각을 저장하고, 수정·삭제를 트리거로 막는다(`migrations/0008_participant_consent_records.sql:18-34`, `:62-73`). 자기 가입은 기록자를 `self`로 허용하는 프로토타입 예외가 있다(`migrations/0022_participant_self_signup.sql:15-19`, `:36-62`). 0043부터 개인정보 동의가 있으면 문안 버전, SHA-256, 오프라인 원본 참조도 필수다(`migrations/0043_privacy_consent_notice_evidence.sql:4-6`, `:33-53`).

서명 기능은 아직 없다. 등록 폼에는 파일 입력 없이 `.consent-upload-slot`과 `준비 중` 배지만 있고, 스캔 동의서 첨부가 동작하지 않는다는 안내만 있다(`apps/web/app/participants/new/register-form.tsx:190-201`). 모바일 가입 전용 레이아웃도 없고, 공용 셸은 `max-width: 767px`에서 페이지 패딩만 바꾸며 768px을 데스크톱으로 취급한다(`design/tokens.css:261-267`).

당사자 허브의 동의서 카드는 `ConsentEditor`를 사용하며, 현재 체크 상태·전문 아코디언·마지막 기록 시각을 표시한다(`apps/web/app/participants/[beneficiaryId]/page.tsx:393-425`, `:169-205`). 이 자리에서 서명 상태와 서명 이미지를 추가로 표시한다. 법률상 전자서명은 D23에 따라 법률 검토 후 대상이고, 당사자 직접 작성 구현은 D26과 L3에 의해 동결되어 있다. ADR-0016은 실제 인증·이메일 발송 없이 화면 흐름만 제공하고 가입 데이터를 가상 시드와 로컬·미리보기 전용으로 제한한다(`docs/adr/0016-mvp-signup-flow-prototype.md:10-19`, `:27-30`).

## 모바일 가입 UX 계약

### 대상과 공통 원칙

- 대상 공개 라우트는 `/join/participant/[token]`과 `/join/worker/[token]` 두 개다. 토큰 조회, 공개 표면 게이트, 미리보기 코드 게이트는 현재 서버 흐름을 그대로 사용한다.
- 두 라우트의 외곽은 기존 `WireCard`와 `page-content`를 재사용한다. 입력은 현재 `SearchInput`, 행동은 `WireButton`, 오류는 `WireError`, 읽기 상태는 기존 완료 패널 구조를 재사용한다. 새 색, 새 그라데이션, 새 디자인 컴포넌트 종류를 만들지 않는다.
- 일반 폼 입력은 보이는 라벨을 위에 두고, 14/400 `--ink` 입력값과 14/600 계열 `--sub` 라벨을 사용한다. 입력 높이는 공용 `--control-height` 계약을 따른다. 카드 좌우 여백은 24px, 페이지 모바일 패딩은 16px을 기준으로 한다.
- 터치 조작 영역은 가로·세로 각각 최소 44px로 확보한다. `WireButton`의 화면상 높이 32px 계약은 유지하되, 모바일에서 버튼을 감싸는 조작 영역과 간격으로 44px hit area를 보장한다. 버튼 면을 40px로 키우거나 별도 버튼 종류를 만들지 않는다.
- 동의 전문은 등록 폼과 같은 `consent-detail` 아코디언과 `CONSENT_DETAIL_*` 정본을 사용한다. 닫힘은 아래 화살표, 펼침은 위 화살표이며 오른쪽 이동용 꺽쇠를 쓰지 않는다. 전문 문안을 자기 가입 폼에 별도로 복사하지 않는다.

### 390px 기준

- 뷰포트 390px에서 페이지 패딩 16px을 적용하고, 카드 안쪽 좌우 24px을 유지한다. 입력은 카드 안 가용 폭을 100% 사용하며 고정 폭 때문에 가로 스크롤을 만들지 않는다.
- 당사자 폼의 이름·연락처·이메일은 한 열로 쌓는다. 라벨, 입력, 도움말 사이의 세로 간격은 기존 폼 묶음의 `gap`을 사용하며 개별 요소에 임의 `margin-bottom`을 추가하지 않는다.
- 동의 구획은 이름과 연락처 입력 뒤에 둔다. 개인정보 수집·이용 동의는 필수 체크, AI를 활용한 녹취기록 동의는 선택 체크라는 기존 의미를 유지한다. 각 체크 라벨은 44px 이상 조작 영역을 갖고, 전문은 기존 아코디언으로 펼친다.
- 제출 행동은 동의 구획 뒤에 두고, 처리 중에는 기존 `working` 상태처럼 중복 제출을 막는다. 오류는 폼 안에서 `WireError`로 표시하고 입력과 동의 상태를 보존한다. 성공 시 기존 `wire-signup-done`의 `role="status"` 패널을 표시한다.
- 실무자 폼은 이름·이메일 두 입력을 한 열로 쌓고 동의 구획을 두지 않는다. 완료 패널은 가입 이메일과 Cloudflare Access 다음 단계를 기존 문안 흐름으로 안내한다.

### 767px과 768px 경계

- `max-width: 767px`에서는 당사자·실무자 모두 모바일 한 열, 줄바꿈 가능한 행동 묶음, 가로 넘침 없는 카드로 렌더한다. 390px과 767px은 같은 모바일 규칙을 쓰고, 폭에 따라 입력은 가용 폭만 늘린다.
- 768px에서는 공용 데스크톱 셸과 기존 `data-grid` 다열 배치를 유지한다. 당사자 세 입력과 실무자 두 입력은 기존 `wire-col-6` 계약을 따르며, 동의 구획과 제출 행동은 현재 폼 순서를 유지한다.
- 767px 이하에서 페이지 제목, 카드 제목, 설명, 전문 문안이 한 음절씩 찢어지지 않도록 긴 단어와 URL에는 줄바꿈 가능한 CSS를 적용한다. 중간 브레이크포인트를 추가하지 않는다.
- 767px, 768px 양쪽에서 공개 라우트의 404, 미리보기 인증 실패, 서버 오류, 완료 패널 의미는 바꾸지 않는다.

## 서명 캡처 설계, 제안

### 캡처 범위와 제출 규칙

- 캔버스 기반 서명 입력을 당사자 자기 가입 폼의 개인정보 수집·이용 동의 구획 안에 둔다. 등록자의 스캔 파일을 받는 기존 `.consent-upload-slot`을 파일 업로드 기능으로 바꾸지 않는다.
- 캔버스는 `pointerdown`, `pointermove`, `pointerup`, `pointercancel` 흐름으로 선을 그리고, 시작 시 `setPointerCapture`를 사용한다. `touch-action: none`을 적용해 모바일 스크롤과 서명 선이 충돌하지 않게 한다. 지우기는 캔버스만 비우며 이미 저장된 append-only 증빙을 삭제하거나 수정하지 않는다.
- 캔버스에는 보이는 라벨과 `aria-label`을 둔다. 빈 캔버스에는 `서명 없음` 상태를 표시한다. PNG로 내보낼 때 장치 픽셀 비율을 정규화하고, MIME·크기·픽셀 한도를 서버에서도 다시 검사한다.
- 제안하는 파일럿 저장 규칙은 기존 개인정보 동의 하드 게이트와 분리한다. 개인정보 체크가 없으면 기존처럼 `privacy_consent_required`로 거부한다. 개인정보 체크가 있고 캔버스가 비어 있으면 기존 가입을 성공시키며 서명 행은 만들지 않는다. 캔버스가 있으면 그 PNG를 해당 개인정보 동의 기록에 연결한다. 이 규칙은 미서명 가입의 기존 경로를 보존하기 위한 파일럿 제안이며, 실서비스에서 서명을 필수 증빙으로 볼지는 Q가 결정한다.
- AI 녹취기록 동의는 서명 이미지의 별도 대상이 아니다. 서명은 개인정보 동의 기록에만 결합하며, 녹취 동의의 현재값과 동의 이력 의미는 D49 계약을 유지한다.

### D1 저장 구조 초안, 마이그레이션은 구현 시 작성

다음은 구현 전 합의할 텍스트 설계 초안이다. 이번 준비 작업에서는 SQL 또는 마이그레이션 파일을 만들지 않는다.

- 전용 표 이름은 `participant_consent_signatures`를 제안한다.
- 컬럼 초안은 `id TEXT PRIMARY KEY`, `org_id TEXT NOT NULL`, `beneficiary_id TEXT NOT NULL`, `support_case_id TEXT NOT NULL`, `consent_record_id TEXT NOT NULL`, `ciphertext BLOB NOT NULL`, `iv BLOB NOT NULL`, `key_version TEXT NOT NULL`, `algorithm TEXT NOT NULL`, `content_type TEXT NOT NULL`, `byte_length INTEGER NOT NULL`, `created_at TEXT NOT NULL`이다.
- `consent_record_id`는 `participant_consent_records(id)`를 참조하는 FK로 둔다. `beneficiary_id`와 `support_case_id`도 각각 기존 당사자·케이스 FK를 두고, 조직과 케이스의 기관 일치 여부를 삽입 가드로 확인한다. 서명 한 장은 한 동의 기록에 연결되도록 `consent_record_id` 유일성을 제안한다.
- `ciphertext`는 PNG 원문이 아니라 AES-GCM 암호문이다. `iv`는 행마다 새로 생성하고, `key_version`으로 Workers 시크릿 교체 이력을 식별한다. `algorithm`은 구현 시 허용 목록으로 고정하고 임의 알고리즘 입력을 받지 않는다. 조직 ID와 동의 기록 ID를 추가 인증 데이터로 묶어 다른 행으로 암호문을 옮겨도 복호화가 실패하도록 한다.
- `participant_consent_records`와 동일하게 삽입 후 수정·삭제를 막는 append-only 트리거를 둔다. 철회는 기존 동의 기록에 새 행을 추가하는 흐름으로 남기며, 서명 행을 UPDATE하거나 DELETE하지 않는다. 보존 만료 뒤의 파기·아카이브 방식은 D32·D46과 서명 증빙의 법적 성격을 함께 검토한 뒤 정한다.
- 모든 D1 접근은 `db/gateway.ts` 공용 함수에서 수행한다. 브라우저와 서버 로그에는 PNG 원문, 암호문, 복호화 결과를 남기지 않는다. 서버는 암호화가 끝난 뒤 일시적인 버퍼를 폐기하고, 오류 메시지는 크기·형식·권한 같은 분류만 반환한다.

### 암호화와 보관 경계

- D3의 앱 레벨 AES-GCM 키 체계를 그대로 사용한다. 키는 클라이언트나 D1에 저장하지 않고 Workers 시크릿에서만 읽는다. 키 값은 문서, 환경 파일, 감사 로그에 기록하지 않는다.
- 서명은 음성 임시 보관용 R2에 저장하지 않는다. 음성의 30일 임시 수명 규칙을 서명에 그대로 적용하지 않으며, 서명은 동의 증빙으로 별도 보존 성격을 가진다.
- 복호화 권한은 기존 당사자 허브의 PII 접근 권한과 동일하게 제한한다. 미리보기는 가상 데이터만 사용하고, 운영 PII에 대한 서명 수집과 복호화는 법률 게이트가 열리기 전에는 허용하지 않는다.

## 당사자 허브 표시

- `/participants/[beneficiaryId]`의 동의서 카드 안 `ConsentEditor`에 서명 상태를 추가한다. 기존 체크박스와 전문 아코디언의 순서는 유지하고, 개인정보 동의 기록 아래에 `서명 있음` 또는 `서명 없음`을 기존 `WireBadge`로 표시한다. 새 배지 톤을 만들지 않는다.
- `서명 있음`을 선택하거나 표시하는 읽기 영역에서만 암호문을 gateway를 통해 복호화한다. 권한이 없거나 복호화에 실패하면 이미 있는 오류 처리 패턴으로 중립 오류를 표시하고 원문이나 암호화 세부사항을 노출하지 않는다.
- 복호화된 PNG는 허용된 당사자 허브의 동의서 카드에서만 표시한다. 이미지 요청마다 감사 행을 만들지 않고, 화면 조회 한 번에 PII 복호화·서명 표시 감사 기록 1건을 남긴다. D14의 열람·PII 복호화 감사 원칙과 D24의 조회당 1건 선례를 따른다.
- 당사자 허브에서 동의 체크를 저장할 때는 현재 `participant_consent_records` append-only 흐름을 유지한다. 체크를 풀어 철회해도 이전 서명과 이전 동의 기록은 지우지 않으며, 새 기록에 서명이 없으면 현재 화면은 최신 기록 기준으로 `서명 없음`을 표시한다.

## 토큰 수명과 재발급, 제안

- `invite_tokens`에 `expires_at TEXT`를 추가하고, 미사용 토큰의 조회·가입·소비 게이트가 `revoked_at IS NULL`과 만료 시각을 함께 확인하도록 한다. 만료·철회·무효 토큰은 외부 응답에서 같은 `not_found` 의미로 처리해 토큰 상태를 열거하지 않는다. 내부 감사에는 만료와 철회를 구분해 남긴다.
- 기본 만료 기간은 발급 시각부터 14일을 제안한다. 이 값은 확정하지 않았으며 Q가 기관 업무 주기와 실제 전달 지연을 확인한 뒤 결정한다. 만료 시간 계산은 기관 시간대가 아니라 UTC 시각으로 고정한다.
- 만료 전에는 기존 가입 폼을 열고, 만료 후에는 만료 안내와 기관에 새 링크를 요청하라는 안내를 보여 준다. 만료된 토큰을 다시 활성화하지 않고 새 토큰을 발급한다. 새 토큰은 이전 토큰과 다른 난수이며 이전 토큰의 사용·철회 이력은 남긴다.
- 발급자가 퇴사·휴직 등으로 부재하면 0044의 발급자 비활성화와 `revoked_at` 절차로 미사용 토큰을 철회한다. 새 링크는 권한이 있는 기관 관리자 또는 기관 기술 관리자 절차로 발급하며, 발급자·사유·시각을 감사한다. 권한 있는 발급자가 없으면 fail-closed로 유지하고 기관 관리자 복구 절차를 거친다.
- 이미 사용된 토큰은 현재처럼 자기 확인 화면의 입구가 될 수 있으므로, `expires_at`이 자기 확인까지 막을지 아니면 가입 수락만 막을지는 별도 결정이 필요하다. 운영 보안 기준이 정해지기 전에는 기존 자기 확인 동선을 임의로 제거하지 않는다.

## 법률 게이트와 운영 범위

- 파일럿에서는 가상 데이터와 프리뷰 환경에서 캔버스 UI, 암호화 저장, 허브 표시, 감사 기록의 왕복을 구현할 수 있다. ADR-0016의 실제 인증 없음, 가상 시드 전용, 미리보기 공개 표면 차단 조건을 유지한다.
- 실제 당사자에게 서명을 받거나 실서비스에서 서명을 전자서명으로 취급하는 개시는 L3 해제와 법률 검토 재개 이후에만 가능하다. L3의 여는 조건은 본인 확인과 기록 보존 요건에 대한 질문 6 회신이다(`docs/consent/consent-implementation-gates-v1.md:61-70`). D46은 L3를 해제가 아닌 동결로 유지하고, 실제 당사자 운영 전 법률 검토를 재개하도록 한다(`docs/consent/consent-implementation-gates-v1.md:87-97`).
- D23의 현재 계약인 오프라인 동의 기록과 전자서명 유보를 바꾸지 않는다. 캔버스 입력을 법적 전자서명으로 부르거나, 본인 확인이 끝났다고 표시하거나, 기존 동의 문안의 DRAFT 상태를 제거하지 않는다.
- 외부 R2 업로드나 별도 서명 사업자 연동은 이 스펙의 범위가 아니다. 사업자·수탁자·본인 확인·보존 연한은 법률 검토 재개 시 Q가 확정한다.

## 결정 포인트 (Q 확인 대상)

1. 캔버스 서명을 파일럿에서 선택 입력으로 둘지, 개인정보 동의 체크와 함께 필수로 둘지 결정한다. 선택 입력으로 둘 때 미서명 기존 가입을 유지한다는 제안이 있다.
2. 캔버스 PNG가 법률상 전자서명인지, 단순 동의 보조 증빙인지, 본인 확인을 어떤 방식으로 결합할지 결정한다. 이 결정 전에는 L3를 해제하지 않는다.
3. 서명 증빙의 보존 연한과 삭제·아카이브 조건을 D32·D46의 5년 상한과 동일하게 볼지, 별도 법적 보존 규칙으로 둘지 결정한다. 음성 30일 임시 보관 규칙을 서명에 적용하지 않는 제안은 유지한다.
4. `invite_tokens.expires_at` 기본값을 제안값 14일로 채택할지 결정한다.
5. `expires_at`을 미사용 가입 수락에만 적용할지, 사용 완료 토큰의 자기 확인까지 제한할지 결정한다.
6. 서명 표시 감사의 세부 action 이름과 복호화 실패 시 운영자에게 보일 분류를 D14 감사 어휘에 맞춰 결정한다.
7. 44px 터치 조작 영역과 DESIGN-RULES의 32px 시각 버튼 높이를 함께 구현하는 CSS 방식을 화면 실측으로 승인한다. 새 버튼 종류와 새 색은 만들지 않는다.

## Acceptance 목록

- 390px에서 `/join/participant/[token]`이 한 열로 표시되고 입력 폭이 카드 가용 폭을 채우며, 터치 조작 영역이 최소 44px이고 가로 스크롤이 없다.
- 767px에서 모바일 한 열 규칙을, 768px에서 기존 데스크톱 셸과 다열 규칙을 적용한다. 두 폭 사이에 임의 중간 브레이크포인트가 없다.
- 동의 전문이 기존 `consent-detail` 아코디언으로 열리고 닫히며, 새 색이나 새 컴포넌트 종류 없이 기존 동의 문안 정본을 표시한다.
- 당사자 폼에서 개인정보 동의 체크, 서명 캔버스 입력, 제출 중 상태, 오류 상태, 완료 상태가 각각 확인된다.
- 실무자 폼은 동의·서명 없이 기존 이름·이메일 가입과 Cloudflare Access 완료 안내를 유지한다.
- 캔버스의 서명이 PNG로 변환되고 앱 레벨 AES-GCM 암호문으로 D1 전용 표에 저장되며, 해당 `participant_consent_records` 행과 FK로 연결된다. R2에는 저장하지 않는다.
- 저장된 서명이 당사자 허브 동의서 카드에 표시되고, 복호화·표시 왕복에서 D14 감사 기록이 화면 조회당 1건 생성된다.
- 미서명 상태에서 개인정보 체크를 한 기존 가입은 성공하며, 개인정보 체크가 없는 제출은 기존 `privacy_consent_required` 규칙으로 실패한다.
- 만료·철회 토큰은 외부에서 동일한 무효 링크 의미로 닫히고, 재발급은 새 토큰을 만들며 이전 이력을 보존한다.
- 가상 데이터와 프리뷰에서만 smoke 검증을 수행하고, 실제 당사자 데이터·실제 서명·운영 키를 사용하지 않는다.

## 구현 단계 분할

### 1단계: UX·법률 계약 확정

- 결정 포인트 1, 2, 3, 7에 대한 Q 답변을 기록하고, 390·767·768px 화면 계약과 캔버스의 파일럿 필수 여부를 확정한다.
- 완료 기준: 두 공개 라우트의 상태 전이표, 동의 아코디언 계약, 서명 선택·필수 규칙, L3와 운영 금지 조건이 승인 문서로 서로 모순 없이 확인된다.

### 2단계: 파일럿 서명 캡처와 D1 저장

- 기존 자기 가입 폼의 개인정보 구획 안에 포인터 캔버스를 연결하고, 서버에서 PNG 검증·AES-GCM 암호화·gateway 저장을 구현한다. `participant_consent_signatures` 표와 append-only 가드는 이 단계에서 마이그레이션으로 만든다.
- 완료 기준: 가상 가입 1건에서 개인정보 동의 기록과 서명 행이 같은 기관·당사자·케이스·동의 기록 FK로 연결되고, 암호화 전 원문이 로그와 D1에 남지 않는다. 빈 캔버스 제출은 기존 가입을 통과한다.

### 3단계: 허브 표시와 감사

- `ConsentEditor`에 최신 서명 상태와 이미지 표시를 연결하고, 권한 게이트와 화면 조회당 감사 1건을 적용한다. 철회와 재동의 시 이전 기록·서명이 보존되는지 확인한다.
- 완료 기준: 서명 있음·없음·복호화 오류 세 상태가 허브에서 구분되고, 한 화면 조회에서 감사 행이 1건만 생성되며, 권한 없는 호출은 원문을 반환하지 않는다.

### 4단계: 토큰 만료와 재발급

- Q가 정한 `expires_at` 기본값, 만료 응답, 발급자 부재 시 철회, 새 링크 발급, 기존 자기 확인 토큰 정책을 API와 화면에 연결한다.
- 완료 기준: 유효·만료·철회·이미 사용 토큰의 외부 오류 의미가 노출 정보를 늘리지 않고, 내부 감사와 재발급 이력이 남으며, 기존 공개 가입 게이트가 계속 fail-closed로 동작한다.

### 5단계: 프리뷰 검증과 운영 개시 게이트

- 프리뷰의 가상 데이터로 390·767·768px 렌더, 서명 캡처 → 암호화 저장 → 허브 복호화 표시, 감사 기록, 미서명 가입, 토큰 만료를 smoke 검증한다.
- 완료 기준: Acceptance 목록을 모두 통과하고, 실제 당사자 대상 운영은 L3 해제와 법률 검토 재개 기록이 확인되기 전까지 열리지 않는다. 운영 개시는 별도 Q 승인 이후에만 진행한다.
