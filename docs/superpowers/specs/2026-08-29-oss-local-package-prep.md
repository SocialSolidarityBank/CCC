# 오픈소스 로컬 패키지 설계 스펙

- 상태: 준비 스펙 (2026-08-29 작성, 구현 착수 전. 결정 포인트는 Q 확인 후 확정)
- 관계: D63·D65·D66(ADR-0035), D57(ADR-0027), D74(ADR-0038), D13

## 배경

레포는 루트 `LICENSE`에 Apache License 2.0을 적용하고 있다(`LICENSE:1-5`, `LICENSE:189-201`). 공개 레포와 Apache 2.0 배포 상태는 D63 원문에도 이미 적용 상태로 기록되어 있다(`docs/adr/0035-contest-scope-and-deployment-doors.md:48-58`). 따라서 이 문서는 라이선스를 새로 정하거나 배포기관이 모든 설치의 자료 관리 책임을 떠맡도록 바꾸는 문서가 아니다. 사용기관이 자료를 관리하는 배포 경계를 패키지와 온보딩 문서에 드러내는 준비 문서다.

D63은 관리형 웹, CCC 박스, 개인 노트북 모드, 기관 자체 클라우드의 네 배포 문을 열고, 자체 클라우드는 맞춤 계약으로 후순위에 둔다. 자료 관리 책임은 사용기관에 있고, 배포기관은 안전 기본값·알림·서식을 제공한다. 유료 관리형 웹에서 저장을 맡는 경우에만 배포기관이 수탁자가 된다(`docs/adr/0035-contest-scope-and-deployment-doors.md:48-58`). D65는 1차 저장소를 로컬로 두고 PostgreSQL 이전을 연기하며, 로컬 모드는 자체 DB 인스턴스를 갖는 배포 문으로 규정한다(`docs/adr/0035-contest-scope-and-deployment-doors.md:78-87`).

현재 루트에는 `README.md`와 `.env.example`이 없다. 따라서 설치 안내와 환경 변수 이름을 한 곳에서 확인할 수 있는 오픈소스 온보딩 표면도 아직 없다. 다만 로컬 실행 경로는 이미 존재한다. 현재 절차는 `apps/api`에서 Wrangler D1 로컬 마이그레이션을 적용하고, `apps/api/.dev.vars`를 준비한 다음, 레포 루트에서 시드를 생성하고, `apps/api`에서 로컬 D1에 SQL을 적재한 뒤, API를 8787 포트로 실행하고, 웹을 `CCC_API_ORIGIN`과 `CCC_LOCAL_PREVIEW`를 사용해 3000 포트로 실행하는 순서다(`docs/ops.md:69-101`). `apps/api/wrangler.toml`은 로컬 D1을 `DB`로, 음성 임시 보관을 `AUDIO_BUCKET` R2로 바인딩하고 마이그레이션 디렉터리를 `../../migrations`로 지정한다(`apps/api/wrangler.toml:21-33`). 이 로컬 D1 상태는 Wrangler가 관리하는 SQLite 파일이다.

키는 Workers 시크릿 구조를 따른다. `CODEX_API_KEY`는 Workers 시크릿으로만 주입하고, `PII_ENC_KEY`도 Workers 시크릿으로 관리한다. 외부 AI 호출은 `AI_PROVIDER_CONFIG`, `CODEX_API_KEY`, `EXTERNAL_AI_CALLS_ENABLED`가 함께 있어야 열리는 fail-closed 구조다(`docs/ops.md:38-56`). 관리자 화면에는 키 입력 칸이 없고, 배포된 런타임의 설정 상태를 조회한 뒤 `approvalRef`를 입력해 활성화하는 폼만 있다(`apps/web/app/admin/ai-provider/ai-provider-control.tsx:12-14`, `apps/web/app/admin/ai-provider/ai-provider-control.tsx:58-76`). 키 자체는 UI·로그·커밋에 두지 않는다는 현재 경계를 유지한다.

D57과 ADR-0027은 OpenAI를 정본 사업자로 두고, 처리 장비가 2차 마스킹한 스냅샷만 사업자에 보내도록 한다(`docs/adr/0027-openai-provider-and-masked-text-queue.md:1-3`, `:29-49`). D66은 공식 기업용 API만 허용하고 무료 등급과 비공식 프록시를 금지하며, 키 등급과 약관 확인 책임을 기관 관리자에게 둔다(`docs/adr/0035-contest-scope-and-deployment-doors.md:94-105`). D74와 ADR-0038은 기관 관리자와 기관 기술 관리자를 독립 역할로 나누고, 기관 기술 관리자가 API와 처리 장비를 관리하도록 한다(`docs/adr/0038-role-and-supervision-access.md:14-29`). 이 두 결정 사이에서 로컬 BYO 키를 누가 실제로 입력하는지는 아직 하나로 확정하지 않는다.

D13은 처리 장비가 R2와 D1에 직접 접근하지 않고 Workers API만 호출하며, FileVault·중간 파일 즉시 삭제·전용 계정을 요구한다(`CLAUDE.md:163-176`). 로컬 패키지는 이 경계를 완화하는 방식으로 설계하지 않는다. 완전 로컬에서 당사자 원격 요청이 필요하면 외부 공개 대신 종단간 암호화 임시 전달함을 사용한다는 ADR-0038의 경계도 유지한다(`docs/adr/0038-role-and-supervision-access.md:64-72`).

법률 미결은 두 갈래다. D63 배포 구조에서 사용기관과 배포기관의 개인정보처리자·수탁자 지위, 유료 관리형 웹의 위탁 계약 여부가 남아 있다(`docs/consent/legal-review-open-items-v1.md:14-15`). D66 BYO API 키 구조에서 AI 처리 위탁자가 사용기관인지 배포기관인지도 남아 있다(`docs/consent/legal-review-open-items-v1.md:16-17`). 이 문서는 법률 판단을 대신하지 않으며, 실제 외부 배포 전 해당 검토를 다시 여는 조건을 체크리스트에 남긴다. 보존·파기 코드 경로는 현재 아카이브·재검토·관리자 승인 파기 흐름으로 구현되어 있지만, 실제 상담 데이터 투입 전 법률 검토와 내부 보존 규정 근거 확인은 별도 운영 게이트다(`docs/policy/deferred-blockers-v1.md:5-26`).

이 스트림은 패키지 형태와 로컬 데이터 저장 범위만 준비한다. 코드, 마이그레이션, 설치 프로그램, Docker 이미지, 루트 README, `.env.example`, `docs/deployment/` 문서는 전체 설계가 Q 확인을 통과한 뒤 후속 구현한다. 후속 구현은 전체 완성 후에만 착수한다.

## 1. 패키지 형태 제안

### 1.1 권고 순서

| 안 | 형태 | 대응 배포 문 | 이번 준비에서 정할 범위 | 상태 |
| --- | --- | --- | --- | --- |
| A | 현행 Wrangler 로컬 경로를 설치 스크립트 하나로 감싼다 | 개인 노트북 모드 | 사전 조건 점검, 로컬 디렉터리 생성, 마이그레이션·시드·실행 순서, 종료와 백업 진입점 | 1차 권고, Q 최종 확인 |
| B | API·웹·로컬 데이터 디렉터리를 Docker Compose로 묶는다 | CCC 박스 | 컨테이너 경계, 영속 볼륨, 시크릿 주입, 업그레이드와 복원 진입점 | 2차 권고, Q 최종 확인 |
| C | 단일 실행 파일 인스톨러를 만든다 | 초보 사용자용 패키지 | 설치·업데이트·권한·복구·서명 배포 체계 | 후순위 제안 |

A를 먼저 권고하는 근거는 현재 로컬 절차와 애플리케이션 경로를 그대로 재사용할 수 있기 때문이다. API는 `wrangler dev`, 로컬 D1 마이그레이션, 기존 `migrations/`, R2 바인딩을 이미 사용하고 웹도 API 원점과 로컬 프리뷰 스위치로 연결된다(`docs/ops.md:79-98`, `apps/api/wrangler.toml:21-33`, `apps/web/wrangler.jsonc:11-23`, `:33-53`). 따라서 별도 런타임 이미지와 데이터 경계를 먼저 만들지 않아 유지 비용과 동작 차이를 줄일 수 있다.

B는 CCC 박스의 반복 설치와 복구를 표준화하는 다음 선택지다. 다만 컨테이너 이미지 제작, 로컬 D1·R2 대응물의 영속 볼륨, 권한 매핑, 이미지와 마이그레이션의 호환성 관리가 추가된다. C는 사용자 경험은 단순해질 수 있지만 운영체제별 서명·업데이트·복구·보안 검토 비용이 가장 크므로 A와 B의 운영 경험을 얻은 뒤로 미룬다.

A·B·C 중 최종 패키지 순서와 1차 배포 대상을 확정하지 않는다. 개인 노트북 모드와 CCC 박스의 지원 범위, 지원 운영체제, 오프라인 동작 범위는 Q 확인 후 확정한다.

### 1.2 배포 문별 책임과 기본 경계

- 관리형 웹: 현재 Workers 시크릿과 Cloudflare 바인딩을 유지한다. 사용기관이 입력한 BYO 키를 배포기관의 문서나 화면에 복사하지 않는다.
- CCC 박스: 사용기관이 운영하는 자체 DB 인스턴스와 로컬 파일 영역을 둔다. 기관 기술 관리자가 기술 설정을 관리하고, 기관 관리자는 업무 권한을 관리한다.
- 개인 노트북 모드: 명시적인 로컬 actor 게이트 없이는 API가 열리지 않게 한다. 로컬 개발 편의와 운영 인증을 섞지 않는다.
- 기관 자체 클라우드: 맞춤 계약과 별도 운영 책임 합의가 끝난 뒤에만 연다. 패키지 기본 경로로 포함하지 않는다.

## 2. BYO 키 수명주기

### 2.1 저장과 입력

로컬 모드 1차 권고는 Git이 추적하지 않는 `.dev.vars` 계열 로컬 파일이다. 이 파일은 운영 데이터 디렉터리와 분리하고, 파일 권한을 설치 과정에서 점검하며, 값은 표준 출력·로그·오류 응답·커밋에 남기지 않는다. 현재 `.dev.vars`가 API 로컬 개발 변수의 주입 경계로 쓰이고 있다는 점과 값은 커밋·로그·채팅에 남기지 않는다는 규칙을 재사용한다(`apps/api/.dev.vars.example:1-21`). OS keychain에 저장할지는 보안성과 설치 난이도를 비교한 뒤 Q가 결정한다.

관리형 웹은 현행 Workers 시크릿 구조를 유지한다. 로컬 패키지가 관리형 웹의 시크릿 저장 방식을 복제하거나, 웹 UI에서 `CODEX_API_KEY`를 받는 흐름을 만들지 않는다. 관리자 화면의 `approvalRef`는 키를 대체하지 않으며, 배포 런타임 설정과 승인 기록을 연결하는 참조다.

입력 주체는 두 결정을 함께 반영해야 한다.

1. D66은 공식 기업용 API 키를 기관 관리자만 입력하도록 한다.
2. D74와 ADR-0038은 API와 처리 장비의 기술 설정 주체를 기관 기술 관리자로 분리한다.

따라서 패키지의 실제 입력 주체는 기관 관리자와 기관 기술 관리자 중 하나로 Q가 확정한다. 어느 주체를 택하더라도 실무자는 키를 보거나 입력하지 않으며, 입력 행위와 승인 참조는 기관 내부 운영 기록에 남긴다.

### 2.2 확인, 표시, 회전, 폐기

- **등급과 약관 확인**: 무료 등급이나 비공식 구독 프록시를 거부하고, 공식 기업용 API인지와 해당 키의 등급·약관을 설정 시점에 확인한다. 확인 기록의 불투명한 참조만 `approvalRef`로 남긴다. 키 값·계정 비밀번호·토큰은 기록하지 않는다.
- **연결 확인**: 로컬 또는 관리형 배포에서 설정 이름과 활성 런타임을 확인하고, 값 자체가 아닌 성공·실패 상태와 설정 해시만 표시한다. 현재 관리자 화면이 활성 설정 해시, 런타임 상태, 일치 여부를 보여 주는 계약을 재사용한다(`apps/web/app/admin/ai-provider/ai-provider-control.tsx:33-56`).
- **마스킹 표시**: 키는 화면에 원문을 표시하지 않고 존재 여부와 마지막 확인 시각 같은 비밀값이 아닌 상태만 표시한다. 로그와 진단 번들에도 키와 인증 헤더를 넣지 않는다.
- **회전**: 새 키를 허용된 시크릿 주입 경로로 교체한 뒤, 새 키가 주입된 배포에서 런타임 활성화 절차를 다시 실행한다. 이전 키와 새 키를 동시에 문서나 로그에 적지 않는다. 키 등급·약관 확인 참조도 새 키 기준으로 갱신한다.
- **폐기**: 사용 중지 또는 기관 계약 종료 시 사업자 콘솔에서 키를 폐기하고, 로컬 파일과 관리형 시크릿 주입 경로에서 제거한 뒤, 런타임 상태를 비활성 또는 불일치 상태로 확인한다. 데이터 삭제와 키 폐기는 서로 대체하지 않으며 각각의 감사 기록을 남긴다.

회전 순서는 `시크릿 교체 → 런타임 재활성화 → 설정 해시·상태 확인`으로 고정한다. 활성 설정의 모델·프롬프트·스키마 버전이 바뀌는 경우에도 동일한 cutover 절차를 적용하고, 새 설정이 검증되기 전에는 외부 호출을 fail-closed로 둔다. D57·ADR-0027이 정한 마스킹 스냅샷 게이트를 패키지 선택에 따라 완화하지 않는다.

## 3. 로컬 데이터 저장 구현 범위

이 절은 설계 상세가 아니라 후속 구현의 경계를 고정한다. 아래 항목은 패키지 전체 설계와 Q 확인이 끝난 뒤 구현할 목록이다. 구체적인 경로 규칙, 포맷, 암호화 방식, 보존 기간, 운영 명령의 세부 옵션은 착수 시점에 정한다.

### 3.1 데이터 디렉터리와 권한

구현할 것:

- 배포 문별 로컬 데이터 디렉터리 기본 위치를 정의한다.
- 데이터 디렉터리·백업 디렉터리·임시 작업 디렉터리를 분리한다.
- 운영 계정과 전용 서비스 계정의 소유권·최소 권한을 설치 과정에서 설정하고 점검한다.
- 권한이 넓거나 경로가 심볼릭 링크로 바뀐 경우 기동을 막는 사전 점검을 둔다.
- 공개 레포와 Git 작업 영역에 상담 데이터·음성·시크릿이 들어가지 않도록 ignore와 사전 점검을 제공한다.

### 3.2 백업과 복원

구현할 것:

- 로컬 DB와 R2 대응물의 일관된 백업 명령 진입점을 제공한다.
- 백업 목록·무결성 확인·복원 전 사전 점검·복원 후 마이그레이션 확인 명령을 제공한다.
- 복원 실패 시 원본 데이터 디렉터리를 보존하고, 부분 복원 상태를 운영 상태로 노출하지 않는다.
- 백업 파일에도 PII와 음성이 포함될 수 있음을 표시하고, 권한·보관·폐기 정책을 적용한다.
- 제안 명령 이름과 옵션은 후속 구현에서 확정한다. 현재 로컬 D1의 마이그레이션과 SQL 적재 경로는 `pnpm exec wrangler d1 migrations apply ccc-local --local`, `pnpm exec wrangler d1 execute ccc-local --local --file <SQL 파일>`을 재사용한다(`docs/ops.md:79-98`).

### 3.3 마이그레이션 적용

구현할 것:

- 현행 `migrations/`를 Wrangler 로컬 D1 적용 경로로 재사용한다.
- 최초 설치와 업그레이드에서 마이그레이션 미적용·실패·중복을 감지한다.
- 앱 버전과 마이그레이션 버전의 호환 여부를 기동 전에 확인한다.
- 운영 DB에 적용해야 하는 명령과 로컬 DB에 적용하는 명령을 분리해 안내한다.
- 마이그레이션 전 백업과 롤백 불가 범위를 설치 안내에 명시한다.

### 3.4 내보내기

구현할 것:

- 기관 관리자 권한과 목적 확인을 거친 데이터 내보내기 진입점을 제공한다.
- 내보내기 요청·범위·실행자·시각을 `audit_log`에 기록한다.
- 결과물에 PII·상담 기록·오디오가 포함되는지 표시하고, 무분별한 전체 내보내기를 기본값으로 두지 않는다.
- 내보내기 파일의 저장 위치와 만료·폐기 진입점을 제공한다.

### 3.5 PII 파기와 아카이브

구현할 것:

- 현재 보존 검토·아카이브·관리자 승인 파기 흐름을 로컬 배포에서도 실행한다.
- 로컬 운영에서 `PII_PURGE_ENABLED`가 닫힌 상태와 승인된 파기 상태를 구분한다.
- 아카이브·재검토·파기 결과와 실패를 기관 단위로 감사한다.
- 파기 이후 가명 기록과 통계가 남는 현재 정책을 로컬 패키지 안내에 반영한다.
- 실제 보존 기간과 법률 근거는 법률 검토 재개 후 확정한다. 패키지가 임의의 기본 보존 기간을 정하지 않는다.

### 3.6 오디오 파일 저장

구현할 것:

- Cloudflare R2 `AUDIO_BUCKET`에 대응하는 로컬 오디오 객체 저장 영역을 제공한다.
- 객체 키에 PII를 넣지 않고 세션 식별자와 불투명 식별자를 사용한다.
- 음성 임시 파일의 처리 종료·실패·만료 시 삭제 진입점을 제공한다.
- 로컬 파일 백업에 음성이 포함되는지 명시하고, DB 백업과 별도 보존·폐기 대상을 관리한다.
- 현재 R2의 음성 임시 보관과 lifecycle 설정을 로컬 저장 정책으로 옮길 때 필요한 차이를 후속 설계에서 확정한다(`apps/api/wrangler.toml:27-33`, `:130-134`).

## 결정 포인트 (Q 확인 대상)

1. **1차 패키지 형태**: A를 개인 노트북 모드의 1차로 확정하고 B를 후속으로 둘지, A와 B를 같은 릴리스에서 제공할지 결정한다. C의 후순위 범위도 함께 확인한다.
2. **지원 매트릭스**: 개인 노트북 모드와 CCC 박스의 지원 운영체제, CPU·메모리 전제, 네트워크 없는 실행 범위를 정한다.
3. **키 저장 위치**: `.dev.vars` 계열 파일을 1차로 채택할지 OS keychain을 기본으로 할지 결정한다. 두 방식을 함께 지원할 경우 우선순위와 마이그레이션 경로를 정한다.
4. **키 입력 주체**: D66의 기관 관리자와 D74의 기관 기술 관리자 중 로컬 패키지에서 실제 BYO 키를 입력하고 회전할 주체를 정한다. 겸임 시에도 두 권한과 감사 주체를 어떻게 기록할지 정한다.
5. **로컬 데이터 경로와 권한**: 배포 문별 데이터 디렉터리 기본 위치, 전용 계정, 백업 저장 위치, 파일 권한 기준을 정한다.
6. **백업·복원 보호**: 백업 파일 암호화, 오프라인 보관, 복원 승인과 실패 복구의 운영 기준을 정한다.
7. **R2 대응물과 음성 보존**: 로컬 오디오 디렉터리의 lifecycle, 백업 포함 여부, 처리 완료 후 삭제 시점을 정한다. R2의 30일 임시 보관 규칙을 로컬에도 그대로 적용할지 별도 정책으로 둘지 확인한다.
8. **내보내기와 임시 전달함**: 로컬에서 당사자에게 요청형 자료를 전달할 때 기관 내부망 QR과 종단간 암호화 임시 전달함 중 적용 범위를 정한다. 로컬 서버 자동 외부 공개는 기본으로 채택하지 않는다.
9. **버전과 호환성**: 제안 semver 태깅(`vMAJOR.MINOR.PATCH`)을 채택할지, 앱 버전·마이그레이션 버전·패키지 버전의 호환표 형식과 기동 차단 규칙을 정한다.
10. **법률 검토 재개**: D63의 사용기관·배포기관 개인정보처리자 및 유료 관리형 웹 수탁자 지위, D66의 BYO 키 처리 위탁 관계, 외부 사업자 처리 고지와 동의 문안을 실제 상담 데이터 투입 전에 재검토한다.
