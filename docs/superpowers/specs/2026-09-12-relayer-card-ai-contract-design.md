# 릴레이어 카드와 AI 소비 계약

- 상태: 확정된 의미와 적용 전 관문을 정리한 설계 문서다. 새 저장 스키마의 승인서나 구현 완료 보고가 아니다.
- 근거: [ADR-0049, D90](../../adr/0049-relayer-card-contract-and-ai-module-criteria.md), [적용 계획](../plans/2026-09-12-relayer-domain-ai-replan.md).
- 범위: W01의 필드 책임, 공식화, 버전 전환과 복구 경계다. 화면 배치와 공유 부품은 DESIGN 레인이 정한다.
- 원본과 우선순위: 적용 계획 §1의 원본 8개와 지문을 그대로 사용한다. 이 문서는 원본을 다시 작성하지 않는다.

## 1. 현재 상태와 목표 계약을 구별한다

현재 기준은 `ad218e8e`다. 기존 AI 초안은 `claims`의 세 구획, 인용 근거, 질문, 대조 세 축을 갖는다. 카드 네 종류와 사례 내 자유 주제의 생산자 또는 저장소가 이미 있다는 뜻이 아니다.

해당 작업의 미결 저장 의미가 닫히기 전에는 그 의미를 적용하는 공개 타입, 저장 코드와 forward migration을 발행하지 않는다. G1은 카드 정본, G3은 약속 결과와 상태, G5/G6은 영역과 첫 상담 입력, G7은 가명 대응표와 날짜 처리에 적용한다. 관련 없는 관문을 모든 수정의 선행조건으로 삼지 않는다. 기존 계약 위의 용어 표시, 기억 입력 차단과 소비 결함 수정은 별도 묶음으로 진행할 수 있다. 그 묶음의 성공으로 W01~W13 전체를 완료 처리하지 않는다.

## 2. 필드 책임과 공식화

다음 표는 의미 계약이다. 물리적 테이블 이름, JSON 필드와 새 버전 번호를 예약하지 않는다. 기존 식별자를 재사용할 수 있는 자리는 함께 적었다.

| 값 | 작성자와 원천 | 공식화와 조회 | 정정 또는 철회 시 조건 |
|---|---|---|---|
| 기관, 사례, 회차 | core가 검증한 actor와 source scope | 기존 사례 접근 권한을 적용한다. 기술 관리자에게 상담 본문을 추가 공개하지 않는다 | 다른 사례의 자료와 연결할 수 없다 |
| 상담일과 순서 | 해당 회차의 상담일 | 입력 시각 대신 상담일로 정렬한다 | 과거 회차를 늦게 넣거나 날짜를 바꾸면 영향 범위를 다시 계산한다 |
| 원문 revision과 hash | 수기 저장 또는 검증된 마스킹 스냅샷 | 현재 원천과 같은 버전임을 검증한다 | 이전 결과가 새 원문이나 사람 수정을 덮어쓰지 못한다 |
| 출처 종류 | 수기, 전사, 첫 상담의 실제 원천 | 같은 내용이어도 원천 둘을 보존한다 | 표시만 남기고 근거를 잃은 결과를 공식 자료로 내보내지 않는다 |
| 근거 인용과 위치 | 스냅샷의 `sourceRef`, hash, quote, offset | 기존 인용 검증을 재사용한다 | core에서 본문을 다시 써 hash와 offset을 맞추지 않는다 |
| 카드 종류 | 수기 구획 또는 AI의 원문 추출 | 수기는 즉시 공식, AI 추출은 회차 승인 뒤 공식이다 | 의견을 사실로, 추정 질문을 명시적 확인 약속으로 바꾸지 않는다 |
| 화자, 행위자, 기한 | 원문에 명시된 값 | 화자와 수행자를 구별한다 | 메모 작성자를 수행자로, 작성일을 기한으로 추정하지 않는다 |
| 주제와 목표 연결 | 사례 안 원문과 등록 목표, 사람의 수정 | 승인된 AI 연결만 공식 결과에서 사용한다 | 재생성이 사람의 주제 수정과 합치기를 되돌리지 않는다 |
| 같은 내용, 결과, 갱신 연결 | 양쪽 원천과 각각의 revision | 연결 양쪽의 접근 권한과 공식화 상태를 확인한다 | 원래 카드와 결과 이력은 보존한다. 무언급과 못 함은 자동 종료가 아니다 |
| 인물과 기관 번호 | G7 뒤 승인된 처리 Agent | 사례 밖 번호를 같은 대상으로 보지 않는다 | 대응표의 권한, 보유기간과 파기 정책이 먼저 필요하다 |
| 승인 근거 | 기존 draft version과 회차 승인 | 수기 재승인이나 항목별 응답 의무를 추가하지 않는다 | 승인 취소, 원천 수정, 철회와 파기의 늦은 결과를 거부한다 |

G1은 기존 수기 구조값을 정본으로 유지하고 카드 조회를 원천 참조로 투영하는 방식으로 확정됐다. AI 추출은 별도 승인 대상이다. 같은 수기 기록을 두 곳에 별도로 쓰거나 다시 승인받지 않는다. 사람의 원천 수정은 기존 공식화 규칙을 따르고, AI의 결과·갱신 연결은 승인 경계를 유지한다.

첫 상담의 개수는 원문에 이름이 적힌 실제 질문 목록에서 계산한다(2026-09-13 Q 추가 확정). 공통 응답 21개와 선택 장기목표 1개가 있고, 연계 기관 표와 다음에 물어볼 것 표는 별도 반복 구조다. 원문의 ‘28개’에 맞추려고 질문을 추가하거나 삭제하지 않는다. 경제·재정의 명시된 입력 6개와 기타의 상세 1개도 그대로 유지한다. 주요 지원방향은 현재 선택지를 사용하며 기관별 선택지 관리는 이번 전환에 넣지 않는다. 정확한 목록과 키는 W03의 공유 계약이 소유한다.

## 3. 처리 상태의 증거

| 사용자에게 말할 수 있는 상태 | 서버가 함께 증명해야 하는 내용 |
|---|---|
| 확인함 | 검사 성공, 대상 revision, 확인한 회차 범위와 그 범위의 결과 개수 |
| 확인 중 | 해당 revision의 실제 실행 상태. 단순히 결과가 없다는 사실로 추정하지 않는다 |
| 확인 못 함 | AI 꺼짐, 자료 없음, 대기, 품질 부족, 권한 또는 안전 차단, 실패 중 실제 이유 |
| 확인함: 일부 범위 | 처리한 범위와 제외 범위 및 이유. 제외 구간은 확인하지 못한 것으로 함께 표시한다 |
| 확인 못 함: 자료 변경 | 원천이 바뀌어 결과 revision이 현재 자료와 다르다는 사실. 재검사 필요를 함께 안내한다 |

성공 0건과 미실행 0건을 같은 배열로만 전달하지 않는다. 표시상의 세 상태와 내부 작업 상태는 같은 enum이라는 뜻이 아니다. W05가 기존 축 적용 상태와 일감 상태에서 근거를 연결하며, 아직 없는 회차 범위나 성공 시각을 클라이언트가 만들어 넣지 않는다.

## 4. 대조 소비의 두 단계

현재 공개 축은 `missing_from_memo`, `missing_from_transcript`, `undiscussed_session_goal`이고 적용 상태는 `applied`, `no_transcript`, `no_text`, `no_session_goal`이다. 존재하지 않는 별칭을 fixture나 클라이언트가 정본으로 쓰지 않는다.

- 메모에 빠진 발언과 미논의 이번 상담 목표는 서로 다른 출력이다. 기존 상태와 인용을 유지한다.
- 메모에 녹음 근거가 없는 내용은 목록, 개수, 경고나 실무자 성과 통계로 표시하지 않는다. 기존 저장 이력을 지우라는 뜻은 아니다.
- 근거가 있는 문장의 작은 표시는 명시적인 양쪽 근거 연결을 필요로 한다. 누락 목록에 없다는 이유로 녹음 근거가 있다고 판정하지 않는다.
- 현재 DTO의 키를 바로잡는 것과 M4의 긍정 근거 연결을 생산하는 것은 별도 수용 기준이다. 후자는 G1 뒤 W07/W08이 소유한다.
- G2의 맥락상 명확한 상충과 M4의 누락을 섞지 않는다. 상충 기준의 정본은 [ADR-0018 보완](../../adr/0018-briefing-three-sections.md#2026-09-12-검출-기준-보완)이다.

## 5. 기억 그림자

D90의 그림자는 제품 생성과 재생성 요청에서 기억 입력을 제거하는 계약이다. 기억 자체의 생성, 저장, 정정과 파기는 유지한다. 설정 화면의 켜짐은 생성 설정이지 제품이 그 기억을 참고했다는 증거가 아니다. 사용하지 않은 기억의 사용 이력과 ‘지난 N회차 참고’ 문구를 만들지 않는다.

## 6. 한 묶음의 버전 전환과 복구

새 저장 의미나 공개 DTO를 바꾸는 담당자는 아래 표를 채운 실행 패킷을 총괄에 넘긴다. 구현 전 승인하지 않은 번호를 정식 버전으로 표기하지 않는다. 릴리스 담당자는 현재 설치와 배포 절차를 재사용한다.

패킷에는 정확한 producer/consumer 버전, 구버전별 읽기·쓰기 허용표, 서버의 거부 조건과 오류 코드, 백업 식별자, 복구와 재개 조건, 실행자 및 검토자를 포함한다. 번호와 코드는 해당 구현에서 기존 계약을 조사해 확정하며 이 문서는 새 값을 발명하지 않는다. 제품 정책은 Q가 승인하고, G7은 지정된 개인정보 담당의 검토도 필요하다. 총괄의 패킷 수령은 보호 브랜치 머지나 운영 배포 승인이 아니다.

| 경계 | 전환 조건 | 구버전 혼재와 복구 |
|---|---|---|
| SQLite와 PostgreSQL | 같은 의미의 forward migration, 기존 자료 읽기와 새 쓰기 구별, parity 확인 | 적용된 migration을 고치지 않는다. 새 자료를 구 코드로 다시 해석하지 않으며 복구 가능한 백업을 확보한다 |
| core와 HTTP | 저장 계약과 공개 응답을 함께 전환하고 권한, 출처와 승인 검사를 유지 | 지원하지 않는 새 쓰기는 기존 오류 경계를 통해 거부한다. 조용한 값 치환이나 장기 별칭은 만들지 않는다 |
| AI provider | prompt/schema/config hash를 함께 고정하고 재활성화 전까지 불일치를 거부 | 구 hash를 인정하도록 검사를 완화하지 않는다. 외부 호출 없이 수기 경로를 유지한다 |
| 처리 Agent와 S5/S6 | G7 뒤 packet, manifest 허용 버전, 마스킹과 core 검증을 함께 전환 | 원문 재마스킹과 새 근거 생성 전에는 옛 초안에 새 의미를 덧씌우지 않는다 |
| client와 서비스워커 | 실제 응답과 화면을 같은 출고 단위로 검증하고 캐시의 버전을 확인 | 새 DTO를 못 읽는 구 클라이언트가 새 의미의 자료를 쓰지 못하게 한다. 실패를 성공 화면으로 바꾸지 않는다 |
| rollback | 해당 릴리스 manifest와 백업에 결합한 복구 절차를 실행한다 | 옛 코드가 새 의미의 데이터를 안전하게 읽는다는 증거가 없으면 해당 쓰기를 닫는다. 데이터 손실을 숨기는 역변환은 하지 않는다 |

첫 인테이크의 권한 수정은 기존 두 응답을 확장하는 공동 변경이다. 등록 결과의 `canWriteIntake`와 인테이크 context의 `canWrite`는 core가 계산하고 client가 소비한다. 기존 context 조회 권한은 유지하며, 쓰기 권한만 폼과 제출에 적용한다. hub와 briefing을 추가 조회해 권한을 계산하지 않는다. 이 응답 확장은 구현 및 검증 중이며 현재 배포본의 계약으로 주장하지 않는다.
공동 출고 전 구 응답에는 이 두 필드가 없다. 새 클라이언트는 누락을 권한 있음이나 권한 없음으로 추정하지 않고 잘못된 응답으로 거부한다. 그러므로 API와 client는 같은 검증·출고 묶음으로 취급하며, 새 client만 먼저 배포하지 않는다.

## 7. 결정이 필요한 경계

결정과 승인 근거의 정본은 적용 계획 §6이다. G1/G3/G5/G6은 2026-09-13 Q가 확정했고, G7도 독립 기술 검토 뒤 추천안을 구현 정책으로 승인했다. 이는 기관의 법적 적합성이나 실제 자료 사용을 승인한 것이 아니다. G8의 남은 개별 정책은 미결로 유지한다.

| 관문 | 상태와 적용 결정 | 실행 시 지킬 경계 |
|---|---|---|
| G1 | 확정: 기존 수기 정본 유지, 카드 읽기는 원천 참조 투영, AI 추출은 별도 승인 | 기존 수기를 카드 정본으로 이전하거나 이중 쓰기하지 않는다 |
| G3 | 확정: 결과 이력과 남은 일의 상태를 분리 | 못 함과 무응답은 열린 채, 기한·내용 변경은 같은 일의 이력으로 남긴다. 완료·중단은 사람이 정한다 |
| G5 | 확정: 과거 값·버전·출처 보존, 새 기록부터 새 기준 | 모호한 과거 값을 자동 분리하지 않는다. 과거 기록을 새 형식으로 고칠 때 사람이 확인한다 |
| G6 | 확정: 공통 질문과 적용한 영역만 필수 판정 | 선택한 영역의 화면 접힘으로 필수를 없애지 않는다. 허용된 무응답 선택의 의미를 보존한다 |
| G7 | 확정: 금고 수준 암호화, 일반 화면 비노출, 기존 개인정보 보존·파기 연동, 기관 내부 신규 개체 등록 | 원문·대응표를 외부 AI나 기존 결과 객체에 싣지 않는다. 모호한 동일인·날짜는 추정하지 않는다. S5/S6 전환과 세 모드의 파기·복구를 검증한 뒤 적용한다 |
| G8 | 주요 지원방향은 이번 전환에서 현재 선택지 유지로 확정. 기관별 관리는 별도로 남김 | 나머지 문안, 보고서 수신자와 목표 검수의 개별 정책을 구현 착수만으로 승인하지 않는다 |

G7의 영속 대응표와 작업용 일회성 사전은 다른 저장물이다. Agent가 이름을 일반 토큰으로 바꾼 뒤 번호만 보낸다고 core가 원래 이름을 알 수 있는 것은 아니다. 처음 발견한 이름·기관을 등록할 별도 기관 내부 경계가 필요하며, 기존 `ResultRequest`에 원문을 몰래 추가하지 않는다. Agent에게 금고 키를 복제하지 않는다. 기존 beneficiary 금고의 보존·파기 절차를 재사용하되 번호 공간은 사례별로 격리하고, 새 사례에 과거 번호를 승계하지 않는다. 미파기 보관본의 복원과 이미 파기한 표의 재생 방지는 구별한다.

생년월일에는 상대 날짜를 적용하지 않는다. 원문 맥락이 분명한 사건일·기한만 상담일 기준으로 바꾸며, 연도나 날짜 의미가 불분명하면 더 정밀한 날짜를 추정하지 않는다. 기존 본문·인용·offset·hash를 사후 덮어쓰지 않고 새 버전의 재마스킹 산출물로 전환한다. 읽기 전용 기술 검토는 코드·계약 대조이며 실제 이름 탐지나 동일인 연결 정확도의 측정 결과가 아니다.

## 8. 검증과 완료 조건

- API와 client의 실제 계약으로 권한, 읽기 전용, 누락 이유, 인용과 승인 경계를 확인한다. fixture가 생산하지 않는 DTO를 꾸며 통과시키지 않는다.
- 두 DB, 이전 revision, 재생성, 정정, 철회와 파기 경합을 별도로 검증한다.
- 실제 브라우저의 desktop/mobile에서 등록과 첫 상담 기록 및 대조 표시를 확인한다. DOM 테스트나 CSS 정적 가드만으로 실화면을 확인했다고 하지 않는다.
- 구조 자기검사, 합성 API 화면 검수, 의미 품질, 실제 Windows 실행과 운영 배포를 별도 증거로 남긴다.
- 독립 정답 작성자와 검토자가 아직 지정되지 않은 새 모듈의 의미 품질은 미측정으로 남긴다. 구현자가 만든 답을 독립 정답으로 쓰지 않는다.
- 해당 작업에 적용되는 관문과 필드 책임이 닫히고 실제 producer/consumer 전환 및 복구가 검증되어야 그 작업을 완료 처리한다. W01 전체는 적용 계획이 요구하는 미결 데이터·권한 결정을 남긴 채 완료 처리하지 않는다.
