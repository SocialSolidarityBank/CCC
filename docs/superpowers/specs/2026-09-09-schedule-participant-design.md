시안: `artifacts/2026-09-09-workflow-prototypes/` (합성 데이터, 저장 없음)
상태: 그릴링 진행 중. 확정된 포크만 아래에 쌓는다. ADR과 `AGENTS.md` D행은 마지막에 한 번에 쓴다.

## 확정 1. 월간 격자는 우리가 그린다

월간 본문은 7열 격자이고 공용 부품이 그린다. 달력 라이브러리를 도입하지 않는다.

- 대체: D54(달력 격자가 아니라 날짜별 목록), CCC-133(월간은 날짜 아코디언), D75(월간 묶음).
- 셀은 높이 148 고정(767 이하 88), 날짜는 숫자만, 요일 줄은 월요일부터 일요일까지 이어지는 `--gradient-brand` 면 하나다.
- 넘치는 일정은 `+N건`으로 접고, 누르면 그 날짜의 일간 보기로 간다. 팝오버는 만들지 않는다.
- 요일 글자는 두 테마 고정 `--on-action` 하나다. 그라데이션 면이 두 테마에서 같은 밝은 파스텔이라 `--ink`를 쓰면 다크에서 흰 글자가 흰 면에 얹힌다. 토·일·공휴일 코랄은 셀 안 날짜 숫자가 가진다.
- 근거: FullCalendar 6.1.19는 gzip 82KB이고 이 화면에서 쓰는 것은 격자 배치뿐이다. 격자와 키보드 이동은 대략 200줄이고, 라이브러리 표면을 CSS로 덮으면 `guard:tokens`와 `guard:hierarchy`가 닿지 않는 자리가 생긴다.

## 확정 2. 종일 일정을 데이터로 갖는다

`counseling_schedules`에 컬럼 둘을 더한다. 마이그레이션 1건.

```sql
ALTER TABLE counseling_schedules ADD COLUMN all_day INTEGER NOT NULL DEFAULT 0;
ALTER TABLE counseling_schedules ADD COLUMN display_color TEXT
  CHECK (display_color IS NULL OR display_color IN ('mint','lavender','coral','cyan','light-magenta'));
```

- 시각 미정을 `00:00`으로 저장하는 규약은 기각했다. 자정에 잡힌 예약과 구분되지 않아 나중에 데이터를 되돌릴 수 없다.
- 색은 실무자가 고르고, 승인된 다섯 이름만 받는다(D47 형제 배지 순서).
- 용어는 `CONTEXT.md`의 `종일 일정`이다.

## 확정 3. 당사자 목록 응답에 이메일과 사업 이름을 싣는다

D31의 2026-09-02 조항 가운데 "일반 기록 응답에는 이메일을 싣지 않는다"를 목록 화면에 한해 개정한다.

- **뒤집는 이유**: 실무자 요청이다. 목록에서 사람을 특정하고 연락 수단을 고르는 일이 실제 업무이고, 지금은 그때마다 허브로 한 번 더 들어가야 한다.
- **뒤집어도 되는 근거(실측)**: 목록 경로는 이미 `enc_email`을 읽어 복호화하고 있다. `loadParticipantContacts`의 `includeEmail` 기본값이 `true`이고(`packages/core/src/gateway.ts:12791`), 값은 직렬화 단계 `assignedParticipantResponse`에서만 빠진다(`packages/http-api/src/request-handler.ts:1069`). 질의도 복호화도 늘지 않는다.
- **감사**: 목록 조회 1건 = 감사 1행을 유지한다(D24·ADR-0005). 행을 늘리지 않고 그 행의 `fields`에 `email`을 더한다. 목록 호출의 `auditParticipantPiiRead`에 `extraFields: ['email']`을 넘긴다.
- 참여 사업은 건수 대신 사업 이름 목록을 싣는다. 케이스를 이미 읽고 있어 새 질의가 없다.
- 검색 범위는 이름, 당사자 ID, 연락처, 이메일, 사업이다.
- 계좌는 계속 목록에 싣지 않는다.

## 확정 4. 목록 간격은 카드 성격이 정한다

D60 ③ 여백 3단을 4단으로 늘린다. 시안 `spacing.html`로 세 안을 나란히 놓고 골랐다.

| 자리 | 값 |
| --- | --- |
| 페이지 세로 스택 | 32 `--section-gap` |
| 읽는 목록 안 카드(브리핑 회차, 기록, 검토 큐) | 20 `--space-5` |
| 고르는 목록 안 카드(당사자 관리, 일정 등록 후보) | **8 `--space-2`** |
| 행 카드 스택 | 16 `--space-4` |

- 가르는 기준은 D59가 이미 쓰던 것과 같다. 훑어 하나를 고르는 목록이면 8, 글을 읽는 목록이면 20이다.
- 전부 8로 좁히는 안은 기각했다. 시안에서 글이 담긴 카드가 8로 붙으니 카드 경계가 글줄 사이 여백처럼 읽혀 한 건의 끝이 흐려졌다.
- 새 토큰은 없다. 8은 `--space-2`다.

## 확정 5. 여백 계단 규칙은 그대로 둔다

`4의 배수 + 하프스텝 2·6·10·14` 규칙을 8의 배수 기준으로 다시 세우자는 안은 기각했다.

- 8의 배수는 이미 4의 배수 안에 있어서 새 제약은 하프스텝 폐지 하나뿐인데, 폐지하면 이미 픽셀로 확정한 값 둘을 되돌려야 한다. 사이드바 메뉴 항목 사이 2px(2026-09-03 Q)과 컨트롤 안쪽 패딩 10px `--control-pad`(전 입력칸과 버튼에 퍼진다)이다.
- 이번 시안이 드러낸 문제는 목록이 성기다는 것이고 계단과 무관하다.

## 확정 6. 월간 격자 셀 글자는 12px 다섯 번째 예외다

`DESIGN-RULES.md:228`의 14px 하한 예외 목록에 한 줄을 더한다.

- 자리 이름: **월간 격자 셀의 날짜 숫자와 일정 이름**. 소유자는 `.month-date`와 `.calendar-event-title`이고 값은 `--text-badge` 12/400이다.
- 셀 밖으로 퍼지지 않는다. 요일 줄과 `+N건`은 이 예외에 들어가지 않는다.
- 14로 올리는 안은 기각했다. 셀 148px에 들어가던 일정이 3줄에서 2줄로 줄어 `+N건`이 잦아지고, 셀을 키우면 다섯 주에서 세로가 100px 늘어난다.
- 13px 레일 예외를 재사용하는 안도 기각했다. 그 조항은 "상담 기록 좌측 레일"이라는 자리 이름에 묶여 있어 두 화면을 함께 가리키면 나중에 어느 쪽 기준인지 셀 수 없다.

## 확정 7. 단계 표시는 `WireSteps`로 두고 지나온 단계만 누르게 한다

시안이 일정 등록의 단계 표시를 탭(`role="tablist"`)으로 바꾼 것을 되돌린다.

- 탭은 순서 없는 화면 전환을 뜻해서, 1단계를 끝내야 존재하는 2단계가 눌릴 것처럼 보인다. 스크린리더도 "선택 안 됨"으로만 읽어 왜 못 가는지 알려주지 못한다.
- 대신 `WireSteps`에 되돌아가기를 더한다. **이미 지나온 단계 칩만 버튼**이고, 현재와 앞 단계는 지금처럼 누르지 못하는 읽기 항목이다. `aria-current="step"`과 완료·현재·대기 어휘(§4-117)는 그대로다.
- 호출부는 `apps/web/app/schedules/new/schedule-wizard.tsx:340` 하나다. 인테이크는 `IntakeStepRail`을 따로 쓴다.

## 확정 8. 당사자 허브 HERO는 일곱 항목이고 생년월일을 싣는다

D38의 세 항목(ID, 연락처, 이메일)을 일곱으로 넓힌다. 당사자 ID, 연락처, 이메일, 생년월일, 기록 현황, 최근 상담, 진행 상태다.

- **생년월일을 싣는 이유**: 실무 요청이다. 값은 이미 등록 때 받아 `enc_birth_date`에 있고(마이그레이션 0015), 지금은 허브 응답에서 빠져 있을 뿐이다.
- **비용**: 같은 금고 행을 읽으므로 질의는 늘지 않고 복호화 1건이 는다. 감사는 행을 늘리지 않고 그 행의 `fields`에 `birth_date`를 더한다(D24 화면 조회 1건 = 감사 1행).
- **동의 범위**: 생년월일은 개인정보 수집·이용 동의로 이미 받은 항목이고 열람 범위도 담당 실무자와 기관 관리자다. 동의 문안은 바꾸지 않는다.
- **상태 태그는 없앤다.** 진행 상태를 정보 격자 항목 하나로 통일한다. 같은 사실을 한 카드에 두 번 두지 않고, 격자 항목이면 종결 시점처럼 값을 함께 적을 자리가 생긴다.
- 4열 규칙(`DESIGN-RULES.md:202`)에서 "네 항목" 제한을 지우고 폭 기준만 남긴다. HERO 내부 폭 960px 이상이면 4열, 760px 초과 960px 미만이면 3열, 760px 이하는 라벨 행이다.

## 확정 10. 좁은 화면에서 카드 행동은 세로 전폭 스택이다

767 이하에서 당사자 카드의 행동 버튼 세 개를 세로로 쌓고 카드 폭 전체로 편다(2026-09-09 Q).

- **버튼 글자를 지우지 않는다.** 시안이 쓰던 아이콘 전용(라벨 `clip-path` 숨김)은 기각했다. 아이콘 셋이 서로 다른 글리프라 짝 비교가 아니라 암기가 되고, 하루 몇 번 여는 목록에는 맞지 않는다.
- 데스크톱 가로 배치와 순서는 같다. 정보 보기, 일정 등록하기, 상담 기록하기다.
- 전폭을 고른 이유는 카드 안 위 요소(사업 선택창)와 좌우 끝선이 맞고 누름 면적이 293px로 넓어지기 때문이다. 내용 폭(144px) 안과 카드 높이는 589px로 같다.
- 실측 390px: 세 줄, 버튼 높이 32, 줄 사이 8, 가로 넘침 없음. 증거 `qa/g7-stack-full.png`, 비교본 `qa/g7-stack-center.png`.

## 확정 11. 같은 대상의 보기와 등록은 같은 글리프에 더하기로 가른다

2026-08-30 Q가 당사자 메뉴에 쓴 어휘(목록은 사람, 등록은 사람 + 더하기, 초대는 고리 두 개)를 일정에도 적용한다. 새 규칙이 아니라 빠져 있던 짝을 채우는 것이다.

| 자리 | 구 | 신 |
| --- | --- | --- |
| 일정 보기 | 시계 | 달력 |
| 일정 등록하기 | 달력 | **달력 + 더하기** `calendar-plus` |
| 상담 기록하기 | 사이드바 화살표, 카드 버튼 펜 | **펜** `record` 하나로 통일 |

- `calendar-plus`를 `shell-icons.tsx`에 신설했다. 더하기는 달력 몸통 안에 넣는다. 사람 아이콘처럼 옆에 붙이면 16px에서 달력 테두리와 겹친다.
- 화살표는 방향만 말하고 무슨 일인지 말하지 않아 기록 행동에서 뺀다. `arrow-right`는 다른 자리에서 그대로 쓴다.
- 시계 글리프 `upcoming`은 일정 메뉴에서 쓰지 않는다.

## 확정 12. 리포트 구획 번호는 부품이 만든다

`01. 상황변화`처럼 제목 문자열에 번호를 박던 방식을 버린다(2026-09-09 Q).

- 번호는 내용이 아니라 순서다. 구획 목록의 순서에서 뽑고 두 자리로 채운다. 제목 문자열은 `상황변화`뿐이다.
- 마크업은 `.report-section-title` 안에 `.report-index` + 제목 두 조각이다. 번호는 제목과 **같은 계단**을 쓰고 색만 `--sub`로 물러선다. 자리는 `2ch` 고정에 `font-variant-numeric: tabular-nums`라 구획이 몇 개든 제목 시작 x가 같다.
- 문자열에 박으면 구획을 넣고 뺄 때 사람이 번호를 고쳐야 하고, 화면 문자열 검사가 중복 번호를 잡지 못한다.
- **정렬 실측**(`align-check`, 1440):
  - 번호 다섯 개 center-x 공유: delta **0px**
  - 번호가 제목 줄 안 세로 중앙: delta **0px**
  - 카드 꺽쇠가 제목 줄 세로 중앙: delta **0.5px**
  - 번호 left 337 다섯 개 동일, 제목 left 365.4 다섯 개 동일, 번호 칸 폭 20.4(`2ch`)
  - 증거 `qa/g9-report-index.png`
