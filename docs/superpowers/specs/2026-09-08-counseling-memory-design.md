# 상담 기억 설계

상태: 2026-09-08 사용자가 상세 설계와 구현 착수를 승인했다. 구현 순서와 파일 소유권은 `../plans/2026-09-08-counseling-memory.md`를 따른다.

## 목적과 범위

상담 기억은 다음 상담에 필요한 당사자의 맥락을 백그라운드에서 유지한다. 실무자 개인의 작성 선호와 업무 방식은 포함하지 않는다. 기억은 사업별 케이스에 속하며 같은 당사자라도 다른 사업의 기억을 합치지 않는다.

## 기억의 형태

- 개별 기억 항목을 기준으로 관리하고, 항목을 묶은 현재 맥락 요약을 함께 제공한다.
- 요약은 별도의 사실 원본이 아니며 항목에 없는 사실을 더하지 않는다.
- 기존 목표와 액션 아이템은 복제하지 않고 연결한다.
- 기록에 명시된 사실과 여러 회차를 종합한 기억 관찰을 구분한다. 반복 양상에는 근거 회차를 붙인다.
- 성격 판단, 심리 진단, 지원 지속·중단 판단은 만들지 않는다.

## 자동 갱신과 정정

- 기억 항목과 현재 맥락 요약은 항목별 승인 없이 자동 갱신한다. 기억 관리를 실무자의 일상 업무로 만들지 않는다.
- 기억은 공식 상담 기록 자체가 아니다. 자동 기억 갱신이 원본 상담 기록을 수정하거나 미승인 상담 초안을 공식화하지 않는다.
- 정정은 필요할 때 기억 내용을 직접 열어 바로잡는 예외적인 행위다.
- 동일한 과거 근거를 재처리해 사람의 정정을 되돌리지 않는다. 이후 명확한 새 근거가 생기면 자동 갱신할 수 있다.
- 애매하거나 충돌하는 근거를 한쪽 사실로 덮어쓰지 않으며 별도의 기억 승인 대기를 만들지 않는다.

항목마다 수정·승인 버튼을 붙이지 않는다. 실제 평문 memory.md 파일을 외부 편집기로 여는 흐름 대신 앱 안에서 내용을 확인하고 예외적으로 정정한다. 기존 암호화 저장, 접근 권한과 감사 경계를 유지한다.

## 기본 탑재와 기관 설정

- 자동 기억은 AI 사용 조건이 갖춰지면 작동하는 기본 기능이다. 실무자는 별도 활성화나 모델·프롬프트 선택을 하지 않는다.
- 기관 설정은 자동 기억 켜기/끄기와 처리 상태를 제공한다. 기관이 꺼 둔 선택은 유지한다.
- 기존 AI 연결과 해당 케이스의 동의·마스킹 조건을 충족해야 작동한다. 기억 기능이 AI를 임의로 활성화하지 않는다.
- 끄면 새 기억 생성과 자동 갱신을 중단한다. 기존 기억은 마지막 갱신 시점을 표시해 읽을 수 있게 한다.
- 동의 철회와 파기는 단순한 기능 끄기와 구분한다.
- Honcho·Hindsight 같은 엔진 선택을 실무자에게 맡기는 설정은 두지 않는다.

## 기존 기록과 기억 재료

- 기능이 작동하기 시작하면 해당 케이스의 기존 공식 기록까지 자동으로 정리해 첫 기억을 만든다. 이후에는 추가·변경된 기록을 반영한다.
- 재료는 저장된 수기 기록, 승인된 AI 기록, 목표와 액션이다. 미승인 AI 초안은 제외한다.
- 과거 기록도 현재 동의와 마스킹 조건을 충족한 것만 사용한다. 기억 자체에는 별도 승인을 요구하지 않는다.
- 초기 소급 처리에는 처리 시간과 AI 비용이 발생할 수 있다.

## 기억의 활용 범위

- 기억은 15초 페이지의 상담 준비와 회차별 AI 정리의 배경 맥락에 활용한다.
- 현재 상담이 과거 사건, 목표와 약속에 어떻게 이어지는지 참고하되, 과거 기억을 이번 상담에서 나온 말처럼 사용하지 않는다.
- 이번 회차의 요약과 인용은 이번 회차 자료로 뒷받침한다. 과거 맥락은 출처를 구분한다.
- 기억이 원문과 충돌해도 기억을 정답으로 취급하지 않는다.

## 갱신 시점과 대기 상태

- 기억의 근거인 수기 기록의 저장·수정, AI 기록 승인, 목표·액션 변경이 생기면 백그라운드 갱신을 예약한다. 기억의 직접 정정도 관련 요약에 반영한다.
- 짧은 시간의 연속 변경은 묶어서 처리하며 매번 전체 이력을 다시 읽지 않는다.
- 기록 저장과 화면 진입은 기억 처리 완료를 기다리지 않는다.
- 처리 중에는 기존 기억과 최근 기록 반영 중 상태를 보여준다. 마스킹이나 처리 장비가 준비되지 않았으면 대기한다.
- 자동 생성된 기억이나 요약의 저장 자체를 새로운 원본 변경으로 간주하지 않는다. 같은 근거로 자기 갱신을 반복하는 순환을 만들지 않는다.

## 오래된 기억과 현재성

- 시간 경과만으로 기억을 삭제하거나 해결된 것으로 판단하지 않는다. 오래된 내용은 현재 중요도에 따라 요약에서 물러날 수 있으나, 여전히 유효한 배경은 유지한다.
- 해결되거나 새 사실로 바뀐 내용은 근거에 따라 과거 상태로 옮기고 출처와 이력을 남긴다.
- 이력 보존은 무기한 보관을 의미하지 않는다. 기존 개인정보 보존·파기 규칙을 따른다.

## 참고한 구조

CCC 내부 기능으로 구현한다. 기존 저장소, 처리 Agent와 OpenAI 연결을 사용하며 별도의 기억 서버나 외부 MCP 연결은 추가하지 않는다. 아래 제품은 자동 기억 구조의 참고 자료이지 설치 의존성이 아니다.

- [Honcho](https://github.com/plastic-labs/honcho#the-honcho-loop): 기록 저장, 백그라운드 처리, 맥락 조회와 사용.
- [Hindsight](https://github.com/vectorize-io/hindsight#core-concepts): 개별 기억과 근거를 종합한 관찰의 구분.
- [Hermes](https://github.com/NousResearch/hermes-agent): 지속 기억과 과거 대화 검색의 조합.

## 상세 설계 제안

이 절은 위 제품 결정을 구현하는 상세 설계다. 구현 순서와 파일 경계는 연결된 구현 계획을 따른다.

### 원본, 항목, 관찰과 요약의 관계

- 원본은 케이스 안의 공식 기록과 목표·액션이다. 원본의 식별자, 수정 버전, 상담 시점과 마스킹 스냅샷을 기억의 근거로 연결한다.
- 기억 항목은 사실과 관찰을 구분하고 현재·과거 상태, 근거, 변경 시점과 수정 이력을 갖는다. 목표·액션 참조는 원본의 상태를 읽으며 문구 복사본을 또 관리하지 않는다.
- 관찰의 반복 횟수는 서로 다른 원본 회차에서 계산한다. 요약, 같은 회차의 재생성본이나 기억 자체를 새로운 독립 근거로 세지 않는다.
- 현재 맥락 요약은 정확한 기억 항목 버전 집합을 참조한다. 항목이 정정되거나 무효화되면 그 항목에 의존한 요약도 갱신 대상으로 바뀐다.
- 기억의 직접 정정은 항목의 원본 근거를 위조하지 않는다. 사람의 정정이라는 출처와 정정 당시 근거 범위를 별도로 기록한다.

### 변경과 동시 처리

- 원본 변경과 기억 갱신 예약을 동일한 업무 DB 원자 경계에 기록한다. HTTP 응답 뒤 일회성 비동기 호출만으로 갱신을 보장하지 않는다.
- 케이스별 요청 세대와 반영 세대, 변경된 원본 목록을 유지한다. 작업자는 받은 세대, 원본 버전, 정정 버전, 기관 설정 버전과 동의 상태를 확인하고 결과를 반영한다.
- 작업 중 새 수정이 생기면 이전 결과가 새 기억을 덮어쓰거나 새 대기 작업을 완료 처리하지 못한다.
- 처음에는 기존 공식 기록을 순서대로 나누어 처리하고 진행 위치를 보존한다. 이후에는 변경된 원본과 관련 기억을 처리한다.
- 처리 상한 때문에 재료를 조용히 버리지 않는다. 처리한 범위와 대기·제외 범위를 구분하고, 제외 사유는 권한 있는 화면에 표시한다.
- 사람의 정정을 바꿀 때는 해당 항목에 관한 새로운 명확한 근거를 요구한다. 케이스의 무관한 목표 하나가 바뀌었다는 이유만으로 정정 보호를 해제하지 않는다.

### LLM과 기억 검색

- LLM은 제공된 마스킹 재료에서 기억 항목의 추가·갱신·과거 상태 이동과 관찰을 제안하고, 코어가 근거와 상태 전이를 검증해 자동 반영한다. LLM에 DB 직접 쓰기나 자유로운 외부 도구 권한을 주지 않는다.
- 조회 범위는 언제나 기관과 케이스로 먼저 제한한다. 현재 목표와 상담 맥락, 관련 주제, 현재성, 근거 시점을 이용해 필요한 기억을 선택한다.
- 화면의 요약과 회차별 AI 배경 재료는 선택된 기억과 원본 근거 연결을 함께 갖는다. 모든 기억을 매번 LLM에 보내지 않는다.
- 과거 기억은 이번 회차 주장이나 인용의 직접 근거가 될 수 없다. 출력 검증에서 현재 회차 근거와 과거 배경을 구분한다.
- 기억 생성용 입력과 기억을 다시 사용하는 입력 모두 기존 외부 AI 검증을 통과해야 한다. 사람의 정정도 외부 전송 전 마스킹을 거친다.

### 무효화와 수명

| 사건 | 기억과 처리의 동작 |
| --- | --- |
| 새 기록 추가 | 기존의 유효한 기억은 표시하면서 추가 내용을 반영 |
| 원본 정정·삭제 | 영향받은 자동 항목과 그 항목을 참조하는 요약을 현재 맥락과 AI 재료에서 제외하고 재처리. 사람이 정정한 항목은 보호하며, 사라진 원본 버전을 AI 재료로 복원하지 않음 |
| 기관이 자동 기억 끄기 | 새 작업과 결과 반영 중단. 현재 권한과 보존 조건을 통과한 기존 기억은 갱신 중단 상태로 읽기 가능 |
| AI 동의 철회 | 새 외부 호출과 진행 중 결과 반영 중단. 보조 기억의 상담 활용을 중단하며 원본 공식 기록은 별도 기존 정책을 따름 |
| 케이스 종결 | 다음 상담을 위한 자동 갱신 중단. 기존 권한과 보존 조건 안에서 종결 시점의 기억을 읽기 전용으로 확인 |
| 개인정보 아카이브 | 일반 상담 화면과 AI 재료에서 기억 제외. 원본의 제한된 보존 경계를 따라 관리 |
| 파기 실행 | 해당 당사자의 기억 본문, 과거 버전, 검색용 파생 자료와 처리 중간물을 함께 파기. 원문 없는 감사 증거만 기존 규칙에 따라 유지 |

AI 동의 철회는 기관의 기능 끄기와 같지 않다. 재동의만으로 중단 전 작업을 재개하거나 과거 기억을 즉시 현행으로 승격하지 않고, 현재 유효한 원본과 동의에서 새 작업을 만든다. 보존이나 파기 실행의 권한·승인 절차는 기존 제도를 바꾸지 않는다.

### 접근과 저장

- 읽기는 기존 케이스 상담 내용 열람 권한을 따른다. 정정은 활성 실무자 역할과 해당 케이스 담당 배정을 모두 요구한다.
- 기관 설정 변경은 기관 관리자 권한을 따른다. 기술 관리자에게 기억 본문이나 상담 출처를 새로 노출하지 않는다.
- 저장과 감사는 gateway facade를 통한다. 기관·케이스 범위를 가진 조회 결과를 클라이언트에서 재필터링하는 방식은 쓰지 않는다.
- 기억 본문과 정정 이력은 상담 데이터와 같은 보호 경계를 따른다. 평문 외부 파일이나 별도 개인 저장소는 만들지 않는다.
- 브라우저 영속 저장소, URL, 로그, 진단 보고서에 기억 내용이나 검색어를 남기지 않는다.
- 원본 정정·철회·파기가 발생한 뒤 늦게 도착한 작업 결과나 백업 복원이 파기된 기억을 다시 살리지 못하도록 원본 수명 상태를 재검사한다.

| 기관에서 끔 | 기존 기억이 있다면 읽기 가능, 자동 갱신 중단 표시 |
| AI 연결·마스킹·동의 조건 미충족 | 사유를 표시하고 외부 호출하지 않음. 동의 철회는 기억 본문 활용도 중단 |
| 처리 실패 | 이전 유효 기억을 최신이라고 표시하지 않음. 현재 상담 기록을 대체하지 않고 관리자에게 처리 상태 제공 |

실패 뒤 다른 사업자나 안전하지 않은 입력으로 자동 전환하지 않는다. 기존 처리 실행기의 재시도와 장애 상태를 재사용하며 사용자가 기억 승인을 해야 풀리는 상태는 만들지 않는다.

### 구현 검증 기준

- 기존 공식 기록에서 기억을 만들고, 새 상담으로 갱신한 뒤 실제 15초 페이지와 기억 상세에 반영되는 흐름을 확인한다.
- 다른 기관·다른 케이스 접근, 비담당 쓰기, 미승인 AI 초안 유입을 차단한다.
- 오래된 작업 결과가 최신 기록이나 사람의 정정을 덮어쓰지 못한다. 정정 이후 무관한 변경과 같은 옛 근거 재처리도 검증한다.
- 사실과 여러 회차의 관찰을 구분하고, 같은 회차의 재생성본을 반복 근거로 중복 계산하지 않는다.
- 현재 회차 출력에 과거 기억을 현재 발언으로 인용하는 결과를 거부한다.
- 동의 철회, 기능 끄기, 원문 수정·삭제, 종결, 아카이브·파기와 작업 완료가 경합할 때 계약을 지킨다.
- 마스킹 미통과나 증명 누락 상태에서 외부 호출이 발생하지 않는다. 실제 NER·공급자 자격이 없는 환경에서는 그 상태를 숨기지 않는다.
- 가상 풀데이터로 390px, 768px, 1280px 화면과 읽기·근거 확인·정정·기관 설정 조작을 검수한다.

### 구현 전 확인한 선행 계약

현재 checkout 조사 결과와 이번 기능에서 지켜야 할 기준을 구분한다.

1. 현재 text Agent 작업은 회차 중심이며 source를 실시간으로 조립한다. 목표·액션·정정만 있는 재료에는 정확한 원본 목적과 버전 연결을 추가해야 한다. 가짜 세션을 만들거나 일반 회차 text_context로 위장하지 않는다.
2. 현재 예약 실행기는 watchdog과 retention 중심이다. 기억 작업에는 실제 cron 진입점과 영속 대기열을 연결해야 하며, 화면 진입이나 프로세스 메모리에만 의존하지 않는다.
3. S6이 요구하는 snapshot 증명 전체 보존과 OpenAI 호출 직전 동의 CAS는 현재 재사용 경로에 완성돼 있지 않다. 기억의 historical/derived-summary까지 동일 검증을 적용하고, 필요한 저장·egress 계약을 구현해야 외부 호출 경로가 완성된다. 이전 스냅샷을 자동으로 신뢰하거나 증명을 꾸며 채우지 않는다.
4. 현재 공급자 입력에는 재료당 24,000자 상한이 있다. 큰 원본 하나도 구간별로 처리하고 근거 위치를 유지해야 하며, 여러 원본 묶음 처리만으로 장문 처리가 끝났다고 보지 않는다.
5. 현재 main에는 최종 Vite 클라이언트, Local 서비스, Supabase Edge 런타임과 PostgreSQL baseline/adapter가 없다. 현행 실행 표면은 Next·Workers·Python Agent다. 이 기억 기능이 세 정식 배포 모드 전체의 이전·설치까지 완료했다고 주장하지 않는다. 대응 SQL 작성과 실제 PostgreSQL parity 증명도 구분한다.
6. 실제 NER release qualification과 사업자 자격은 코드로 가정하지 않는다. 충족하지 않은 환경에서는 외부 AI가 차단된 상태를 보여주며, 실데이터나 운영 자격증명을 가상 프리뷰에 연결하지 않는다.
