# relayer 설치와 설정 온보딩 설계

- 상태: 제품 설계 승인. 2026-09-13 Q가 전체 설계안을 승인하고 독립 워크트리와 구현 계획 및 핸드오프를 요청했다.
- 결정 정본: [ADR-0050 / D91](../../adr/0050-relayer-assisted-onboarding.md). 제품 이름, 전체 설치 범위, PC 실행, 단계별 승인, 자유 질문과 필요 시 연결이라는 여섯 결정은 다시 묻지 않는다.
- 범위: 최초 가입과 설치, 이후 AI/STT/DB 연결 설정. 실행 주체는 사용자 PC의 설치 도구와 기존 코딩 에이전트, Cloud의 설정 도우미다.
- 구현 계획: [온보딩 실행 계획](../plans/2026-09-13-relayer-onboarding-implementation.md)
- 인계: [새 세션 시작 문서](../plans/2026-09-13-relayer-onboarding-handoff.md)
- 구현 경계: N01의 단계 안내 CLI와 승인 내용 결합은 `scripts/onboarding/`에 있다. 아래 전체 여정은 구현 목표이며, 실제 설치, 외부 자원 생성, 자유 질문과 AI/STT 설정 실행이 연결된 것은 아니다. 작업별 완료 근거는 실행 티켓과 커밋에 남긴다.

## 기준과 승인 경계

기준 코드는 `ad218e8eafa646a524674fe4ef8cf9c20c0b68bb`다. main의 D89는 Cloud MFA 선택, D90은 초대 수락의 신원 결속이다. Cloud에서 `aal1`을 허용하는 최신 개정을 유지하고 `POST /identity/link`를 복원하지 않는다. Local 인증 차이는 S2/S4를 유지한다.

오케스트레이터의 동명 D89/D90과 S2/S11을 통째로 복사하지 않는다. 독립 Cloud 실행 및 최초 관리자 초대라는 이 설계의 요구는 ADR-0050을 따른다. 실제 자원 생성, 결제, 새 권한 부여, 배포와 제품 활성화에는 별도 실행 승인이 필요하다.

## 사용자 여정과 공통 동작

### 서로 구분할 주체

| 주체 | 역할 | 하지 않는 일 |
|---|---|---|
| 사용자 | 사용 방식 선택, 계정 인증, 약관과 결제 동의, 설치 대상과 변경 승인 | 비밀값을 채팅에 붙이거나 API 호출마다 승인하지 않는다 |
| 설치 도구 | 사용자 PC에서 승인된 설치 계획을 실행하고 결과를 검사한다 | Cloud의 일반 업무 API에 설치 관리자 자격을 남기지 않는다 |
| 설치를 맡은 코딩 에이전트 | 저장소의 설치 절차를 읽고 설치 도구를 호출하며 질문을 전달한다 | 임의 SQL이나 설정 파일 수정으로 설치 검증을 우회하지 않는다 |
| 설정 도우미 | 현재 단계 설명, 자유 질문 답변, 허용된 다음 행동 제안을 맡는다 | 스스로 권한이나 준비 완료 상태를 만들지 않고 비밀값을 읽지 않는다 |
| 처리 Agent | 기관 PC에서 상담 자료의 전사와 가림 처리를 수행한다 | 설치를 맡은 코딩 에이전트나 설정 도우미와 같은 주체가 아니다 |

설치 도구를 실행한 PC가 이후 처리 Agent 장비가 되는 것은 자동 결정하지 않는다. AI를 준비할 때 현재 PC와 다른 기관 장비 중 실제 처리 장비를 확인한다. 설치 도구를 종료해도 Cloud의 수기 업무는 계속되지만, 처리 장비의 가용성은 상담 AI의 처리 가능 여부에 영향을 준다.

### 공통 진행 규칙

각 단계는 다음 순서를 따른다.

1. 저장된 설정, 설치 기록과 실제 검사 결과를 읽어 이미 끝난 부분을 확인한다.
2. 지금 필요한 질문 하나와 선택 이유를 보여준다. 모드, 역할이나 이미 확인된 값으로 답을 알 수 있으면 다시 묻지 않는다.
3. 사용자가 값을 입력하거나 선택한다. 비밀값은 채팅과 분리된 입력 경로로 받는다.
4. 변경 대상, 바뀌는 설정, 비용 발생 가능성과 외부로 나가는 정보를 보여준다.
5. 사용자가 `이대로 설정`으로 해당 묶음을 승인한다.
6. 실제 실행 도구가 권한과 계획의 유효성을 다시 확인하고 적용한다.
7. 결과를 검사하고 다음 질문 또는 현재 단계의 복구 안내로 이동한다.

비용 표시는 예상치이지 공급자의 결제 상한 보장이 아니다. 비용이나 권한의 변화가 승인한 계획을 벗어나면 다시 승인받는다.

자유 질문을 하는 동안 현재 입력과 단계는 유지한다. 답변이 설정 변경 제안으로 이어지면 입력과 변경 요약으로 돌려보내고, 대화만으로 적용하지 않는다. LLM이 없거나 응답에 실패해도 고정 안내와 입력 경로는 계속 사용할 수 있다.

### Cloud의 첫 설치와 가입

| 단계 | 질문과 안내 | 실행 및 다음 단계의 조건 |
|---|---|---|
| 1. 시작 확인 | 처음 설치인지 기존 설치를 이어가는지 확인한다. 설치할 기관과 사용할 계정을 구분한다 | 기존 설치와 데이터는 먼저 관찰하고 덮어쓰지 않는다 |
| 2. 계정과 대상 준비 | 계정 로그인, 소유 기관, 필요한 권한과 예상 비용을 확인한다 | 사용자가 인증과 동의를 마친 뒤 승인한 대상에 한해 자원 생성 계획을 만든다 |
| 3. 클라우드 자원 생성 | 기관 소유 저장소와 업무 API 실행 환경을 어떤 곳에 만들지 설명한다 | 단계별 승인 후 자원을 생성하고 실제 대상, 리전과 소유권을 확인한다 |
| 4. relayer 설치 | DB, 인증, 비공개 파일 저장소와 업무 API에 적용할 내용을 안내한다 | 기존 서명, 소유권, read-only plan, 적용과 검사 계약을 통과한다 |
| 5. 최초 관리자 가입 | 지정한 최초 관리자에게 초대를 보내고 인증을 마치도록 안내한다 | 인증 사용자를 기관 생성자에 연결하고 첫 설정 화면으로 넘긴다. 비밀번호와 초대 토큰은 채팅에 넣지 않는다 |
| 6. 설정 도움 선택 | OpenAI를 지금 연결해 설정 도움을 받을지, 고정 안내로 계속할지 묻는다 | 연결을 검사하고 설정 도우미용 전송 범위를 확인한다. 연결하지 않아도 다음 단계로 갈 수 있다 |
| 7. 기관 초기 설정 | 기관 이름, 첫 사업, 동의 문안과 보유기간을 필요한 순서로 묻는다 | 저장 상태와 사업 도입 확인을 검증한다. 미확인 항목 때문에 잠긴 기능을 구체적으로 알린다 |
| 8. 상담 AI와 음성 인식 준비 | 처리 장비, AI와 STT 사용 여부, 필요한 연결을 묻는다 | 연결 상태와 제품 사용 가능 상태를 구분하고 승인 조건을 통과한 기능만 연다 |
| 9. 사용 시작 | 지금 사용할 수 있는 기능과 아직 준비가 필요한 기능을 보여준다 | 필수 기관 준비를 마쳤다면 AI 없이 수기 업무를 시작할 수 있다 |

3단계의 신규 자원 생성은 현재의 기존 프로젝트 대상 설치 명령 앞에 필요한 추가 구현이다. 자원을 만든 뒤 얻은 식별정보로 설치 대상과 서명 문서의 결합을 검증한다. 이 선행 단계를 이유로 S11의 DB 변경 전 서명·소유권 검증을 생략하거나 관찰한 소유자를 자동 승인값으로 삼지 않는다.

최초 관리자의 첫 로그인 전까지 필요한 생성과 연결은 설치 도구의 제한된 권한으로 처리한다. 로그인 뒤에는 현재 사용자와 기관 권한으로 전환한다. 기관 초기 설정이 끝나지 않았다는 이유로 설정 준비 동작까지 막는 순환 의존성은 없애되, 일반 상담 자료 접근을 함께 열지 않는다.

### Local Single의 첫 설치

사용자가 저장소를 주고 설치를 요청하는 것이 입구다. 특정 코딩 에이전트 제품에만 의존하지 않도록 설치 절차, 필요한 입력, 실행 명령과 비밀값 없는 결과 형식을 저장소에 둔다. 별도의 범용 에이전트 프레임워크를 만들지 않고 기존 설치 실행 기능을 재사용한다.

1. 에이전트가 사용 방식과 기존 설치 유무를 확인하고 운영체제, 저장 공간과 설치 전제를 검사한다. 현재 정식 Local Single 대상은 S12의 Windows 11 x64다. 지원하지 않는 환경을 정식 설치 성공으로 보고하지 않는다.
2. 설치 위치, 앱 잠금과 복구 준비를 안내하고 사용자 확인을 받는다. DB 종류는 임의로 고르게 하지 않고 암호화 SQLite 계약을 따른다.
3. 검증된 설치 산출물을 적용하고 로컬 서비스와 클라이언트를 연결한다. 저장소의 코드를 직접 실행한 개발 상태를 서명된 정식 설치와 혼동하지 않는다.
4. 암호화 저장, `127.0.0.1` 접속 경계, 앱 잠금과 실제 기동을 확인한다.
5. 초기 설정을 마친 뒤 AI와 음성 인식을 지금 준비할지 묻는다. 건너뛰면 `off` 상태로 수기 업무를 사용할 수 있다.

Local 설치를 안내하는 외부 코딩 에이전트의 모델 연결과 relayer 내부의 AI 연결은 별개다. relayer에 키가 없다는 이유로 외부 에이전트의 설치 안내를 막지 않는다.

Local Office도 별도 온보딩 엔진을 만들지 않고 같은 진행 규칙을 사용한다. 서버와 클라이언트 구분, 내부망 HTTPS, 로컬 계정과 복구 항목은 기존 S4 계약에 따라 달라진다. Office에 필요한 항목을 Single에 그대로 표시하지 않는다.

### 나중에 연결 설정을 바꿀 때

새 AI 설정 페이지를 만들지 않고 기존 `연결 상태` 영역에서 해당 항목의 안내를 시작한다. 처음 가입한 일반 실무자에게는 역할에 필요한 이용 안내만 제공하고 기관의 기술 설정 권한을 부여하지 않는다.

| 대상 | 진행할 내용 | 지킬 경계 |
|---|---|---|
| OpenAI 연결 | 연결 준비, 비밀값의 안전한 공급, 검사, 변경 영향 확인, 승인과 적용 | 설정 도우미 사용과 상담 AI 활성화는 별개다. 키를 넣었다는 사실만으로 상담 AI를 열지 않는다 |
| 음성 인식 | 현재 모드, 처리 장비, 허용 엔진과 준비 조건 확인, 연결 검사, 사용 가능 여부 안내 | 기본은 `off`다. 승인되지 않은 엔진은 켜지지 않으며 `sttEngine=null`을 성공으로 포장하지 않는다 |
| DB 연결 | 현재 설치의 연결 상태와 권한 검사, 필요한 복구 안내 | Cloud의 Supabase와 Local의 암호화 SQLite라는 설치 경계를 유지한다. 저장 위치나 모드 변경은 별도 데이터 이전 절차다 |

설치의 AI/STT 설정 변경으로 다시 확인해야 하는 사업이 있으면 적용 전에 해당 범위를 보여준다. 사업 도입 확인이나 당사자 동의는 도우미가 대신 결정하지 않는다. 사용 중인 설정과 진행 중인 일감에 영향을 주는 변경은 적용 시점과 실패 시 유지할 상태까지 계획에 포함한다.

### 대화와 비밀값의 경계

- LLM에는 허용된 모드, 현재 단계, 검사 코드와 비민감 설정 정보만 보낸다. 전체 환경변수, 전체 로그, 관리 토큰, 연결 문자열과 상담 자료는 보내지 않는다.
- 자유 입력은 외부 전송 전에 검증된 안전 처리 경로를 거친다. 그 경로가 준비되지 않았거나 안전 여부를 확인할 수 없다면 원문을 보내지 않고 상태와 선택지 기반 안내로 전환한다.
- 설정 도움용 호출은 상담 자료를 다루는 기존 AI Packet 경로와 목적 및 권한을 구분한다. 이를 상담 자료의 가림 관문을 피하는 통로로 사용하지 않는다. 전송 필드와 거부 조건은 구현 전에 공통 계약으로 고정한다.
- Cloud의 설치 관리자 자격은 사용자 PC의 승인된 자격 공급 경로에서만 사용한다. 일반 업무 API나 설정 도우미에 원문을 전달하지 않는다.
- 대화 기록은 설정 완료의 증거가 아니다. 실제 선택값과 변경 승인, 실행 결과와 검사 결과를 기준으로 이어간다. 채팅 원문 전체를 영구 저장하는 기능은 이번 설계에 넣지 않는다.

### 중단, 실패와 재개

| 상황 | 동작 |
|---|---|
| 사용자가 질문하거나 잠시 중단함 | 현재 입력과 단계를 유지한다. 재개할 때 저장된 설정과 실제 상태를 다시 대조한다 |
| 인증이나 설치 승인이 만료됨 | 필요한 인증을 다시 받고 동일한 설치 대상인지 확인한 뒤 재개한다. 과거 대화만으로 권한을 복원하지 않는다 |
| 설정 적용 중 연결이 끊김 | 실행 결과를 먼저 관찰한다. 이미 끝난 작업을 무조건 반복하지 않고 해당 설치 기록과 도구의 재개 계약을 따른다 |
| LLM이 연결되지 않거나 실패함 | 고정 안내와 입력 경로로 계속한다. 다른 제공자로 자동 전환하지 않는다 |
| 입력 변경으로 이전 확인이 낡음 | 영향을 받은 항목을 다시 확인한다. 전체 설치를 지우고 시작하지 않는다 |
| 검사에 실패함 | 완료로 표시하지 않는다. 변경되지 않은 정상 설정을 유지하고 가능한 복구 행동을 안내한다. 이미 발생한 외부 변경을 되돌릴 수 있다고 임의 약속하지 않는다 |

### 화면 구성과 구현 소유

화면은 진행 단계, 현재 질문과 입력, 변경 요약과 실행 결과, 자유 질문 영역으로 나눈다. 단계 표시는 기존 `WireSteps` 규칙대로 지나온 단계만 이동할 수 있게 한다. 입력과 상태 표시는 기존 `WireCard`, `WireFormField`, `WireCallout`, `WireDataRows`를 우선 재사용하며 새 스타일 체계를 만들지 않는다. 채팅 안에 별도의 설정 저장 기능을 복제하지 않는다.

설치기와 외부 코딩 에이전트는 같은 설치 실행 기능을 호출한다. Cloud 설정 화면은 로그인한 사용자의 권한으로 같은 설정 기능을 소비하되 설치 관리자 권한이 필요한 작업은 PC의 설치 도구에 넘긴다. 서로 다른 주체의 권한을 하나로 합친다는 뜻은 아니다.

- 온보딩 설계와 설치 안내는 베타 작업과 별도 문서 작업 공간에서 진행한다. 새 작업 공간을 실제로 만들기 전에는 실행 상한과 소유권을 확인한다.
- `apps/client` 연결은 frontend 레인, 공유 UI와 CSS는 DESIGN 레인이 맡는다. 기존 `연결 상태` 확장 계획과 동일 파일을 동시에 수정하지 않는다.
- 설치 명령, HTTP와 코어의 쓰기 계약은 각각 현재 소유자에게 인계한다. 베타의 상담 AI 모듈을 온보딩 구현을 위해 복제하거나 바꾸지 않는다.
- 프로젝트와 도구의 표시 이름은 `relayer`다. 아래 근거에 남은 `ccc` 경로, 환경변수와 내부 식별자는 조사 시점의 실제 이름이며 이 문서가 일괄 개명을 실행한 것은 아니다.

### 구현에서 증명해야 할 결과

아래는 향후 수용 기준이며 아직 실행한 검증 결과가 아니다.

1. 깨끗한 Cloud 대상에서 자원 생성부터 최초 관리자 가입, 기관 초기 설정과 수기 업무 시작까지 실제로 이어진다.
2. 지원되는 깨끗한 Windows 환경에서 저장소를 받은 에이전트가 Local Single 설치를 시작하고, 암호화 저장소와 실제 클라이언트 기동을 확인한다.
3. 중간 자유 질문 뒤 입력과 현재 단계가 유지되고, 대화상의 제안만으로 설정이 변경되지 않는다.
4. 승인 범위를 벗어난 대상, 비용, 권한 또는 전송 변경은 실행되지 않는다.
5. 적용 결과를 모르는 상태에서 재개해도 자원과 최초 관리자 연결을 중복 생성하지 않는다.
6. 키가 없는 경우와 LLM 장애에서도 고정 안내가 이어진다. 준비되지 않은 자유 입력이나 비밀값이 모델 요청과 로그에 들어가지 않는다.
7. 연결 성공, 설치 완료, 기관 준비 완료와 상담 AI/STT 사용 가능 상태를 각각 구분한다.
8. 사업 재확인과 동의가 필요한 경우 실제 API가 제한을 집행하고 화면만으로 차단을 대신하지 않는다.
9. DB 저장 위치 변경은 기존 설치 덮어쓰기가 아니라 검증된 이전 절차로 안내한다.

## 실행 계약의 구체화

### 단계별 승인

승인된 묶음은 설치 대상, 단계, 원하는 설정의 해시와 그때 관찰한 상태 지문에 결합한다. 계정, 대상, 권한, 과금 구성 또는 외부 전송 대상이 바뀌면 기존 승인은 사용할 수 없다. 승인 전/후에 관찰값이 달라진 경우에도 다시 계획한다. 예상 비용은 정보이지 결제 상한 보장이 아니며 새 SKU, 인스턴스 수나 전송 경로를 자동으로 승인 범위에 넣지 않는다.

실행 결과를 관찰하지 못한 작업은 미실행으로 단정하지 않는다. 기존 설치 journal과 provider 소유권을 확인한 뒤 완료, 재개 가능 또는 확인 필요로 구분한다. 일반 대화 저장소를 별도 설치 journal로 사용하지 않는다.

### 필요할 때만 연결하는 PC 도구

사용자가 설치 또는 재설정을 위해 PC 도구를 열었을 때만 설정 연결을 만든다. 연결은 검증된 기관, 설치 대상과 현재 사용자 권한에 결합하고 종료나 인증 만료 뒤 새 실행 요청을 받지 않는다. Cloud가 임의 셸, SQL, URL 또는 설치 파일 경로를 보내 실행하게 하는 인터페이스는 만들지 않는다. 관리자 자격은 PC를 떠나지 않는다.

초기 Cloud가 아직 없을 때는 로컬 도구의 안내로 먼저 설치한다. Cloud와의 인계가 가능해진 뒤에도 실제 적용은 현재 계획과 승인 및 소유권 검증을 다시 통과해야 한다. PC 도구가 닫혀 있으면 연결이 필요한 작업에 재실행 안내를 보여주며 일반 업무를 잠그지 않는다. 처리 Agent의 신원이나 일감 권한을 이 설정 연결에 재사용하지 않는다.

### 첫 관리자와 자유 입력

첫 관리자 초대는 지정된 이메일 하나, 해당 설치와 검증된 Auth 신원에 결합한다. 실패나 중단 뒤 이미 생성되거나 수락된 초대를 확인하지 않고 다시 만들지 않는다. 공급자의 원문 오류나 링크를 보고서에 남기지 않는다. 2026-09-14 Q 부분 개정에 따라 이후 직원도 `disable_signup=true`를 유지한 권한 있는 Auth 초대로 계정을 만들며, 검증된 `subject`와 초대 이메일이 일치하지 않으면 사용자 생성, 역할 부여와 초대 소비를 모두 거부한다.

#### 2026-09-14 직원 Auth 초대 callback

`/auth/invite`는 업무 셸과 분리된 공개 route지만 signed manifest의 exact client origin과 Supabase Auth origin만 신뢰한다. 초대 이메일의 유일한 링크는 query와 fragment가 없는 `{{ .RedirectTo }}`이고 본문은 여섯 자리 `{{ .Token }}`을 표시한다. `{{ .ConfirmationURL }}`, `{{ .TokenHash }}`, `{{ .Email }}`, `{{ .Data }}`, session credential과 marker는 넣지 않는다. implicit success와 error fragment 방식은 사용하지 않으며 Chrome 진단 보존 예외도 없다.

앱은 router, React root, 설치 로딩과 network/Auth 동작 전에 exact `/auth/invite`의 search와 hash가 모두 비었는지 동기 확인한다. 하나라도 있으면 내용을 읽거나 복사하지 않고 `history.replaceState`로 깨끗한 path만 남긴 뒤 `invite_invalid`로 끝낸다. 첫 진입이 아닌 SPA 이동도 `invite_invalid`이며 Auth 호출은 0건이다. legacy `/staff/join`의 search와 fragment는 같은 시점에 버리지만 당사자 `/join`은 건드리지 않는다.

정상 화면은 uncontrolled email, 여섯 자리 code, password와 password confirmation 네 필드만 받는다. submit 안에서만 email을 trim하고 소문자로 바꾸며, code는 ASCII 숫자 여섯 자리, password는 여덟 자 이상과 확인 값 일치를 검사한다. 값을 지역 변수로 옮긴 뒤 FormData와 form을 즉시 비우고 Auth를 호출한다. email, code와 password는 React state, context, props, 오류나 serialization에 들어가지 않는다.

기존 `persistSession=false`, `detectSessionInUrl=false` Supabase client가 `verifyOtp({ email, token: code, type: 'invite' })`를 호출한다. 일반 session이 이미 있으면 `invite_session_conflict`로 거부하고 그 session을 바꾸지 않는다. 성공하려면 반환된 session과 user가 있고 subject가 같으며 양쪽 email이 입력 email과 일치해야 한다. 이어 같은 session에서 비밀번호를 설정한 뒤 local sign-out과 client 폐기를 수행한다. 초대 session이 살아 있는 동안 `getToken`은 `null`이고 업무 API, MFA와 일반 로그인 전이는 잠긴다.

`invite_invalid`, `invite_expired`, `invite_session_conflict`, `password_rejected`, `provider_unavailable`만 화면 상태에 둔다. 비밀번호 설정의 비만료 4xx나 확인할 수 없는 network 결과에서는 검증된 메모리 session만 남겨 password만 다시 받을 수 있다. reload하거나 새 tab을 열면 메모리 session은 사라지고 전체 입력부터 다시 시작한다. 소비된 code가 더 이상 유효하지 않으면 installer가 새 초대를 발급해야 한다.

완료는 Auth가 OTP, 동일 신원과 비밀번호 변경을 확인하고 초대 session을 폐기했다는 뜻뿐이다. 업무 화면으로 자동 이동하지 않고 installer 결속 대기를 표시한다. installer `resume`이 같은 marker, email, subject, `confirmedAt`과 `lastSignInAt`을 확인해 `linkFirstAdmin`을 마친 뒤에만 새 password로 별도 `aal1` 로그인하고 기관 초기 설정에 진입한다.

실화면 검수는 clean URL에서 수동 code 흐름이 동작하고 localStorage, sessionStorage, IndexedDB, CacheStorage, console, analytics, network URL, referrer와 history에서 email, code, password, bearer, refresh token과 invitation token이 0건인지 확인한다. installer source `bf456337d2f952b124ddf923524a4e65ecee2892`와 FRONTEND source `8bfe49d6c05aaa3c23062b6a9ec3c80cd4251747`의 검증은 통과했지만 hosted template 변경, 실제 초대와 운영 수용은 아직 승인되지 않았다.

Auth 초대 발급은 업무 API가 아니라 기존 PC 설치 및 관리 경계를 우선한다. 첫 관리자 이후 직원 발급의 trigger, CCC 직원 초대와 Auth 초대를 묶는 비공개 표식, TTL 정렬과 미결속 Auth 사용자 정리는 아직 작성 슬롯과 세부 계약이 필요하다. 이 설계는 새 서비스나 권한을 승인하지 않으며 N04를 N03의 선행으로 만들지 않는다.

설정 도우미의 외부 입력은 허용된 상태 필드와 안전 처리가 끝난 질문으로 제한한다. 전체 환경변수나 로그를 보내고 모델에게 비밀값을 지워 달라고 하지 않는다. 자유 질문의 안전 처리 경로가 없거나 실패했으면 원문 전송은 0건이고 고정 안내를 계속 제공한다. 전송 허용 필드와 거부 코드의 정확한 형식은 실행 계획 N05에서 생산자와 소비자가 함께 고정한 뒤 외부 호출을 구현한다.

## 현재 구현과의 중요한 차이

- 신규 Cloud 자원 생성, 자동 첫 관리자 초대, on-demand 설정 연결과 자유 질문 처리는 실제로 새로 연결해야 한다.
- 기존 `plan --target local`은 로컬 Supabase 점검이지 Local Single 설치기가 아니다.
- 기존 클라이언트는 Local Single/Office를 거부한다. 해당 제품 실행 경로와 서명된 설치물을 확보하지 않고 이 거부만 지우지 않는다.
- 단순한 LLM 키 입력 UI로 DB에 저장된 설치 정책, 제공자 활성화, Agent 준비와 사업 확인을 대체하지 않는다.
- 상세 화면 배치와 공용 부품 변경은 frontend에서 실제 API 계약을 확정한 뒤 DESIGN에 인계한다. 이 문서는 디자인 소유권 예외가 아니다.
