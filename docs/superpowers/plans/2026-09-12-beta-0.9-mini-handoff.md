# 베타 0.9 오케스트레이터 인계: MacBook에서 Mac mini로

2026-09-12. Q가 이동하면서 MacBook 세션이 끊긴다. 이 문서가 인계 패킷이다.
아래 사실은 전부 이 세션에서 직접 확인한 것이고, 추정은 추정이라고 적었다.

## 1. 소유와 경계

- 인계 대상 브랜치는 `orchestrate/beta-0.9`이고 이 문서 직전 tip은 `19e6f397`이다.
  2026-09-12에 처음 origin에 push했다. 그 전까지 37개 문서 커밋이 MacBook에만 있었다.
- **MacBook은 이 브랜치에 더 쓰지 않는다.** 인계 시점부터 작성자는 mini 하나다.
- MacBook 워크트리에 남긴 제외 항목: 미추적 `artifacts/relayer-landing/index.html`
  (랜딩 시안 17,754바이트). 이번 인계 범위가 아니라서 커밋하지 않았다.
  mini에서 랜딩을 건드리지 않는다. 필요해지면 Q가 MacBook에서 다시 꺼낸다.
- 다른 레인은 그대로다. mini의 `CCC : BACKEND`(idle)와 `CCC : PUBLIC SITE` 워크스페이스,
  MacBook의 DESIGN, frontend, VALIDATION, API 워크트리를 건드리지 않는다.
- CCC 디자인 소유권 잠금은 그대로다. 화면 코드, 공유 CSS, 디자인 토큰,
  `DESIGN.md`, `DESIGN-RULES.md`는 `DESIGN` 워크트리 소유다.

## 2. 이 워크트리의 상태 경고

`orchestrate/beta-0.9`는 `origin/main`보다 **8커밋 뒤, 37커밋 앞**이고 비문서 파일 336개가 다르다.
여기서 `packages/`나 `apps/client/`를 grep하면 옛 트리를 본다.
코드 사실 확인은 반드시 `git grep <패턴> origin/main -- <경로>`로 한다.
문서 작업만 이 브랜치에서 하고, 코드 수정이 필요하면 `origin/main`에서 새 토픽 브랜치를 딴다.

## 3. PR #335: 지금 머지 가능

- CI 5개 전부 SUCCESS: `verify`, `design-sweep`, `hierarchy-measure`, `pipeline-test`, `secret-scan`.
- `mergeable: MERGEABLE`, `mergeStateStatus: CLEAN`, base `main`, head `auth/invite-role-cap`.
- `origin/main`은 아직 `ad218e8e`이고 이것이 지금 베타에 떠 있는 커밋이다. 머지하면 main이 1커밋 앞선다.
- 머지 명령: `gh pr merge 335 --squash --delete-branch=false`.

**Q 안내와 PR 실제 내용이 다르다.** Q에게는 "실무 책임자만 빼고 고르세요"라고 안내했는데,
PR은 초대 선택지를 기관 관리자와 실무자 **둘**로 줄인다. 기술 관리자도 초대에서 빠지고
가입 뒤 `계정 관리`에서 준다. 지금 배포본에서는 기술 관리자 초대가 201로 통과하므로
Q의 현재 테스트는 막히지 않는다. 머지 뒤 그 선택지가 사라진다. Q에게 이 차이를 알린다.

같이 들어가는 변경: 역할 개수 상한 3이 초대와 계정 양쪽에서 사라진다
(`createStaffInvite`, `normalizedDirectRoles`, `requestDirectoryRoles`).
이제 허용 역할인지와 중복 여부만 본다.

## 4. 재배포: 절차가 레포에 없다

확인한 구멍 셋이다.

1. **Azure 배포 스크립트나 문서가 main에 0건이다.** `scripts/`의 deploy는 전부 Cloudflare용이고
   (`deploy-preview.mjs`, `deploy-production.mjs`), `az acr`나 `containerapp`을 언급하는 파일이 없다.
   `docs/superpowers/plans/2026-09-10-cloud-beta-deploy-runbook.md`는 배포 **전** 상태에서 멈춰 있다.
   절차는 PR #335 코멘트와 실행한 에이전트의 셸에만 있었고 셸 히스토리에도 남지 않았다.
2. **클라이언트 이미지 Dockerfile이 없다.** 레포의 Dockerfile은 `apps/community-cloud/Dockerfile` 하나뿐이다.
   PR 코멘트가 말한 "site 디렉터리"는 main에도, `/tmp/ccc-deploy` 워크트리(clean, `ad218e8e`)에도 없다.
3. **코멘트 3단계의 "(서명 키 주입 후) client build"는 사실과 다르다.**
   `apps/client`가 빌드 때 읽는 env는 `CCC_STT_LOCAL_API`와 `CCC_STT_TRIAL_FIXTURES` 둘뿐이다.
   서명 키(`CCC_INSTALL_SIGNING_PRIVATE_KEY` 등)는 community-cloud **런타임** env다.
   클라이언트 빌드를 키 대기로 막을 이유가 없다.

### mini의 제약

**mini에는 Azure CLI가 없다**(`command -v az` 미설치). MacBook에는 설치돼 있고
`account@socialsolidaritybank.onmicrosoft.com`으로 로그인된 활성 세션이 있다.
과거에 device code 흐름이 AADSTS530035로 막혔고 대화형 브라우저 로그인만 통과했으므로,
헤드리스 mini에서 `az login`을 자동으로 끝낼 수 있다고 가정하지 않는다.

**따라서 이미지 빌드와 컨테이너 교체는 mini 단독으로 할 수 없다.**
mini는 배포를 실행하지 말고, 배포를 실행할 수 있는 상태까지만 만든다.
실제 `az acr build`와 `az containerapp update`는 Q가 MacBook으로 돌아오거나
mini에 az 설치와 대화형 로그인을 별도 승인할 때 한다.

## 5. 남은 결정 둘, 실측 근거

### A. 화면 격차 "8 대 30"은 파일 수 비교라 과장이다

`origin/main` 기준 실측이다. 클라이언트는 라우트 21개(`apps/client/src/app.tsx`)에
`/settings` 모듈 9개를 더해 8개 스크린 파일에 담았고, 웹은 `page.tsx` 30개다.
클라이언트에 대응이 **없는** 기능은 둘뿐이다.

- `/admin/ai-provider`: AI와 STT 설정 상태 화면. `CLAUDE.md`의 프런트엔드 레인 예외가
  명시한 소유 대상인데 클라이언트로 안 옮겨졌다.
- `/participants/[beneficiaryId]/programs/[supportCaseId]/close`: 사업 종결.

나머지 차이는 격차가 아니라 통합이다. 웹의 `/admin/*` 6개는 클라이언트에서
`/settings` 모듈 9개와 `/staff-invites`로 접혔고, `/programs/[type]/schedule`과
`/schedule/all`은 D75와 CCC-133에 따라 `/schedule` 하나로 합쳤으며,
`/kit`, `/preview`, `/preview/admin`은 개발용이다.
결정할 것은 위 두 화면을 베타에 넣을지다.

### B. 실무 책임자는 화면이 없는 게 아니라 부여 경로 자체가 없다

`supervisor`는 저장되는 역할이 아니라 `team_supervisor_grants` 행에서 파생된다
(`packages/core/src/gateway.ts`가 grant가 있으면 roles에 끼워 넣는다).
그런데 `origin/main` 제품 코드에 `teams`, `team_memberships`, `team_supervisor_grants`
**INSERT가 0건**이다. 테스트 픽스처와 마이그레이션에만 있다.
`packages/http-api/src/request-handler.ts`에 `/teams` 계열 라우트도 없다.
해지(`UPDATE ... SET revoked_at`)만 두 군데 구현돼 있다.

즉 지우기는 되고 만들기는 안 된다. 계정 화면의 `감독 팀` 행은 구조상 영원히 "없음"이다.
결정 범위는 화면 하나 추가가 아니라, 베타에서 실무 책임자를 접을지 아니면
팀 생성, 소속, 감독 지정 API를 D74와 ADR-0038대로 새로 만들지다.
PR #335는 이 사실을 주석으로 굳혔을 뿐 해결하지 않았다.
분량으로 보면 접는 쪽이 훨씬 싸다. 표만 있고 API, 화면, 감사가 통째로 없다.

## 6. 13개 테스트 목록이 레포에 0건이다

Q에게 안내한 13개 목록(관리자 5개, 실무자 8개)이 어느 파일에도 없다.
Q의 테스트 메모가 돌아왔을 때 대조할 정본이 없다.
Q가 안내받은 원문은 다음과 같다.

- 관리자 5개: 로그인, 설정 둘러보기, 초대 발행, 시크릿 창 가입, 목록 확인
- 실무자 8개: 일정 등록, 일정 보기, 당사자 등록, 인테이크, 상담 기록, 기록 확인, 리포트, 15초 페이지
- Q는 각 화면에 `되다` / `막혔다` / `이름 이상하다` 하나만 붙이고 스크린샷에 번호를 매긴다.

## 7. mini가 할 일

1. **PR #335 머지.** CI는 이미 초록이므로 재확인 없이 머지한다.
   머지 뒤 Q에게 초대 선택지가 둘로 줄었다는 사실을 알린다.
2. **13개 테스트 목록을 파일로 고정한다.** 위 6장 목록이 정본 재료다.
   Q의 메모가 도착하면 결함과 이름 정리 재료로 가른다.
3. **배포 절차를 레포에 남긴다.** 4장의 실측 표가 재료다.
   클라이언트 정적 이미지의 Dockerfile을 새로 쓰고, 두 이미지의 빌드 맥락과
   태그 규약, 컨테이너 교체 명령, 서비스워커를 지운 뒤 확인한다는 항목을 담는다.
   **문서와 Dockerfile까지만 만들고 실제 배포는 하지 않는다**(5장 mini 제약).
4. 결정 A와 B는 Q의 판단이 필요하다. 근거는 위에 있으니 실행하지 말고 물어본다.

## 9. Q가 인계 중에 추가한 것 (2026-09-12 18:1x)

### 테스트에서 나온 결함 세 개

1. 당사자 등록에 **당사자 초대**가 빠졌다. 당사자가 링크로 직접 자기 정보를 쓰고 동의까지 마치는 단계다.
   D86 ④의 요청 링크 하나 경로이고, 클라이언트 라우트로는 `/participants/invite`와 공개 `/join`이다.
   `public_signup` feature 스위치가 꺼져 있어 자리가 안 보이는 것인지부터 확인한다.
2. 페이지를 옮길 때마다 서버 연결을 다시 확인한다.
   "설치 능력과 내 계정을 확인하고 있습니다"가 너무 자주 뜬다. `GET /capabilities`와 `GET /me`의
   호출 시점과 캐시 경계 문제로 보인다. 추정이므로 실제 호출 횟수를 먼저 재라.
3. 당사자 등록을 마친 뒤 **인테이크로 이어지는 단계가 없다.** 등록 완료 화면에서 인테이크 기록으로 가는
   길이 끊겨 있다.

### 이 묶음이 작업 범위를 바꾼다

7장의 할 일 네 개는 이 문서들을 읽기 전에 만든 것이다. 문서 묶음이 상담기록지, 인테이크, AI 모듈,
결과물 정의를 한꺼번에 다시 정하므로, mini는 먼저 `handoff-decisions`를 읽고 7장 목록과 겹치는 곳,
어긋나는 곳, 새로 생기는 곳을 갈라서 작업 계획을 다시 세운다.
계획을 세우기만 하고 구현은 Q의 승인을 받고 시작한다.

### 이 pane은 Q가 직접 쓴다

RELAYER ORCHESTRATOR MINI pane(`w19:p1`)에 Q가 직접 입력한다.
MacBook 쪽에서 이 pane에 키를 보내지 않는다.
