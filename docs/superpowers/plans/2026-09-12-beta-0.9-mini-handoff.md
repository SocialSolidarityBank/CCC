# 베타 0.9 오케스트레이터 인계: MacBook에서 Mac mini로

2026-09-12. Q가 이동하면서 MacBook 세션이 끊긴다. 이 문서가 인계 패킷이다.
아래 사실은 전부 이 세션에서 직접 확인한 것이고, 추정은 추정이라고 적었다.

## 1. 소유와 경계

- 인계 대상 브랜치는 `orchestrate/beta-0.9`이고 이 문서 직전 tip은 `19e6f397`이다.
  2026-09-12에 처음 origin에 push했다. 그 전까지 37개 문서 커밋이 MacBook에만 있었다.
- **MacBook은 이 브랜치에 더 쓰지 않는다.** 인계 시점부터 작성자는 mini 하나다.
- MacBook 워크트리에 남긴 제외 항목: 미추적 `artifacts/relayer-landing/index.html`
  (랜딩 시안 17,754바이트). 이번 인계 범위가 아니라서 커밋하지 않았다.
  mini에서 랜딩을 건드리지 않는다. 필요해지면 Q가 MacBook에서 다시 꺼낸다.
- 다른 레인은 그대로다. mini의 `CCC : BACKEND`(idle)와 `CCC : PUBLIC SITE` 워크스페이스,
  MacBook의 DESIGN, frontend, VALIDATION, API 워크트리를 건드리지 않는다.
- CCC 디자인 소유권 잠금은 그대로다. 화면 코드, 공유 CSS, 디자인 토큰,
  `DESIGN.md`, `DESIGN-RULES.md`는 `DESIGN` 워크트리 소유다.

## 2. 이 워크트리의 상태 경고

`orchestrate/beta-0.9`는 `origin/main`보다 **8커밋 뒤, 37커밋 앞**이고 비문서 파일 336개가 다르다.
여기서 `packages/`나 `apps/client/`를 grep하면 옛 트리를 본다.
코드 사실 확인은 반드시 `git grep <패턴> origin/main -- <경로>`로 한다.
문서 작업만 이 브랜치에서 하고, 코드 수정이 필요하면 `origin/main`에서 새 토픽 브랜치를 딴다.

## 3. PR #335: 지금 머지 가능

- CI 5개 전부 SUCCESS: `verify`, `design-sweep`, `hierarchy-measure`, `pipeline-test`, `secret-scan`.
- `mergeable: MERGEABLE`, `mergeStateStatus: CLEAN`, base `main`, head `auth/invite-role-cap`.
- `origin/main`은 아직 `ad218e8e`이고 이것이 지금 베타에 떠 있는 커밋이다. 머지하면 main이 1커밋 앞선다.
- 머지 명령: `gh pr merge 335 --squash --delete-branch=false`.

**Q 안내와 PR 실제 내용이 다르다.** Q에게는 "실무 책임자만 빼고 고르세요"라고 안내했는데,
PR은 초대 선택지를 기관 관리자와 실무자 **둘**로 줄인다. 기술 관리자도 초대에서 빠지고
가입 뒤 `계정 관리`에서 준다. 지금 배포본에서는 기술 관리자 초대가 201로 통과하므로
Q의 현재 테스트는 막히지 않는다. 머지 뒤 그 선택지가 사라진다. Q에게 이 차이를 알린다.

같이 들어가는 변경: 역할 개수 상한 3이 초대와 계정 양쪽에서 사라진다
(`createStaffInvite`, `normalizedDirectRoles`, `requestDirectoryRoles`).
이제 허용 역할인지와 중복 여부만 본다.

## 4. 재배포: 절차가 레포에 없다

확인한 구멍 셋이다.

1. **Azure 배포 스크립트나 문서가 main에 0건이다.** `scripts/`의 deploy는 전부 Cloudflare용이고
   (`deploy-preview.mjs`, `deploy-production.mjs`), `az acr`나 `containerapp`을 언급하는 파일이 없다.
   `docs/superpowers/plans/2026-09-10-cloud-beta-deploy-runbook.md`는 배포 **전** 상태에서 멈춰 있다.
   절차는 PR #335 코멘트와 실행한 에이전트의 셸에만 있었고 셸 히스토리에도 남지 않았다.
2. **클라이언트 이미지 Dockerfile이 없다.** 레포의 Dockerfile은 `apps/community-cloud/Dockerfile` 하나뿐이다.
   PR 코멘트가 말한 "site 디렉터리"는 main에도, `/tmp/ccc-deploy` 워크트리(clean, `ad218e8e`)에도 없다.
3. **코멘트 3단계의 "(서명 키 주입 후) client build"는 사실과 다르다.**
   `apps/client`가 빌드 때 읽는 env는 `CCC_STT_LOCAL_API`와 `CCC_STT_TRIAL_FIXTURES` 둘뿐이다.
   서명 키(`CCC_INSTALL_SIGNING_PRIVATE_KEY` 등)는 community-cloud **런타임** env다.
   클라이언트 빌드를 키 대기로 막을 이유가 없다.

### mini의 제약

**mini에는 Azure CLI가 없다**(`command -v az` 미설치). MacBook에는 설치돼 있고
`account@socialsolidaritybank.onmicrosoft.com`으로 로그인된 활성 세션이 있다.
과거에 device code 흐름이 AADSTS530035로 막혔고 대화형 브라우저 로그인만 통과했으므로,
헤드리스 mini에서 `az login`을 자동으로 끝낼 수 있다고 가정하지 않는다.

**따라서 이미지 빌드와 컨테이너 교체는 mini 단독으로 할 수 없다.**
mini는 배포를 실행하지 말고, 배포를 실행할 수 있는 상태까지만 만든다.
실제 `az acr build`와 `az containerapp update`는 Q가 MacBook으로 돌아오거나
mini에 az 설치와 대화형 로그인을 별도 승인할 때 한다.

## 5. 남은 결정 둘, 실측 근거

### A. 화면 격차 "8 대 30"은 파일 수 비교라 과장이다

`origin/main` 기준 실측이다. 클라이언트는 라우트 21개(`apps/client/src/app.tsx`)에
`/settings` 모듈 9개를 더해 8개 스크린 파일에 담았고, 웹은 `page.tsx` 30개다.
클라이언트에 대응이 **없는** 기능은 둘뿐이다.

- `/admin/ai-provider`: AI와 STT 설정 상태 화면. `CLAUDE.md`의 프런트엔드 레인 예외가
  명시한 소유 대상인데 클라이언트로 안 옮겨졌다.
- `/participants/[beneficiaryId]/programs/[supportCaseId]/close`: 사업 종결.

나머지 차이는 격차가 아니라 통합이다. 웹의 `/admin/*` 6개는 클라이언트에서
`/settings` 모듈 9개와 `/staff-invites`로 접혔고, `/programs/[type]/schedule`과
`/schedule/all`은 D75와 CCC-133에 따라 `/schedule` 하나로 합쳤으며,
`/kit`, `/preview`, `/preview/admin`은 개발용이다.
결정할 것은 위 두 화면을 베타에 넣을지다.

### B. 실무 책임자는 화면이 없는 게 아니라 부여 경로 자체가 없다

`supervisor`는 저장되는 역할이 아니라 `team_supervisor_grants` 행에서 파생된다
(`packages/core/src/gateway.ts`가 grant가 있으면 roles에 끼워 넣는다).
그런데 `origin/main` 제품 코드에 `teams`, `team_memberships`, `team_supervisor_grants`
**INSERT가 0건**이다. 테스트 픽스처와 마이그레이션에만 있다.
`packages/http-api/src/request-handler.ts`에 `/teams` 계열 라우트도 없다.
해지(`UPDATE ... SET revoked_at`)만 두 군데 구현돼 있다.

즉 지우기는 되고 만들기는 안 된다. 계정 화면의 `감독 팀` 행은 구조상 영원히 "없음"이다.
결정 범위는 화면 하나 추가가 아니라, 베타에서 실무 책임자를 접을지 아니면
팀 생성, 소속, 감독 지정 API를 D74와 ADR-0038대로 새로 만들지다.
PR #335는 이 사실을 주석으로 굳혔을 뿐 해결하지 않았다.
분량으로 보면 접는 쪽이 훨씬 싸다. 표만 있고 API, 화면, 감사가 통째로 없다.

1. **PR #335 머지.** CI는 이미 초록이므로 재확인 없이 머지한다.

4. 결정 A와 B는 Q의 판단이 필요하다. 근거는 위에 있으니 실행하지 말고 물어본다.

## 10. 결함 세 개의 원인과 다시 세운 계획 (mini, 2026-09-12)

### 10-0. 이 장의 증거가 어디서 왔나

두 가지를 썼다. 코드 사실은 `origin/main` `ad218e8` 에서 `git grep`, `git show` 로 읽었다.
동작 사실은 **실제 브라우저 실측**이다. 추정으로 적은 자리는 그렇다고 표시했다.

- 측정 장치: `origin/main` 을 detached 로 꺼낸 임시 워크트리 `/tmp/ccc-measure` 와
  레포에 이미 있는 합성 미리보기 `apps/client/tools/synthetic-preview.mjs`.
  Playwright 스크립트 네 개는 레포 밖(`/tmp/ccc-measure-*.py`)에 뒀다.
- 제품 코드 수정 0, 커밋 0, 배포 0. 임시 워크트리는 측정이 끝난 뒤 지웠다.
- 이 실측 대상은 **지금 베타에 떠 있는 것과 같은 코드**다(이미지 태그 `0.9.0-ad218e8e` = `ad218e8`).
  다른 것은 저장소와 환경변수뿐이다.
- 합성 미리보기의 로그인은 아무 이메일과 비밀번호, 인증번호 `123456` 이다. 실제 기관 자료는 쓰지 않았다.

### 10-1. 결함 1: 당사자 초대가 안 보인다. 화면이 아니라 스위치다

**원인**: `GET /capabilities` 의 `features.public_signup` 이 꺼져 있으면 사이드바가 그 자리를 지운다.
그 값은 업무 API 컨테이너의 환경변수 `PUBLIC_SIGNUP_ENABLED` 하나로 정해진다.

| 고리 | 자리 |
|---|---|
| 값을 만드는 곳 | `packages/http-api/src/capabilities.ts:81` `publicSignupEnabled: env.PUBLIC_SIGNUP_ENABLED === '1'` |
| 능력표에 싣는 곳 | `packages/contracts/src/capabilities.ts:112` `public_signup: input.publicSignupEnabled` |
| 자리를 지우는 곳 | `apps/client/src/business/navigation.ts:20-21`(`feature: 'public_signup'`)과 `:58-59` 필터 |
| 주소로 들어와도 막는 곳 | `apps/client/src/screens/invites.tsx:131`, `:156-166` |
| 서버가 404 를 주는 곳 | `packages/http-api/src/request-handler.ts:2652-2653`, `:3034` |

**재현(실측)**: 같은 빌드를 스위치만 바꿔 두 번 띄웠다.

| `public_signup` | 사이드바 | `/participants/invite` 직접 열기 |
|---|---|---|
| `true` | 16개. `당사자 목록` `당사자 등록` `당사자 초대` | 요청 링크 발급 폼이 뜬다 |
| `false` | 15개. `당사자 목록` `당사자 등록` 까지만 | "이 설치는 요청 링크를 쓰지 않습니다" 안내와 `당사자 등록` 버튼 |

꺼진 쪽 메뉴 15개가 Q가 본 화면과 같다. **화면 결함이 아니다.**

**이미 있는 것**: 당사자가 링크로 자기 정보를 쓰고 동의까지 마치는 경로는 코드에 다 있다.
발급은 `ParticipantInviteScreen`, 당사자 쪽은 공개 라우트 `/join` 의 `ParticipantJoinScreen`(동의 여섯 영역 포함),
전송은 업무 Bearer 를 붙이지 않는 `PublicTransport` 의 공개 경로 다섯이다(`transport.ts:126-132`).
토큰은 주소 조각(`#t=`)으로 받고 읽자마자 주소에서 지운다(`invites.tsx:209-220`, S2 §2.10).

**고칠 자리**: 배포 환경변수 한 줄이다. 클라이언트 코드는 건드릴 것이 없다.
4장의 실측 API env 목록에 `PUBLIC_SIGNUP_ENABLED` 가 **없다**. 이것이 지금 근거다.
`yellow` 확정 확인은 mini 에서 못 한다(az 미설치). MacBook 이나 az 승인 뒤 한 줄로 끝난다.

```
az containerapp show -g ccc-beta-krc -n relayer-api-beta \
  --query "properties.template.containers[0].env[].name" -o tsv
```

이 목록에 이름이 없으면 스위치 문제로 확정된다. 이름이 있고 값이 `1` 인데도 메뉴가 없으면
그때 비로소 화면 문제이고, 볼 자리는 `navigation.ts:54-60` 과 `/capabilities` 응답의 `features` 다.

**켜기 전에 Q가 정할 것**: 이 스위치는 D86 ④의 당사자 요청 링크를 실제로 여는 것이다.
링크를 어디로 보낼지는 제품이 모르고 기관이 정한다. 베타 시연 범위에서 켤지, 아니면
가상 당사자에게만 쓸지를 Q가 정한 뒤 켠다.

### 10-2. 결함 2: 페이지를 옮길 때마다 다시 확인한다

먼저 실측부터 적는다. **라우트 전환은 이미 아무것도 다시 부르지 않는다.**

| 구간 | `/capabilities` | `/me` | 그 화면 자기 자료 |
|---|---|---|---|
| 로그인 직후 1회 | 1 | 1 | 1 |
| 사이드바 이동 6회(일정, 당사자 목록, 감사 기록, 당사자 목록, 일정, 내 정보) | 0 | 0 | 각 1 |
| 화면 안 버튼 이동(당사자 목록 → 정보 보기) | 0 | 0 | 4 |
| 브라우저 뒤로가기 | 0 | 0 | 1 |
| 탭 숨김과 복귀(visibilitychange) 3회 | 0 | 0 | 0 |

세션 전체에서 문서(HTML) 요청은 **처음 1건**뿐이었다. 사이드바 링크도 화면 안 버튼도 전부 SPA 이동이다.
즉 "페이지를 옮겨서" 다시 부르는 일은 일어나지 않는다.

그러면 Q가 본 화면은 무엇인가. 그 문구는 `apps/client/src/app.tsx:178` 한 곳에만 있고,
`VerifiedSession` 이 세션을 아직 못 받은 동안에만 나온다. 이 부품은
`<VerifiedSession key={snapshot.revision} …>`(`app.tsx:120`)로 달려 있어서
**인증 revision 이 1 오를 때마다 통째로 다시 태어난다.** 다시 태어나면 진행 중인 화면이 사라지고
`await transport.initialize()` 와 `await api.me()` 를 **직렬로** 기다린다(`app.tsx:150-151`).
`/me` 는 능력 확인보다 먼저 부를 수 없다. 전송기가 능력 확인을 통과한 토큰만 받기 때문이다(`transport.ts:117-118`).

revision 이 오르는 자리는 다섯이다. 모두 `apps/client/src/business/auth.ts` 다.

| 자리 | 언제 |
|---|---|
| `:120-126` `onAuthStateChange` | SDK 가 세션을 알릴 때마다. `SIGNED_IN`, `TOKEN_REFRESHED`, `USER_UPDATED`, `MFA_CHALLENGE_VERIFIED` 가 전부 여기로 들어온다 |
| `:190-195` `recheck()` | 서버가 `mfa_required`(403)를 주면 `app.tsx:98` 이 부른다. 화면의 `연결 다시 확인` 버튼도 같다 |
| `:283-284` `signOut()` | 로그아웃과 30분 무입력 |

여기에 더해 `app.tsx:127` 의 `identityNonce` 가 있다. `기관 준비` 화면이 저장 뒤
`session.reloadIdentity()` 를 부르면(`screens/institution.tsx:57`, `:112`) 같은 두 콜을 다시 돈다.

**따라서 원인은 "라우트마다 부른다"가 아니라 "인증 상태가 한 번 흔들릴 때마다 업무 화면을 통째로 비우고
직렬 두 콜을 기다린다"이다.** 캐시를 넣을 자리가 아니라, 흔들림을 화면 밖에서 흡수할 자리가 문제다.

**같이 확인된 사실 하나**: 새로고침, 주소 직접 입력, 새 탭, 즐겨찾기로 들어가면 **로그아웃된다**.
SDK 세션을 메모리에만 두기 때문이다(`auth.ts:76` `persistSession: false`).
실측에서 새로고침 뒤 화면 제목이 `로그인` 으로 바뀌었고 업무 API 호출은 0건이었다.
이것은 보안 설계의 결과이지 버그가 아니지만, 테스트 중에 주소창으로 화면을 옮기면
매번 로그인부터 다시 하게 된다. Q의 체감에 이 경로가 섞였는지 확인이 필요하다.

`yellow` **아직 못 잰 것**: 합성 환경에서는 여섯 번 이동, 탭 복귀 세 번 동안 재확인이 한 번도 안 일어났다.
베타에서 자주 뜬다면 revision 을 올린 실제 사건이 있다는 뜻이고, 후보는 토큰 자동 갱신
(그 프로젝트의 JWT 만료 시간), `mfa_required` 재확인, `기관 준비` 저장 셋이다.
**어느 것인지는 Q의 실제 세션에서만 갈린다.** 재는 법은 아래 세 줄이면 된다.

1. 베타에 로그인한 탭에서 개발자도구 Network 를 열고 필터에 `capabilities` 를 넣는다. 기록 보존을 켠다.
2. 평소처럼 10분 쓴다. 줄이 생길 때마다 직전에 무엇을 했는지(이동, 저장, 탭 전환, 대기)를 적는다.
3. 줄 하나를 골라 Timing 을 본다. 그 시간이 화면이 비어 있던 시간이다.

**고칠 자리(설계 후보, 소유 레인과 Q 승인 뒤)**

| 후보 | 자리 | 성격 |
|---|---|---|
| 같은 사람이면 화면을 비우지 않는다 | `app.tsx:120`, `:123-180` | revision 이 올라도 이전 세션을 지운 뒤가 아니라 새 값을 받은 뒤에 바꾼다. 화면 깜빡임이 사라진다 |
| 같은 세션의 토큰 회전은 revision 을 올리지 않는다 | `auth.ts:120-126` | 사용자와 인증 등급이 같으면 토큰만 갈아 끼운다. **보안 계약과 닿는다**(세션 경계 재검증) |
| 능력 확인과 신원 확인을 한 번에 받는다 | `transport.ts:91-107`, `app.tsx:150-151` | 직렬 두 왕복을 하나로. API 계약 변경이라 백엔드 레인과 함께 정한다 |

세 후보 모두 `apps/client` 소유 레인의 일이고, 두 번째와 세 번째는 S11 의 세션 결속 규칙을 건드린다.
**mini 가 임의로 고르지 않는다.**

### 10-3. 결함 3: 당사자 등록 뒤 인테이크로 가는 길

**등록 응답에는 필요한 값이 다 온다.** `POST` 결과는 `beneficiaryId` 와 `supportCaseId` 를 함께 주고
화면도 그것을 받아 둔다(`apps/client/src/business/participants.ts:89-94`, `:242-251`).
그런데 등록 화면은 `supportCaseId` 를 쓰지 않고 사람 허브로만 보낸다.

```
apps/client/src/screens/participants.tsx:214
  void navigate(`/participants/${encodeURIComponent(created.beneficiaryId)}`);
```

**허브에는 인테이크로 가는 길이 없다.** 실측한 허브 화면의 링크는 세 개뿐이다.
`기본정보 수정`, `상담 기록 확인하기`, `15초 페이지`.
같은 화면이 `인테이크: 아직 없음` 이라고 적어 두고도(`participants.tsx:386`) 그 줄은 누를 수 없다.

**레포 전체에서 인테이크로 들어가는 링크는 한 곳뿐이다.**

| 자리 | 목적지 |
|---|---|
| `screens/records.tsx:274` | `…/records/intake` (유일) |
| `screens/records.tsx:269-271` | `…/records/new` |
| `screens/schedules.tsx:464` | `…/records/new` (15초 페이지의 기록 버튼) |

그래서 새 당사자의 첫 기록으로 가는 길은 전부 일반 상담 기록(`records/new`)으로 흐르고,
인테이크는 `상담 기록 확인하기` 안에 들어가야 보인다. 등록에서 세 번 더 눌러야 닿는다.

**데이터는 이미 알고 있다.** 상담 등록 화면은 그 사업의 `intakeAt` 이 비어 있으면
상담 유형을 자동으로 인테이크로 잡는다(`screens/schedules.tsx:213`, `:225`).
즉 "이 사람은 아직 인테이크 전"이라는 사실을 화면이 이미 계산하고 있는데, 기록 입구만 그 사실을 안 쓴다.

**고칠 자리(네 곳, 전부 `apps/client` 소유 레인)**

1. `participants.tsx:200-214`: 등록 성공 뒤 `created.supportCaseId` 로 인테이크 화면으로 보낸다.
   또는 등록 완료 화면을 두고 첫 행동으로 `첫 상담 기록` 을 놓는다.
2. `participants.tsx:380-392`: 허브의 `인테이크` 줄이 비어 있으면 그 자리에서 인테이크로 가는 버튼을 준다.
3. `screens/schedules.tsx:464`: 그 사업의 `intakeAt` 이 없으면 `records/intake` 로 보낸다.
4. `screens/records.tsx:269-274`: 인테이크 전에는 인테이크 버튼이 주 행동, 그 뒤에는 보조로 내린다.

1번만 해도 Q가 말한 끊김은 없어진다. 2~4번은 같은 사실을 다른 입구에서도 지키는 일이다.
어느 범위까지 할지는 결정 문서의 화면 이름 개편(`첫 상담 기록`)과 함께 정하는 것이 싸다.

### 10-4. Q 문서 묶음과 7장 할 일의 대조

`handoff-decisions-2026-09-12.md` 를 읽고 7장(mini 가 할 일 네 개)과 맞대어 봤다.

**겹치는 곳은 하나다.** 7장 2번(13개 테스트 목록 고정)과 결정 42, 43(화면 이름 여섯 개 변경)이
같은 문자열을 만진다. 목록을 구 이름으로 고정하면 이름 교체 뒤 곧바로 낡는다.
**목록은 경로와 새 이름을 함께 적어 고정한다.**

**어긋나는 곳은 두 개다.**

1. 5장 A(화면 격차)의 전제. 결정 01이 정본을 `apps/client` 로 못박았으므로 `/admin/*` 비교는 기준이 아니다.

2. 7장 4번이 Q에게 물으려던 결정 B(실무 책임자)는 결정 문서의 철회 목록과 충돌하지 않는다.
