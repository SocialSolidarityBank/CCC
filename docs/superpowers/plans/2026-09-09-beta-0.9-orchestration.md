## 통합 순서와 단일 작성자

1. P0: frontend가 기존 계획을 최신 main 및 settings 후보와 대조해 route별 재사용/이전/신규/선행 대기를 고정한다. 디자인은 필요한 공용 export를 확인한다.
2. BACKEND: 원본 settings 후보를 보존하고 최신 main 위의 전용 통합 브랜치에서 충돌을 해결한다. SQLite 0051/0052, PostgreSQL 0007~0009 중복 번호는 이미 적용된 main 파일을 변경하지 않고 새 forward migration으로 통합한다. 번호는 실제 통합 시점에 배정한다.
3. gateway.ts, request-handler.ts, runtime.ts 및 backend 소유 계약의 첫 통합 작성자는 BACKEND 하나다. privacy 후속도 이 파일에 동시 배정하지 않는다.
4. 잠긴 wire 컴포넌트/CSS/기존 디자인 하니스 변경은 BACKEND가 적용하지 않는다. 필요한 원본 후보 diff와 소비 계약을 DESIGN에 인계한다. apps/client 소스도 FRONTEND가 적용한다. 공유 파일까지 포함한 원본 커밋 전체 cherry-pick은 금지한다.
5. 루트 package.json/pnpm-lock.yaml, contracts package exports, migration parity/schema snapshot 등 공용 파일은 패킷별로 작성자와 슬롯을 먼저 정한다. 첫 backend 범위의 실제 소비 파일은 BACKEND가 소유하되 FRONTEND/DESIGN은 동시에 수정하지 않는다.

## 첫 실행 인계

FRONTEND는 P0의 완료 대응표와 P1 소비 계약을 준비한다. settings 후보의 client 소스를 재구현하지 말고 경계를 분석하되 backend API를 추측해 성공 화면을 만들지 않는다. 실제 구현은 인계된 계약에 한해 자기 client 파일에서 진행한다.

BACKEND는 먼저 TAKEOVER_READY로 머신/경로/브랜치/HEAD/추적 파일 상태와 보존된 미추적 경로, 원본 후보를 자기 Herdr pane에 보고한다. 총괄이 인수를 확인한 뒤 별도 구현 지시를 받아 backend-owned slice를 통합한다. hosted Supabase 작업, 시크릿 조회, provider 호출, 모델 활성화, migration 운영 적용, push/merge/deploy는 하지 않는다. 실제 호스팅 검증은 후속 단계의 별도 승인 뒤 수행하며 이 첫 배치의 로컬 증거로 대체하지 않는다. 디자인/client 변경 없이 성립하지 않는 컴파일 경계는 담당 레인 인계로 해결한다.

## 완료 증거

코드 존재, 계약 확정, 합성 fixture, 로컬 실제 HTTP, 실제 호스팅 인증, 사용자 브라우저 동작, 운영 배포를 구분한다. 각 인계에는 변경 경로, 기준/결과 커밋, 소비 DTO와 거부 코드, 실행한 명령과 결과, 실제 화면/저장 증거, 미완료 관문이 있어야 한다. 작업 도중 여러 레인이 공용 검사와 빌드를 동시에 돌리지 않으며 총괄이 검증 슬롯을 조정한다. 원문/키/토큰은 어떤 보고에도 넣지 않는다.

정리 전에 원본 경로/파일 목록/hash, 보존 커밋 또는 복사본의 일치, 실행 프로세스와 소유자의 인계를 확인한다. 워크트리 이름 변경이나 서버 종료를 소스 보존 증거로 간주하지 않는다. 기존 원본 삭제/reset/clean/stash와 브랜치 삭제는 첫 실행 범위가 아니다.

## 실제 런타임 검증 1차 (2026-09-10 11:3x)

합성 하네스가 아니라 실제 업무 런타임으로 확인했다. 구성은 실제 `handleRequest`, 실제 PostgreSQL 컨테이너에
`migrations/postgres/*.sql` 전부 적용, 실제 `apps/client` production 빌드, HTTPS 세 origin이고, 신원 공급자만
합성이다(hosted Supabase Auth 미프로비저닝). 통합 tip은 `105b151`이다.

- 통과: 로그인과 2단계 인증, 업무 셸 라우팅, `GET /me` 200, `/programs` 200, `/program-options` 200(admissionState ready),
  `/participants` 200(실제 빈 목록), `/settings/retention-policy` 200, `/settings/counseling-memory` 200,
  `/pii-retention/reviews` 200, `/staff-invites` 200, `/audit-log` 200.
- 막힌 것: `GET /me` 의 `institution.consentCopy.status` 가 `provider_registry_unavailable` 이고 여섯 영역 전부
  `disclosureAvailable:false` 다. 그래서 `initialSetupState` 가 `not_set_up` 이고 실제 당사자 등록 화면이 거부한다.
- 원인: `consent_provider_registry_snapshots` 에 운영 writer가 없다. 저장소 전체에서 마이그레이션(sqlite 0051,
  postgres 0007)과 테스트 픽스처 `seedProviderRegistry` 뿐이다. 합성 하네스가 이 표를 대신 채워 가려져 있었다.
- 배정: API 레인이 설치·기관 초기 설정 경로의 실제 writer와 계약 테스트를 구현한다. PostgreSQL 에서 `ccc_api` 는
  이 표에 SELECT 만 있으므로 신뢰 설치 경로에서 써야 한다.

### 같은 런타임에서 통과한 쓰기 흐름

- 실무자 초대 발급: 관리자 화면에서 이메일과 역할을 골라 만들면 서버가 1회용 토큰을 한 번만 보여 준다.
- 초대 수락: 공개 `/staff/join` 이 주소에서 토큰을 지우고 실제 기관 이름과 역할, 만료를 서버에서 받아 보여 준다.
  이름과 초대 이메일로 수락하면 가입이 끝난다.
- 소비 확인: `GET /staff-invites` 가 같은 초대를 `status:"used"`, `usedAt` 채워진 상태로 돌려준다. 전부 실제
  PostgreSQL 행이다.
- 읽기 화면: 일정(기관 시간대 Asia/Seoul), 실무자 초대, 당사자 초대, 내 정보, 기관 준비가 실제 응답으로 렌더된다.

### PWA 확인 범위 (2026-09-10)

실제 빌드가 `/manifest.webmanifest`(이름 CCC 사례관리, display standalone, start_url `/schedule`)와 `/sw.js`
(200, `text/javascript`)를 제공한다. 브라우저의 워커 등록 자체는 자체 서명 인증서 때문에 `SecurityError` 로 막힌다.
Community Cloud 매니페스트가 https 를 요구해 http 로 내려서 우회할 수 없으므로, 워커 등록의 실제 증거는 신뢰된
인증서를 쓰는 호스팅 배포에서 확인한다. 등록 로직 자체는 `apps/client` 단위 검사 64건(11파일)이 통과한다.

## 실제 런타임 검증 2차 (2026-09-10 12:2x)

API 레인이 `145d364` 로 동의 provider registry 설치 writer를, `89a1b9a` 로 통합 tip의 라우트 단언 3건을 닫았다.
통합 체크아웃에서 `routes.test.ts` 82건과 새 설치 계약 8건을 합쳐 90건이 통과한다.

같은 실제 런타임에 설치 writer를 태우고 화면으로 이어서 확인했다.

- 동의 문안: registry 설치 뒤 `consentCopy.status` 가 `available` 로 바뀌고 여섯 영역이 전부 발행 가능해진다.
- 기관 초기 설정: 관리자 화면에서 기관 이름과 첫 사업 이름을 저장하면 초기 설정이 `완료` 가 되고 첫 사업이 실제로 생긴다.
- 사업 도입 확인(D87): 저장 위치 기본형과 처리 경로 외부 허용을 고르고 관리자 확인을 저장하면 `확인 완료` 가 되고
  확인 시각이 남는다.
- 당사자 등록 화면: 잠금 안내가 사라지고 실제 사업과 실제 실무자 디렉터리, 서버가 발행한 여섯 영역 고지가 렌더된다.
- 막힌 것: 등록 제출이 `409 provider_scope_mismatch` 로 거부된다. 클라이언트가 여섯 영역 전부에
  `retentionDuration:"default_temporary_d85"` 를 보내는데, 게이트웨이는 `voice_original_retention_period` 에만
  그 값을 허용하고 나머지는 `null` 을 요구한다. 화면 문구도 이 코드에 맞지 않는 낙관적 동시성 문구를 쓴다.
  FRONTEND 레인에 정확한 요청 본문 증거와 함께 배정했다.
