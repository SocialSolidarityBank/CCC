# 릴레이어 분류체계, 용어, AI 계약 적용 계획

> 실행 담당자는 승인된 작업 묶음에 한해 `executing-plans` 또는 `subagent-driven-development`를 따른다. 이 문서는 조사와 계획의 산출물이며 구현, 머지, 배포, AI 활성화 승인이 아니다.

> **2026-09-13 Q 실행 승인:** 베타 구현을 시작하고 현재 Herdr + OMP 세션을 총괄로 삼아 MacBook, Mac mini, Windows PC에 작업을 배치한다. 워크트리별 기준 PANE을 두고 같은 작업군의 브랜치/동시 작업은 그 PANE의 split으로 관리한다. 다른 브랜치의 동시 작성은 독립 체크아웃으로 격리한다. 종료된 이번 작업의 서브에이전트는 정리하되 다른 세션과 미커밋 자료는 보존한다. 위 ‘구현 승인이 아니다’는 계획 작성 시점의 상태이며, 이제 승인된 범위의 구현 착수는 가능하다. 미결 개인정보 정책, 실데이터 사용, 외부 AI 활성화, 보호 브랜치 머지와 운영 배포의 별도 관문은 유지한다.

**Goal:** 카드 분류, 용어의 의미, AI가 할 수 있는 일, M1~M11의 입출력과 판정 기준을 데이터부터 화면까지 일관되게 적용한다.
**Architecture:** 기존 코어 관문, 마스킹 스냅샷, 승인 뷰, 목표와 할 일, 대조 저장을 재사용한다. 화면마다 별도 프롬프트를 만들지 않고 공통 근거 계약의 생산자와 소비자를 함께 전환한다. M1~M11은 논리적 책임이며 11개 서비스나 11번의 API 호출을 뜻하지 않는다.
**Tech Stack:** `packages/contracts`, `packages/core`, `packages/http-api`, `packages/ai-runtime`, Python 처리 Agent, SQLite/PostgreSQL, `apps/client`, 공용 `@ccc/wire`.
**Spec:** 아래 S-D, S-R, S-F, S-A가 제품 요구다. S-Q는 질문과 검증 자료이며 추가 기능 승인서가 아니다.
**해석한 요청:** 기존 결함 중심 계획에서 빠진 Taxonomy, Glossary, AI 역할과 모듈 기준을 원문과 구현에 대조하고 실행 의존관계를 다시 세운다. 이번에는 제품 코드를 고치지 않는다.

**승인 주체:** Q는 이 대화의 사용자이자 제품 결정권자다. 총괄은 G1~G8의 해당 선택, 이유, 적용 범위, 실제 담당자, 승인 날짜와 이 대화/티켓의 승인 근거를 기록한다. 개인정보·평가 담당자의 검토가 필요한 관문은 그 담당자가 지정되고 검토가 끝나기 전에는 닫지 않는다. 이 계획의 ‘권고’는 Q의 확정 결정이 아니다.

| 동의 6영역 | 개인정보/민감정보/녹음/외부 STT/외부 LLM과 국외 처리/원음 보유기간 | 처리 허용의 법적·제품 경계 | 생활영역이나 카드 주제와 전혀 다른 축 |
| 출처/행위자/역할 | 수기·전사·첫 상담이라는 출처, 말한 화자, 약속을 할 행위자, 접근 권한 역할 | 각각 독립 | 메모 작성자를 약속 담당으로 추정하거나 ‘기관’ 행위자를 관리자 권한으로 읽지 않음 |

`CONTEXT.md`에는 정의와 구별되는 말만 넣는다. 분류 값·필드·마이그레이션은 공통 계약과 스펙에 둔다. 사용자 화면 이름과 코드 식별자의 대응을 유지한다. 예: `repeated_noncompliance`와 수기 flag `source='counselor'`를 문서에 등장한 ‘약속 불이행’/`manual` 문자열 때문에 일괄 바꾸지 않는다.

### 사용자에게 보여 줄 의미

- 화면 이름은 명사: 상담 전 톺아보기, 첫 상담 기록, 오늘 상담 기록, 상담 기록, 경과 리포트, 사례 종결. 사이드바 이름 변경은 상담 등록 하나다.
- ‘확인할 것’은 **확인하기로 명시한 기록**이다. AI가 필요해 보인다고 추정한 질문과 다르다.
- ‘약속한 일’은 원문상의 약속이고 ‘할 일’은 사람이 등록한 업무다. ‘실천과제’는 보고서에서 당사자가 하기로 한 것만 가리킨다.
- ‘했음/진행 중/못 함’은 명시적 응답이다. 무응답은 이번에 확인 안 함이지 진행 중이나 완료가 아니다. 못 함과 그만둠도 다르다.
- ‘위기도’는 사람이 판단한다. 미선택은 판단 안 함이며 안정으로 채우지 않는다.
- 안내, 오류, 빈 화면에는 뜻·출처·다음 행동을 붙인다. 해요체 원칙을 적용하되 S6의 고정 fail-closed 문구, 동의 전문과 서명된 고지를 단순 라벨 작업에 섞어 바꾸지 않는다.

## 4. AI 역할, 근거와 상태

### 사람 / AI / 규칙의 책임

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 사람 | 수기 기록, 합의 목표, 위기도, 약속 결과, 위험 신호 확정, AI 초안 회차당 1회 승인 | 매 문장 카드 분류나 모든 AI 제안에 대한 응답을 강요받지 않음 |
| 글쓰기 AI | 근거가 있는 카드 추출, 내용/짝 비교, 주제와 목표 연결 제안, 요약·질문 문장 | 진단, 지원 지속/중단, GAS, 위험 등급, 담당/기한 추정, 자동 완료/삭제 |
| 결정론 코드 | 권한·동의·마스킹 증거 검증, 조회·정렬·그룹화·숫자 계산·상태/개수·버전 판정 | 배열이 비었다는 이유만으로 ‘검사했고 문제 없음’ 판정, 누락된 현실 사실 생성 |

수기 메모는 즉시 공식 기록이며 AI가 없어도 저장과 조회가 된다. AI 추출 카드와 그 연결은 승인 전 공식 결과의 근거가 아니다. 승인 전 요약에서 다시 카드를 뽑아 승인 조건을 우회하지 않는다. 같은 회차의 수기 카드와 녹음 카드를 하나로 덮어쓰지 않고 출처를 각각 보존한다. 늦은 결과, 재생성, 철회·파기 이후 작업이 이전 자료를 되살려서는 안 된다.

### 새 공통 계약에서 반드시 정할 필드

이는 **요구 필드의 의미**이며 이미 존재하는 API 서명이 아니다. W01에서 저장 정본과 버전을 먼저 확정한다.

- 카드: 사례, 회차, 상담일, 출처 종류와 원본 revision/hash, 마스킹 근거 인용/offset, 카드 종류, 화자, 명시된 행위자/기한, 주제들, 목표 연결, 인물/기관 번호, 승인 출처.
- 연결: 같은 내용 / 결과 / 갱신. 원본 카드와 결과 카드, 각각의 회차·근거·승인 상태를 보존한다. 불일치 쌍과 위험 신호 제안은 기존 저장 구조와의 관계를 명시한다.
- 처리 상태: 대상 자료 revision, 검사한 회차 범위, 처리 중인지, 성공했는지, 미적용/차단 이유, 결과 개수, 부분 제외 범위. 성공 0건과 미실행 0건을 다른 상태로 보낸다.
- 수기 구조값과 AI 추출 카드가 하나의 저장물인지 별도 투영인지는 G1에서 정한다. 어느 안에서도 수기 승인 의무는 만들지 않는다.

`확인함(N회차까지)`은 그 범위와 revision의 검사가 성공했을 때만 쓴다. `확인 못 함(이유)`은 AI 꺼짐, 자료 없음, 품질 부족, 차단을 구별한다. `확인 중`은 실제 처리 상태일 때만 쓴다. 일부만 처리했으면 그 범위를 함께 표시한다. 리포트의 재료 없는 섹션 생략과 대조 영역의 검사 상태 표시는 다른 규칙이다.

## 6. 충돌 처리와 결정 관문

### 이미 문서로 닫힌 것은 다시 묻지 않는다

- S-D 25/31: 톺아보기는 읽기 전용이고 회차 기록은 기록 탭으로 간다. 시안에 남은 ‘직접 확인 필요 추가’와 확인 버튼은 쓰기 화면으로 연결하는 방식으로 정리한다. 서버 쓰기 권한을 제거한다는 뜻이 아니다.
- S-D 철회 목록: AI 설정/열람 기록/기관 설정 단일 페이지를 새로 만들지 않는다. `system`, `audit` 등의 기존 모듈을 확장한다.
- S-D 36: ‘약속 불이행’이라는 표시명은 확정이다. 코드 키 유지와 여러 회차 근거 요건은 별개의 계약이다.
- S-A D-A4: 메모에 녹음 근거가 없는 사실을 실패/성과 통계로 만들지 않는다. 대조 3종 전체를 삭제하는 결정으로 확대하지 않는다.
- 수기 즉시 공식, AI 초안 승인 1회, 제안 응답 선택, 자동 완료 금지는 공통 불변조건이다.
- G2 검출 기준은 2026-09-12 Q가 확정했다. ‘맥락이 확실한 불일치’는 검출하되 단순 값 차이를 별도 알림으로 확대하지 않는다. 아래 G2는 미결 질문이 아니라 닫힌 기준의 색인이다.

### W01에서 닫거나 해당 쓰기 작업을 차단할 관문

| ID | 서로 다른 근거/미결 | 권고와 적용 전 조건 |
|---|---|---|
| G1 | S-R §1은 수기 구조입력을 카드로, S-A M2는 AI-off에 카드가 없다고 표현 | 개념 카드와 AI 추출 산출물을 구분한다. 수기 구조값은 기존 저장 정본을 재사용하는지 카드로 일원화하는지 먼저 확정. 이중 쓰기, 수기 재승인 금지 |
| G2 | **검출 기준 확정(2026-09-12 Q): 맥락이 확실한 불일치는 잡는다** | [ADR-0018 검출 기준](../../adr/0018-briefing-three-sections.md#2026-09-12-검출-기준-보완)을 따른다. 회차별 기록과 같은 회차의 음성 전사/수기 기록을 대조한다. 단순 값 차이의 자동 알림 확대는 하지 않으며, 숫자도 맥락이 분명한 상충이면 포함한다. 정상 변화·표현 차이·맥락 불확실성은 불일치로 단정하지 않는다. 누락 확인과 내용 상충은 구분한다 |
| G3 | S-A M6의 ‘결과가 생기면 아래 구역’과 §7의 ‘못 했어요는 열린 채’ | 결과 존재와 업무 종료를 독립 축으로 표현하는 안을 확정. 못 함/다시 약속/언급 없음은 열린 상태, 결과 기록은 보존. 목록 이동을 `resolved_at` 쓰기로 구현하지 않음 |
| G4 | S-A의 그림자 요구 vs ADR-0046의 내부 배경 활용, S-D 50의 참고 표시 | 생성·저장은 보존하되 그림자 동안 제품 생성 요청의 memory 입력을 차단하는 계약과 적용 범위를 기록. 참고 표시는 실제 사용한 경우만; 그림자에서 ‘참고했어요’ 금지 |
| G5 | S-D Q2: 6→9 영역, family/care와 employment/education 분리, 기존 위기도 4값→새 3값 | 기존 값을 원문/버전/출처와 함께 보존하고 모호한 항목은 사람 확인 전 분리하지 않는 안. 기존 `declined/unknown/not_applicable`을 빈칸으로 합치지 않음 |
| G6 | S-D Q3와 S-F의 28+모듈 필수 범위 | 적용되는 질문 목록과 무응답 허용을 서버/클라이언트에 같은 계약으로 적용. 단순 접힘과 ‘적용하지 않는 모듈’을 구별. 현재 whitelist 검사가 필수 완성을 보장한다고 가정하지 않음 |
| G7 | M1 번호 대응표 보관/열람/파기, 상대 날짜 vs S6 연월 일반화 | 개인정보 담당의 보관·권한 결정, S6 버전·manifest·재마스킹 전환을 먼저 확정. 영구 대응표를 기존 일회성 mask dictionary로 몰래 대체하지 않음 |
| G8 | S-D Q1/Q4/Q5/Q6/Q7/Q8, S-A §8의 잔여 질문 | STT 용어 병기, 고정/법적 문구 적용, 파기 범위, 보고서 수신자, 선택지 관리, 미결 목표 4건을 유지. 관계 가명은 이번 범위 밖; ‘오래됨’의 5회차는 예시이지 확정 숫자가 아님. 스킬 수정 소유자도 확정 |

`ccc-counseling-cards`, `ccc-full-report`는 현재 세션의 스킬 목록과 확인한 로컬 경로에서 확보하지 못했다. S-A §4-3의 변경 요구는 읽었지만 스킬 원문까지 적용됐다고 주장하지 않는다. 소유자가 원문 위치를 제공하면 정본과의 차이를 확인한다. 사용자 소유 스킬을 이 세션에서 임의 수정하거나 같은 이름으로 새로 만들지 않는다.

## 7. 실행 작업과 의존관계

**소유:** 총괄은 이 문서와 결정 인계만 작성한다. 코어/HTTP/AI/DB는 해당 기능 레인, `apps/client`는 승인된 frontend 레인, 공유 UI/CSS/토큰과 시안 수정은 DESIGN 레인이 맡는다. `.worktrees/frontend`의 소유를 다른 머신/폴더로 자동 확대하지 않는다. 옮길 경우 저장소 소유권 조항을 먼저 갱신한다. 같은 파일과 공용 lockfile은 한 작성자만 맡는다.

### W01. 요구 정본과 공통 계약을 확정한다

- [ ] S-D 01~54, D-A1~7을 아래 대응표로 추적하고 G1~G8 중 데이터/권한에 닿는 결정을 기록한다. 순수 표시명 확정은 재질문하지 않는다.
- [ ] `CONTEXT.md`에 분류 축과 개념 구별을 연결한다. ADR-0018/0032/0036/0037/0046에는 변경 범위와 대체 관계만 명시하고 역사 용어를 일괄 교체하지 않는다. 신규 ADR 번호는 실행 시 문서 번호 가드로 정한다.
- [ ] 공통 카드/연결/처리상태 계약은 `packages/contracts`의 새 `counseling-cards.ts`를 제안 경로로 삼아 기존 근거/동의/기억 타입을 참조하도록 설계한다. 스펙은 `docs/superpowers/specs/2026-09-12-relayer-card-ai-contract-design.md`에 통합하는 안이며 이번 계획 작성에서 그 파일이나 코드는 만들지 않는다.
- [ ] API/클라이언트/Agent/DB의 버전 전환과 rollback 표를 먼저 만든다. 과거 자료 읽기와 새 쓰기를 분리하고, 오래된 클라이언트나 Agent가 새 의미로 쓰지 못하도록 버전 경계를 정한다. 한 출고 묶음의 producer/consumer와 manifest를 함께 전환하며 장기 호환 별칭을 만들지 않는다. 복구 시 새 의미의 자료를 옛 코드가 잘못 읽지 않는 백업·읽기 전용/거부 경로까지 정한다.
- 완료 기준: 필드별 작성자, 공식화 시점, 원천 revision, 조회 권한, AI-off, 정정/철회/파기 전파가 모두 정해져 생산자와 소비자가 같은 계약을 받는다. 스키마 선택이 안 끝난 상태로 migration을 발행하지 않는다.

### W02. Glossary와 화면 소비 키를 맞춘다

선행 W01. 소유 frontend, 고정 고지/공유 UI는 각 소유자 인계.

- [ ] `business/navigation.ts`, `records.ts`, `ai-review.ts`, `report.ts`, `intake-form.ts`와 해당 `screens/*.tsx`의 표시명을 S-D 32~45에 맞춘다. URL, DB 키, 권한 ID는 유지한다.
- [ ] 대조는 서버 `missing_from_memo/missing_from_transcript/undiscussed_session_goal`과 실제 상태를 소비한다. 존재하지 않는 옛 키를 synthetic fixture가 대신 제공해 통과하는 경로도 바로잡는다(`apps/client/tools/synthetic-api.mjs`).
- [ ] 근거 인용, 약속/할 일, 목표/욕구, 위기도/위험 신호의 설명을 S-F §6에 맞춘다. 한글 label 교체와 타입 계약 수정을 별도 검수한다.
- 완료 기준: 실제 서버 DTO의 축과 미적용 이유를 올바르게 해석하고 route/역할 접근은 그대로다. **키 정합성 수정으로 금지된 ‘녹음 근거 없는 메모’ 목록을 새로 드러내서는 안 된다.** 이 대조 표시 변경은 W08의 조용한 표시와 같은 출고 묶음으로 내보내며, W02만 먼저 배포한다면 해당 표시 변경은 포함하지 않는다. 라벨만 고정하는 test assertion은 제거하고 권한/경로/접근성 동작 검사는 유지한다.

### W03. 생활영역과 첫 상담 입력 계약을 전환한다

선행 W01 G5/G6. 소유 core/DB → frontend → DESIGN.

### W04. 수기 기록과 명시적 약속 상태를 연결한다

선행 W01, 영역/위기도 쓰기는 W03. 소유 core/HTTP → frontend → DESIGN.

- [ ] `CounselingRecordDetailsInput`, `action_items`, 인테이크 `additionalItems`, `schedule_custom_questions`의 기존 저장을 재사용하여 기록 [0]~[6]의 데이터를 연결한다. 기존 없는 per-session 위기도와 확인할 것 수명주기는 계약 없이 화면 값으로만 만들지 않는다.
- [ ] 결과 3버튼, 기본 미확인, 못 함 뒤 계속/그만둠과 사유, 확인함→내용/회차 연결을 구현한다. 기존 `hold` 이력은 소거하지 않는다.
- [ ] `screens/records.tsx`의 실제 베타 구조를 기준으로 메모 필수 하나, 이전 기록 보조 패널, 다음 약속/질문, 달라진 것, 위기도/의견, 수기 위험 표시, 목표 닫기를 연결한다. web의 ‘11구획’ 코드를 그대로 옮기지 않는다.
- [ ] 등록 뒤 첫 상담 기록 연결은 기존 인계 10-3의 확인된 응답 두 ID를 사용한다. 새 명칭과 권한/동의·사업 잠금을 함께 지킨다.
- 완료 기준: AI 꺼짐에서도 수기 한 건 저장→공식 조회→다음 회차 확인이 성립한다. ‘못 함/확인 안 함’은 자동 완료되지 않고, 무입력 위기도가 안정으로 저장되지 않는다. 첫 상담에 적은 질문이 다음 회차까지 이어진다.

### W05. 검사 상태와 기억 그림자를 계약으로 만든다

선행 W01 G4. 소유 core/HTTP/AI → frontend.

- [ ] 기존 축별 적용 상태와 일감 상태를 공통 처리상태에 연결한다. 브리핑/리포트에 결과 0건뿐 아니라 검사 대상 revision/범위/실패 이유를 제공한다.
- [ ] `loadCounselingMemoryContext`, `request-handler.ts`의 preview/실제 생성 경로와 재생성 소비를 함께 제어한다. 그림자에서는 어떤 제품 모듈 요청에도 memory가 섞이지 않으며 생성/저장·정정·파기 기능은 보존한다.
- [ ] `business/schedules.ts`, `ai-review.ts`, `screens/schedules.tsx`, `records.tsx`, `settings-modules.tsx`가 실제 상태와 사용 여부를 표시한다. 필요한 응답 필드를 먼저 만들고 UI가 성공 상태를 추측하지 않게 한다.
- 완료 기준: 동일 자료에 성공 0건/미실행/대기/차단/부분 처리/오래된 결과가 구별된다. 그림자 on에서는 API 요청의 memory 영향이 없고 실제 사용 전 ‘지난 N회차 참고’가 나오지 않는다. 승인 대기 원문을 공식 자료처럼 읽지 않는다.

### W06. M1의 번호 가명과 날짜 계약을 적용한다

선행 W01 G7. 소유 개인정보/Agent + core. W12의 독립 평가 설계를 함께 시작한다.

- [ ] `apps/pipeline/ccc_pipeline/masking.py`, 실제 privacy packet 조립과 core 검증, S6/S5에 사례 단위 번호와 상대 날짜를 같은 버전으로 적용한다. 코어는 사후 본문 재작성으로 hash/offset을 고치지 않는다.
- [ ] 대응표의 접근/암호화/폐기, 사례 간 번호 격리, 날짜 간격 보존, 짧은 목표와 기관명의 감지 실패를 검증한다.
- [ ] 새 manifest/허용 버전, 기존 자료 재마스킹·재생성·실패 경로를 함께 제공한다. 기존 초안/기억에 새 버전을 조용히 덧씌우지 않는다.

### W07. M2/M3 카드 생산자와 색인을 만든다

선행 W01 G1, 완전한 번호 계약은 W06. 소유 contracts/core/DB/AI.

- [ ] 실제 `AiProviderOutput`, parser, JSON schema, 저장, 근거, 승인 projection을 카드 계약으로 연결한다. 기존 `claims_json`을 보존 이력으로 읽을지 전환할지 W01 결정대로 처리하고 새 결과의 이중 정본은 두지 않는다.
- [ ] 카드 4종과 원문상의 화자/행위자/기한, 사례 안 주제 재사용·사람 수정 우선, 목표 연결, 같은 내용/결과/갱신을 생성한다. 열린 약속 입력도 마스킹·범위 검증을 거친 근거만 사용한다.
- [ ] 회차 순서는 상담일 기준이며 늦은 입력/정정/재생성/철회와 결과 경합을 처리한다. 예전 결과가 새 승인 카드나 사람의 주제 수정을 덮어쓰지 못한다.
- 완료 기준: 메모/전사 같은 내용의 출처 둘 보존, 짧고 모호한 문장 억지 카드 생성 금지, 명시적 약속이 없는 의견의 확인 카드 승격 금지. SQLite/PostgreSQL과 API 소비자가 같은 필드를 읽는다.

### W08. M4/M5 대조를 새 의미로 전환한다

선행 W05, W07, G2. 소유 AI/core/HTTP → frontend.

- [ ] 기존 `ai_draft_contrast_axes`, `session_discrepancies`를 확장한다. 새 엔진을 병설하지 않고 현재 자료/근거/승인 전이를 재사용한다.
- [ ] M4의 메모 누락 목록과 녹음 근거의 문장 표시를 구별한다. 메모의 녹음 근거 부재는 경고 목록·집계·관리자 성과자료에서 제외한다. 미논의 이번 상담 목표는 별도 축으로 계속 검증한다.
- [ ] M5는 사실만 비교하고 판단 카드를 제외한다. G2의 확정 기준대로 같은 대상·사건·시점의 맥락이 원문에서 분명하고 두 내용이 양립할 수 없는 경우를 검출한다. 단순 값 차이, 정상 변화, 뒤 회차의 명시적 정정, 표현 차이와 맥락 불확실성을 구분하며 원본 두 기록은 불변이다.

### 실행 레인이 사용할 기존 검사 명령

아래 명령은 실행 계획이며 이번 조사에서 돌린 결과가 아니다. 각 작업에서 변경한 계약의 검사와 실제 스모크를 먼저 수행하고, 통합 명령은 작업자 간 검증 슬롯을 모아 한 번 실행한다.

```sh
# 저장소 루트, client 소비 계약과 빌드
pnpm --filter @ccc/client run typecheck
pnpm --filter @ccc/client run test
pnpm --filter @ccc/client run build

# 저장소 루트, 기존 AI/대조/리포트 계약의 표적 회귀
pnpm exec vitest run --config apps/api/vitest.config.ts --maxWorkers=4 apps/api/test/ai-quality-v4.test.ts apps/api/test/ai-contrast-materials.test.ts apps/api/test/discrepancies.test.ts apps/api/test/support-case-report.contract.test.ts

# 저장소 루트, 의미 품질이 아닌 평가기 자기검사
pnpm --filter @ccc/api eval:memory -- --fixtures

# 저장소 루트, 문서/공유 화면 경계
node scripts/guard-doc-numbers.mjs
pnpm run guard:tokens
pnpm run guard:align
pnpm run guard:hierarchy
```

W03의 영역 전환은 `gateway-domain.test.ts`, `gateway-intake.test.ts`, `gateway-record-onepage.test.ts`의 기존 기록·잘못된 키 거부 계약과 두 DB parity를 포함한다. W06은 `apps/pipeline/tests/test_masking.py`와 S6의 packet/attestation/egress 계약을 함께 검사한다. 새 모듈의 의미 평가와 실제 browser/API 동작은 위 기존 검사로 대체하지 않는다. 외부 AI가 필요한 live 평가와 운영 배포는 별도 승인 전 실행하지 않는다.

## 10. 이전 계획과 인계의 처리

- 이 문서가 [기존 인계](2026-09-12-beta-0.9-mini-handoff.md)의 7장 및 10-5의 **전체 작업 순서**를 대체한다. 10장의 결함 실측과 12장의 설정 확인은 증거로 보존하며 재조사하지 않는다.
- `inbox/.../handoff-prompt-client-defects.md`는 이 계획을 먼저 읽는 전달 프롬프트로 교체한다. ‘세 결함이 제품 전체 계획’이라는 지시와 이미 확인된 ID를 다시 찾게 하는 지시를 제거한다.
- 원본 8개와 승인된 결정을 이번 작업에서 덮어쓰지 않는다. 미래 스펙·ADR·CONTEXT 통합은 W01의 별도 실행이다. 새로운 장을 계속 덧붙여 상충하는 실행 순서를 늘리지 않는다.
- 총괄 작성 위치는 `orchestrate/beta-0.9`다. 다른 레인, 미추적 랜딩 시안, 운영 자원, 계정/시크릿, shared UI/CSS는 이번 작업에서 변경하지 않는다.
