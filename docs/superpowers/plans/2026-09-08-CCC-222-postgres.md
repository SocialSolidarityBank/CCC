# CCC-222 PostgreSQL adapter implementation plan

> For agentic workers: use executing-plans. Work only in this worktree. This is E3-3, not E3-4 baseline/parity or production deployment. Main coordinates the two Herdr split panes and runs validation after concurrent writes finish.

**Goal:** Implement the existing Database port using postgres 3.4.9 and prove actual database round trips, structured errors, and atomic failed-batch rollback.

**Architecture:** New `adapters/db-postgres` implements the unchanged `@ccc/contracts/database` interfaces. Reuse `scanSqlPlaceholders` from `@ccc/contracts/sql`; no SQL translator, ORM, gateway refactor, migration baseline change, or compatibility alias. The adapter owns its connection pool. Runtime consumers receive Database; composition roots may close the pool.

**Spec:** `docs/specs/S1-database-sql-subset.md`, especially sections 2.1, 2.2, F01-F05 and F10; current SQLite adapter behavior; `CCC_OPEN_PILOT_PLAN.md` E3-3. Full migration parity, F06/F09 migration semantics and hosted Supabase remain E3-4 and later tickets.

## Shared API and ownership

```ts
import type { Database } from '@ccc/contracts/database';
export interface PostgresDatabaseOptions {
  connectionString: string;
  maxConnections?: number;
  ssl?: 'verify-full' | false;
}
export interface PostgresDatabase extends Database {
  close(): Promise<void>;
}
export function createPostgresDatabase(options: PostgresDatabaseOptions): PostgresDatabase;
```

Package name `@ccc/db-postgres`, entry `src/index.ts`, ESM. TLS verifies server certificate/hostname by default; loopback disposable tests explicitly set `ssl:false`. There is no unverified TLS mode: the initially proposed `require` option was removed during security review because postgres.js skips certificate verification in that mode. Private-CA deployments must configure the runtime trust store, not disable verification. Never print or retain connection strings, SQL values, vendor error detail, notices, stack causes or keys. Allowlisted trigger application codes are the S1 three plus current source-verified `counseling_memory_fence` from the merged memory implementation. Unknown trigger messages never become application codes.

## Task 1: Adapter

- [x] Add the package and factory using postgres 3.4.9. `prepare` performs lexical validation without I/O. `bind` returns independent statements, copies only mutable bytes at binding time, and checks arity before sending a query. Rebinding must not mutate previous statements.
- [x] Return owned Uint8Array values; decode bigint/aggregate numbers only within safe JS range. Keep text, null and ISO timestamp text intact. `first` differentiates no-row/null from missing-column syntax error. `run` has empty results and affected-row count; `all` and batch preserve result rows and order.
- [x] Execute batch statements sequentially in one postgres transaction. Reject statements from another adapter without executing any. On SQL, constraint or decoding failure roll back the entire batch and return no partial success. Empty batch returns an empty array. Queries must execute on the transaction connection, not the outer pool.
- [x] Normalize unique, primary key (including nonconventional constraint names), FK, check/not-null and allowlisted trigger errors. Do not infer primary keys solely from `_pkey` suffixes. Unknown and network failures use sanitized DatabaseError without leaking vendor detail. Mapping a transaction failure must not attempt a query on an aborted transaction.
- [x] Make close end the owned pool and reject further execution with a sanitized error. Do not add migration APIs or expose raw SQL clients to the core.

## Task 2: Real PostgreSQL contract harness

- [x] Build an isolated, automatically disposed Docker PostgreSQL harness. Use a random container name and loopback ephemeral port; own only containers created by this invocation. Use pinned image `postgres@sha256:18cfe3ef5e6815560c98237d6216d1e5119702fb0f3894c8785dd58b8bbe5d73` (available postgres:17-alpine image). No host/production DB URL is accepted. Docker unavailable is a clear failing/unavailable result, never skipped PASS.
- [x] Preserve the existing shared D1/SQLite tests, supplying PostgreSQL-specific logical fixture DDL for trigger syntax and bytea/bigint types rather than translating SQL. The test DB may use adapter prepare for DDL. The harness may use raw driver calls for fixture provisioning only.
- [x] Defend immutable statements, byte ownership including offset views, first/NULL/missing-column, returning/run changes, quoted-placeholder scanning and arity. Include safe/unsafe bigint and aggregate values.
- [x] Prove committed mutation+audit together and failed mutation+audit rollback for unique/custom-named primary/FK/check/trigger failures. Check rows after rejection through a subsequent statement so a pool escape or swallowed error fails observably. A decoding failure within batch must also roll back.
- [x] Include concurrent transaction isolation, foreign-statement rejection, closed-pool rejection, and absence of synthetic sensitive values in public errors. Avoid source-text assertions, mock echo tests, arbitrary sleeps and broad retries. Only readiness polling is bounded; normal calls do not silently retry.

## Composition-root usage

```ts
import { createPostgresDatabase } from '@ccc/db-postgres';

// Resolve the connection string through the deployment's approved secret path.
const database = createPostgresDatabase({ connectionString, maxConnections: 4 });
try {
  // Supply database through the existing Database port; do not expose the driver.
  await application(database);
} finally {
  await database.close();
}
```

`pnpm test:contracts --db=postgres` requires Docker and provisions its own synthetic database. It does not accept a production connection string. `ssl:false` is reserved for isolated loopback fixtures or an already authenticated local tunnel, not a remote-database fallback.
