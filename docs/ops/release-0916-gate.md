## 2. 실제 사람 자료 전에 한 번 밟을 가상 자료 흐름

**첫 상담을 맡을 팀원이, 운영 개시 대상으로 삼은 동일 배포 후보에서, 허가된 가상 자료로 먼저 한 번 완주한다.** 운영자만 개발용 인증으로 실행한 결과나 다른 preview 버전의 성공으로 대체하지 않는다. 친구의 이름·연락처·건강·채무·상담 내용을 미리 넣어 테스트하지 않는다. 가상 자료의 사용 환경·식별·보관/정리 방법은 운영 담당자가 확인하며 실제 자료와 섞지 않는다.

1. **정상 로그인과 당사자 등록 진입:** 팀원 본인 계정으로 로그인한다. 등록 화면에서 현재 기관과 선택 사업을 확인하고 구별 가능한 가상 기본정보를 입력한다. Access 거부, 다른 사람의 계정 표시, 다른 사업 선택이면 멈춘다. 등록에 동의가 필요한 현재 계약을 우회해 먼저 실제 저장하지 않는다.
2. **여섯 영역 동의 입력과 등록 확정:** 화면에 표시된 고지문을 읽고 각 영역의 가상 선택을 기록한 뒤 제출한다. 영역별 결정과 그때 보여 준 고지 스냅샷이 같이 전달되는지 검증 담당자가 확인한다. 당사자 페이지를 다시 열어 기본정보·사업·담당 실무자와 저장된 동의 선택·근거가 일치하는지 본다. 동의 화면 나머지 두 곳도 C1~C3에서 빠짐없이 확인한다. 정확한 화면·서버 근거 조회 경로는 확인 필요다.
3. **누락 거부 확인:** 검증 담당자가 동일 후보의 가상 요청에서 동의 결정 또는 고지 스냅샷을 각각 누락시킨다. 서버 거부 결과를 보고, 입력한 자료가 성공 등록된 것처럼 남지 않는지 확인한다. 실제 당사자의 동의를 지우거나 실제 기록을 실험 대상으로 삼지 않는다.
4. **인테이크:** 같은 당사자·선택 사례에서 인테이크를 작성한다. 적용되는 질문에 답변 또는 허용된 비응답을 넣고 저장한 뒤 다시 연다. 입력값·비응답·목표가 그대로 보이고, 접힌 영역 때문에 값이 사라지거나 미선택 영역 때문에 저장이 막히지 않는지 확인한다.
5. **수기 상담 기록:** 같은 사례에 상담일시와 구별 가능한 가상 메모를 입력하고, 사용하는 목표·질문·과제 항목도 저장한다. 목록에서 해당 회차가 한 건 생기고 상세·새로고침 후에도 저장값이 같은지 확인한다. 상담일시가 입력한 현지 날짜·시간으로 다시 보이는지 확인한다. 저장 실패를 성공으로 보이게 하거나 두 회차로 중복 생성하면 실패다.
6. **15초 페이지:** 같은 사례의 15초 페이지를 연다. 방금 저장한 수기 기록과 필요한 목표·질문·과제를 확인하고 출처 회차로 이동한다. 다른 당사자·사업·회차 자료가 섞이지 않고, 저장한 본문으로 돌아갈 수 있어야 한다. 없는 AI 요약이나 미실행 검사를 완료로 표시하지 않는다.
7. **재로그인과 최종 대조:** 로그아웃 후 본인 계정으로 다시 로그인하여 같은 당사자·사례·회차를 찾는다. 기본정보, 동의, 인테이크, 상담일시·본문과 15초 페이지의 연결이 남아 있는지 관찰자가 대조한다. 결과와 후보 SHA를 1장의 판정 기록에 연결한다. 중간에 수정·재배포됐다면 최종 후보에서 흐름을 다시 완주한다.

그 다음에야 실제 당사자의 문안 확인·동의 취득과 첫 실제 입력을 진행한다. 첫 실제 저장 시각을 남겨 북마크 시점과 구분하고, 이후 DB 복원은 상담 자료 손실을 일으킬 수 있다는 점을 승인자와 실무자가 확인한다. 동의가 없거나 고지 근거를 저장할 수 없으면 실제 자료 입력을 시작하지 않는다.

## 3. 개시 뒤 문제 발생 시 되돌리기

### 3.1 공통 순서

1. **새 입력·수정·재시도를 중단하도록 알린다.** 장애 발견 시각, 영향받은 작업, 마지막 성공 저장 시각을 확인한다. 화면에서 사라진 자료가 DB에서도 지워졌다고 단정하지 않는다.
2. **현재 상태와 복귀 대상을 식별한다.** 실행자가 현재 웹·API 배포 ID와 D1 `ccc`, 복귀할 검증된 코드 버전, DB 스키마 호환 여부를 확인한다. 자격 로테이션 셋의 완료 상태를 되돌려 폐기한 자격을 다시 사용하지 않는다.
3. **코드만 복귀할지 먼저 판단한다.** 현재 D1 스키마·저장값과 호환되는 코드 복귀로 해결할 수 있으면 DB는 되돌리지 않는다. 호환을 확인하지 못하면 옛 코드를 먼저 배포하지 않는다.
4. **DB 복원이 필요할 때만 별도 손실 판정과 승인을 한다.** 사용자의 입력 중단 안내와 실제 API·자동 작업의 쓰기 정지는 다르다. 쓰기가 정지됐다는 확인과 3.3의 자료 보존·손실 판단이 끝나기 전에는 Time Travel을 실행하지 않는다.
5. **복귀 후 재개를 별도로 판정한다.** 버전·DB 상태·자료·동의·권한·감사를 대조하고 가상 자료로 2장의 흐름을 확인한다. 보호 조건이나 자료 정합성이 미확인인 채 로그인만 된다고 재개하지 않는다.

### 3.2 코드 배포만 되돌리기

웹과 API는 별도 배포 단위이며 D1의 마이그레이션이나 저장 자료는 코드 복귀와 함께 돌아가지 않는다. 복귀할 코드가 현재 D1의 19건 적용 후 스키마와 호환되는지 확인해야 한다. **정상 복귀 대상 웹·API 배포 ID·태그와 호환 근거는 확인 필요**다.

다음은 기존 [운영 런북](../ops.md)과 [복구 안내 함수](../../scripts/deploy-gates.mjs)에 기록된 명령이다. 이번 배정에서 새로 조사하거나 실행하지 않았으며, **각 Worker의 직전 배포가 확인한 복귀 대상일 때만** 사용할 수 있다. 승인된 실행자가 레포 루트에서 API 다음 웹 순서로 실행한다. 다른 복귀 버전을 선택해야 하는데 명령의 대상 지정법이 확인되지 않았다면 임의 명령을 만들지 말고 멈춘다.

```bash
pnpm --filter @ccc/api exec wrangler rollback --env production
pnpm --filter @ccc/web exec wrangler rollback
```

첫 명령이 실패하면 두 번째를 무조건 이어서 실행하지 않는다. 두 Worker가 서로 다른 버전일 수 있으므로 새 쓰기를 재개하지 않은 채 상태를 확인한다. 웹에는 `--env production`을 추가하지 않는다.

| 구분 | 무엇을 잃거나 다시 확인해야 하는가 |
| --- | --- |
| 코드·화면 | 새 버전의 수정·기능이 사라진다. 과거 화면이 새 저장 형식을 표시하지 못할 수 있다. 화면에서 안 보인다는 사실과 DB 손실을 구분한다. |
| 처리 중 요청·미저장 입력 | 성공 여부와 미저장 내용의 보존을 보장하지 않는다. 저장 결과를 재조회한 뒤 재시도 여부를 정하며 중복 저장을 확인한다. |
| 이미 저장된 D1 자료 | 코드 복귀 자체는 D1을 과거 시점으로 되돌리지 않는다. 다만 비호환 옛 코드가 이후 쓰기로 자료를 훼손할 수 있으므로 호환 확인이 선행한다. |
| 설정·자격·외부 상태 | DB·파일·회전한 자격까지 함께 원복하는 조치가 아니다. 폐기 자격을 다시 살리거나 다른 저장소를 같이 초기화하지 않는다. |

### 3.3 D1 Time Travel로 되돌리기

북마크는 확보돼 있고 **2026-10-16까지 유효**하다는 제공 사실을 사용한다. 기존 전달 위치는 `artifacts/prod-migration-2026-09-16/before.md`다. **실제 북마크 값·복원 시각, 적용 전후 어느 스키마를 가리키는지, 만료 시각·시간대는 확인 필요**다. 제공된 유효 기한과 첫 주 안에 만료하는 번들의 기한을 혼동하지 않는다.

**실제 개인정보가 들어온 뒤 북마크 시점으로 DB를 되돌리면 그 사이에 기록한 상담 자료가 복원 DB에서 사라진다.** 동의·권한·감사·일정·목표도 함께 영향을 받을 수 있고, 이후 철회·비활성화·파기한 상태가 과거로 돌아갈 수도 있다. 특정 잘못된 행이나 마이그레이션만 골라 취소하는 작업으로 설명하지 않는다.

복원 전에는 아래 순서로 확인한다.

1. 운영 대상이 D1 `ccc`인지 확인하고, 웹·API·cron·Agent 등 현재 DB에 쓰는 경로가 정지됐는지 확인한다. **전체 쓰기 정지·재개 실행 절차는 확인 필요**다. 없는 유지보수 스위치를 가정하지 않는다.
2. 북마크 시각, 첫 실제 입력 시각, 마지막 성공 저장 시각을 비교한다. 북마크 이후 새로 생성·변경·삭제된 당사자·사례·회차·동의·권한·감사의 범위를 비식별 건수·식별자로 확인한다. 실제 본문을 공개 문서나 Git에 옮기지 않는다.
3. 복원 전에 현재 자료를 안전하게 보존할 수 있는 방법, 필요한 자료를 다시 반영할 수 있는 방법, 불가피하게 잃는 자료와 영향을 승인자가 확인한다. **북마크 이후 실자료의 보존·재적용 절차는 확인 필요**다. 확인되지 않으면 무손실이라고 말하지 않고 복원을 멈춘다. 업무용 CSV나 북마크 하나가 전체 최신 자료의 복구를 보장하지 않는다.
4. 복원할 DB·북마크·손실 범위·보존 방법·실행자·승인자를 기록한 뒤에만 복원한다. 아래 명령은 기존 [운영 마이그레이션 기록](../../artifacts/prod-migration-2026-09-09/0051-0053.md)에 있는 **형식**이다. `<위 값>`은 확인한 2026-09-16 북마크로 바꿔야 하며 과거 문서의 북마크를 복사하거나 템플릿 그대로 실행하지 않는다.

```text
wrangler d1 time-travel restore ccc --env production --bookmark=<위 값>
```

5. 쓰기를 재개하기 전에 복원된 스키마와 호환되는 API·웹 조합을 맞춘다. 코드 복귀와 DB 복원은 자동으로 함께 처리되지 않는다. 검증된 복귀 조합과 실행 순서가 없으면 중단 상태를 유지한다.
6. 복원 후 사례·회차와 동의·권한·감사·파기 상태를 대조한다. 보존한 자료의 재적용 여부, 누락·중복, 철회한 동의·권한이나 파기 자료의 재등장을 확인하고 가상 자료로 2장을 다시 밟는다. **최신 철회·파기 상태와의 대조·보정 및 D1 밖 자료의 정합성 복구 절차는 확인 필요**다. 확인되지 않은 상태에서 실사용을 재개하지 않는다.

북마크가 19건 적용 전 지점이라면 이후 스키마 변경과 데이터도 되돌아간다. 개별 마이그레이션을 역순 취소하는 `down` 절차는 확인되지 않았으므로 명령을 적지 않는다. Time Travel 기한이 지난 뒤에도 이 복원 경로를 쓸 수 있다고 가정하지 않는다.

## 4. 개시 뒤 첫 주에 지켜볼 것

| 무엇을 보는가 | 바로 알아야 할 이상 | 대응 |

| 매일 배포·API 오류와 보호 작업 상태 | 반복 5xx·저장 거부, 배포 버전 혼합, 보존·파기 등 보호 작업 중단 | 영향 작업을 중지하고 3장의 코드/DB 복귀 판단을 분리한다. |
