이 문서는 사회연대은행 팀원이 친구를 당사자로 상담하는 **첫 실제 사람 자료 입력 전**에 사용한다. 이번 대상은 기존 Cloudflare 웹·API와 운영 D1 `ccc`다. **전사는 이번 범위 밖이며 원음 업로드도 열지 않는다.** 기존 스택에 서명 URL 생산자가 없어 업로드할 수 없다는 오케스트레이터의 확인을 전제로 한다. 이전 Supabase·Azure 전사 출고안의 완료 조건을 이번 판정에 가져오지 않는다.

## 2. 하나라도 해당하면 개시하지 않는 조건

- `verify`가 실패·진행 중·미실행이거나 후보 SHA와 다르다. 알려진 API 회귀가 남아 있다.
- preview 오류 다섯 건 중 하나라도 미해결이거나 재현 위치·수정 증거를 확인할 수 없다.
- 정상 로그인 가능한 관리자 또는 첫 실무자가 없거나, 인증 우회 계정으로만 흐름을 열 수 있다.
- 저장 성공 안내 뒤 자료가 없거나, 다른 당사자·사업·회차에 저장되거나, 재시도로 같은 기록이 중복된다.
- 권한 없는 사람이 보호 본문을 보거나 수정·반출할 수 있다. 관리자 조회·반출 허용을 비담당 작성·승인 허용으로 잘못 확장했다.
- 여섯 영역의 실제 동의 선택과 적용 문안·기록 근거를 확인하지 못했다. 화면은 옛 두 항목만 보여 주는데 여섯 영역을 받았다고 처리했다.
- 원음 업로드·전사 경로가 열려 있거나, 별도 도구·저장소·사업자로 원음을 우회 전송한다. 원음 업로드 불가를 동의·보호 조건 우회로 해결하려 한다.
- 수기 기록을 읽으려면 전사나 AI 승인을 기다려야 한다. 미승인 AI 초안이나 미실행 검사가 공식 기록·완료 상태로 보인다.
- 약속한 CSV 내용이 빠지거나 다른 사례 자료가 섞인다. 반출 감사가 남지 않는다.
- 필수 암호화·감사·보존·파기·복구 검증의 증거가 없거나, 기능 OFF와 함께 보호 작업까지 중단된다.
- 복귀 대상 버전·DB 북마크·스키마 호환·손실 범위·쓰기 정지 방법이 확인되지 않아 3장의 복구 경로를 실제로 사용할 수 없다.
- 위 조건 중 하나를 날짜, 번들 게시, 마이그레이션 완료 또는 담당자의 구두 낙관만으로 통과 처리하려 한다.

## 3. 배포 뒤 문제가 생겼을 때 되돌리는 계획

### 3.1 먼저 정할 순서

1. 실무자에게 새 등록·수정·재시도를 멈추도록 알리고 장애 발견 시각을 남긴다. 실제 상담 내용·비밀값을 Git 문서나 공개 로그에 복사하지 않는다.
2. 실행자는 문제가 난 웹·API 배포 식별자, D1 대상, 마지막 성공 저장 시각과 영향받은 사례·회차를 확인한다. 원인 규명 전 반복 재배포나 시드 초기화를 하지 않는다.
3. **코드만 되돌려도 현재 D1 스키마·자료를 안전하게 읽고 쓸 수 있는지 먼저 확인한다.** 확인되면 3.2를 선택한다. 코드 오류만으로 D1까지 되돌리지 않는다.
4. D1 자체의 복원이 필요하면 3.3의 별도 손실 판정을 한다. 모든 쓰기 경로의 정지와 복원 대상·보존 계획을 확인하기 전에는 복원 명령을 실행하지 않는다.
5. 되돌린 뒤 버전·DB 대상을 기록하고 G03~G12를 다시 확인한다. 누락·중복·권한·동의·파기 상태까지 재판정한 뒤에만 사용을 재개한다.

**확인 필요:** 직원에게 입력 중단을 알리는 것과 시스템의 쓰기를 막는 것은 다르다. 웹·API·cron·Agent를 포함한 운영 `ccc` 전체 쓰기를 일괄 정지하고 다시 여는 승인된 절차는 이 작업본의 확인 범위에서 찾지 못했다. 존재하지 않는 유지보수 스위치나 명령을 가정하지 않는다.

### 3.2 웹과 API 배포만 되돌리기

전제는 웹과 API 각각의 직전 배포가 실제로 복귀할 검증된 조합이며, **현재 19건 적용 후 D1 스키마와 호환된다는 확인**이다. 직전 배포가 정상이라는 가정만으로 실행하지 않는다. 실제 복귀할 두 배포 식별자는 확인 필요다.

[docs/ops.md의 스모크 실패 시 복구](../ops.md)와 [rollbackGuidance](../../scripts/deploy-gates.mjs)에 있는 순서는 **API 다음 웹**이다. 승인된 운영 인증 환경을 준비한 실행자가 레포 루트에서 실행한다. 이 문서 작성 중에는 실행하지 않았다.

```bash
pnpm --filter @ccc/api exec wrangler rollback --env production
pnpm --filter @ccc/web exec wrangler rollback
```

웹에는 `--env production`을 붙이지 않는다. 웹 최상위 설정이 운영 `ccc`이며 API만 해당 named env를 사용한다. 첫 명령 실패 시 다음 명령을 무조건 실행하지 말고, 혼합 버전의 상태를 확인한 채 입력 중단을 유지한다. 두 Worker는 따로 되돌아가므로 하나의 원자적 복구라고 설명하지 않는다.

| 대상 | 되돌리는 것 | 잃거나 영향을 받는 것 | 이 조치가 되돌리지 않는 것 |
| --- | --- | --- | --- |
| API | API의 직전 배포 | 새 API 수정·기능이 사라진다. 처리 중인 요청의 결과는 재조회로 확인해야 하며 미저장 요청의 성공을 보장하지 않는다. | D1의 마이그레이션과 이미 저장된 업무 자료를 이전 시점으로 복원하지 않는다. |
| 웹 | 웹의 직전 배포 | 새 화면·수정이 사라진다. 사용자의 저장 전 입력은 보호를 보장할 수 없으며 복귀 화면에서 새 형식의 자료가 보이지 않을 수 있다. | API 배포나 D1 자료를 함께 되돌리지 않는다. 화면에서 안 보인다고 자료가 삭제됐다고 판정하지 않는다. |

배포 버전에 결속된 바인딩·설정과 암호화 키의 호환도 확인한다. Worker 복귀가 D1, 별도 저장소, 외부 처리 결과나 이미 내려받은 파일까지 원복한다는 절차는 없다.

레포에는 이전 태그를 다시 배포하는 대안도 있다. `<이전태그>`는 [배포 이력](../releases.md)과 실제 검증 결과로 선택해야 하며 **이번 복귀 태그는 확인 필요**다. `0.9.0-dev.3` 번들명이나 이 작업본의 과거 운영 버전을 자동으로 복귀 태그에 대입하지 않는다.

```text
gh workflow run deploy-production.yml --ref <이전태그> -f confirm=deploy-production
```

이 대안도 기존 `verify`, 스키마, 운영 승인 게이트를 거친다. 게이트를 우회하는 긴급 재배포 명령은 추가하지 않는다.

### 3.3 D1 마이그레이션과 자료를 함께 되돌리기

**D1 Time Travel은 잘못된 마이그레이션 한 건만 취소하는 작업이 아니다.** 복원 지점의 스키마·자료 상태로 돌아가는 경로다. 개별 마이그레이션의 `down` 명령이나 오늘 19건을 역순으로 취소하는 절차는 확인 범위에서 찾지 못했다.

- 지정 북마크 위치: `artifacts/prod-migration-2026-09-16/before.md`.
- 북마크 확보는 오케스트레이터가 전달한 사실이다. **이 PLANNER 작업본에는 지정 파일이 없어 실제 값·대상 DB·복원 시각·유효 여부는 확인 필요**다. 다른 워크트리의 파일을 읽거나 복사하지 않았다.
- 운영 `ccc` 복원 명령의 형식은 [2026-09-09 마이그레이션 기록](../../artifacts/prod-migration-2026-09-09/0051-0053.md)에 있다. 아래는 그 문서의 템플릿이며 그대로 실행하지 않는다. `<위 값>`에는 실행자가 확인한 **2026-09-16 지정 파일의 북마크**를 사용한다. 링크된 9월 9일 북마크를 복사하지 않는다.

```text
wrangler d1 time-travel restore ccc --env production --bookmark=<위 값>
```

명령 존재와 복원 성공은 다르다. 실행 위치·인증은 해당 운영 실행자의 승인된 Wrangler 환경을 확인하며, 시크릿을 출력하는 새 명령은 만들지 않는다. `ccc-preview`의 복원/초기화 절차를 운영 `ccc`로 이름만 바꿔 사용하지 않는다.

복원 순서는 다음 조건을 따른다.

1. 새 업무 입력뿐 아니라 자동 쓰기도 정지했는지 확인한다. 일괄 정지·재개 절차는 3.1의 확인 필요 항목이다.
2. 북마크 대상이 운영 `ccc`인지, 시점이 19건 적용 전인지와 해당 시점의 스키마·자료를 확인한다. 현재 자료와 비교해 어느 기간의 등록·상담·동의·권한·감사가 사라지거나 과거 상태로 바뀌는지 적는다.
3. 북마크 이후 실제 자료가 있으면 그 자료의 보존·재적용 방법과 손실 수용 여부를 승인자가 확인한다. **현재 업무 자료의 손실 없는 보존·선택적 재적용 절차는 확인하지 못했다.** 확인 없이 복원을 무손실이라고 보고하지 않는다. CSV는 전체 DB 복구 수단이 아니다.
4. 복원 대상·손실 범위·승인을 기록한 실행자가 확인된 명령과 북마크로 D1을 복원한다. 확인 전에는 이 단계에서 멈춘다.
5. 트래픽과 쓰기를 재개하기 전에 복원된 스키마에 맞는 검증된 API·웹 조합으로 맞춘다. 자동 동시 복귀 절차는 없으며, 필요하면 3.2의 검증된 복귀 경로를 사용한다. 새 코드가 복원 전후의 DB에 계속 쓰도록 두지 않는다.
6. 마이그레이션 목록, 필요한 표·열, 사례·회차와 동의·권한·감사 상태를 확인하고 G03~G12를 다시 판정한다. 예전 북마크 복원으로 철회된 권한·동의나 파기된 개인정보가 되살아나지 않았는지도 확인한다. 이 대조·보정의 실제 실행 절차가 없으면 사용을 재개하지 않는다.

| 복원으로 영향을 받는 것 | 손실·위험 |
| --- | --- |
| 북마크 이후의 스키마 변경과 migration 이력 | 오늘 19건 적용 전 지점이라면 그 이후 변경도 되돌아간다. 복원 후 새 코드와 스키마가 맞지 않을 수 있다. |
| 이후 생성한 당사자·사례·상담·일정·목표·동의·감사 | 복원 DB에서 없어질 수 있다. 특히 첫 실제 상담을 기록한 뒤에는 테스트 초기화와 같은 작업이 아니다. |
| 이후 변경·삭제한 기존 자료와 권한 | 과거 값이 다시 나타날 수 있다. 동의 철회·계정 비활성·개인정보 파기 이후라면 단순 로그인 성공만으로 재개하면 안 된다. |
| D1 밖의 파일·키·외부 상태 | 함께 복원된다는 근거가 없다. DB 복원만으로 암호화 키나 별도 저장소와의 정합성이 맞는다고 가정하지 않는다. |

## 4. 첫 상담이 실제 사람 자료일 때의 입력 전 조건

친구가 참여하고 내부 팀원이 진행해도 실명·연락처·건강·채무·상담 내용은 실제 사람 자료다. 합성 시드나 운영자 본인의 비민감 시험으로 취급하지 않는다. 첫 실제 저장을 개시 판정의 테스트로 사용하지 않는다.

### 4.1 동의 여섯 영역

영역의 정본은 [CONSENT_DOMAINS와 문안](../../packages/contracts/src/consent.ts)이다. 여섯 영역을 각각 설명하고 **실제 동의·거부·철회 선택을 받아 기록**한다. 옛 두 항목의 동의나 구두로 한 번 받은 포괄 동의를 여섯 영역의 동의로 자동 승격하지 않는다. 미확인 상태를 동의함으로 채우지 않는다.

| 영역 | 입력 전에 눈으로 확인할 것 |
| --- | --- |
| 개인정보 수집·이용 | 이번 상담의 목적·수집 항목·열람 범위·보유기간이 포함된 적용 문안을 당사자가 확인했고, 실제 선택과 효력 시각을 확인할 수 있다. |
| 민감정보 처리 | 건강·채무 등 실제 기록할 민감정보의 목적·범위를 설명한 문안과 실제 선택을 확인할 수 있다. 필요한 동의가 없으면 해당 민감정보를 수집·기록하지 않는다. |
| 상담 녹음 | 선택을 별도로 확인하되 이번에는 제품 녹음·원음 업로드를 제공하지 않는다는 안내가 있다. 동의 여부와 별개로 이번 개시에서 녹음 경로는 열지 않는다. |
| 외부 STT 처리 | 외부 전사에 관한 문안과 실제 선택을 별도로 확인한다. 동의함이어도 이번에 전송하거나 전사를 켜지 않는다. |
| 외부 LLM·국외 처리 | 수기 자료도 외부 AI 재료가 될 수 있다는 적용 문안에서 실제 수령자·국가·처리 항목·목적·기간·거부 영향을 확인하고 실제 선택을 기록한다. 문안이나 필요한 동의·가림·활성화 조건이 확인되지 않으면 외부 AI 호출 없이 수기 경로를 유지한다. |
| 음성 원본 보유기간 | 해당 문안과 선택을 별도로 확인하되, 이번 제품에 원음이 저장되는 것처럼 안내하지 않는다. 업로드 불가를 개인 기기나 외부 파일 보관으로 우회하지 않는다. |

여섯 영역 모두에서 적용 문안의 버전·hash, 당사자/사례 연결, 실제 선택, 기록자와 시각을 확인할 수 있어야 한다. 화면에 보이지 않는 근거는 권한 있는 동의 기록 조회로 확인한다. **그 조회 경로가 실제 배포에서 제공되는지는 확인 필요**이며 화면의 체크 표시만으로 근거가 있다고 추정하지 않는다. 여섯 영역을 확인한다는 뜻은 모든 선택 항목의 동의를 강제한다는 뜻이 아니다. 이번 기록에 필요한 동의가 충족되지 않으면 그 기록은 시작하지 않는다.

### 4.2 첫 실제 저장 전에 남길 확인

- G01~G13이 같은 판정 대상 버전의 증거로 통과했고, 5장에 개시 승인자와 실제 확인자가 기록돼 있다.
- 본인 정상 계정으로 로그인한 실무자와 담당 사례가 확인된다. 친구의 정보를 누가 볼 수 있고 CSV 파일의 보관·전달 책임이 누구에게 있는지 당사자에게 설명한 문안과 실제 동의 기록이 있다.
- 운영 주소와 D1 `ccc`를 확인했다. preview, 합성 API, 개인 파일, 채팅 또는 Git에 실제 상담 자료를 넣지 않는다. 판정 증거에는 합성 자료와 비식별 상태·건수만 남긴다.
- 실제 적용할 보유기간, 동의 철회·파기 요청을 접수할 담당자, 보호·복구 검증 근거를 확인한다. 이 문서의 작성이 법률 검토나 기관의 실데이터 사용 승인을 대신하지 않는다.
- 첫 실제 입력 시작 시각과 북마크 시각을 구분할 수 있다. 북마크가 있다는 이유로 그 이후 상담까지 복구된다고 설명하지 않는다.
- 실제 자료가 생긴 뒤의 복원은 손실 판정이 필요하다는 점을 승인자와 실무자가 확인했다. 복원 전 업무 자료 보존, 동의·권한 철회와 파기 내역의 복원 후 대조 절차가 확인되지 않았다면 첫 입력을 시작하지 않는다.
- 친구의 음성으로 업로드 실패를 재현하지 않는다. 전사 OFF를 수기 저장 실패로 오인하지 않고, 원음 없이 상담 기록 저장·재조회가 가능함을 먼저 확인한다.
