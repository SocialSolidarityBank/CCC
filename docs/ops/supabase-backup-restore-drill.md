# Supabase 백업과 복구 연습 절차

- 대상: 기관 소유 Supabase 프로젝트에서 이 프로그램을 운영하는 기관 관리자 또는 설치 담당
- 상태: 절차 문서다. 이 문서를 쓴 시점에 연습을 실행하지 않았고, 실제 백업·복구·자원 생성은 0건이다
- 배경: E6-7(Community Cloud backup/restore 구현)은 이번 출고 범위 밖이다. 대신 Supabase 관리형 백업과 이 문서의 복구 연습 한 번을 증거로 인정한다(2026-09-15 Q 결정)

## 1. 무엇을 보호하는가

백업이 지켜야 하는 것은 네 가지다.

| 대상 | 담긴 것 | 표 |
| --- | --- | --- |
| 상담 기록 | 회차 기록, 목표, 일정, 액션, 플래그 | `sessions`, `goals`, `counseling_schedules`, `action_items`, `flags` 등 |
| 금고의 암호문 | 당사자 실명·연락처·계좌의 암호화된 값 | `participant_pii_vault` |
| 동의 기록 | 당사자 동의 여섯 영역의 결정과 이력 | `participant_consent_records` |
| 감사 기록 | 열람·변경·복호화·반출의 append-only 기록 | `audit_log` |

원음 파일은 상시 보관 대상이 아니다. 원음은 처리가 끝나면 서버가 즉시 삭제하고, 업로드 뒤 7일을 절대 상한으로 둔다(D85). 백업에 원음이 남아 있어야 한다고 요구하지 않는다.

## 2. 어떤 백업이 있는가

Supabase가 프로젝트 데이터베이스를 관리형으로 백업한다. 이 문서는 백업 방식이나 유료 여부를 단정하지 않는다. 연습 전에 기관 프로젝트의 Supabase 대시보드에서 아래를 직접 확인한다.

- Database > Backups 메뉴에 예약 백업이 보이는지
- Point in Time Recovery가 이 프로젝트의 요금제에서 켜져 있는지
- 복원 가능한 가장 오래된 지점이 언제인지

확인한 내용은 4절의 증거 파일에 적는다.

## 3. 복구 연습 절차

원칙 하나: 운영 프로젝트에 복구 결과를 다시 쓰지 않는다. 복원은 항상 별도의 보존용 프로젝트로 한다.

1. Supabase 대시보드에서 기관 프로젝트를 연다.
2. Database > Backups에서 복원할 백업 지점을 고른다. 고른 지점의 날짜와 시각을 적어 둔다.
3. 복원 대상으로 새 프로젝트를 만들거나, 대시보드가 제공하는 별도 프로젝트 복원 경로를 선택한다. 운영 프로젝트를 덮어쓰는 선택지는 고르지 않는다.
4. 복원이 끝나면 보존용 프로젝트의 SQL Editor 또는 Table Editor에서 아래 네 가지를 확인한다.

| 확인 | 방법 | 통과 |
| --- | --- | --- |
| 상담 기록 개수 | `sessions` 행 수를 운영 프로젝트와 대조 | 두 수가 같다 |
| 금고 행 개수 | `participant_pii_vault` 행 수를 대조 | 두 수가 같다 |
| 감사 기록 개수 | `audit_log` 행 수를 대조 | 두 수가 같다 |
| 스키마 버전 | `private.ccc_schema_migrations`의 마지막 마이그레이션 ID를 대조 | 운영과 같다 |

복원한 프로젝트에서 로그인이나 업무 화면을 열 필요는 없다. 이 연습은 데이터가 살아 있는지만 증명한다.

## 4. 통과 기준과 증거를 넣는 자리

연습이 끝나면 결과를 `artifacts/backup-restore-drill-<연습-날짜>.md` 파일 하나에 남긴다. 파일에는 아래만 적는다.

- 연습 일자와 실행한 사람
- 복원에 사용한 백업 지점(날짜와 시각)
- 3절 표의 네 가지 행 개수 대조 결과(운영 수와 복원 수)
- 대시보드에서 확인한 백업 방식과 PITR 여부

암호문, 당사자 이름, 연락처, 상담 내용 같은 개인정보는 증거에 적지 않는다. 개수와 날짜만 적는다. 네 가지 대조가 모두 같으면 통과이고, 하나라도 다르면 그 사실을 그대로 적고 통과로 보고하지 않는다.
