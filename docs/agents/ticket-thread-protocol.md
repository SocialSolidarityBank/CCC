# 티켓 스레드 규칙 (#ccc-tickets)

2026-07-26 Q 확정. **에이전트가 `#ccc-tickets`에 올리는 모든 티켓 소식**에 적용한다.

## 왜 이 규칙이 있나

지금까지는 티켓 내용을 통째로 채널에 흘렸다. 완료 기준·그릴링 질문 10개·근거 문서 경로가 한 덩어리로 쏟아지니, 팀원은 **자기가 무엇을 봐야 하는지 알 수 없었다.** 길이가 문제가 아니라 **층이 없는 것**이 문제다.

그래서 채널에는 얇은 한 줄만 남기고, 깊이는 스레드 안으로 밀어 넣는다.

## 규칙

### R1. 티켓 소식은 반드시 스레드로 올린다

채널 본문에는 **부모 글 하나만** 둔다. 상세는 전부 그 글의 댓글로 들어간다. 채널 타임라인에 두 번째 글을 남기지 않는다.

여러 티켓을 한 번에 알릴 때도 **티켓 1건 = 스레드 1개**다. 묶어서 올리면 다시 한 덩어리가 된다.

### R2. 부모 글은 `티켓 번호 + 쉬운 한 줄`

```
CCC-18 · 메뉴를 화면 위에서 왼쪽으로 옮깁니다
```

- 티켓 번호를 맨 앞에 둔다(검색·참조용)
- 한 줄은 **개발 용어 없이**, 그 티켓이 팀원의 무엇을 바꾸는지로 쓴다
- Linear 티켓 제목을 그대로 복사하지 않는다. 제목은 개발자용이고 이 줄은 팀원용이다

| 나쁨 | 좋음 |
| --- | --- |
| `CCC-18 12. 사이드바 셸 + 사업 워크스페이스 전환기 (상단 헤더 폐기)` | `CCC-18 · 메뉴를 화면 위에서 왼쪽으로 옮깁니다` |
| `CCC-17 참여자 정보 허브 승격 + PII 표시 (D31)` | `CCC-17 · 참여자 한 명의 정보를 모아 보는 페이지를 만듭니다` |

### R3. 첫 댓글만 읽어도 이해되게 쓴다

첫 댓글은 **비개발자가 30초 안에 읽고 끝낼 분량**이다. 이 세 가지만 담는다.

1. **무엇이 달라지나** — 쓰는 사람 입장에서
2. **왜 하나** — 지금 무엇이 불편한지
3. **나에게 무슨 영향이 있나** — 없으면 "없습니다"라고 쓴다

첫 댓글에 넣지 않는 것: 파일 경로, 함수 이름, 마이그레이션 번호, ADR·D번호, 완료 기준, 선행 티켓 관계.

**두 번째 댓글부터** 상세를 넣는다. 완료 기준, 기술 결정, 근거 문서, 선행 관계는 전부 여기다. 길어도 된다 — 접혀 있으니까.

### R4. 꼭 봐야 하는 것은 눈에 띄게 표시한다

강조는 **이모지 또는 인라인 코드**로만 한다. 굵게만 쓰면 다른 굵은 글씨에 묻힌다.

| 표시 | 뜻 | 언제 |
| --- | --- | --- |
| 🚨 | 지금 확인 필요 | 팀원이 안 보면 문제가 생기는 것 |
| ⚠️ | 주의 | 일하는 방식이 바뀜 |
| ✅ | 완료 | 티켓이 끝남 |
| 🔵 | 진행 중 | 착수 알림 |
| 🧭 | 방향 결정 | 그릴링·설계 결과 |
| `코드` | 그대로 눌러야 하는 값 | 티켓 번호, 명령어, 화면 이름 |

한 글에 강조는 **최대 2개**다. 셋이 넘으면 강조가 아니라 배경이 된다.

### R5. 올리기 전에 윤문한다

부모 글과 첫 댓글은 반드시 `humanize-korean` 스킬(`/humanize-korean:humanize-korean`)로 다듬는다. 상세 댓글은 선택이다.

윤문의 목적은 멋 부리기가 아니라 **짧고 쉽게** 만드는 것이다. 윤문 후에도 개발 용어가 남아 있으면 윤문이 아니라 번역이 덜 된 것이다.

## 올리기 전 점검 (5개 전부 예여야 한다)

- [ ] 채널 본문에 부모 글 1개만 있는가
- [ ] 부모 글 한 줄에서 개발 용어를 뺐는가
- [ ] 첫 댓글만 읽고 "그래서 나한테 뭐가 달라지지?"에 답할 수 있는가
- [ ] 강조가 2개 이하인가
- [ ] 윤문을 거쳤는가

하나라도 아니오면 올리지 않는다.

## 예시

**채널 본문(부모 글)**

```
🧭 CCC-18 · 메뉴를 화면 위에서 왼쪽으로 옮깁니다
```

**첫 댓글**

```
지금은 메뉴가 화면 맨 위에 가로로 있습니다. 이걸 왼쪽 세로 막대로 옮깁니다.

규칙은 하나입니다. 왼쪽은 "어디를 보는가", 오른쪽 위는 "무엇을 하는가".
그래서 상담 등록 같은 버튼은 왼쪽에 넣지 않습니다.

⚠️ 익숙한 자리가 바뀝니다. 바뀐 뒤에 못 찾는 메뉴가 있으면 알려주세요.
```

**두 번째 댓글부터**

```
완료 기준, 선행 티켓, 근거 문서(ADR-0014), 화면 계약...
```

## 채널 분리 (2026-07-26 Q 결정)

Linear의 Slack 연동 봇이 올리는 글에는 **이 규칙을 적용할 수 없다.** 티켓을 만들거나 코멘트를 달면 연동이 자동으로 이슈 전문을 흘리는데, **메시지 서식을 바꾸는 설정이 Linear에 존재하지 않는다**(2026-07-26 공식 문서 확인). 이벤트 단위 선택도 뷰(view) 구독에만 있고 팀 알림에는 없다.

그래서 형식을 고치는 대신 **채널을 갈랐다.**

| 채널 | 무엇이 오나 | 누가 쓰나 |
| --- | --- | --- |
| `#ccc-tickets` (`C0BKSEDMJ0Z`) | **에이전트가 이 규칙대로 만든 스레드만** | 사람이 읽는 곳 |
| `#ccc-linear` (Q가 공개 채널로 생성 예정) | Linear 자동 알림 전문 | 원본 확인·상태 변경 버튼용 |

### Linear에는 "채널 변경" 기능이 없다 (2026-07-26 API로 확인)

팀 CCC의 알림은 `slackPost` 연동(`Integration.team = CCC`)으로 걸려 있었고, Linear 뮤테이션 359개를 전수 확인한 결과 관련 조작은 **생성(`integrationSlackPost`)과 삭제(`integrationDelete`·`integrationArchive`)뿐이다.** 채널을 바꾸는 뮤테이션도, Linear UI의 채널 선택 항목도 없다 — 채널은 **연결할 때 Slack 인증 화면에서 고르는 값**이기 때문이다.

따라서 채널을 옮기려면 **끊고 다시 연결**해야 한다.

- 2026-07-26: 기존 연결(팀 CCC → `#ccc-tickets`, `d44e159b-…`)을 `integrationDelete`로 삭제 → Q가 `#ccc-linear` 채널 생성 후 재연결. **새 연결 `9982197f-e764-434e-905c-798166a45984`(`slackPost`, team=CCC, 2026-07-26T05:34Z) 확인 완료.**
- **2026-07-26 Q 육안 확인 완료 — 채널 분리 운영 시작.** 이후 티켓 소식은 이 규칙대로만 `#ccc-tickets`에 올린다.
- 참고: **대상 채널은 API로 검증할 수 없다.** `Integration`에 settings/채널 필드가 노출되지 않고, 에이전트 Slack 계정(`account`, `U0BKSMCEJLW`)이 `#ccc-linear`의 멤버가 아니라 채널 목록에도 안 잡힌다. 다음에 다시 검증할 일이 생기면 **그 계정을 채널에 초대**하거나 티켓 1건으로 육안 확인한다.
- `yellow` **채널은 공개로 만든다.** Slack에는 비공개→공개 전환 API가 없고(반대 방향만 있으며 그것도 Enterprise Grid 전용), 이 워크스페이스는 Enterprise가 아니다. 비공개로 만들면 나중에 공개로 바꾸려면 채널을 새로 파야 한다.
