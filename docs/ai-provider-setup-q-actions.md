## 0. 지금 어디까지 와 있나

코드는 **켤 수 있는 상태**까지 왔고, **아직 아무것도 OpenAI를 부르지 않는다.** 시크릿·스위치가 어느 환경에도 없어 호출 경로 전체가 잠겨 있다(fail-closed).

AI 기능은 두 갈래이고 준비물이 다르다.

| 갈래 | 무엇이 보이나 | 필요한 것 | 상태 |
|---|---|---|---|
| **내용 불일치 검출** | 브리핑 영역 ③ — 회차 간 말이 어긋난 곳을 양쪽 원문 그대로 나란히 | 시크릿 2개 + 스위치 1개 + 마이그레이션(**2026-08-19 운영 적용 완료** — 아래 4단계) | `green` 남은 것은 1~3단계 |
| **승인 대상 초안** | 핵심 한 줄, AI 제안 3개 | 위에 더해 **활성 사업자 등록** | `red` 등록할 경로가 코드에 없다 |

`red` **활성 사업자 등록이 왜 막혀 있나.** "지금 어느 모델·프롬프트 버전을 승인해서 쓰는가"를 DB에 못 박는 안전장치인데, 등록하는 **함수는 있으나 그것을 부르는 화면도 API 주소도 없다**(테스트에서만 호출된다). 이번 작업으로 생긴 문제가 아니라 원래 그 상태였다. **별도 티켓이 필요하다** — 그 전까지 초안 생성은 계속 막혀 있고, Q가 무엇을 세팅해도 열리지 않는다.

## 1. OpenAI — Q만 할 수 있는 일 `green`

- [ ] **1-1. API 키 발급** — OpenAI 플랫폼 대시보드 → API keys → 새 키 생성.
- [ ] **1-2. 결제 수단 + 월 사용 한도 설정** — 낮게 잡는다(예: $20). 상담 텍스트는 짧아 실제 비용은 훨씬 적고, 한도는 사고 방지용이다.
- [ ] **1-3. 쓸 모델 이름 확인** — 대시보드에서 계정이 실제로 쓸 수 있는 모델명을 확인해 알려준다.
  - 권장: **`gpt-5-mini`**. 상담 기록 정리·인용 대조는 무거운 추론이 아니고 비용이 훨씬 싸다.
  - 계정별로 열려 있는 모델이 달라 **에이전트가 대신 확인할 수 없다.**

`red` **키를 채팅창에 붙여넣지 않는다.** 대화와 로그에 남는다. 아래 2단계 경로면 값이 어디에도 남지 않는다.

## 2. Infisical에 보관 — Q `green`

조직 시크릿의 원본은 Infisical이다(CLAUDE.md §10). CCC 프로젝트에 **이름 그대로** 넣는다.

- [ ] **2-1.** `CODEX_API_KEY` ← 1-1에서 발급한 OpenAI 키

이름이 `OPENAI_…`가 아닌 이유: 코드가 이 사업자를 `codex`라는 별명으로 부르고, 그 별명이 설정 해시에 묶여 있다. 이름을 바꾸면 다른 안전장치가 어긋나므로 그대로 둔다(ADR-0027).

## 3. Cloudflare 등록 — 에이전트가 실행, Q는 승인만 `yellow`

값이 화면·로그에 닿지 않는 방식으로 넣는다. 셋이다.

| 이름 | 값 | 무엇인가 |
|---|---|---|
| `CODEX_API_KEY` | Infisical에서 주입 | OpenAI 키 |
| `AI_PROVIDER_CONFIG` | 아래 JSON | 어느 모델을 쓰는지 |
| `TEXT_AI_PILOT_ENABLED` | `1` | AI 텍스트 기능 On/Off 스위치 |

```json
{"registryVersion":"phase1.v1","providerId":"codex","adapterVersion":"v1","configVersion":"v1","model":"gpt-5-mini"}
```

앞 네 값은 코드가 요구하는 고정값이라 그대로 둔다. **`model` 한 칸만** 1-3에서 확인한 이름으로 바꾼다.

- [ ] **3-1.** Q 승인 → 에이전트가 미리보기 환경에 등록
- [ ] **3-2.** 확인 후 운영 환경에 등록

## 4. DB 마이그레이션 — 적용 완료 `green`

`green` **운영 D1 은 0035 까지 전부 적용 완료다**(2026-08-19 기준 미적용 0건). 0012~0029(텍스트 일감 큐 포함)는 2026-08-01(`artifacts/prod-migration-2026-08-01/`), 0030 은 2026-08-08(`artifacts/prod-migration-2026-08-08/`), 0032~0035(D69 구현분)는 v0.2.0 운영 배포에 앞서 2026-08-19 에 적용했다(`artifacts/prod-migration-2026-08-19/`). 이 절의 할 일은 남아 있지 않다.

- [x] **4-1.** 미리보기 DB에 적용
- [x] **4-2.** 운영 DB에 적용 — 2026-08-19 완료(위 기록)

### 4-1. 호출 ① v4 배포 때 재활성화 순서

`phase1.grounded.v4`와 `phase1.grounded-draft.v4`는 요약 3구획과 리스크 플래그
제안을 한 번에 올린 계약이다(D70, D72). 버전이 바뀌면 활성 설정 해시가 일부러
어긋난다. 구 v3 설정으로 생성이 계속되는 것을 막는 정상 동작이므로, 다음 순서를
바꾸지 않는다.

1. 레포의 미적용 D1 마이그레이션을 미리보기 DB에 먼저 적용한다.
2. v4 Worker를 미리보기에 배포한다. 이 시점에는 호출 ①이
   `ai_provider_unavailable`로 닫혀 있어야 한다.
3. 배포한 코드의 `canonicalAiProviderConfigHash`로 현재 모델과 설정 튜플의 새 해시를
   계산한다. 해시를 사람이 조립하거나 구 값을 재사용하지 않는다.
4. 같은 `adapterId`, `adapterVersion`, `configVersion`, `model`로 새 설정 행을
   등록하고 활성화한다. 기존 행을 수정하지 않는다.
5. 가상 녹음 회차로 생성해 `schemaVersion=phase1.grounded-draft.v4`, 구획 라벨,
   전사 인용 플래그 제안 또는 빈 배열을 확인한다.
6. 같은 순서로 운영 DB 마이그레이션, Worker 배포, 새 설정 등록과 활성화를 진행한다.

`red` 현재 설정 등록과 활성화는 게이트웨이 함수만 있고 운영자 API와 화면이 없다.
운영 경로가 생기기 전에는 테스트 밖에서 4단계를 실행할 수 없으므로, 그 상태에서
DB를 직접 고치지 않는다.

## 5. 켜는 순서 — 미리보기부터 `green`

- [ ] **5-2.** 가상 당사자로 상담 기록 2회차 저장 → 브리핑 영역 ③에 불일치가 뜨는지 확인
- [ ] **5-3.** 문제 없으면 운영에 적용

## 6. DeepSeek 폴백 — 결정이 먼저 필요하다 `red`

**설정만으로는 붙지 않는다.** Q 지시(2026-07-31)를 받아 조사한 결과, 두 종류의 장벽이 있다.

### 6-1. 기술 — 코드 작업이 필요하다

| 항목 | 지금(OpenAI) | DeepSeek | 영향 |
|---|---|---|---|
| 호출 주소 | `/v1/responses` | `/chat/completions` (`https://api.deepseek.com`) | 어댑터를 하나 더 만들어야 한다 |
| 출력 형식 강제 | `json_schema` + `strict: true` — **모양까지 보장** | `{"type":"json_object"}` — **JSON이긴 하나 모양은 미보장** | 검증 실패가 늘어난다(틀린 출력은 버려지므로 안전은 유지, 대신 결과가 안 나오는 회차가 생긴다) |
| 사업자 ID | `codex` 하나로 **코드에 못 박혀 있음** | — | 레지스트리·설정 해시 구조를 함께 손봐야 한다 |

즉 **티켓 하나 분량의 개발**이다. Q가 할 일은 아니고, 아래 6-2가 정리돼야 착수할 수 있다.

### 6-2. `red` 법적 — 이게 진짜 관문이다

이번 브랜치가 OpenRouter를 기각한 이유가 **"수령자가 여럿이면 국외 이전 고지(개인정보보호법 제28조의8)가 성립하지 않는다"** 였다. 법이 요구하는 고지 항목에 **받는 자의 이름·연락처**와 **이전되는 국가**가 들어 있기 때문이다.

DeepSeek를 붙이면 **미국(OpenAI) + 중국(DeepSeek), 두 나라 두 수령자**가 된다. 폴백이라 평소엔 안 쓰더라도, **동의서에는 "보낼 수 있다"고 적혀 있어야 한다** — 실제로 보낸 적이 있느냐가 아니라 보낼 수 있는 구조인가가 기준이다.

관련 문서 3종(`docs/consent/`)은 모두 **단일 수령자**를 전제로 쓰여 있고, 법률 검토 트랙은 D46으로 동결 중이다.

**Q의 선택지 (하나 고르면 그대로 진행한다)**

| # | 선택 | 뜻 | 에이전트 권고 |
|---|---|---|---|
| A | **만들되 끄고 둔다** | 코드는 넣되 기본 비활성. 동의 문안에 "제2 사업자(중국)" 항목을 미리 반영하고, 켜는 것은 법률 검토 재개 시점으로 미룬다 | **권장** — 지금 쓸 일이 없고, 나중에 필요할 때 코드가 이미 있다 |
| B | 지금 켠다 | 폴백이 실제로 동작한다 | 동의 문안·국외 이전 고지를 **먼저** 손봐야 한다. 문안은 아직 DRAFT 배지 상태다 |
| C | 만들지 않는다 | OpenAI 단일 유지 | 가장 단순하다. 장애 시 그 회차의 AI 정리가 다음 영업일로 밀린다(D8 SLA 안이고, 브리핑은 수기 메모로 계속 동작한다) |

- [ ] **6-a.** A / B / C 중 선택
- [ ] **6-b.** (A·B 선택 시) DeepSeek 키 발급 + Infisical에 `DEEPSEEK_API_KEY` 저장 — 이름은 확정 후 안내
- [ ] **6-c.** (A·B 선택 시) 동의 문안에 제2 수령자·국가 반영 여부 결정

## 8. 세팅해도 안 되는 것 (기대치 조정)

- **승인 대상 초안**(핵심 한 줄·AI 제안)은 위 티켓 전까지 열리지 않는다. 1~5단계를 다 해도 그렇다.
- **법률 검토 동결(D46)은 이 세팅으로 풀리지 않는다.** L1(동의서 확정본)·L3(전자서명)·L4(수령자 명시)는 그대로 잠겨 있고, 실제 당사자 대상 운영 개시 전에 재개해야 한다.
- **보존·파기 파이프라인은 여전히 미구현**이다(CLAUDE.md 8장). AI 세팅과는 별개 트랙이지만, 실서비스 개시 전 필수라는 점은 같다.

## 9. 리스크 플래그 제안 품질 평가 — 수동 `yellow`

D72 리스크 플래그 제안이 실제 사업자에서 어떻게 동작하는지 보는 **수동 평가**다. CI에 없다. 합성 상담 전사 30건(유형 6종 × clear 2 · ambiguous 2 · trap 1)을 실제 Codex 어댑터로 돌려, `validateAiProviderOutput` 검증을 거쳐 유형별 정밀도·재현율과 실패 사례 id를 보고하고, 기대 판정과 어긋나면 0 아닌 종료 코드를 돌려준다.

```bash
# 실제 호출 — 아래 3개 환경값 필요 (2~3단계 값 + 운영 스위치)
AI_PROVIDER_CONFIG='{"registryVersion":"phase1.v1","providerId":"codex","adapterVersion":"v1","configVersion":"v1","model":"gpt-5-mini"}' \
CODEX_API_KEY='...' EXTERNAL_AI_CALLS_ENABLED=1 \
pnpm --filter @ccc/api run eval:flags

# 네트워크 없이 파이프라인 점검 (설정·키 불필요, 픽스처 어댑터)
pnpm --filter @ccc/api run eval:flags -- --preview
```

- 구현: `apps/api/eval/` (데이터셋 `flag-eval-cases.ts`, 점수·보고 `flag-eval-core.ts`, 실행기 `run-flag-eval.ts`)
- 데이터셋·점수 계산의 결정적 테스트(네트워크 없음): `apps/api/test/flag-eval.test.ts` — CI의 일반 `pnpm test`에 포함된다.
- 데이터셋은 전부 합성·가명 처리본이고 실명·연락처·계좌가 없다(R3).
- 기대 판정은 D72 민감도 2단을 그대로 따른다. 위기 발언과 폭력·착취 피해는 애매한
  사례도 제안이 기대되고, 나머지 4종은 명확한 사례만 제안이 기대된다. 함정 사례는
  6종 모두 제안이 없어야 한다.
