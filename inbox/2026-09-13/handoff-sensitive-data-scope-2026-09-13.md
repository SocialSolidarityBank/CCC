## 1. 한눈에 보는 결론

1. 릴레이어는 대화를 민감/비민감으로 스스로 나누지 못한다. 자유 글은 한 통로로 들어가 같은 규칙을 탄다. 그래서 범위는 상담 한 건 단위가 아니라 밸브 세 개(기관 설정, 메모 작성 규칙, 녹음 여부)로 미리 정한다.
2. 경계를 가르는 진짜 기준은 "문장을 누가 고르느냐"다. 수기 메모는 실무자가 고르므로 범위를 지킬 수 있다. 전사 기록은 당사자가 말한 전부라서 지킬 수 없다.
3. 가장 넓게 쓸 수 있는 조합은 STT 끄고 AI 켜기다. AI 가치를 살리면서 범위를 지킬 수 있는 유일한 자리다.
4. 가림 처리(마스킹)는 법정 민감정보를 없애지 못한다. 이름과 주소만 찾는다. 건강, 피해 경험, 기관 이름은 그대로 나간다.
5. Azure STT는 국외가 아니다. 코드에 서울 리전(Korea Central)이 상수로 고정되어 있다. 다만 가리기 전 원음이 기관 밖으로 나가는 것은 그대로다.
6. 저장 쪽에서는 등록 항목 8칸만 앱 암호화된다. 수기 메모와 요약 같은 자유 글은 평문으로 쌓인다.

## 2. 데이터가 가는 길은 세 층이다

| 층 | 뜻 | 여기에 해당하는 것 |
|---|---|---|
| 기관 안 | 기관 PC를 벗어나지 않음 | 로컬 STT(Qwen3-ASR), 마스킹 처리, 금고 암호화 |
| 국내 외부 위탁 | 기관 밖 회사 서버, 서버는 한국 | Azure Speech Korea Central, Supabase(Community Cloud) |

동의 6영역 중 "외부 STT"와 "외부 LLM과 국외 처리"가 따로 있는 것은 이 구분과 맞는다. 문구만 고친다. Azure는 "국외"가 아니라 "외부 위탁, 국내 처리"다.

## 3. 설정 조합별 가능한 대화 범위

| 조합 | 밖으로 나가는 것 | 다룰 수 있는 대화 범위 |
|---|---|---|
| STT 끔 + AI 끔 (설치 기본값) | 없음 | 제한 없음. 기록 최소화 원칙만 지키면 됨 |
| STT 끔 + AI 켬 | 가린 메모 글 | 넓음. 실무자가 적는 방식을 통제할 수 있음. 4장 규칙으로 관리 |
| STT 로컬 + AI 켬 | 가린 전사 글 | 중간. 원음은 기관 안에 남지만 전사 글은 통제 안 된 발화 전체 |
| STT Azure + AI 켬 | 가리기 전 원음(국내) + 가린 전사 글(국외) | 좁음. 상담에서 나온 모든 말이 그대로 기관 밖으로 나감 |

권하는 기본값: 두 번째 조합. Azure는 문서상 선택지로만 두고, 시연과 파일럿에서는 켜지 않는다.

## 5. 지금 가림 처리(ner-mask-v1)가 못 지우는 것

가림 처리는 사람 이름과 주소만 찾는다. 아래는 그대로 나간다.

- 기관 이름: OO병원, OO공장, OO교회, OO학교, OO저축은행
- 질병과 치료 서술: 입원, 투석, 정신과 진료
- 피해 경험 서술: 폭력, 성폭력
- 범죄 이력 서술
- 나이와 지역 구간화 (S6가 요구한 v2 기능. 코드는 아직 v1)

"OO병원 정신과 다녀왔다"는 이름을 가려도 건강정보가 남는다. 법정 민감정보는 가림으로 없어지지 않는다.

### AI 처리 시 민감정보 목록과 대안

| 종류 | 지금(v1) | 대안 |
|---|---|---|
| 직접 식별자 (이름, 전화, 주소, 생년월일, 계좌) | 이름, 주소만 가림 | 번호 가명 `[인명1]`, `[가족1]`. 대응표는 금고와 같은 등급으로 보관. 주민번호, 계좌는 글자 규칙 검사(정규식)로 추가 차단 |
| 준식별자 (나이, 시군구, 가족 구성, 직업) | 안 가림 | 나이는 5세 구간, 지역은 시도까지 (S6 v2) |
| 기관 이름 | 안 가림 | 종류 표시 `[의료기관]`, `[직장]`, `[종교시설]`, `[금융기관]` |
| 법정 민감정보 | 안 가림, 가려도 남음 | (a) 실무자는 종류만 적기. (b) 동의 문안에 "가린 뒤에도 건강, 피해 경험은 남아 전송될 수 있다" 명시 |
| 신용정보 (채무 금액, 채권자, 연체) | 안 가림 | 금액은 구간, 채권자는 `[금융기관]`. 상세는 인테이크 반복표에만 두고 AI에는 안 보냄 |
| 제3자 | 이름만 가림 | 관계 가명 + "제3자의 민감한 내용은 필요한 만큼만" 운영 지침 |
| 날짜 | v2는 연월로 자름 | 상대 날짜("상담일 +12일")로 기한 간격 유지 |
| 위기 발언 (자해, 폭력) | 그대로 나감 | 가릴 수 없음. 나가는 것이 오히려 목적(위험 신호). 동의 문안에 명시하고 AI 판정 금지(R5) 유지 |

처리 순서 대안 세 가지:
1. 구조화 값 먼저. 위기도, 영역, 할 일 상태, 인테이크 선택값은 가림 부담이 없다. AI 재료의 기본은 이것으로 깔고 자유 글은 위에 얹는다.
2. 보내기 전 2차 검사. 가린 결과를 한 번 더 훑어 전화번호나 계좌 패턴이 남으면 전송을 막는다 (fail-closed와 같은 원칙).
3. 로컬 LLM 선택지. 법정 민감정보가 많은 사업(정신건강, 폭력 피해)은 외부 AI 대신 기관 PC의 작은 모델로만 처리하는 길을 열어 둔다. 지금이 아니라 D87 사업별 확인 항목에 넣는다.

## 6. 저장 암호화 규칙 (Supabase)

Supabase 쪽 사실: 프로젝트는 기본으로 저장 시 암호화된다(디스크 수준). 열 단위 암호화 기능 pgsodium은 Supabase가 새로 쓰지 말라고 안내하며 곧 없앨 예정이다. Vault는 API 키 같은 비밀값 용도다. 즉 상담 기록 암호화는 릴레이어가 직접 해야 한다.

| 규칙 | 내용 | 지금 상태 |
|---|---|---|
| R1 두 겹 | Supabase 기본 암호화는 "디스크를 통째로 훔쳐가도 못 읽게" 하는 수준. 관리자 화면, 서비스 키, 백업 파일로 들어오면 그대로 보임. 그래서 앱 암호화(릴레이어가 저장 전에 스스로 잠그는 것)가 따로 필요 | 금고 8칸만 앱 암호화 |
| R2 범위 | 앱 암호화 대상 = 금고 8칸 + 자유 글 전부(수기 메모, AI 정리, 전사 기록, 인테이크 자유 글, 목표 문장, 위험 신호 인용문) + 녹음 파일 | 자유 글, 녹음 파일은 평문 |
| R3 키 위치 | 열쇠는 DB 밖. 기관 PC의 Agent 환경 변수나 OS 키 저장소. Supabase Vault에도 넣지 않는다 | 확인 필요 |
| R4 키 버전 | 암호문 옆에 `key_version` 칸. 열쇠를 바꿔도 옛 자료를 풀 수 있게 | 없음 |
| R5 AAD | 암호화할 때 "이 행의 ID + 칸 이름"을 함께 묶는다. A 당사자의 암호문을 B 칸에 붙여 넣는 바꿔치기가 막힘 | 없음 |
| R6 검색 | 이름 검색이 필요하면 검색용 지문(HMAC 블라인드 인덱스)을 따로 만든다 | 확인 필요 |
| R7 파일 | 녹음 파일은 이미 선언된 `FILE_ENC_KEY`로 실제 잠근 뒤 저장소에 올린다 | 선언만 있고 사용 안 함 |
| R8 사본 | 백업, 내보내기, 복원 파일도 암호문 상태 유지. 푸는 곳은 Agent뿐 | P09와 연결 |
| R9 로그 | 서버 로그, 오류 메시지에 평문 금지 | 확인 필요 |
| R10 모드 | Local Single, Local Office도 같은 규칙. 로컬이라서 안 잠그는 예외 없음 | 확인 필요 |

제출 설명서 문구: "Supabase 기본 암호화 + 등록 항목 8종 앱 암호화 완료. 자유 글과 녹음 파일 앱 암호화는 구현 중. 지금은 접근 권한과 감사 기록으로 보호."

## 7. STT 현황

### 로컬 STT
- 구현됨. 격리된 Python 환경에서 `Qwen/Qwen3-ASR-1.7B`와 `Qwen3-ForcedAligner-0.6B` 고정 가중치 사용. 외부 호출 없음.
- 원음이 기관 밖으로 안 나가는 유일한 STT 경로.
- 남은 것: 고령자, 사투리 화자 품질 미측정(1차 점검 2-7), 권장 사양과 처리량 미측정(T04).

### Azure STT (코드 확인 결과, 2026-09-13)
- `apps/pipeline/ccc_pipeline/azure_stt.py` 20~24행: 전사 주소와 인증 주소 모두 `koreacentral.api.cognitive.microsoft.com` 상수. 언어 `ko-KR`, 화자 최대 2명 고정.
- 환경 변수로 바꿀 수 있는 값은 `AZURE_SPEECH_KEY` 하나. 리전이나 주소를 바꾸는 설정은 없다.
- 엔진 ID `azure-speech-koreacentral`. 서버(`gateway.ts`, `capabilities.ts`, `request-handler.ts`)와 계약(`stt-readiness.ts`)이 이 ID가 아니면 거부한다. 다른 리전으로 바꾸면 워커가 아니라 서버가 막는다.
- CLAUDE.md, S13, PRD, pipeline README 모두 "koreacentral, ko-KR, api-version 2025-10-15 고정, 다른 리전이나 공급자 전환 없음". 코드와 문서 일치.
- 2026-09-09 Korea Central S0 계정에 비민감 합성 음성을 보내 실제 응답 받음. 연결 확인이지 품질 검증은 아님.
- STT 시험 화면(`stt-trial-page.tsx` 228행)은 "koreacentral, 2025-10-15. 원본 파일이 외부로 나갑니다" 표시. "국외"가 아니라 "외부"로 적혀 있어 정확.
- 없는 것: 리전 고정을 검증하는 자동 시험(`test_azure_stt.py`에 koreacentral 확인 줄 없음). 실제 계정 가격과 상담 음성 정확도(ADR-0040 후속 과제).
- Azure Speech는 자원을 만든 리전 밖에서 데이터를 저장하거나 처리하지 않는다(공식 문서). 따라서 서울 리전 고정이면 원음은 국내에서만 처리된다.

### Azure 사전 가림은 안 된다
- 소리가 글자로 바뀌기 전에는 기계가 어느 부분이 이름인지 모른다. 가림은 글 위에서만 된다.
- "로컬 1차 전사 → 이름 나온 구간 무음 처리 → Azure 2차 전사" 방식은 기술적으로는 가능하지만 권하지 않는다. 로컬이 못 잡은 이름은 그대로 나가고(로컬이 부정확해서 Azure를 쓴다는 전제와 모순), 무음 구간이 늘수록 Azure 품질도 떨어지고, 건강이나 피해 서술은 이름이 아니라 못 지우며, 두 전사본을 시간축으로 맞추는 작업이 크다.

### 권하는 2단계
1차 로컬 전사(원음은 기관 안) → 가림 → 2차 LLM 교정(가린 글의 오탈자와 끊긴 문장을 문맥으로 보정) → 요약과 대조

원음은 한 번도 밖으로 나가지 않고, 나가는 것은 이미 가린 글뿐이며, 읽기 품질은 로컬 전사만 쓸 때보다 올라간다. 비용은 전사 글 길이만큼의 토큰이라 요약에 쓰는 양과 비슷하다. 이번 제출 범위에는 넣지 않고 "설계 확정, 구현은 이후"로 설명서에 적는다.

### 국내 처리를 할 수 있는 다른 선택지 (참고, 결정 아님)

| 선택지 | 회사 | 처리 위치 | 비고 |
|---|---|---|---|
| 로컬 STT | 없음(오픈소스) | 기관 안 | 이미 구현 |
| Azure Speech | Microsoft(미국) | 서울 리전 | 이미 구현. 외국 회사의 국내 리전 |
