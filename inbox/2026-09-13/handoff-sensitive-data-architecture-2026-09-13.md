# 릴레이어 민감정보 처리 구조: 최종 구현 형태 (2026-09-13)

- 이 문서의 쓰임: 내부망을 만들 수 없는 기관이 릴레이어를 쓸 때, 상담 자료를 어디에 두고 어디로 보내는지를 확정하고, 그대로 구현할 수 있게 작업 목록으로 옮겼다.
- 성격: 팀 결정 기록과 구현 인계다. 법적 판단이 아니다. 법률 검토가 필요한 항목은 8장에 따로 모았다.
- 정본 관계: ADR-0040, ADR-0041(D76~D83), D84~D87, S13, `docs/ai-provider-setup-q-actions.md`, `apps/community-cloud/RUN.md`와 충돌하지 않는다. 이 문서는 그 결정들 위에 "왜 이 조합이 최선인지"와 "무엇을 더 해야 하는지"를 얹는다.
- 조사 기준일: 2026-09-13. 웹 조사 결과의 출처는 7장에 있다.
- 작업 원칙: 코드 식별자와 ADR 용어는 바꾸지 않는다. 화면 문안, 매뉴얼, 동의 문안, 결정 기록만 바꾼다(D-2026-09-12-02).

---

## 1. 한 줄 결론

**저장은 서울, 음성은 서울에서 즉시 폐기, AI 요약은 가린 글만 국외로 보낸다. 지금 베타 기본형이 이 구조다. 바꿀 것은 구조가 아니라 문안, STT 기본 외부 경로, 확인 절차다.**

## 2. 누구를 위한 구조인가

| 항목 | 대상 기관의 모습 | 근거 |
|---|---|---|
| 기술 인력 | 기술 관리자 없음. AI 에이전트나 매뉴얼로 설치 | D86 ⑧ |
| 장비 | 서버 없음. 업무 PC는 있음 | 현장 조사 |
| 접속 | 여러 장소에서 접속 | D76 Community Cloud 대상 |
| 예산 | 월 수만 원에서 십수만 원 | Supabase Pro 월 25달러 + 사용량, OpenAI 월 한도 20달러 안팎 |
| 자료 | 건강, 폭력 피해, 채무 같은 민감정보 포함 | 개인정보보호법 제23조, 신용정보법 가능성(P04) |
| 발주처 | 대부분 민간 위탁이나 자체 사업. 공공 클라우드 요구는 소수 | D87 |

이 조건에서 "기관 안에서 다 처리"는 서울아산병원처럼 직접 만들 수 있는 곳만 가능하다. "네이버 공공 존"은 어댑터가 없고 비용이 더 든다. 그래서 답은 국내 리전 클라우드와 가림 처리의 조합이다.

## 3. 최종 구현 형태

### 3-1. 자료가 가는 길

| 자료 | 어디에 | 누가 소유 | 밖으로 나가는 것 | 국외 이전인가 |
|---|---|---|---|---|
| 상담 기록, 목표, 할 일 | 기관 소유 Supabase 서울 프로젝트 (AWS 서울 위) | 사용기관 | 없음 | 아님 (서울에서 전부 처리. 다만 처리방침에는 예방 차원으로 기재 권고) |
| 이름, 연락처, 주소 (PII 금고) | 같은 Supabase, 별도 표, AES-256-GCM 암호화 | 사용기관 (키도 기관) | 없음 | 아님 |
| 녹음 원음 | 기관 Supabase 비공개 Storage에 임시 보관 → Azure Speech 서울로 1회 전송 → 처리 뒤 즉시 삭제 | 사용기관 | 원음 그대로 (가리기 전) | 물리적으로는 아님 (서울 리전, 보관 없음). 계약 상대 법인과 원격 접근은 법률 확인 |
| 전사 텍스트 | 기관 PC의 Agent가 가림 처리 → Supabase 저장 | 사용기관 | 없음 | 아님 |
| AI 요약 재료 | 가림 처리된 텍스트만 OpenAI로 전송, store:false | 사용기관 (키도 기관) | 이름, 연락처, 주소를 지운 글 | 국외 이전임. 고지와 동의 필요. 오남용 로그 최대 30일 가능 |
| AI 초안 | Supabase 저장, 실무자 승인 뒤 공식 기록 | 사용기관 | 없음 | 아님 |

### 3-2. 설정값으로 보면

| 축 | 값 | 설치 직후 | 켜는 조건 |
|---|---|---|---|
| 저장 모드 | Community Cloud (Supabase 서울) | 고정 | 서명된 install manifest |
| `sttMode` | `azure` 권장 (실측 통과 뒤) | `off` | S13 후속 품질 단계 통과 + Q 승인 + 기관 관리자 명시 선택 + 외부 STT 별도 동의 |
| `sttEngine` | `azure-speech-koreacentral` | `null` | 위와 같음 |
| `llmMode` | `openai` | `off` | `AI_PROVIDER_CONFIG` + `CODEX_API_KEY` + `EXTERNAL_AI_CALLS_ENABLED=1` + `TEXT_AI_PILOT_ENABLED` + 활성 사업자 등록 + 외부 LLM 동의 |
| Agent PC | 기관 업무 PC 1대 | 없음 | AI를 켜면 필수. 2차 마스킹 NER이 여기서 돈다(D77) |
| OpenAI 모드 | Standard De-identified | 고정 | ZDR은 Enhanced로 별도 |

### 3-3. 왜 STT 기본 외부 경로를 Azure 서울로 두는가

| 비교 항목 | 로컬 Qwen | Azure Speech 서울 | CLOVA Speech |
|---|---|---|---|
| 원음이 밖으로 나가나 | 안 나감 | 나감 (서울 리전) | 나감 (한국 리전) |
| 파일 보관 | 없음 | 없음 (메모리 처리, 처리 즉시 폐기) | 저장소 기록 7일 (재확인 필요) |
| 학습에 쓰나 | 안 씀 | DPA로 금지 | 약관 확인 필요 |
| 기관 PC 부담 | 사양 있는 PC 필요, 최소 사양 미측정 | 없음 | 없음 |
| 화자 구분 | 있음 | 있음 (2명, 처리 뒤 신호 폐기) | 있음 |
| 릴레이어 어댑터 | 있음 | 있음 | 없음 |
| 공공 존 | 해당 없음 | 하등급만 (개인정보 시스템 불가) | 장문 인식의 공공 존 제공 여부 미확인 |

내부망을 못 만드는 기관은 사양 있는 PC도 없을 가능성이 크다. Azure 서울은 "국내 리전 + 보관 없음 + 학습 미사용"으로 CLOVA와 같은 수준이면서 어댑터가 이미 있다. 그래서 실측 통과를 전제로 Azure를 기본 외부 경로로 둔다. CLOVA는 공공 존 요구가 있을 때의 대체재다.

### 3-4. 기관 유형별 조합

| 기관 상황 | 저장 | STT | AI | 무엇을 안내하나 |
|---|---|---|---|---|
| 기본 (민간 위탁, 자체 사업, 업무 PC 1대 가능) | Supabase 서울 | Azure 서울 (실측 뒤) | OpenAI 가림 텍스트 | 이 문서의 최선책 |
| 업무 PC도 여유 없음 | Supabase 서울 | 끔, 수기 | 끔 | 수기 기록은 즉시 공식. 톺아보기와 회차 목록은 AI 없이 동작(D-2026-09-12-22) |
| 계약서가 국외 처리를 금지 | Supabase 서울 | 끔 (PC 있으면 로컬 Qwen) | 끔 | D87 "기관 안" 경로. 국내 LLM(CLOVA Studio)은 후속 |
| 발주처가 국내 공공 클라우드나 보안 검증을 요구 | 네이버 공공 존 PostgreSQL | CLOVA (공공 존 확인 뒤) | CLOVA Studio | 후속 어댑터. 지금은 비활성 + 준비 중 안내(ADR-0045 결정 5) |

## 6. 이 조합이 왜 안전한가: 선례 대조

| 규제기관이나 현장이 본 것 | 선례 | 릴레이어 상태 |
|---|---|---|
| 해외 LLM에 텍스트를 보내는 구조가 성립하나 | SKT 에이닷: 자체 STT + MS 클라우드 요약. 개인정보위 2024년 점검에서 구조 자체는 문제 삼지 않음 | 같은 구조 |
| 국외이전 고지가 정확한가 | 에이닷: 고지 일부 누락으로 제28조의8 근거 미비 지적. 점검 중 고지 구체화 | 빈 칸. A1이 채움 |
| 접속기록이 남는가 | 에이닷: 미보관으로 시정권고 | 감사 로그 있음. A6이 보강 |
| 텍스트를 얼마나 오래 두나 | 에이닷: 보관 기간 최소화 개선권고 | 원음 즉시 삭제, 7일 절대 상한 |
| 비식별을 하나 | 에이닷: 비식별 강화 개선권고 | 가림 처리 게이트웨이, fail-closed 7코드 |
| 복지 현장이 국내 클라우드 LLM으로 건강 발화 처리를 받아들이나 | 네이버 클로바 케어콜: 128개 시군구, 건강 발화와 기억 기능 | 1층(국내 처리) 선례. 공공형 프로필의 근거 |
| 가장 민감한 상담은 어디서 처리하나 | 서울아산병원: 정신건강의학과 포함 16개 과, 자체 구축 | Local Office와 로컬 Qwen이 같은 자세. 선택지로 유지 |
| 가명처리 + 국내 저장이 규제기관 눈높이인가 | 금융위 망분리 로드맵: 가명처리된 신용정보의 생성형 AI 처리 허용, 클라우드 처리 시 국내 설치 | 가림 처리 + Supabase 서울이 같은 패턴 |

## 9. 감수하는 약점

| 약점 | 완화 |
|---|---|
| OpenAI 오남용 로그 30일은 없앨 수 없음 | 문안에 정확히 적음. ZDR은 Enhanced 경로로 별도 승인 |
| Azure는 원음이 나감. 로컬 Qwen보다 반출 범위가 큼 | 외부 STT 별도 동의 유지. STT 끄기가 기본값. 원하는 기관은 PC를 갖추고 로컬 Qwen |
| 해외 사업자 두 곳(AWS 위 Supabase, Azure)과 국외 한 곳(OpenAI)에 기댐 | 조건 변경 시 재확인 절차(P14). 자동 전환 없음(D8) |
| AI를 켜면 기관 PC 1대가 필요함 | 안내에 명시. PC 없으면 AI 끄고 수기 |
| Azure 실측이 끝날 때까지 STT는 꺼져 있음 | 수기 기록이 즉시 공식 기록이므로 업무는 멈추지 않음 |
