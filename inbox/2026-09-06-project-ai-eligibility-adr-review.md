# 사업별 데이터·STT·LLM 사용 조건: ADR 검수 요청

- 작성일: 2026-09-06
- 상태: **검수용 제안. 새 ADR 결정이나 법적 적합성 승인 아님**
- 목적: 사업 담당자에게 묻는 핵심 질문 8개와 답변별 CCC 처리 결과를 검수하고, 적절한 내용을 ADR에 기록할 수 있게 한다.
- 대상: 기관 전체가 아니라 **사업명 + 연도 + 계약 범위 + 처리 경로**별 판단
- 사용자 요청: 앞선 질문 세트와 답변별 결과를 문서화해 작업 에이전트의 ADR 검수용으로 진입 폴더에 둔다.
- 이번 작업 범위: 이 문서만 추가한다. 기존 ADR 수정, 새 번호 발급, 코드 구현, 운영 설정 변경, 외부 티켓 게시와 커밋은 하지 않는다.

## 1. 검수자가 먼저 알아야 할 결론

사업 유형만으로 모델을 고르지 않는다. 사업별 계약·법적 처리 근거로 허용 경로를 좁힌 뒤, 실제 서비스의 계약·상품·API·모델·리전·보관 조건과 대조한다.

최종 판정은 아래 세 가지를 따로 내린다.

1. **법적·계약상 허용 여부**: 권한 있는 담당자의 확인과 근거 문서가 있는가?
2. **제품 설계상 지원 여부**: 현재 ADR과 계약이 그 경로를 허용하는가?
3. **구현·운영 준비 여부**: 차단, 설치, 보안, 삭제·복구가 실제 검증됐는가?

세 가지 중 하나라도 미확인이면 곧바로 사용 가능으로 표시하지 않는다. 아래의 ‘후보’는 이 세 조건을 모두 통과했다는 뜻이 아니다. 이 문서는 법률 의견서가 아니며, 모델을 자동 추천·활성화하는 기능 명세도 아니다.

### 우선 검수할 충돌 4건

1. **원음은 로컬, 나머지는 Supabase라는 혼합 경로**: 법적 요구에서 도출될 수 있지만 ADR-0041의 Community Cloud 원음 저장은 Supabase private Storage다. 기존 옵션처럼 안내하면 안 된다. 원음 반출 금지라면 Local 모드를 검토하거나 별도 설계 변경이 필요하다.
2. **STT 허용과 엔진 활성화는 다르다**: ADR-0041 D77의 후보 축은 `off/local/azure`다. 실행계획은 승인 registry가 비어 있어 STT-G1~STT-G3 결정 전에는 `local`과 `azure` 모두 비활성이라고 명시한다. ‘Azure는 법적으로 허용되면 즉시 사용’으로 쓰지 않는다.
3. **법적 민감정보와 제품 문안의 범위가 다를 수 있다**: S7 문안은 건강·채무·주거를 함께 언급한다. 채무·주거정보 전체를 법적 민감정보로 자동 분류하지 말고, 법적 범주와 제품상 보호 범주를 검수한다. 승인 문안을 몰래 고치지 않는다.
4. **사업별 정책과 기존 승인 단위의 차이**: ADR-0044는 사업별 확인을 요구하지만 사업별 차단·provider 선택 기능의 구현 완료는 확인하지 않았다. 기관·설치 단위 설정을 여러 사업이 공유할 때 느슨한 승인이 다른 사업에 번지지 않는지 확인한다.

## 2. 현재 레포의 기준과 근거

| 영역 | 확인한 설계·코드 | 근거 |
|---|---|---|
| 배포 | Community Cloud는 기관 소유 Supabase, Local Single은 개인 PC, Local Office는 내부망 서버 | [ADR-0041 D76](../docs/adr/0041-one-core-three-deployment-modes.md) |
| STT | `off`, `local`, `azure`. 설치 기본 `off`, 엔진 승인 전 `sttEngine=null`. faster-whisper·Azure는 승인 완료 엔진으로 단정하지 않음 | [ADR-0041 D77](../docs/adr/0041-one-core-three-deployment-modes.md), [실행계획](../CCC_OPEN_PILOT_PLAN.md)의 ApprovedSttEngineId와 STT 게이트 |
| LLM | `off`, `openai`. Managed AI, CLOVA, RTZR, 로컬 LLM은 범위 밖. 자동 provider 전환 없음 | [ADR-0041 D77](../docs/adr/0041-one-core-three-deployment-modes.md) |
| 외부 전송 | Azure에는 마스킹 전 원음, OpenAI에는 Agent가 마스킹한 AI Packet을 전달하는 설계 | [ADR-0041 D81](../docs/adr/0041-one-core-three-deployment-modes.md) |
| OpenAI 코드 | `store: false` 설정 존재. 이것만으로 업체의 모든 로그·보관이 없음을 증명하지 않음 | [ai-provider.ts](../apps/api/src/ai-provider.ts) |
| 동의 | 수집·이용, 민감정보, 녹음, 외부 STT, 외부 LLM·국외 처리, 원음 보유기간의 6영역. 사건에 supportCaseId와 공급자·국가·목적·문안 버전 등을 연결하는 계약 | [S7](../docs/specs/S7-consent-six-domains.md) |
| 국내 처리 | 서울 DB가 모든 처리의 국내 한정을 뜻하지 않음. Edge는 전 세계 분산이며 region evidence와 잔여 국외 처리 검토 필요 | [S11 §3.1](../docs/specs/S11-supabase-edge-template.md) |
| 원음 | 처리 후 즉시 삭제, 업로드부터 7일 절대 상한, 실제 첫 처리 기회 후 24시간과 절대 상한 중 빠른 기한. 동의·건강한 Agent 입장 조건 | [ADR-0043](../docs/adr/0043-audio-admission-seven-day-hard-cap.md) |
| 공공사업 | 사업별 계약·보안·외부 처리 미확인은 해당 사업 실데이터 도입 보류. 세 모드 합성 개발은 계속 | [ADR-0044](../docs/adr/0044-public-project-admission-and-cloud-selection.md) |
| 구현 성숙도 | Supabase bootstrap은 `plan` 외 작업을 OPERATION_UNSUPPORTED로 거부. 설치 계약과 완성된 설치기는 다름 | [bootstrap.mjs](../scripts/supabase/bootstrap.mjs), [S12](../docs/specs/S12-install-release.md) |

`inbox/`에 있는 ADR 사본보다 위 `docs/adr/` 원본을 먼저 읽는다. 검수 시 최신 변경을 다시 확인한다. `docs/specs/S14-legal-gates.md`는 앞선 확인에서 없었으므로 그 확정·구현을 전제로 삼지 않는다.

## 3. 사업 담당자 질문 8개와 답변별 결과

### 공통 입력

- 사업명 / 연도 / 계약·협약 식별자:
- 대상 업무: 신규 접수 / 상담 / 심사 / 상환·사후관리 / 기타
- 답변자 / 확인 권한 / 확인일:
- 각 답변의 근거 문서·조항·버전:

모르면 ‘미확인’으로 기록한다. 실제 계약서, 서명, 당사자 자료와 비공개 보안조건은 공개 레포에 넣지 않는다. 제한된 증빙 저장소의 비밀 없는 식별자만 연결한다.

### 질문 1. 이 사업의 법적 성격은 무엇인가요?

선택: 자체사업 / 보조사업 / 민간위탁 / 용역 / 기타 협약 / 미확인

| 답변 | 결과 |
|---|---|
| 자체사업 | 기관이 처리 근거와 공급자 계약을 검토한다. 공공위탁 조건이 자동 적용되는 것은 아니지만 개인정보 요건은 남는다. |
| 보조사업 | 교부조건·사업지침의 외부 시스템·자료 관리 조건을 확인한다. 보조금만으로 CSAP 필수 또는 Supabase 금지를 판정하지 않는다. |
| 민간위탁·용역·기타 협약 | 실제 계약의 지정 시스템·보안·외부 처리 조건과 승인권자를 확인한다. 공급자 임의 선택을 허용하지 않는다. |
| 미확인 | 해당 사업 실데이터 도입 보류. 합성 시험은 계속한다. |

**판정 의미:** 어떤 모델인지가 아니라 어느 문서와 누구의 승인을 따라야 하는지 결정한다. 법적 계약 형태를 이름이나 수행기관 선정 공고만으로 확정하지 않는다.

### 질문 2. 이 자료의 개인정보처리자는 누구이며, 우리 기관은 어떤 역할인가요?

선택: 직접 개인정보처리자 / 수탁자 / 업무별로 다름 / 미확인

| 답변 | 결과 |
|---|---|
| 직접 개인정보처리자 | 기관이 외부 업체와의 처리 구조·계약·적법한 근거를 확인한다. 직접 처리자라고 외부 이용이 무제한 허용되는 것은 아니다. |
| 수탁자 | 외부 업체 이용의 재위탁 해당 여부와 위탁자의 동의·승인 등 필요한 절차를 확인한다. 미충족 경로는 열지 않는다. |
| 업무별로 다름 | 접수·상담·심사·사후관리 자료를 나눠 판정한다. 기관 전체 승인값으로 합치지 않는다. |
| 미확인 | 처리 책임과 승인권자가 정해질 때까지 해당 실데이터 도입 보류. |

### 질문 3. 처리할 자료에 어떤 정보가 포함되나요?

복수 선택: 개인정보 / 건강 등 법적 민감정보 / 주민등록번호 등 고유식별정보 / 개인신용정보 / 합성·익명정보 / 미확인

| 답변 | 결과 |
|---|---|
| 개인정보 | 금고 암호화, 역할별 접근, 감사, 외부 전송 전 마스킹 등 현재 보호 계약과 처리 근거를 검증한다. |
| 법적 민감정보 | 별도 동의나 법령 등 해당 처리 근거를 확인한다. 암호화·마스킹으로 그 근거를 대신하지 않는다. |
| 고유식별정보 | 식별자별 법적 요건과 필요성을 따로 확인한다. 주민등록번호는 일반 동의만으로 충분하다고 보지 않는다. 일반 금고의 존재는 수집 허가가 아니다. |
| 개인신용정보 | 관련 법령의 추가 적용을 검토한다. 채무 상담 내용 전부를 자동으로 같은 법적 범주에 넣지 않는다. |
| 합성·익명정보 | 실제 개인과 연결되지 않는지 확인한 범위에서 시험을 검토한다. CCC 가명 ID·마스킹 결과는 자동으로 익명정보가 되지 않는다. |
| 미확인 | 실제 입력 범위를 먼저 정한다. ‘자유 메모’라고 개인정보가 없다고 처리하지 않는다. |

### 질문 4. 녹음·전사·AI 분석은 각각 어떤 동의나 법령에 근거하나요?

기록: 수기 기록 / 녹음 / 로컬 전사 / 외부 전사 / 외부 LLM 처리별 근거와 목적

| 답변 | 결과 |
|---|---|
| 수기 기록만 가능, 녹음 불가 | 녹음·STT를 끈다. 수기 자료의 LLM 정리는 별도 근거가 필요하다. |
| 녹음·로컬 전사 가능, 외부 STT 불가 | 로컬 STT만 후보. Azure 전송 금지. 로컬 엔진 실측·승인 전에는 활성화하지 않는다. |
| 외부 STT까지 가능 | Azure 후보를 검토하되 업체·국가·보관 조건과 엔진 게이트를 별도 확인한다. LLM 허가로 확대하지 않는다. |
| 외부 LLM까지 가능 | OpenAI 후보를 다음 질문들과 대조한다. 동의가 있다는 이유만으로 계약상 반출 금지를 무시하지 않는다. |
| 동의 대신 법령상 근거 사용 | 법적 검토와 별개로 현재 동의 중심 S7이 그 근거를 표현·검증할 수 있는지 확인한다. 가짜 동의 사건을 만들지 않는다. |
| 근거 없음·미확인 | 해당 처리를 보류한다. 기본 기록 자체의 근거가 없으면 수기 CCC도 자동 대안이 아니다. |

### 질문 5. 외부 저장·STT·LLM 업체 이용이 허용되나요? 어떤 절차가 필요한가요?

기록: 경로별 허용 / 조건부 / 금지 / 미확인, 위탁·재위탁·제3자 제공 중 법적 관계

| 답변 | 결과 |
|---|---|
| 외부 저장·STT·LLM 모두 허용 | Supabase·Azure·OpenAI를 각각 다음 조건과 대조한다. 아직 최종 통과는 아니다. |
| 외부 저장만 허용 | Supabase 후보, 외부 STT·LLM은 끔. 로컬 STT와 원음 저장 허가는 별도로 확인한다. |
| 음성 반출 금지, 마스킹 텍스트 반출 허용 | 로컬 저장·로컬 STT + OpenAI가 후보. **Supabase 원음 업로드도 반출**이다. Community Cloud의 원음만 로컬에 두는 혼합은 기존 지원으로 간주하지 않는다. |
| 해당 자료의 외부 처리 전부 금지 | Local Single/Office + 로컬 STT 후보 + LLM 끔. 현재 즉시 대체할 로컬 LLM 선택지는 없다. |
| 필요한 승인·계약 미완료 | 영향받는 외부 경로를 보류한다. 녹음 허가나 기관 관리자 승인으로 대신하지 않는다. |

위탁, 재위탁, 제3자 제공은 임의로 골라 붙이는 설정값이 아니다. 실제 목적과 역할로 법적 관계를 확인하고 그 관계에 맞는 절차를 적용한다.

### 질문 6. 해외 저장·추론·백업·해외 인력의 접근이 허용되나요?

각 항목별 선택: 허용 / 조건부 / 금지 / 미확인

| 답변 | 결과 |
|---|---|
| 필요한 근거·절차를 갖춰 허용 | 실제 국가·수령자·기능·계약과 일치하는 외부 경로를 계속 검토한다. |
| 국내 처리만 허용 | 현재 OpenAI 국외 처리 경로는 제외한다. Supabase 서울 DB만으로 국내 한정 충족을 판정하지 않는다. Azure 서울 endpoint도 전체 처리 범위 확인이 필요하다. |
| 해외 저장 금지, 해외 추론 등은 별도 조건 | 저장·추론·로그·백업·지원 접근을 분리해 검토한다. ‘리전=서울’ 한 항목으로 판정하지 않는다. |
| 미확인 | 국외 처리가 발생하거나 배제됐다고 입증하지 못한 경로 보류. |

### 질문 7. 지정 시스템이나 CSAP 등 인증·망 제한이 있나요?

선택: 제한 없음이 확인됨 / 지정 시스템 / 인증 요건 / 내부망·반출 제한 / 미확인

| 답변 | 결과 |
|---|---|
| 특별한 제한 없음이 확인됨 | 기존 세 모드 안에서 다른 조건을 대조한다. 문서에서 조항을 못 찾은 것과 명시적 확인은 구분한다. |
| 지정 시스템만 사용 가능 | CCC 보조 사용과 자료 사본 저장을 허용하는지 확인한다. 불가하면 해당 자료를 CCC에 넣지 않는다. |
| CSAP 등 특정 인증 필수 | 실제 상품·존·기능·인증기간과 CCC 자체 적용 범위를 확인한다. 현재 Supabase 구성을 충족으로 표시하지 않는다. |
| 인증된 국내 클라우드 허용 | 네이버 공공형 등을 별도 검토한다. 네이버 선택이 CCC·STT·LLM 전체 승인으로 이어지지 않는다. |
| 내부망·외부 반출 금지 | Local 모드와 외부 API 끔을 검토한다. 로컬이라는 이유로 나머지 요건을 면제하지 않는다. |
| 미확인 | 해당 사업 운영 적합성 판정 보류. |

### 질문 8. 원음·전사·AI 입력과 출력·로그는 언제 삭제하며 업체의 학습·재사용은 허용되나요?

자료별 기록: 최대 보관 / 최소 의무 보관 / 삭제 시점 / 백업·로그 예외 / 학습·재사용 허용 여부

| 답변 | 결과 |
|---|---|
| 처리 후 원음 삭제, 최대 7일 이내 허용 | ADR-0043과 일치하는지 대조한다. 7일은 상시 보관기간이 아니라 실패 상황까지 포함한 절대 상한이다. |
| 24시간 등 더 짧은 상한 | 현재 7일 기준만으로 부족하다. 단축 상한을 강제·검증하는 설계·구현이 필요하다. |
| 원음을 수개월 의무 보관 | 처리 후 즉시 삭제 계약과 충돌한다. 별도 적법한 보존 체계와 설계 승인이 필요하다. |
| 전사·기록·AI 출력의 별도 보관 규칙 | 원음 7일 규칙을 그대로 복사하지 않는다. 각 저장물·백업·감사 로그의 생명주기를 따로 검수한다. |
| 업체 보관·학습·재사용 금지 | 실제 API 계약과 로그·하위 처리자 보관 조건을 확인한다. `store:false`만으로 모든 보관·재사용 금지 충족을 판정하지 않는다. |
| 재사용 허용 | CCC가 학습 기능을 자동 활성화하지 않는다. 기존 처리 목적을 바꾸려면 별도 검토한다. |
| 미확인 | 필요한 보관·삭제 조건과 일치함을 증명할 수 없는 경로 보류. |

다른 질문의 조건도 모두 충족한다는 가정 아래의 후보이며 실제 사업 승인표가 아니다.

| 사업 조건 | 검토할 조합 | 현행 설계와 추가 확인 |
|---|---|---|
| 외부 저장·원음·국외 LLM 허용 | Supabase + Azure STT + OpenAI | 후보 축 안. 동의·엔진 승인·설치·보안·삭제 검증 필요 |
| 음성 반출 금지, 마스킹 텍스트 LLM 허용 | Local Single/Office + 로컬 STT + OpenAI | 후보 축 안. 로컬 엔진 승인과 텍스트 국외 처리 조건 필요 |

| 외부 처리 전부 금지 | Local Single/Office + 로컬 STT + LLM 끔 | 로컬 엔진 승인 전에는 수기 경로. 로컬 저장의 적법성·보안도 검증 |

| 핵심 근거 미확인 | 실데이터 도입 보류 | 합성 개발은 계속 |

## 5. ADR 반영 후보와 미결 설계

### 기존 ADR-0044를 구체화할 후보

- 질문을 기관 단위가 아닌 사업·연도·계약·업무 범위별로 받는다.
- 저장, 원음 업로드, STT, LLM, 로그·백업·지원 접근을 독립 판정한다.
- 모든 답변에 증빙 식별자·버전·확인자·적용 범위·확인일을 붙인다.
- 법적 허용, 제품 지원, 구현 준비를 분리해 표시한다.
- 미확인과 충돌 경로는 열지 않고, 더 느슨한 다른 사업의 허가를 공유하지 않는다.

이는 **검수 후 반영할 후보**다. 이 문서 추가만으로 Accepted 결정을 늘리지 않는다.

### Q 또는 담당자 확인이 필요한 설계

| 미결 | 검수 질문 |
|---|---|
| 승인 단위 | 사업 정책, supportCaseId에 연결되는 당사자 동의, 기관·설치의 provider 설정을 어떻게 합성할 것인가? |
| 혼합 저장 | 원음 반출 금지 사업을 Local 모드로 한정할 것인가, Cloud 업무 DB + 로컬 원음 경로를 새로 허용할 것인가? |
| 동의 외 근거 | 법령상 처리 근거를 지원할 것인가? 지원한다면 실제 동의 사건과 다른 구조로 어떻게 남길 것인가? |
| 보존기간 | 짧은 사업별 상한을 지원할 것인가? 최소 의무 보관과 현재 즉시 삭제의 충돌은 어떻게 해결할 것인가? |
| 공급자 | 국내 한정 또는 CSAP 조건을 기존 모드로 충족하지 못할 때 신규 공급자·모드를 추가할 것인가? |
| 승인 변경 | 계약 갱신, 동의 철회, 공급자·국가·보관 정책 변경 시 어떤 경로를 언제 재검토·차단할 것인가? |

새로운 사업 정책 테이블, 런타임 DTO, 게이트 코드나 승인 우선순위는 이 문서에서 확정하지 않는다.

## 6. 작업 에이전트의 검수 절차와 산출물

1. §2의 현행 원본을 읽고 사실·설계·구현 상태를 다시 확인한다. 현재 존재하는 ADR-0044를 먼저 검토하고 중복 ADR이나 D번호를 만들지 않는다.
2. §3의 각 질문·분기를 `유지 / 수정 / 근거 부족 / Q 결정 필요`로 판정한다. 법적 주장에는 법령·공식 지침·실제 계약 중 필요한 근거를 구분한다.
3. §1의 충돌 4건을 우선 검수한다. 승인되지 않은 혼합 모드나 국내 서비스 사용을 현행 기능처럼 표현하지 않는다.
4. 수정안은 ADR-0044 보완, 별도 ADR이 필요한 설계 변경, 실행 스펙 보완으로 나눈다. 공급자 변경과 새 저장 경로는 명시적 결정 없이 확정하지 않는다.
5. 실행 연결은 E11-1a/SG14의 증빙, E11-1b의 승인, E9-3의 API 차단, E6-6b/E12-5의 실데이터 전환, E9-4/E10-4의 안내를 검토한다. 화면 숨김만으로 충족했다고 판정하지 않는다.
6. 문서 수정 시 기존 사용자 변경을 보존하고 `git diff --check`와 `node scripts/guard-doc-numbers.mjs`를 실행한다. 실제 코드 검증 없이 구현 완료라고 보고하지 않는다.
