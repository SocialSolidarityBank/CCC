## A. 핵심 결론

**A1. 축 자체는 맞다. 판단 주체를 사용기관에 두고 선택지에 조건만 붙이는 구조는 D63과 어긋나지 않는다**(`CLAUDE.md:244`). 질문으로 결과를 계산하지 않는다는 결정도 유지할 만하다. 문제는 축이 아니라 **문안이 현재 제품에 없는 것을 있는 것처럼 말한다**는 데 있다.

**A2. 사업(program)은 데이터로 존재하지 않는다. 사업 등록 폼도 없다.** 온보딩이 기관 이름과 "첫 사업 이름" 문자열 하나를 `organization_settings`에 저장할 뿐이고(`apps/web/app/onboarding/onboarding-wizard.tsx:71-75`, `packages/core/src/gateway.ts:10639-10659`), `programs` 표는 **의도적으로 만들지 않기로** 결정된 상태다(`migrations/sqlite/0023_organization_onboarding_names.sql:5-7`, `db/schema.sql:1439`). 핸드오프 4장 6번 ①의 "programs 표에 `storage_mode`, `processing_mode` 추가"는 없는 표를 전제한다. 이 ADR은 컬럼 추가가 아니라 **사업 실체 신설**을 결정해야 한다. 참고로 스펙 층은 이미 `programId`를 가정하고 있어(`docs/specs/S7-consent-six-domains.md:169`) 계약과 스키마가 지금도 어긋나 있다.

**A3. 저장 위치는 현재 설치 단위 축이라 사업 단위로 쪼갤 수 없다.** 배포 모드는 서명된 install manifest 하나가 정하고(`packages/http-api/src/capabilities.ts:62`), 세 모드의 저장소는 ADR-0041 D76 표가 고정한다(`docs/adr/0041-one-core-three-deployment-modes.md:28-32`). 한 기관 안에서 사업마다 저장 위치를 다르게 하려면 사실상 설치가 두 벌이 된다. Local Single과 Local Office 설치에서는 "기본형(Supabase 서울)"이라는 선택지 자체가 성립하지 않는다.

**A4. `기관 안에서만 처리`의 STT `local`은 오늘 고를 수 없는 값이다.** 승인 registry가 비어 있어 `sttMode`는 `off`, `sttEngine`은 `null`이며 local과 azure 선택지는 모두 비활성이다(`CCC_OPEN_PILOT_PLAN.md:135`, `docs/specs/S2-auth-capability-manifest.md:220`, `CLAUDE.md:28`, `CLAUDE.md:157`). 즉 이 선택지의 현재 실제 동작은 **녹음 AI 없음, 수기 기록**이다. 문안이 `local`만 적으면 로컬 전사 기능이 있는 것처럼 숨긴다. 반드시 고친다.

**A5. 외부 처리 선택지의 "마스킹 후"는 사실과 다르다.** OpenAI는 장비가 만든 마스킹 스냅샷만 받지만(R3, `CLAUDE.md:104`, `docs/adr/0041-one-core-three-deployment-modes.md:95`), Azure STT는 **마스킹 전 원음**을 받는다(`docs/adr/0043-audio-admission-seven-day-hard-cap.md:15`, `docs/specs/S8-audio-lifecycle-store.md:94`). 두 사업자를 한 괄호에 묶고 "마스킹 후"를 붙이면 고지가 틀린다. 이건 문체 문제가 아니라 사실 오류다.

**A6. Azure는 지금 어떤 사업에서도 켤 수 없다.** 승인 registry가 비어 있고 서버는 Azure 키 존재를 항상 `false`로 본다(`packages/http-api/src/capabilities.ts:74`). D77이 요구하는 관리자 명시 선택과 health check(`docs/adr/0041-one-core-three-deployment-modes.md:38`, `:40`), 별도 외부 STT 동의(`docs/specs/S7-consent-six-domains.md:194`, `docs/adr/0043-audio-admission-seven-day-hard-cap.md:15`)도 문안에 없다. 문안은 D77과 정면으로 어긋나지는 않지만 **조건을 빠뜨려 고를 수 있는 것처럼 읽히게 한다**.

**A7. `나중에 정하기`의 잠금은 코드에 한 줄도 없다.** `storage_mode`, `processing_mode`, `admission_confirmed*` 문자열은 레포 전체 0건이다. 실데이터 거부는 E9-3이 소유하는 미구현 티켓이고(`CCC_OPEN_PILOT_PLAN.md:358`), 원음 입장 조건과 `audio_objects`는 E5-6과 마이그레이션 `0050`이 소유하는데 SQLite 마이그레이션은 `0048_agent_jobs.sql`에서 끝난다(`CCC_OPEN_PILOT_PLAN.md:303`). 동의 6영역 표 `0049`도 없다. **문구는 결정이지 차단이 아니다.** ADR은 이 사실을 결과 절에 명시해야 한다.

**A8. 네이버 클라우드 공공형은 레포에 근거가 0건이다.** `네이버`, `NCP`, `CSAP` 어느 것도 문서와 코드에 없고, ADR-0041 D76의 저장 위치 표에도 없는 네 번째 선택지다. 핸드오프 자신이 티켓 ③을 "별도 ADR 후"로 적어 두었으므로(핸드오프 73행), 지금 라디오에 **고를 수 있는 값**으로 올리면 화면이 문서보다 앞선다.

**A9. 재원 유형과 계약 형식이 조건 문장에 섞여 있다.** "기관 자체 예산 사업", "위탁이나 용역으로 맡긴 사업"은 결과를 바꾸지 않는 앞절이면서 담당자에게 법적 성격 판단을 요구한다. 실제로 결과를 가르는 조건은 각각 뒤쪽 하나(발주처 요구 유무, 계약서 조항 유무)뿐이다. 앞절을 지우면 개인정보 처리위탁과 사업 재원 유형이 섞이는 문제도 함께 사라진다.

**A10. 조언형 프롬프트는 한 곳만 빼면 판단을 요구하지 않는다.** "어느 쪽을 고를지 판단하지 말고", "없으면 찾지 못함이라고만" 두 문장이 잘 잡고 있다. 다만 마지막 "최종 확인할 부서를 제안해 주세요"는 제안, 곧 판단이고 LLM이 알 수 없는 조직 구조를 추측하게 한다. 매뉴얼의 고정 목록으로 옮긴다.

### B5. 녹음과 AI 정리, 기관 안에서만 처리

| 항목 | 내용 |
| --- | --- |
| 원문 | "기관 안에서만 처리: 계약서가 외부 처리를 금지하거나 확인하지 못한 사업. STT는 `local`만, LLM `off`" (핸드오프 23행) |
| 판정 | **수정** |
| 문제 1 | LLM `off`는 정확하나 STT `local`은 오늘 존재하지 않는 값이다. registry가 비어 있어 `sttEngine`이 `null`이고 local 선택지는 비활성이다. 문안이 로컬 전사 기능의 부재를 숨긴다 |

| 문제 4 | `local`과 `off`는 코드 식별자다. 화면 문안에 그대로 노출하지 않는다 |
| 근거 | `CLAUDE.md:28`, `:102`, `:157`, `docs/specs/S2-auth-capability-manifest.md:220`, `:223`, `CCC_OPEN_PILOT_PLAN.md:135`, `docs/adr/0041-one-core-three-deployment-modes.md:39` |
| 최소 수정안 | "기관 안에서만 처리: 계약서가 외부 처리를 금지하는 경우." 아래 사실 한 줄: "이 사업의 상담 내용은 기관 밖으로 나가지 않습니다. **지금은 기관 안에서 도는 음성 인식이 아직 없어 녹음 AI 없이 수기 기록으로 진행합니다.** 기관 안 음성 인식이 준비되면 이 설명이 바뀌고 다시 확인을 받습니다." |

## C. ADR-0045 반영안

ADR-0044의 형식(상태, 결정일, 결정 번호, 관련, 대체 / 배경 / 결정 / 결과 / 구현 소유)을 그대로 쓴다. 아래는 각 절에 들어갈 내용이다.

### C1. 머리

- 관련: ADR-0035 D63(판단 주체), ADR-0041 D76·D77·D79, ADR-0043 D85, ADR-0044 D86(기관 초기 설정), S7, S8
- 대체: 없음. `inbox/0044-public-project-admission-and-cloud-selection.md`, `inbox/public-project-admission-review.md`, `inbox/2026-09-06-project-ai-eligibility-adr-review.md`는 채택하지 않은 초안이라 대체가 아니라 **폐기**로 적는다

### C2. 배경

세 문장이면 된다. 공공 발주 사업이 늘면서 저장 위치와 외부 처리 가능 여부가 사업마다 갈리는데, 배포기관이 계약서를 받아 심사하면 자료 관리 책임을 사용기관이 진다는 D63이 무너진다. 그래서 심사표가 아니라 선택지와 고지를 만든다.

### C3. 결정

1. **판단 주체는 사용기관이다.** 배포기관은 선택지와 정확한 고지, 확인 기록만 제공한다. 계약서 확인 기록지는 만들지 않는다
2. **두 축을 사업 단위 속성으로 둔다.** 저장 위치(기본형 / 공공형 / 나중에 정하기), 처리 경로(외부 허용 / 기관 안 / 나중에 정하기). 기존 `program_type`(`financial_support_v1`)은 상담 기록 템플릿 식별자이고 이 축과 **별개**다. 근거: `migrations/sqlite/0006_participant_support_case_cutover.sql:176-177`의 CHECK가 값 하나만 허용하고, `users.last_program_type`은 화면 상태다(`migrations/sqlite/0017_user_last_program_type.sql:24`)
3. **사업 실체를 신설한다.** 지금은 기관당 사업 표시 이름 하나뿐이고 `programs` 표를 만들지 않기로 되어 있다. 이 축은 표 없이는 붙지 않는다. 표 신설과 온보딩의 "첫 사업"에서 사업 목록으로의 이행을 이 ADR의 결정에 넣거나, 넣지 않는다면 **기관 단위 선택으로 범위를 줄인다**(아래 D1 질문)
4. **저장 위치는 설치 경계를 넘지 않는다.** 한 설치는 한 저장 위치를 갖는다(D76). 사업마다 저장 위치가 다르면 설치가 둘이다. Local 두 모드에서는 저장 위치 구획을 렌더하지 않는다
5. **처리 경로 선택은 상한이지 능력이 아니다.** 실제 가능 여부는 설치의 `sttMode`와 `llmMode`, 승인 registry가 정한다. 사업이 "외부 허용"이어도 설치가 꺼져 있으면 꺼진 것이고, 사업이 "기관 안"이면 설치가 외부를 켰어도 그 사업의 원음과 텍스트는 외부로 나가지 않는다. 즉 실효 값은 두 값의 **더 좁은 쪽**이다
6. **선택지 문안을 결정에 그대로 싣는다.** B1, B4, B5, B6의 수정안 문장을 ADR 본문에 literal로 넣고, 문안 변경은 새 버전과 sha256을 발행한다
7. **확인 체크의 계약**: 저장 항목은 관리자 ID, 시각, 선택값 스냅샷, 문안 버전, 문안 sha256이다. 무효화 사건은 셋이다. 선택 변경, 설치의 STT·LLM 설정 변경, 문안 버전 변경. `나중에 정하기` 상태에서는 체크를 요구하지 않는다
8. **기본 선택 없음.** 미선택은 저장 불가가 아니라 `나중에 정하기`이며, 명시 선택과 무선택은 같은 값이라도 감사 기록에서 구분한다
9. **네이버 공공형은 별도 ADR 선행.** D79 Database 포트 어댑터 결정 전에는 비활성 안내로만 표시한다

### C4. 결과

- **이 ADR은 문안과 계약을 정할 뿐 잠금을 구현하지 않는다.** `나중에 정하기`와 미확인의 차단은 API 거부로 구현하며 현재 코드에 없다. 화면 숨김으로 구현하지 않는다(E9-3의 문장과 같다)
- 사업 표 신설은 마이그레이션 1건 이상과 온보딩 화면 변경을 부른다. `programs` 표를 만들지 않기로 한 온보딩 결정을 이 ADR이 되돌린다는 사실을 명시한다
- 처리 경로가 사업 단위가 되면 원음 입장(SG8)과 Agent claim(SG5)에 사업 축이 추가된다. S8의 admission CAS와 S5의 claim 계약이 영향받는다
- `기관 안에서만 처리`는 STT-G1~G3과 Q 승인 전까지 수기 경로다. 승인 뒤 문안이 바뀌면 그 사업들의 확인이 무효화되고 재확인을 받는다
- S14가 아직 없다. S11이 국외 이전 잔여 위험을 S14와 E9-3 소유로 넘기고 있는데(`docs/specs/S11-supabase-edge-template.md:205`, `:330`, `:388`) 그 문서가 비어 있어, 외부 처리 선택지의 고지 문안은 S14가 생길 때 다시 대조해야 한다

### C5. 구현 소유

- 화면 배치표와 시안: `design-adjustments` 워크트리(디자인 잠금). 이 ADR과 DESIGN-RULES.md가 입력
- 사업 표와 두 컬럼, 확인 기록: 신설 티켓(마이그레이션 포함)
- 실데이터, import, 원음, AI 거부: E9-3 계열. 원음 입장은 E5-6과 SG8
- 매뉴얼과 조언형 프롬프트: 문서 티켓
- 네이버 공공형 어댑터: 별도 ADR 뒤 후속

### C6. CLAUDE.md와 CONTEXT.md 반영 시 주의

- `CLAUDE.md` 9장 D87 행에는 "사업 표 신설"과 "잠금은 미구현"을 반드시 넣는다. 결정만 적고 구현 상태를 빼면 다음 세션이 있는 기능으로 읽는다
- `CONTEXT.md` 용어 3개 중 **저장 위치**의 `_Avoid_`에 "배포 모드"를 넣는다. 둘은 다른 층인데 문안이 섞고 있다
- **처리 경로**의 `_Avoid_`에 "AI 모드"를 넣는다. AI 모드는 설치 단위 값이다

## D. Q 확인 최소 질문

여섯 개다. 전부 Q가 지금 답할 수 있고, 답이 없으면 ADR을 쓸 수 없는 것만 남겼다.

**D1. 사업을 표로 만드는가.** 지금은 기관당 사업 이름 문자열 하나뿐이고 사업 등록 폼이 없다. ADR-0045가 (a) 사업 표 신설까지 결정에 포함하는가, (b) 이번에는 **기관 단위** 선택으로 좁히고 사업 단위는 표가 생길 때 여는가.

**D2. 한 기관에서 사업마다 저장 위치가 다를 수 있는가.** 다르다면 설치가 두 벌이 된다. 아니면 저장 위치는 기관(설치) 단위로 두고 **처리 경로만 사업 단위**로 하는가.

**D3. 네이버 공공형을 지금 폼에 어떻게 두는가.** (a) 비활성과 "준비 중, 도입 문의" 안내, (b) 고를 수 있게 두고 선택 시 `나중에 정하기`와 같은 잠금. 저장 어댑터 ADR 전이라 (a)를 권한다.

**D4. `기관 안에서만 처리`의 현재 상태를 문안에 직접 쓰는가.** "지금은 기관 안에서 도는 음성 인식이 아직 없어 녹음 AI 없이 수기 기록으로 진행합니다"를 선택지 아래 고정 문구로 넣는 것에 동의하는가. 대안은 선택지 이름을 "AI 정리를 쓰지 않음"으로 바꾸는 것이다.

**D5. 미확인을 `나중에 정하기`로 보내는가.** `기관 안에서만 처리` 설명에서 "확인하지 못한"을 빼고, 확인하지 못한 사업은 `나중에 정하기`로 가게 하는 것에 동의하는가. 확인 체크 문구와의 모순이 이걸로 사라진다.

**D6. 확인 무효화 사건 세 가지가 맞는가.** 선택 변경, 설치의 STT·LLM 설정 변경, 설명 문안 버전 변경. 특히 두 번째는 설치 설정 한 번 변경이 그 설치의 모든 사업 확인을 한꺼번에 무효화한다는 뜻이다.
