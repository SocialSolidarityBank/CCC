# ADR-0044: 공공사업 도입 조건 확인과 클라우드 선택 보류

- 상태: Accepted (확인 절차와 문서 적용 범위만)
- 기록일: 2026-09-06
- 요청 근거: Q가 경기극저신용자 지원사업의 조건을 확인하고 실제 작업에 적용할 ADR에 문서화하도록 요청했다.
- 미승인: 해당 사업의 법적 계약 유형, CSAP 적용 범위, Supabase 운영 적합성, 네이버 전환, 새로운 STT 또는 LLM 도입
- 관련: [ADR-0040](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/adr/0040-community-cloud-policy.md), [ADR-0041](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/adr/0041-one-core-three-deployment-modes.md), [ADR-0042](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/adr/0042-supabase-read-only-preflight.md), [ADR-0043](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/adr/0043-audio-admission-seven-day-hard-cap.md), [도입 확인 기록지](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/policy/public-project-admission-review.md)
- 효력: ADR-0041의 세 배포 모드와 공급자 선택은 유지한다. 이 ADR은 특정 공공사업의 실데이터 도입 판단을 추가하며, 기존 선택을 그 사업의 보안 요건 충족 증명으로 사용하지 못하게 한다. 법령이나 계약에 대한 유권해석이 아니다.

## 배경

Q는 사회연대은행이 경기극저신용자 지원사업을 수행한다고 밝혔다. CCC가 그 상담 기록을 처리한다면 공공사업 요건은 먼 미래의 납품 문제가 아니라 최초 도입 때 확인할 조건이다.

경기복지재단 공고 제2026-08호(2026-02-11)의 [수행기관 선정 결과](https://ggwf.gg.go.kr/archives/70349)는 선정기관을 `(사)함께만드는세상`으로 명시한다. 평가위원 모집 공고의 첨부 원문은 지방계약법 시행령 제43조에 따른 낙찰자 선정 절차를 인용한다. 공공사업 수행기관 선정은 확인됐지만, 이것만으로 체결 계약의 법적 형식, 개인정보 처리 역할 또는 특정 클라우드 사용 승인을 확정할 수 없다. CCC에 넣으려는 기록이 신규 2.0 업무인지 기존 대출의 상환·사후관리인지도 구분해야 한다.

ADR-0040이 Supabase를 선택한 이유는 개발자가 없는 기관의 가입과 운영을 단순화하면서 기관이 데이터와 계정을 소유하게 하기 위해서다. 이 이유는 유지하지만, 편의성이 사업별 보안 요건보다 우선하지는 않는다.

## 결정

### 1. 사업 수행, 개인정보 처리위탁, 정보시스템 공급을 구분한다

- 정부 지원금 수령만으로 모든 도구에 CSAP 의무가 있다고 단정하지 않는다.
- 공공사업 수행기관이라는 이유만으로 법적 계약 유형을 민간위탁으로 확정하지 않는다. 위수탁협약, 용역계약, 교부조건 등 실제 문서를 확인한다.
- CCC가 자체 개발 도구라는 이유만으로 위탁사업의 데이터 처리 조건에서 제외하지 않는다.
- 클라우드 인프라 인증과 그 위에서 제공하는 CCC 서비스의 인증을 구분한다. 국내 사업자 또는 국내 저장이라는 사실만으로 적합 판정을 내리지 않는다.
- 건강정보 등 법적 민감정보와 기관이 특별히 보호하는 채무·소득·주거 상담정보를 구분한다. 신용정보 관련 법령의 추가 적용 여부도 기관 법무 검토 대상으로 남긴다.

### 2. 실제 작업의 선행 조건은 사업별 확인 기록이다

해당 사업의 실데이터 생성, 가져오기, 원음 업로드 또는 외부 AI 활성화를 승인하기 전에 [도입 확인 기록지](/Users/seongqkim/developer/PROJECTS/CCC-new/docs/policy/public-project-admission-review.md)를 채운다.

확인 범위는 다음과 같다.

1. 정확한 사업명, 연도, 계약 당사자, 신규 대출 또는 기존 대출 사후관리 범위
2. 개인정보처리자, 수탁자와 재수탁자, 승인 권한을 가진 발주·위탁 주체
3. 지정 시스템과 CCC의 관계, 상담 기록의 관리·보관·반환·파기 조건
4. DB, 업무 API, 인증, 원음 저장, STT, LLM, 로그, 백업, 원격지원 각각의 제공자와 처리 위치
5. CSAP 등 요구되는 인증의 종류, 상품·존·기능 범위와 유효기간, CCC 자체 검토 범위
6. 외부 처리·재위탁·국외 처리 허용 조건과 서면 근거
7. 데이터 주체의 동의 또는 다른 적법한 처리 근거, 공급자 계약과 보관·삭제 조건
8. 설치비, 월 고정비, 종량비, 운영지원과 장애 복구 책임

발주·위탁 담당부서의 사업 범위 확인, 해당 정보보안 담당자의 기술 요구 확인, 기관 개인정보·법무 담당자의 처리 근거 검토를 구분한다. 한 사람의 일반적인 사용 허가로 서로 다른 확인을 대체하지 않는다. Q의 제품 결정과 계약상 승인 권한도 구분한다.

### 3. 미확인 상태는 해당 사업의 실데이터 도입을 막고 개발 전체를 막지 않는다

- 상태는 `미확인`, `조건부`, `확인 완료`, `불가`로 기록한다. 각 상태에 근거, 확인자, 확인일, 적용 경로와 남은 조건을 붙인다.
- `미확인`, 이행되지 않은 `조건부`, `불가`인 경로에는 해당 사업의 실데이터를 넣지 않는다. 로컬 저장도 자동 면제가 아니다.
- 합성 데이터 개발, 기존 세 모드 계약 테스트, 읽기 전용 사전 점검은 계속할 수 있다. 기존 승인 게이트를 낮추지 않는다.
- 저장만 허용되고 외부 AI가 미허용이면, 허용된 저장 경로에서 수기 업무만 검토한다. STT·LLM 중 한 경로의 허가를 다른 경로로 확대하지 않는다.
- 사업별 차단을 시스템이 구분하지 못하는 설치에서는 더 넓은 실데이터 허용값을 공유하지 않는다. 분리된 승인 환경을 마련하기 전에는 해당 사업을 투입하지 않는다.
- 이 문서는 실행 코드의 차단이 이미 구현됐다는 증거가 아니다. E9-3과 E11-1b의 구현·운영 검증이 남는다. 기존 운영 데이터를 삭제하거나 기존 서비스를 임의 중단하라는 지시도 아니다.

### 4. Supabase 기본형은 유지하되 공공사업 적합성은 미확정이다

- ADR-0041의 Community Cloud는 계속 기관 소유 Supabase다. 이 ADR로 기본 공급자를 바꾸지 않는다.
- 서울 프로젝트는 모든 서비스가 국내에서만 실행된다는 증명이 아니다. S11 §3.1의 Edge 실행 위치 증거와 잔여 국외 처리 검토를 유지한다.
- Azure STT는 마스킹 전 원음을 받는 경로이고 OpenAI는 마스킹된 AI Packet을 받는 별도 경로다. 마스킹과 `store:false`만으로 계약·국외 처리·민감정보 검토가 끝나지 않는다.
- OpenAI의 한국 지역 저장 옵션은 한국 내 추론 처리와 구분한다.
- 네이버 공공 클라우드는 요구조건이 확인된 경우의 비교 후보다. 가입 자격, 서비스별 인증 범위, 앱 인증 구성, 비용, 설치·복구 검증과 Q의 별도 설계 승인 전에는 운영 선택지로 열지 않는다.
- 네이버를 선택해도 공공용 CLOVA Studio, 상용 CLOVA Speech, 구축형 STT 또는 로컬 LLM을 자동 채택하지 않는다. D77의 허용 목록과 STT-G1~STT-G3은 그대로다.

### 5. 설치 편의성은 사용자가 아니라 공급 측이 책임진다

확인한 로컬 `scripts/supabase/bootstrap.mjs`는 `plan`만 지원하며 다른 작업은 `OPERATION_UNSUPPORTED`로 거부한다(2026-09-06). S11·S12의 `apply`, `doctor`, `update`, `rollback` 계약을 완성된 원클릭 설치기의 증거로 쓰지 않는다. 네이버 공공형도 CCC 설치·업데이트·복구를 실제로 검증한 상태가 아니다.

공공 환경에도 API, CLI, Terraform의 `gov` 설정과 Init Script가 있다. 다만 공급자 가입 심사, 계약, 결제, 권한 위임과 운영 책임은 자동으로 사라지지 않는다.

선택 가능한 공공형을 만들 때의 원칙은 다음과 같다.

- 기관 관리자는 계약·예산·권한·운영 시점을 승인한다. 일반 실무자가 클라우드 콘솔, 방화벽, DB 설정을 직접 조작하게 하지 않는다.
- LLM은 안내와 승인된 도구 호출을 맡는다. 실행은 버전이 고정되고 검증된 설치 절차로 한정한다. 오류를 고치려고 DB를 외부 공개하거나 권한을 임의 확대하지 않는다.
- 설치 전 변경 없는 검사, 변경·비용 계획 승인, 적용, 완료 검사, 재실행 안전성, 업데이트 전 백업과 복구를 한 흐름으로 제공한다. 비밀값은 채팅·명령행·로그로 받거나 출력하지 않는다.
- 설치 후 업데이트, 인증서, 백업·복원, 패치, 비용 알림과 장애 대응의 담당자를 계약으로 정한다. 기관 소유 계정이라고 운영지원자의 개인정보 처리 책임이 없어지는 것은 아니다.
- 비개발자가 기술 설정을 직접 하지 않고 새 환경 설치, 로그인, 합성 상담, 업데이트 실패 복구를 완료하는 시험으로 편의성을 검증한다. 현재 클릭 수나 설치 시간을 미리 보장하지 않는다.

### 6. 비용과 호환성 비교에는 조건을 붙인다

2026-09-06 공식 공개 요금 확인 예시는 다음과 같다. 최종 견적이나 CCC 성능 산정이 아니다.

| 항목 | 확인 또는 계산 | 제외·조건 |
|---|---:|---|
| Supabase Pro 기본 | 월 25달러 | 첫 Micro 프로젝트 포함. 예산 비교 환율 1,400원 가정 시 35,000원이며 실시간 환율이 아님 |
| 네이버 공공 DB High CPU 2 vCPU, 4GB 한 대 | 176원/시간 × 720시간 = 126,720원 | VAT, 데이터·백업 저장소 별도 |
| 네이버 공공 High CPU-g2 앱 서버 2 vCPU, 4GB, 50GB | 월 81,620원 | 공개 요금표의 월 요금. 공급 가능 존·세대는 실제 견적 재확인 |
| 위 앱 서버 한 대 + DB 한 대 | 월 208,340원 + 추가 비용 | 저장소·보안·네트워크·운영지원·AI·기관 장비·개발비 제외, 이중화 없음 |
| 위 앱 서버 두 대 + DB 두 대 | 월 416,680원 + 추가 비용 | 동일한 제외 항목, 로드밸런서 등 포함 전 부분합 |

사양과 가용성이 달라 동일 성능 가격 비교로 쓰지 않는다. 필요 없는 대규모 구성을 강제하지 않되, 운영비를 줄이려고 여러 기관을 중앙 DB로 합치는 것도 별도 결정 없이 하지 않는다.

공공 PostgreSQL은 VPC, 공공 Cloud Functions는 확인일의 공식 사양상 Classic 전용이다. 서버리스로 단순 치환해 비용을 계산하지 않는다. VPC 앱 실행기 등 실제 연결 가능한 구성을 검증한다. 네이버에 Supabase를 자체호스팅하면 관리형 Supabase의 운영대행과 Management API가 그대로 생기지 않으며 패치·백업·복구 책임이 증가한다.

## 실행 작업에 반영할 범위

| 기존 작업 | 적용할 내용 | 완료로 보지 않는 것 |
|---|---|---|
| E11-1a / SG14 | 기록지로 사업별 계약·처리 경로·승인 증빙을 정리. 기존 LG1~LG3에 어떻게 연결할지 명시 | 기록지 작성만으로 법무 통과 |
| E11-1b | 사업·모드·처리 경로별 증빙과 승인 연결. 해당 사업 미확인은 열린 상태 유지 | 기관 전체에 포괄 허가 |
| E9-3 | 생성·import·upload·AI 활성화가 승인 범위를 넘지 못하도록 API 검증과 거부 테스트 설계·구현 | 안내 문구만 추가하거나 이미 구현됐다고 표시 |
| E6-1a / E6-5a | 기술 사전 점검 결과와 계약 적합성을 별도 표시. 기존 설치기의 구현 범위 확인 | `plan` 성공을 실데이터 사용 허가로 해석 |
| E6-6b / E12 실데이터 시험 | 대상 사업과 실제 배포 경로의 승인 증거를 소비 | 합성 시험 성공만으로 운영 전환 |
| E9-4 / E10-4 | 관리자 승인과 설치기 작업 분리, 운영 책임·복구 안내 | 공급자 콘솔 조작을 실무자 매뉴얼로 떠넘김 |

SG14의 `docs/specs/S14-legal-gates.md`는 확인한 로컬 작업트리에 없었다. 이 ADR은 그 파일이 확정됐거나 새 게이트가 이미 구현됐다고 표시하지 않는다. 관련 실행 티켓에서 계약과 테스트를 먼저 보완한다. GitHub·Linear 상태 변경은 이 문서 작업에 포함하지 않는다.

## 결과와 재검토 조건

- Supabase 기본 개발과 세 모드 구현은 계속한다. 해당 공공사업 실데이터의 도입 승인만 별도로 확인한다.
- 공공용 네이버는 후속 선택지로만 미루지도, 확인 없이 확정하지도 않는다. 실제 도입 대상 사업의 요구와 견적을 확보한 뒤 별도 공급자 변경 결정을 한다.
- 계약 연도, 수행 범위, 공급자·상품·리전·모델, 재위탁자, 원음 보관, 인증 범위, 운영지원 방식이 바뀌면 영향받는 경로를 다시 검토한다.
- 서면 회신이 없으면 확인을 추정하지 않는다. 해당 사업의 승인 증빙은 공개 저장소가 아니라 기관의 접근 제한 저장소에 보관하고 이 기록지에는 비밀이 없는 문서 식별자·버전·검토 상태만 남긴다.
