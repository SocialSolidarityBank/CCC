FINDINGS

D01 | P2 | Audit filter emits malformed select markup
Location: J:206-209, specifically prototype.js:209.
Evidence: auditPanel opens <select id="audit-filter">, maps its options, and immediately appends the chevron SVG and </span></label>. There is no </select>. The following event list is concatenated into the same card-body string. In contrast fieldMarkup correctly closes its select at J:110.
Rule: approved plan Task 1 requires all 19 screens and controls to be usable; Task 4 explicitly requires audit filtering and accessibility checks. Valid form structure is prerequisite to that behavior.
Impact: the generated markup puts the chevron and following content inside an unterminated select in the source. Browser error recovery can discard/reparent subsequent audit content. This is a definite markup defect; exact resulting DOM and missing content are not browser-observed by this reviewer.
Precise fix: insert </select> immediately after the options join and before ${chevron}. Keep the chevron as the select's sibling inside wire-input-box, as in fieldMarkup. Main should verify all five audit events and each filter after the fix, with the guide link outside the select.

D02 | P2 | Memory 'syncing' scenario contradicts the same screen's off/current-processing facts
Location: J:43,60,176-179,194,266-268.
Evidence: memory exposes syncing in scenariosFor. scenarioPanel says '가상 동기화 중 2건 / 대기 4건'. render treats syncing as normal and renders the unchanged base current-setting rows, including '꺼짐 / 설치 LLM off'. detailsFor(memory) simultaneously renders '이번 처리: 0건 / 외부 호출 없음' and either '꺼짐' or '사용 준비 시연 / 설치 LLM off로 처리 중지'. The state=syncing path does not change any of these facts.
Rule: approved DESIGN-RULES '디자인 미리보기의 기본 상태' requires mutually incompatible conditions in separate states; approved plan Task 3 requires off/syncing/masking-wait/failure to be distinguished. Shared contract forbids invented live success.
Impact: one screen teaches both active synchronization and stopped/no current processing. This is not actual data exposure, but makes the required state demonstration internally inconsistent.
Precise fix: render scenario-specific memory facts from one coherent dummy fixture. If the fixture demonstrates current processing, label its compatible enabled/processing conditions explicitly as simulation and do not retain the stopped/zero-current-work statements. If installed off/null is held invariant for this demonstration, describe the alternate example as queued or historical synchronization rather than currently processing. Do not change real capability or add a case-content response.

D03 | P2 | Required input fields lack the required visual marker
Location: J:105-113 and J:301-305.
Evidence: every text/email input receives native required at J:112. J:113 emits a bare label containing only field.label. There is no wire-required-marker. validateCurrentForm also rejects blank string values, including the consent copy, without identifying requiredness in the form schema/label.
Rule: current and approved DESIGN-RULES.md section 5, current file line 131: actual required inputs use WireBadge's .wire-required-marker, with the defined lavender outline and 8px label gap. Requiredness is not indicated by a placeholder or a later generic error.
Impact: required fields look optional until validation blocks progression. The missing marker is source-visible; final pixel spacing has not been measured.
Precise fix: give form fields explicit required metadata and render the existing artifact equivalent of .wire-required-marker only on required field labels. Preserve native required semantics for text/email/textarea as appropriate. Do not add duplicate required badges to card titles or invent another badge style. Keep the existing input values and failure preservation.

D04 | P2 | Visual navigation groups are not named groups for assistive technology
Location: J:245-246.
Evidence: each group is <div class="navigation-group"><p class="navigation-section-title">...</p><div class="navigation-items">...</div></div>. Group titles have no id; the link container has no aria-labelledby, role=group or list semantics. I:18 labels only the entire nav as '설정'.
Rule: approved DESIGN.md section 4-5, snapshot line 456: group title is a non-clickable p and names its list via aria-labelledby. Task 1/Task 4 require keyboard and accessibility behavior, not only a visual grouped menu.
Impact: the five visible headings are ordinary paragraphs, not programmatically named link groups. Current link names and aria-current remain useful, but do not expose the specified group relationship.
Precise fix: assign a stable unique id to each visible title and reference it from a semantic list or role=group container using aria-labelledby. Keep links at one level and retain the separate ungrouped 내 정보 and 사용 가이드 entries; do not add a common heading for those two.

Keep it one logical control/state per active surface. Preserve the sidebar top return-to-work action and one settings navigation.
