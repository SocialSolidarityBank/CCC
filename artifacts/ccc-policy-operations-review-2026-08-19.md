# CCC 정책·운영 전반 검토

- 검토일: 2026-08-19
- 범위: 정책, 개인정보, 동의, AI 처리, 권한, 감사, 배포, 장애 대응, 백업·복구, 문서 거버넌스
- 검토 방식: 저장소 문서와 코드의 현재 동작 대조, 분야별 독립 검토 5개, 핵심 경로 직접 확인
- 한계: GitHub Environment 설정, Cloudflare 실계정 설정, Infisical, 운영 D1·R2, 실제 알림 전달은 조회하지 않았다. 저장소 밖 통제는 문서에 적혀 있어도 별도 검증이 필요하다.
- 문서 지위: 저장소 기반 검토 의견이며 법률 검토 결과나 출시 승인서를 대신하지 않는다.

## 1. 결론

**현재 승인 판단(2026-08-19): 가상 데이터 시연은 사전 조건을 확인한 뒤에만 진행할 수 있다. 실제 당사자 데이터 처리와 외부 기관 운영 시작은 승인하지 않는다. 운영 배포 경로가 구현됐다는 사실은 실서비스 승인을 뜻하지 않는다.**

이 판단은 저장소에서 확인한 문서와 코드에 한정된다. 조회하지 못한 GitHub Environment, Cloudflare 실계정, Infisical, 운영 D1 및 R2, 실제 알림 전달은 완료된 통제로 인정하지 않는다.

저장소에서는 인증 설정이 없을 때 요청을 거부하고, 외부 AI 호출은 사업자 설정, API 키, 명시적 기능 스위치가 모두 있어야 허용하도록 구현돼 있다. 마스킹된 사본이 없는 텍스트는 OpenAI에 전달되지 않으며, 승인 전 AI 결과는 공식 기록에 포함되지 않는다.

문제는 안전 원칙과 실제 운영 경로가 몇 군데에서 어긋난다는 데 있다.

1. 실제 등록 화면의 동의 문구가 동의서 초안과 다르다.
2. 가상 데이터 전용으로 결정한 당사자 가입 링크가 운영 환경에서도 공개돼 있다.
3. 보존 정책은 아카이브와 사람 검토를 요구하지만 코드는 기한이 되면 PII를 직접 파기한다.
4. 기관 관리자는 정책상 담당 케이스만 봐야 하지만 코드에서는 기관 내 모든 케이스에 접근한다.
5. AI 동의를 철회해도 과거 동의 근거가 남아 텍스트 AI 처리가 계속될 수 있다.
6. 현재 승인 화면은 대조 3종의 항목별 처리와 화자 확인 없이 AI 초안을 공식 기록으로 만들 수 있다.
7. 배포는 가능하지만 백업·복구, 사고 대응, 사후 점검이 실데이터 운영 수준에 이르지 못했다.

**실제 당사자 데이터**는 실제 서비스 대상자의 개인정보, 상담 내용, 녹음과 그로부터 생성된 전사문, 요약, 통계를 포함한다.

**동의받은 내부 테스트 녹음**은 실제 당사자와 무관한 테스트 참여자가 작성된 대본을 읽은 녹음으로 한정한다. 실제 상담 내용이나 실제 당사자 정보가 포함되면 실제 당사자 데이터로 판정한다. 음성 자체에 대한 동의 근거와 삭제 예정일도 기록한다.

### 우선순위 기준

- **P0(승인 차단):** 해당 항목이 해결되고 완료 증거가 확인되기 전에는 명시된 범위를 승인하지 않는다.
- **P1(운영 전 필수):** 명시된 운영 단계 전에 책임자, 절차와 검증 증거를 갖춰야 한다.
- **P2(후속 개선):** 현재 승인 범위를 직접 바꾸지는 않지만 담당자와 처리 시점을 정해야 한다.

각 발견 사항의 판정은 전체 승인 판단에 예외를 만들지 않는다. 특정 항목이 `외부 AI 사용 전 차단`이라고 적혀 있어도 실제 당사자 데이터에 대한 전체 중단 판정은 그대로 적용된다.

## 2. 저장소에서 확인된 통제

### 2.1 데이터와 환경이 분리돼 있다

- 미리보기와 운영은 Worker, D1, R2를 분리하고 미리보기 cron을 끈다. `apps/api/wrangler.toml:67-126`
- 미리보기 D1은 가상 시드 전용이고, R2는 합성 음성과 동의받은 내부 테스트 녹음만 허용한다. `docs/ops.md:201-211`
- 운영 인증 설정이 없으면 로컬 헤더 인증으로 폴백하지 않고 닫힌다. `apps/api/wrangler.toml:32-42`

### 2.2 외부 AI 사용 조건이 정의돼 있다

- 처리 장비는 D1·R2에 직접 접근하지 않고 Workers API만 쓴다. 임시 파일은 작업 종료 시 삭제하고 내용·PII를 로그에 남기지 않는다. `apps/pipeline/README.md:7-14`
- 인명 NER 모델이 없거나 라벨이 맞지 않으면 장비가 뜨지 않는다. 조용히 마스킹 0건으로 진행하지 않는다. `apps/pipeline/README.md:67-74`, `apps/pipeline/README.md:143-152`
- 외부 AI는 장비가 만든 마스킹 스냅샷만 재료로 사용한다. `docs/adr/0027-openai-provider-and-masked-text-queue.md:29-49`
- 외부 호출은 프로바이더 설정, API 키, `EXTERNAL_AI_CALLS_ENABLED=1`이 함께 있어야 열린다. `docs/ops.md:38-51`
- 승인 전 AI 결과는 공식 기록, 브리핑, 통계, 보고서에 들어가지 않는다. `docs/policy/internal-operations-policy.md:145-149`

### 2.3 변경과 배포 통제가 구현돼 있다

- CI가 타입 검사, 테스트, DB 관문 검사, 문서 번호 검사, 디자인 가드, 파이프라인 테스트, 전체 이력 시크릿 검사를 수행한다. `.github/workflows/ci.yml:22-45`, `.github/workflows/ci.yml:77-120`
- 운영 배포는 수동 확인 문구, 테스트, 운영 D1 스키마 게이트, GitHub Environment 승인을 순서대로 거친다. `.github/workflows/deploy-production.yml:31-120`
- 배포 스크립트는 작업본과 `origin/main`, 세 패키지 버전, 최신 CI, 운영 D1 마이그레이션 상태를 먼저 확인한다. `scripts/deploy-production.mjs:42-139`
- 운영 마이그레이션마다 Time Travel 북마크와 적용 전후 검증을 기록한 사례가 있다. `artifacts/prod-migration-2026-08-19/0032-0035.md:1-29`

### 2.4 미해결 위험이 문서화돼 있다

- 보존·파기와 관리자 접근 문제를 코드 위치, 재개 조건, 착수 지점까지 적어 두었다. `docs/policy/deferred-blockers-v1.md:1-81`
- 법적 검토 항목을 법률 의견처럼 단정하지 않고 검토 질문 14건으로 정리했다. `docs/consent/legal-review-open-items-v1.md:1-33`
- 배포 성공과 실서비스 개시 가능성을 분리해 기록한다. `docs/releases.md:37-39`

## 3. 최우선 발견 사항

### P0-1. 등록 화면의 동의 문구가 현재 동의서 초안과 다르다

**판정: 실제 당사자 데이터 투입 전 차단**

화면 파일은 동의서 초안 1~6절을 그대로 반영한다고 선언하지만 실제 문구는 다르다. `apps/web/app/participants/new/consent-copy.ts:1-5`

| 항목 | 화면 문구 | 동의서 초안 |
| --- | --- | --- |
| 수집 항목 | 성명, 연락처, 이메일, 상담 기록 | 생년월일·연령대, 거주 지역, 계좌, 긴급 연락처, 상세 주소까지 구분 |
| 보유 기간 | 1년 뒤 PII 파기 | 1년 뒤 아카이브, 종결 후 총 5년 이내 파기 |
| 가명 기록 목적 | 통계·서비스 개선 | 통계 작성 |
| 거부 효과 | 각 항목 거부 시 불이익 없음 | 개인정보 동의 거부 시 등록·상담 제공이 어려움 |

근거:

- 화면 문구: `apps/web/app/participants/new/consent-copy.ts:18-50`
- 현재 초안: `docs/consent/consent-draft-v0.md:18-49`
- 내부 PII 표시 정책: `docs/policy/internal-operations-policy.md:108-127`, `docs/policy/internal-operations-policy.md:175-179`
- 데이터 설계 요약의 관리자 전용 원칙: `AGENTS.md:34`

이 문제는 단순한 문서 불일치가 아니다. 실제 당사자가 수집 범위, 보존 기간, 거부 효과, 열람 범위를 잘못 이해한 채 정보를 입력할 수 있다.

화면과 동의서 초안의 PII 열람 문구는 모두 담당 실무자와 기관 관리자를 중심으로 적혀 있다. 문제는 이 두 문구가 내부 운영 정책과 다르다는 데 있다. 데이터 설계 요약은 관리자 전용, 화면과 동의서 초안은 담당 실무자와 관리자, 내부 운영 정책은 인증된 모든 실무자에게 기본 표시라고 서로 다르게 약속한다.

**권고**

1. 실제 데이터 등록을 막은 상태에서 화면 문구를 현재 검토본과 맞춘다.
2. 문구를 여러 파일에 손으로 복사하지 않는다. 검토 완료된 단일 문안에서 화면과 해시 입력을 생성하거나, CI에서 완전 일치 검사를 한다.
3. 개인정보 동의에도 문안 버전, 해시, 오프라인 원본 참조를 남긴다. 현재 버전·해시 증거는 AI 동의 쪽이 더 강하다.
4. PII 열람 대상을 하나로 확정하고 정책, 동의 문구, 코드 검사를 함께 맞춘다.

### P0-2. 가상 데이터 전용 가입 링크가 운영에서 공개돼 있다

**판정: 즉시 오사용 방지 필요, 실제 데이터 투입 전 차단**

ADR은 당사자 가입 링크를 법률 검토 전 화면 흐름 프로토타입으로 정의하고, 가입 데이터는 로컬·미리보기 가상 시드에서만 쓰도록 제한한다. `docs/adr/0016-mvp-signup-flow-prototype.md:27-30`

하지만 현재 웹 미들웨어는 운영에서 `/join`을 Access 없이 공개하고, API도 운영에서는 인증 없이 초대 조회와 가입을 처리한다. `apps/web/middleware.ts:17-44`, `apps/api/src/request-handler.ts:1917-1976`

토큰은 32바이트 난수이고 한 번 사용되면 다시 쓸 수 없다. 다만 만료 시각과 발급 후 취소 상태가 없다. 마이그레이션도 수명 정책을 실제 인증 설계 이후로 미뤘다고 적는다. `migrations/0021_invite_tokens.sql:14-20`, `apps/api/test/gateway-participant-signup.test.ts:117-159`

**권고**

1. 운영에서는 명시적 기능 스위치가 없으면 `/join`과 공개 가입 API를 닫는다.
2. 실제로 열기 전 토큰 만료, 취소, 재발급, 접근 감사, 운영 책임자를 정한다. 이미 구현된 1회 사용은 유지한다.
3. 승인된 동의 문구와 개인정보 처리방침이 준비되기 전에는 운영 스위치를 켤 수 없게 한다.

### P0-3. 보존 정책과 실제 자동 파기가 충돌한다

**판정: 실제 당사자 데이터 투입 전 차단**

정책은 보관 기간이 끝나면 자동 아카이브로 전환하고, 접근 제한, 보존 사유 검토, 기관 관리자 확인을 거친 뒤 파기하도록 요구한다. `docs/policy/internal-operations-policy.md:203-220`

실제 동작은 다르다.

1. 마지막 활성 케이스 종결 시 트리거가 `purge_due`를 설정한다. `migrations/0006_participant_support_case_cutover.sql:1773-1792`
2. 매일 03:00 UTC cron이 `runPurge`를 호출한다. `apps/api/src/index.ts:59-61`, `apps/api/src/index.ts:81-89`
3. 테스트는 도래한 PII 1건이 실제로 파기되는 것을 증명한다. `apps/api/test/watchdog-purge.test.ts:280-291`

아카이브 상태, 접근 축소, 검토 큐, 법적·업무상 보존 사유 확인, 관리자 승인 단계는 없다. `docs/policy/deferred-blockers-v1.md:24-38`

**권고**

1. 실데이터 전까지 자동·수동 즉시 파기 진입점을 비활성화한다.
2. cron은 파기가 아니라 아카이브 전환과 검토 큐 생성까지만 수행하게 한다.
3. 법적 보존 중지와 업무상 보존 사유를 확인한 뒤 별도 승인으로 파기한다.
4. 요청자, 검토자, 사유, 대상, 결과 건수를 불변 기록으로 남긴다.

### P0-4. 기관 관리자가 배정 없이 상담 내용에 접근한다

**판정: 여러 실무자가 실제 데이터를 쓰기 전 차단, 외부 기관 온보딩 전 차단**

정책은 기관 관리자도 자신이 담당 실무자로 배정된 케이스만 상담 내용을 볼 수 있다고 정한다. 예외는 사유, 시간 제한, 케이스 제한, 전건 감사, 담당 실무자 통지를 갖춘 긴급 접근뿐이다. `docs/policy/internal-operations-policy.md:102-130`, `docs/policy/internal-operations-policy.md:155-165`

현재 `assertSupportCaseAccess`는 기관 관리자에게 기관 소속만 확인하고 바로 케이스를 돌려준다. 배정 확인은 실무자에게만 적용된다. `db/gateway.ts:8176-8206`

**권고**

1. 평상시 기관 관리자도 활성 담당 배정을 요구한다.
2. 긴급 접근은 별도 권한 상승 레코드와 API로 분리한다.
3. 긴급 접근 레코드에 케이스, 사유, 만료, 실행자, 통지 결과를 남긴다.
4. 수정 전에는 기관 관리자 계정을 최소화하고 비배정 케이스 접근을 운영 규칙으로 금지한다. 사람 규칙은 임시 통제일 뿐 최종 해법으로 보지 않는다.

### P0-5. 동의·법률 검토가 실운영 수준으로 닫히지 않았다

**판정: 실제 당사자 데이터 투입 전 차단. 외부 AI 또는 외부 음성 문자 변환 서비스 사용 전에도 차단.**

현재 동의서는 법률 검토 전 초안이며 실제 동의서로 쓰지 말라고 명시한다. `docs/consent/consent-draft-v0.md:1-8`

다음 항목이 높은 긴급도로 열려 있다.

- 배포 방식별 개인정보처리자·수탁자 지위
- OpenAI 국외 이전 고지
- CLOVA 또는 RTZR 처리위탁 고지
- 건강·채무 정보의 민감정보 동의
- 신용정보법 적용 여부
- 보존 기간과 자동 파기 절차

근거: `docs/consent/legal-review-open-items-v1.md:14-27`

현재 배포된 처리 경로의 기본 전사 엔진은 로컬 Whisper다. CLOVA 또는 RTZR 관련 항목은 외부 음성 문자 변환 서비스가 이미 활성화됐다는 뜻이 아니라, 앞으로 채택하기 전에 닫아야 할 조건이다. `apps/pipeline/ccc_pipeline/config.py:166-167`, `apps/pipeline/ccc_pipeline/transcribe.py:32-53`

**권고**

1. 법률 검토 책임자를 지정하고 실제 제공할 배포 방식과 AI 또는 음성 문자 변환 사업자로 검토 범위를 한정한다.
2. 검토 결과를 개인정보 처리방침, 동의서, 위탁 계약, 국외 이전 고지와 시스템 화면 문구에 동일하게 반영한다.
3. 각 문서에 버전, 승인자, 승인일과 적용 시작일을 기록한다.
4. 미해결 법률 항목이 하나라도 있으면 실제 당사자 데이터 처리와 해당 외부 사업자 사용을 승인하지 않는다.

### P0-6. 서비스 전체 백업·복구 체계가 없다

**판정: 실제 당사자 데이터 투입 전 차단**

운영 마이그레이션 전 Time Travel 북마크와 복구 명령을 남긴 사례는 있다. `artifacts/prod-migration-2026-08-19/0032-0035.md:13-29`

그러나 이는 변경 직전 롤백 지점이지 서비스 전체의 백업·복구 운영은 아니다. 저장소 검토에서는 다음을 확인하지 못했다.

- 업무가 허용하는 데이터 손실 범위인 RPO
- 목표 복구 시간인 RTO
- 정기 백업과 보관 정책
- 격리된 복구 훈련
- D1, R2, Worker, Access, 시크릿, 암호화 키를 함께 복구하는 절차
- 이전 키 버전 암호문 복호화 검증

원본 녹음의 선택형 백업도 기본 OFF이고 현재 목적지 연결 모듈이 없어 켤 수 없다. `apps/pipeline/README.md:77-94`

**권고**

1. 실제 데이터 전 RPO·RTO를 승인한다.
2. 먼저 D1 Time Travel이 승인된 RPO와 RTO를 충족하는지 복구 훈련으로 확인한다. 충족하지 못하면 독립 백업 또는 내보내기 방식을 추가한다.
3. 암호화 키 버전별 복구 책임과 이중 통제를 정한다.
4. 격리된 환경에서 복원 후 로그인, D1 조회, PII 복호화, 감사 로그 무결성까지 확인하는 훈련을 한다.

### P0-7. AI 동의 철회가 실제 AI 사용을 막지 않는다

**판정: 실제 당사자 데이터와 외부 AI 사용 전 차단**

현재 저장소 설정은 외부 호출을 기본 OFF로 두고 있고 운영 프로바이더 활성화 기록도 0건이므로, 실제 유출이 일어났다고 판단한 것은 아니다. `apps/api/wrangler.toml:99-109`, `artifacts/prod-migration-2026-08-19/0032-0035.md:25-29` 아래 문제는 외부 AI를 켜기 전에 막아야 하는 잠재 경로다.

동의 철회는 `support_cases.consent_text_ai_at`을 `NULL`로 만들지만 과거 동의 근거 행은 append-only로 남긴다. 이 설계 자체는 이력 보존에 맞다. 문제는 실제 사용 허용 검사가 현재 동의값이 아니라 과거 근거 행의 존재만 본다는 데 있다.

- 서비스와 재생성 경로의 허용 검사는 과거 `pilot_text_ai_consent_evidence`만 조회한다. `db/gateway.ts:1321-1364`
- 사람·사업자 호출 전 허용 검사도 같은 과거 근거만 조회한다. `db/gateway.ts:2873-2917`
- 텍스트 일감 목록도 현재 `consent_text_ai_at`이 아니라 과거 근거 존재만 조건으로 쓴다. `db/gateway.ts:6400-6444`
- 철회 테스트는 현재값이 `false`가 되는 것만 확인하고 철회 후 AI 처리를 시도하지 않는다. `apps/api/test/participant-consent.test.ts:339-350`

따라서 한 번 동의한 뒤 철회한 케이스의 수기 메모가 계속 마스킹되고, OpenAI 재료나 재생성에 쓰일 수 있다.

**권고**

1. 모든 AI 사용 허용 검사와 텍스트 큐 조건에 현재 `consent_text_ai_at IS NOT NULL`을 함께 요구한다.
2. 동의, 큐 적재, 철회, 큐 숨김, 스냅샷·생성 거부, 외부 호출 0건을 한 종단 테스트로 고정한다.
3. 과거 근거 행은 삭제하지 않고 증거로만 보존한다. 사용 허용 여부와 이력 보존을 분리한다.

### P0-8. 실제 승인 화면이 요구사항 R2의 승인 절차를 우회한다

**판정: 실제 AI 기록 승인 전 차단**

이 절의 `요구사항 R2`는 Cloudflare 파일 저장 공간 R2가 아니라 `AGENTS.md`에 정의된 승인 요구사항을 뜻한다.

R2는 승인을 대조 3종을 실무자가 처리하는 정합성 검증으로 정의한다. 녹음 회차는 화자 매핑 확인도 필요하다. `AGENTS.md:60-63`, `AGENTS.md:84-89`

현재 검토 화면은 대조 결과를 보여 주지만 승인 요청에는 `expectedVersion`과 `decision`만 보낸다. 항목별 처리 결과와 화자 확인은 없다. `apps/web/app/participants/[beneficiaryId]/programs/[supportCaseId]/records/[sessionId]/review/fixture-draft-view.tsx:245-288`

실제 웹 경로가 쓰는 `reviewGeneratedAiDraft`도 근거 인용 완전성만 확인한 뒤 바로 `approved_at`을 기록한다. 대조 항목 처리와 `speaker_mapping_confirmed_at`을 요구하지 않는다. `db/gateway.ts:4200-4299`

반면 별도 `approveSession` 함수는 화자 확인과 대조 항목 전체 처리를 검사한다. `db/gateway.ts:6782-6859` 현재 승인 함수가 둘이고 서로 다른 계약을 강제하는 상태다.

**권고**

1. 공식 승인 명령을 하나로 합친다.
2. 각 대조 항목에 처리 결과가 없으면 승인하지 않는다.
3. 녹음 재료가 있는 회차는 화자 매핑 확인을 승인 전제에 넣는다.
4. 현재처럼 `decision: approved`만 보내는 요청이 실패하는 회귀 테스트를 추가한다.

### P0-9. 상담 초안이 브라우저 저장소에 남는다

**판정: 실제 당사자 데이터 투입 전 차단**

정기 상담 작성 화면은 작성 중인 값을 브라우저 `localStorage`에 저장한다. 이 저장소는 브라우저를 닫아도 같은 기기에 남는다. 저장 대상에는 전체 상담 메모, 안전 관련 메모, 실무자 의견이 포함된다. `apps/web/app/lib/form-draft.ts:1-12`, `apps/web/app/participants/[beneficiaryId]/programs/[supportCaseId]/records/new/record-onepage.tsx:293`, `apps/web/app/participants/[beneficiaryId]/programs/[supportCaseId]/records/new/record-onepage.tsx:404`, `apps/web/app/participants/[beneficiaryId]/programs/[supportCaseId]/records/new/record-onepage.tsx:428`

12시간 수명은 정의돼 있지만 브라우저가 나중에 앱을 다시 읽거나 정리 함수를 실행할 때만 지워진다. 앱을 다시 열지 않으면 실제 저장값은 12시간이 지나도 기기에 남을 수 있다. `apps/web/app/lib/form-draft.ts:55-69`, `apps/web/app/lib/form-draft.ts:117-128`, `apps/web/app/lib/use-dom-draft.ts:79-86`

공용 PC, 개인 노트북, 분실 기기에서는 서버의 권한·감사·파기 통제를 우회한 상담 내용 사본이 된다.

**권고**

1. 실데이터 운영 전에는 상담 메모, 안전 메모, 실무자 의견을 `localStorage`에 저장하지 않는다.
2. 초안 복구가 필요하면 서버의 DB 접근 관문과 권한·감사를 거치는 초안 저장 기능으로 옮긴다.
3. 제출, 로그아웃, 계정 비활성화 때 브라우저 초안을 지우고, 기존 초안 형식을 한 번 정리하는 버전 절차를 둔다.
4. 공용 기기 사용 금지, 화면 잠금, 분실 신고를 현장 운영 절차에 포함한다.

## 4. 높은 우선순위 운영 피드백

### P1-1. 배포 성공이 서비스 정상 동작을 증명하지 않는다

운영 워크플로는 API와 웹을 순차 배포한 뒤 시크릿 확인 명령과 cron 목록을 출력할 뿐 실제 요청을 보내지 않는다. `.github/workflows/deploy-production.yml:132-151`

배포 스크립트도 배포가 끝난 뒤에야 시크릿 이름을 보고, `PII_ENC_KEY`가 없어도 경고만 남긴다. 시크릿 조회 실패도 배포 성공으로 처리한다. `scripts/deploy-production.mjs:231-245`

**권고**

- 기능별 필수 시크릿과 바인딩을 배포 전에 검사하고 누락 시 실패시킨다.
- 배포 뒤 인증된 API 요청, 안전한 D1 읽기·쓰기, 웹 렌더, R2 바인딩, cron 등록을 확인한다.
- API 배포 후 웹 배포나 기본 동작 점검이 실패하면 이전 정상 버전으로 돌아가는 절차를 둔다.
- GitHub `production` Environment의 필수 리뷰어 설정을 저장소 밖 증적으로 정기 확인한다. 워크플로도 설정이 없으면 승인 게이트가 아니라고 경고한다. `.github/workflows/deploy-production.yml:16-18`, `.github/workflows/deploy-production.yml:115-120`

### P1-2. 감시 범위와 알림 전달이 좁다

폴링 워치독은 구현돼 있지만 알림 채널이 없으면 `console.error`만 남는다. 웹훅 발송 실패도 로그만 남기고 계속 진행한다. `docs/ops.md:16-24`

파이프라인 문서는 기동 후 모델 로드 실패나 라벨 불일치 정체를 현재 감시가 잡지 못한다고 명시한다. `apps/pipeline/README.md:143-152`

현재 워치독은 최근 `poll_pipeline` 시각과 오디오 대기 건수만 본다. 텍스트 일감, 가장 오래된 대기 시간, 최근 성공, 반복 실패는 보지 않는다. 폴링만 계속되면 모든 작업이 실패해도 `ok`가 될 수 있다. `db/gateway.ts:6673-6715`

워커도 개별 작업 실패를 로컬 로그에 남기고 다음 폴링에서 다시 시도하므로, 외부 감시가 없으면 영구 실패를 알아채기 어렵다. `apps/pipeline/ccc_pipeline/worker.py:201-245`

웹·API 가용성, 인증 실패 급증, D1·R2 오류, cron 미실행, 파기 시도, 큐 대기 시간, 백업 실패를 한 곳에서 보는 기준도 없다.

**권고**

1. 실제 운영 환경에서는 알림 목적지를 필수로 한다.
2. 웹, API, D1, R2, 처리 장비, cron이 정해진 시간 동안 신호를 보내지 않으면 알리는 감시를 둔다.
3. 오디오와 텍스트 큐를 합산하고, 가장 오래된 대기 시간, 최근 성공, 실패 횟수를 별도로 경보한다.
4. 각 알림에 담당자, 확인 시간, 재알림, 에스컬레이션 기준을 붙인다.

### P1-3. 서비스 사고 대응 책임과 절차가 없다

현재 저장소의 사후 분석은 개발 도구 과부하 사례이고, CCC 서비스 사고를 다루는 런북은 확인되지 않았다. `docs/postmortems/2026-07-30-codemap-overload.md:1-18`

**권고**

한 장짜리 사고 대응 런북부터 만든다.

- 심각도와 목표 응답 시간
- 주 담당자와 백업 담당자
- AI 호출 중지, 자동 파기 중지, Access·서비스 토큰 폐기
- Worker 롤백과 D1 복원 권한
- 증거 보존과 기관 통지
- 사후 분석을 여는 기준

### P1-4. 감사 로그는 있으나 검토 절차가 없다

열람, 변경, PII 복호화, 내보내기를 추가 전용 로그로 남기는 설계는 좋다. `docs/policy/internal-operations-policy.md:222-224`

하지만 누가 얼마나 자주 보고, 무엇을 이상 징후로 보고, 조사와 종결을 어떻게 기록하는지가 없다. 정책은 다른 담당자의 케이스 접근 시도가 감사에 남는다고 적지만, 현재 접근 검사 함수는 거부 전에 감사 행을 만들지 않는다. `docs/policy/internal-operations-policy.md:228-230`, `db/gateway.ts:8176-8206`

**권고**

- `deny_access`를 내용 없는 감사 이벤트로 기록한다.
- 비배정 접근, 대량 PII 조회, 관리자 상담 내용 열람, 내보내기, 동의 변경, 역할 변경을 우선 검토 대상으로 정한다.
- 최소 월 1회 정기 검토와 즉시 검토 조건을 둔다.
- 검토 완료와 조치도 별도 기록으로 남긴다.

### P1-5. 배정·이관·퇴사 운영이 정책보다 단순하다

정책은 배정 요청과 수락, 강제 이관 사유, 당사자 안내를 요구하지만 현재 상태는 `확정·미구현`이다. `docs/policy/internal-operations-policy.md:135-143`

사용자 API는 같은 이메일을 다시 등록하면 역할을 바꾸고 `active=1`로 재활성화한다. 비활성화는 사용자 행만 끄며 케이스 배정 정리 절차는 계약에 없다. `docs/api-contract-pipeline.md:192-210`

**권고**

- 배정 상태를 요청, 활성, 종료로 나누고 수락 시 권한을 전환한다.
- 강제 이관은 별도 명령으로 두고 사유와 통지 확인을 강제한다.
- 퇴사·휴직 시 케이스 이관, 계정 비활성화, Access 그룹 제거, 토큰 폐기, 세션 무효화를 한 체크리스트로 묶는다.
- 재활성화 시 과거 배정을 자동 복원하지 말고 재승인한다.

### P1-6. 개인정보 처리 동의 철회와 파기 요청의 연결이 없다

정책은 동의 철회와 삭제 요청이 있으면 별도 즉시 파기 경로를 쓰도록 한다. `docs/policy/internal-operations-policy.md:218-220`

현재 동의 수정은 동의 시각을 `NULL`로 만들고 이력과 감사를 추가하지만 파기 검토나 법적 보존 확인 작업을 만들지 않는다. `db/gateway.ts:8984-9050`, `apps/api/test/participant-consent.test.ts:339-350`

**권고**

AI 동의 철회와 개인정보 처리 동의 철회를 구분한다. 개인정보 철회·삭제 요청은 추가 처리 차단과 함께 파기 검토 작업을 만들고, 법적 보존 사유 확인 후 처리하도록 한다.

### P1-7. STT 실패가 승인 전 구조화된 품질 게이트가 아니다

전사는 무음 경계로 나누고 반복 붕괴를 감지한다. 다만 전사가 신뢰하기 어렵다고 판정돼도 경고를 로컬 로그에 남긴 뒤 같은 결과를 마스킹하고 서버에 보낸다. `apps/pipeline/ccc_pipeline/worker.py:80-129`

반복 경고는 구조화된 품질 필드가 아니라 전사 텍스트 안의 경고 문장이다. 현재 검토 화면에도 경고 구간을 별도로 확인·처리하는 단계가 없다.

**권고**

- `transcriptReliable`과 경고 시간 구간을 구조화해 저장한다.
- 경고 구간을 실무자가 확인하거나 바로잡기 전에는 승인하지 않는다.
- 신뢰 불가 구간은 OpenAI 요약 재료에서 제외하거나, 사용 사실을 승인 화면에서 명시한다.

### P2-1. 텍스트 일감과 감정 보류를 서버에서도 강제해야 한다

텍스트 일감은 `pending`과 `done`만 있고 작업자가 일감을 선점하는 임대 상태가 없다. 완료 API도 같은 회차의 스냅샷이 실제로 만들어졌는지 연결해 확인하지 않는다. 처리 장비가 둘이면 중복 스냅샷과 중복 호출이 생길 수 있다. `docs/api-contract-pipeline.md:103-139`

감정 보류는 공식 워커의 `EMOTION_DEFERRED = True` 상수로만 구현돼 있다. `apps/pipeline/ccc_pipeline/worker.py:27`, `apps/pipeline/ccc_pipeline/worker.py:98-112` API는 빈 객체가 아닌 숫자형 감정값도 받아들일 수 있어 오래된 처리 장비가 감정을 다시 보낼 수 있다. `db/gateway.ts:6006-6019`

**권고**

- 텍스트 일감에 `processing`, 임대 소유자, 만료, 시도 횟수, 완료 스냅샷 ID를 둔다.
- 완료 시 같은 회차의 스냅샷을 필수로 연결한다.
- D64 보류 중에는 서버가 비어 있지 않은 감정값을 거부하도록 한다.

### P2-2. 문서 상태를 한 단어로 표현해 오해가 생긴다

`확정`, `완료`, `동결`, `미구현`, `보류`가 결정 상태, 구현 상태, 법률 상태를 섞어 표현한다. 예를 들어 결정은 확정됐지만 구현되지 않았거나, 구현은 됐지만 법률 검토가 동결된 항목이 있다.

**권고**

문서 머리에 다음 필드를 분리한다.

```yaml
decision_status: approved
implementation_status: partial
legal_status: draft
owner: role-or-team
last_verified: 2026-08-19
review_trigger: before-real-data
supersedes: []
```

### P2-3. 운영 문서에 책임자와 재검토 주기가 없다

`docs/ops.md`, `docs/releases.md`, `docs/policy/internal-operations-policy.md`는 현재 상태를 계속 갱신해야 하는 문서지만 소유자와 재검토 조건이 없다.

**권고**

- 배포 뒤 `docs/ops.md`와 `docs/releases.md`를 확인한다.
- AI 사업자, 데이터 흐름, 동의 문구가 바뀌면 동의 문서 검토를 자동 재개한다.
- 실제 데이터 투입 전 정책 전체를 재검토하고, 운영 중에는 최소 분기 1회 검토한다.
- 완료된 `.omo` 계획·초안은 비정본 실행 기록으로 표시하고 보관 상태를 명확히 한다.

## 6. 권장 실행 순서

### A. 다음 가상 데이터 시연 전

1. 시연 D1·R2 자료 목록을 만들고 `가상 데이터` 또는 `동의받은 내부 테스트 녹음`으로 구분한다.
2. 실제 당사자 데이터 금지를 시연 체크리스트에 넣고 승인자를 기록한다.
3. 운영 `/join`을 기능 스위치로 닫는다.
4. 실제 알림 채널과 주 담당자·백업 담당자를 지정한다.
5. 배포 후 인증 API와 웹 기본 동작 점검을 자동화한다.

### B. 실제 당사자 데이터 투입 전

1. 화면 동의 문구와 법률 검토본을 단일 출처로 맞춘다.
2. 개인정보 처리방침과 동의서 검토를 완료한다.
3. 자동 파기를 중지하고 아카이브, 보존 사유, 검토 큐, 승인 후 파기를 구현한다.
4. 기관 관리자 평상시 접근을 담당 배정으로 제한하고 긴급 접근을 분리한다.
5. 개인정보 철회·삭제 요청 절차를 구현한다.
6. AI 동의 철회가 큐·스냅샷·OpenAI 사용을 실제로 차단하게 한다.
7. 대조 항목 처리와 화자 확인을 단일 승인 경로에서 강제한다.
8. 민감한 상담 초안을 브라우저 `localStorage`에 남기지 않는다.
9. RPO·RTO를 정하고 D1·R2·시크릿·암호화 키 복구 훈련을 통과한다.
10. 사고 대응 런북과 감시·알림 체계를 운영한다.
11. 배포 전 시크릿 검사와 배포 후 실동작 검사를 실패 차단으로 바꾼다.

### C. 외부 기관 온보딩 전

1. 관리형, CCC 박스, 개인 노트북, 기관 자체 클라우드별 책임 분담표를 만든다.
2. 개인정보처리자·수탁자, AI·STT 위탁, 사고 통지, 파기, 계약 종료 책임을 방식별 계약에 반영한다.
3. 실제 제공할 배포 방식에만 설치, 업데이트, 마이그레이션, 백업, 복구, 폐기 런북을 만든다.
4. 여러 기관과 여러 역할을 함께 둔 권한 검증과 기관별 데이터 분리 검증을 통과한다.
5. 기관 사용자 등록, 퇴사·휴직, 역할 변경, 비상 접근, 정기 감사 절차를 기관 관리자 교육에 넣는다.

## 7. 단계별 승인 점검표

다음 체크를 저장소에 보이는 한 장으로 두고, 단계별로 모두 닫혀야 다음 단계로 넘어가도록 권한다.

2026-08-19 기준 `[ ]`는 `미충족 또는 미검증`을 뜻한다. 각 항목에는 `충족`, `미충족`, `미검증` 중 하나와 책임자, 확인일, 완료 증거, 승인자를 기록한다. 해당 단계에 `미충족` 또는 `미검증`이 하나라도 있으면 승인하지 않는다.

- [ ] 개인정보 처리 동의 철회와 삭제 요청 처리
- [ ] AI 동의 철회 후 큐 적재, 스냅샷 생성과 외부 호출 차단
- [ ] 대조 항목 처리와 화자 확인을 거친 단일 승인 경로
- [ ] 브라우저 저장소의 상담 초안 제거 또는 서버 초안으로 전환
- [ ] 백업·복구 훈련과 암호화 키 복구 검증

- [ ] 서비스 종료와 데이터 반환·파기 절차

## 8. 최종 승인 판단

2026-08-19 기준, 저장소에서 확인된 상태만으로 실제 당사자 데이터 처리와 외부 기관 운영 시작을 승인할 수 없다. 가상 데이터 시연도 섹션 6의 사전 조건을 확인하고 승인자와 증거를 기록한 뒤에만 진행한다.

실제 당사자 데이터 처리 또는 외부 기관 운영 시작은 해당 단계의 P0 및 P1 항목이 모두 `충족`으로 기록되고, 각 항목의 완료 증거와 승인자가 확인된 뒤에 다시 심사한다.
