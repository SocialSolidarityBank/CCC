3. 구현에 둔 시연 경계
- URL: ?module=<ID>&role=all|admin|tech|both|lead|counselor. 선택 상태는 state, 안내 목적지는 topic. 폼 값은 URL에 넣지 않음.
- 기본 진입: 전체/기관 관리자/겸임은 기관 정보, 기술 관리자는 첫 허용 메뉴인 계정 및 권한, 개인 역할은 내 정보.
- unknown module은 없는 화면, 허용되지 않은 module은 권한 없음. 실제 권한 검사는 아님.
- 메뉴가 선택되면 하나의 본문으로 교체. 별도 admin 탭이나 두 번째 sidebar 없음.
- 업무 복귀는 module=work의 업무 메뉴 시연. 실제 상담 화면이 없다는 안내와 설정 복귀를 제공하며 운영 주소로 나가지 않음.
- 기본 fixture는 직원 12명, 팀 5+4+3명, 진행 사업 2개와 종료 1개, 케이스 30+18개, 기관 장비 1대. 신규 사업 시연은 케이스 0개의 준비 항목을 추가함.
- 역할 전환 시 미적용 초안과 확인 상태를 지움. 적용한 일반 가상 값은 페이지 메모리 안에 남음. 새 역할의 select에서 허용되지 않는 이전 선택값은 해당 역할 기본값으로 재설정.
- 단순 변경만 페이지 메모리에 적용. 외부 연결, 설치, 파일 생성, 백업/복원, DB 변경은 선택과 절차 확인만 기록. 실행 완료로 표시하지 않음.
- 실제 키 입력칸 없음. 가상 자격 상태를 고르는 선택창만 존재. 기술 관리자 단독은 키 상태 선택과 최종 시작 불가.
- 기관 관리자 단독의 '준비된 결과 예시 보기'는 미리 준비된 기술 결과 fixture를 읽는 프리뷰 조작. 기술 점검 실행으로 취급하지 않음.
- 기술 관리자 단독의 '기존 승인 예시 보기'는 기존 기관 관리자 승인 fixture를 읽는 프리뷰 조작. 자기 승인으로 취급하지 않음.
- 겸임은 직접 준비 점검 및 가상 키 설정 또는 복원 승인과 점검을 한 흐름에서 수행.
- AI 경로와 자격 선택 변경 시 준비 확인, 키 상태 확인, 최종 확인을 해제. 설치 변경 시 진행 사업 재확인 상태를 남김.
- STT off, 엔진 null, 실제 LLM off 유지. Azure는 마스킹 전 원음, OpenAI는 가려진 텍스트라는 차이를 입력 옆에 표시.
- 사업 저장/처리 중 하나라도 나중에 정하기면 도입 확인 체크를 받지 않고 준비 상태로 등록하는 시연. 공공형은 비활성. 실제 실데이터 잠금은 구현했다고 주장하지 않음.
- 메모리 화면은 기관 기능과 처리 건수뿐. 당사자 이름, 상담 원문, 요약 원문, 근거 인용, memory.md, 항목별 승인/정정 UI 없음.
- 가이드는 기능별로 실제 시안 내 이동 링크를 제공. 기존 docs/manual/project-admission-check.md는 서버 허용 범위 밖이므로 원문 제공 불가를 표시하고 필요한 조건 확인 설명을 가이드에 둠. 404 문서 링크나 외부 운영 주소는 만들지 않음.

4. 정확히 미검증인 동작
아래 항목은 소스를 작성했으나 실행 결과를 관측하지 않았습니다.

- 19개 메뉴의 표시 개수, 라벨, 그룹, 아이콘, 활성 표시와 역할 조합별 최종 DOM.

5. Main이 실행할 필수 시각 및 행동 사례
A. Main이 작업 충돌 없는 시점과 전용 포트를 먼저 지정. 기존 3112 서버를 차지하거나 재기동하지 말 것.
   이 파일의 CCC_PREVIEW_HOST와 CCC_PREVIEW_PORT를 지정하여 전용 프로세스로 실행 가능. 사용 가능 포트는 이 lane에서 확인하지 않음.
   프로세스 readiness, tailnet 원격 자산 응답, /settings 로드를 확인한 뒤 검수 링크를 제시.
B. 1280px 및 390px에서 전체 19개 기본 화면을 열고 캡처. 320/767/768px 경계와 다크 모드도 확인.
   긴 메뉴, 폼 영향 구획, 6영역 문안, 사용 가이드, 카드 배지와 버튼의 넘침 및 서체 위계 확인.
C. all/admin/tech/both/lead/counselor 각각 메뉴와 빈 그룹 숨김, 직접 권한 밖 URL, 내 정보 역할 합 확인.
D. institution → programs → ai → guide 이동 후 뒤로/앞으로, 직접 URL 새로고침. unknown module과 work 복귀 확인.
E. institution 이름을 가상 값으로 수정 후 현재 정보와 사이드바 반영, 새로고침 초기화 확인.
F. programs의 나중에 정하기 등록과 두 조건 선택 후 확인 등록을 각각 시연. Naver 선택 불가와 기관 안 설명 확인.
G. both의 ai: 질문 2개 → 준비 점검 → 가상 키 설정 → 확인 → 최종 시작 절차 시연.
   이전으로 돌아가 경로를 바꾸면 준비/키/최종 확인이 풀리는지 확인. 적용 후 사업 재확인 유지 확인.
   admin 단독은 준비된 fixture 읽기 후 키/시작, tech 단독은 준비만 가능해야 함.
H. speech Azure 설명과 off/null 유지, 로컬 비활성. speech와 ai를 합친 폼으로 보이지 않는지 확인.
I. exports에서 역할별 범위 선택 후 state=conflict 및 failure에서 적용 시 입력 유지, 파일 생성 없음 확인.
J. backup에서 admin 승인만, tech 기존 승인 fixture와 점검, both 승인+점검+실행 절차를 각각 확인.
   검증 전 백업은 점검 완료가 되지 않아야 함. 실제 성공/다운로드 메시지는 없어야 함.
K. memory basic/off/unavailable/failure/masking/syncing 상태를 각각 확인. 내용, 인용, 승인 큐가 없어야 함.
L. audit 종류 필터, account의 실무자 배정 요청 수락, reset의 즉시 초기화 확인.
M. 모바일 드로어에서 첫/마지막 포커스 순환, Escape/스크림/메뉴 선택 닫힘, 복귀 초점과 본문 잠금 확인.
N. 네트워크와 브라우저 저장소 관측. static asset 외 요청 없음, localStorage/sessionStorage/cookie/IndexedDB 사용 없음 확인.
O. 19개 모듈별 basic/empty/off/unavailable/failure/conflict. 추가 disconnected는 agent/system/ai/speech/database에서 확인.
P. Main이 별도 rule-reviewer와 화면 검수 일정을 잡고 관문 실행 여부를 결정. 정적 아티팩트가 React guard 대상이라고 간주하지 말 것.
