## 1. 문제 — 왜 팀원마다 다르게 보이나

네이티브 `<input type="date">` 는 **제출되는 값**과 **보이는 글자**가 다른 부품이다.

- 제출값은 규격이 `YYYY-MM-DD` 로 고정한다. 이건 어디서나 같다.
- **보이는 글자는 보는 사람의 브라우저 UI 언어를 따른다.** 페이지 로케일(`lang="ko"`)은
  무시된다. MDN 이 명시한다 — *"the displayed date is formatted based on the locale of the
  user's browser, while the value is normalized to the format yyyy-mm-dd."*

즉 훑기에서 본 `mm/dd/yyyy` 는 헤드리스 브라우저의 기본 언어였고, 실제로는 **팀원마다
다른 것을 본다**(영문 Chrome=`mm/dd/yyyy`, 한글 Chrome=`YYYY. MM. DD.`, Firefox 는 OS 설정,
Safari 는 지역 설정). 달력 팝업의 모양과 월·요일 표기도 같은 이유로 제각각이다.

**그래서 CSS·`lang` 속성·로케일 설정으로는 못 고친다. 부품을 바꿔야 한다.**
(`work-design.md` §3 이 이미 내린 결론이고, 이 레인이 그 실행이다.)

## 2. 조사 — 한국 서비스는 어떻게 받나

Q 지시는 "직접 만들기부터 시작하지 않는다. 다른 부품으로 갈아타거나 **한국어 사이트에서
실제로 쓰는 방식을 찾아서 넣는다**" 였다. 찾아보니 **정본이 있었다.**

### KRDS — 대한민국 정부 디자인 시스템

정부 서비스의 공식 디자인 규격이다. `날짜 입력 필드(Date input)` 와 `달력(Calendar)` 이
별도 컴포넌트로 있고, **둘을 언제 쓰는지 판단 기준까지 적혀 있다.**

| 방식 | KRDS 가 말하는 용도 | 원문 |
| --- | --- | --- |
| **단일 입력 필드** | 아는 값을 적는 자리 | "사용자가 이미 알고 있는 날짜를 입력받는 데 유용" · 예시로 **"주민등록번호 앞자리, 생년월일"** |
| 다중 입력 필드(년/월/일 3칸) | 문서에 적힌 값을 정확히 옮길 때 | "연속된 입력 필드 간 이동 동작이 필요하기 때문에 **가장 효율성이 낮은 입력 방식**" |
| 날짜 선택기(달력) | 먼 날짜·요일이 중요한 자리 | "서비스 이용 시점으로부터 **멀리 떨어진 과거 날짜나 미래 날짜**를 입력해야 하거나, **요일 정보가 중요한 상황**" |

**생년월일은 단일 입력 필드다.** 달력을 넘겨 찾는 값이 아니라 아는 값을 적는 값이라는
`lane-b-prep.md` §9-3 의 예상이 규격으로 확인됐다.

KRDS 가 함께 요구하는 것:

- 자리 표시자 `YYYY-MM-DD`
- **입력칸 아래 도움말**에 자릿수 + 예시 — *"플레이스홀더는 사용자가 입력을 시작하면
  사라지기 때문에 입력 필드 하단의 도움말 텍스트를 사용하는 것이 바람직하다"*
- 라벨을 컨트롤에 프로그래밍적으로 연결(KWCAG 2.2 레이블 제공 / WCAG 2.1 A)
- 키보드만으로 입력·이동 가능(달력을 쓰더라도 입력칸을 읽기전용으로 만들지 않는다)
- 개인정보 칸에 브라우저 자동완성 지원

## 3. 후보 비교와 기각 이유

| 후보 | 판정 | 이유 |
| --- | --- | --- |
| **KRDS 단일 입력 필드를 직접 구현** | **채택** | 규격이 정본이고, 글자 입력칸에는 **브라우저 편차가 원천적으로 없다.** 새 의존성 0. 제출값이 네이티브와 글자 그대로 같아 서버를 안 건드린다 |
| 네이티브 유지 + 도움말만 추가 | 기각 | 문제 자체(보는 사람마다 다른 표기)가 그대로 남는다 |
| `react-day-picker` + `date-fns` (MIT) | **이 레인에서 기각** | ① 이 레포의 화면 의존성은 `lucide-react`·`pretendard`·`qrcode.react` 뿐이고 `wire/` 부품은 전부 손으로 만들었다 — 부품 라이브러리 도입은 스윕 항목이 아니라 **ADR 급 결정**이다 ② `react-day-picker` 에는 시간 입력이 없어 `datetime-local` 3곳이 '달력+시간칸' 리팩터가 된다 ③ 달력 팝오버는 D34 에 선례가 없다(D34 는 화면 1개 기반이라 "입력칸·모달·포커스 미관찰"을 스스로 적어 뒀다) — 형식 수정 레인 안에서 시각 언어를 발명하게 된다 |
| 년/월/일 3칸 분리 | 기각 | KRDS 가 스스로 "가장 효율성이 낮은 입력 방식"이라 하고, 생년월일은 단일 필드 예시로 든다 |

`green` **라이선스 확인 불필요** — 새 의존성을 넣지 않았다(§5 모델 라이선스 규칙과 같은
기준을 적용할 대상이 없다).

## 4. 이번에 한 것 — 1군(생년월일) 2곳

새 부품 **`apps/web/app/components/wire/date-text-input.tsx`** 하나를 두 화면이 공유한다.

- `type="text"` + `inputMode="numeric"` + `autoComplete="bday"` + `maxLength={10}`
- **자동 하이픈**: `19850327` 을 치면 `1985-03-27` 이 된다. 점·슬래시 붙여넣기도 받는다
- 자리 표시자 `YYYY-MM-DD` + **칸 아래 도움말**(자릿수 + 예시, KRDS)
- `pattern="\d{4}-\d{2}-\d{2}"` 로 화면에서 형식 검증, `aria-describedby` 로 도움말 연결
- **제출값은 예전과 글자 그대로 같다** — 서버 액션·게이트웨이·마이그레이션 변경 0

적용한 곳:

| 화면 | 파일 | 감싸는 부품 |
| --- | --- | --- |
| 당사자 등록 | `participants/new/register-form.tsx` | `SearchInput type="date"`(안에서 새 부품을 그린다) |
| 기본정보 수정 | `participants/[beneficiaryId]/edit/basic-info-form.tsx` | `WireFormField` + 새 부품 직접 |

`green` **"대상 파일 7개"의 정체** — `lane-b-prep.md` §9-3 이 말한 7개는 **날짜 칸 6곳 +
공유 부품 `search-input.tsx` 1개**다(§5 표의 4곳 + 위 표의 2곳 + 감싸는 부품). 일곱 번째
화면을 더 찾을 필요 없다.

`red` **`SearchInput type="date"` 는 비제어 전용이다.** `value` 를 주면 **초기값으로만**
쓰인다 — 다른 type 처럼 매 렌더 반영되지 않는다. 값을 부모가 쥐어야 하는 화면이 생기면
`DateTextInput` 에 제어형 경로(`value`+`onChange`)를 먼저 만들어야 한다. 지금 호출부
(등록 화면)는 값을 주지 않아 드러나지 않지만, prop 이름만 보면 되는 것처럼 보인다.

두 화면이 감싸는 부품은 다르지만(등록은 검색칸 계약 높이 61, 수정은 폼칸 계약 높이 40)
**안에 든 입력 부품은 하나**다. 이걸 안 맞추면 다음 수정에서 두 화면이 갈라진다.

곁가지로 `basic-info-form.test.tsx` 에 `afterEach(cleanup)` 을 넣었다 — 이 레인이 만지는
파일이라 여기서 닫는다(남은 9개는 STATUS 다음 할 일 3번).

### 알고 남기는 것

`yellow` **자릿수가 안 맞는 붙여넣기는 바로잡지 않는다.** `1985년 3월 27일` 을 붙여넣으면
숫자가 7개라 `1985-32-7` 이 되고 `pattern` 이 제출을 막는다. 부품이 "3월은 03월이겠지"
하고 추측하면 다른 오입력도 조용히 고쳐 **틀린 값을 통과시킨다.** 막는 쪽을 골랐다.

`yellow` **가운데 하이픈만 지우면 되돌아온다.** 커서를 중간에 놓고 하이픈만 지우면 자동
하이픈이 즉시 다시 넣는다(맨 뒤에서 지우는 흔한 경로는 정상). 부품을 복잡하게 만들 값어치가
없다고 판단해 남긴다.

## 5. 2군(달력이 정당한 값) 4곳 — **Q 결정 후 같은 날 구현 완료**

> **2026-07-30 갱신.** 아래는 1군을 끝낸 시점의 미결 기록이고, 그날 Q 가 **달력 + 직접 입력
> 병행**으로 결정해 **D48 · ADR-0020** 으로 구현까지 마쳤다. 달력 알맹이는 공개 부품
> **`react-day-picker`(MIT, v10)** 이며 **이 레포의 첫 화면 라이브러리**다 — 직접 만들지 않은
> 이유는 키보드 격자 이동·스크린 리더 낭독이 손으로 만들 때 가장 조용히 틀리는 영역이기
> 때문이다(Q 선택). 아래 §3 표의 `react-day-picker` 기각은 **"이 레인 안에서 조용히 정할 일이
> 아니다"** 라는 뜻이었고, ADR 로 올라오면서 그 조건이 풀렸다. 새 부품
> `components/wire/date-picker-control.tsx`(`DatePickerControl` · `DateTimePickerControl`),
> 겉모습은 **기존 D34 토큰 조합만** 사용(새 색·반경·그림자 0개). 상세: `docs/adr/0020-date-picker-calendar.md`.

KRDS 기준으로 **달력이 맞는 자리**가 4곳 남는다(1군 시점 기록).

| 화면 | 파일 | 값 |
| --- | --- | --- |
| 인테이크 위저드 | `records/intake/intake-wizard.tsx:698` | 상담 일시 |
| 상담 기록 작성 | `records/new/record-onepage.tsx:208` | 상담 일시 |
| 상담 등록 | `schedules/new/schedule-wizard.tsx:328` | 상담 일시 |
| 액션 아이템 | `records/new/action-item-fields.tsx:47` | 기한 |

**왜 미뤘나**: 이 값들은 "요일 정보가 중요"하고(상담 일정은 요일로 잡는다) 가까운 미래
날짜다 — KRDS 가 **날짜 선택기를 쓰라**고 지정한 조건이다. 그런데 달력을 넣는 것은 §3 표의
`react-day-picker` 항목대로 **의존성 + 시각 언어 결정**이고, 형식 수정 레인 안에서 조용히
정할 일이 아니다.

**Q 에게 물어야 할 것 하나**: 상담 일시를 `YYYY-MM-DD` 글자칸 + `HH:mm` 시간칸으로 받아도
되는가?

- **된다면** — 레인 D 와 같은 방식으로 끝난다. 새 의존성 0, 달력 없음. 다만 상담을 잡을 때
  **요일이 안 보인다**(`2026-08-12` 가 무슨 요일인지 머리로 세야 한다).
- **안 된다면** — 달력 부품 도입이 맞고, 그건 **D 번호를 받는 결정 + ADR** 이다(D34 에 없는
  팝오버·포커스·모바일 시각 언어를 함께 정해야 한다).

`green` **해소됨(2026-07-30)** — Q 가 위 두 갈래 중 **"안 된다"**(달력 필요)를 골랐고 같은 날
